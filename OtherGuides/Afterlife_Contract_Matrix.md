# Afterlife Contract Matrix — Chaos Sea and Shining Abode

This guide is mandatory operational context for every GM turn where `game_state/meta/soul_state.json.currentRealm` is `Chaos Sea`, `Море Хаоса`, `Shining Abode`, or `Сияющая Обитель`, and for any turn whose `progressionControl` contains afterlife debt.

The GM normally does not need to read client code. Use this matrix to decide which afterlife contracts are active, which files must be read, which canonical surfaces must be written, and which Mortal World substitutions are forbidden. Use `Examples/E_CLI_Afterlife_Turns.txt` for full worked JSON fragments after selecting the relevant contract rows here. If the matrix and examples still leave a mechanical contract unclear, or a validation repair points at an exact schema/surface mismatch, the GM may inspect client code as a fallback source of truth for file mappings, allowed fields, validators, canonical state surfaces, receipts, reports, and normalizers. This fallback never replaces the prompts and must not be used to invent new gameplay outcomes or bypass afterlife rules.

## Universal Afterlife Rules

- Always run realm gate first: ordinary `Chaos Sea`, ordinary active `Shining Abode`, or `Shining Abode pending-bootstrap handoff`.
- Always read `input/turn_request.json.progressionControl` before selecting the scene, tone, relevant actors, or player-action resolution.
- Always inspect `game_state/control/` pending afterlife files before deciding that the turn is only narrative.
- Always inspect non-pending afterlife control guards such as `system_guardian_attraction.json` and `afterlife_return_guard.json`; these are client-owned contracts/guards, not optional lore.
- If a pending file exists, it is a client-authored contract. It must close through the exact canonical state/receipt surface named below.
- Realm-wrong pending files are not free authoring prompts. A valid MortalWorldProfile-only companion manifestation file is preserved as next-life context, while valid empty request files may be removed as stale clutter; malformed pending files are preserved for repair. Non-empty or malformed Mortal-only NPC social/trade pending files block Soul Gates until repair or Mortal resolution. The GM must not close realm-wrong files by inventing afterlife receipts, Mortal NPCs, world events, or manual notifications.
- If afterlife scheduler debt is due, write `game_state/control/progression_report.json` through `progressionProcessingReport`.
- `game_state/control/progression_schedule.json` is client-owned scheduler state. The GM reads `input/turn_request.json.progressionControl` as the turn contract and writes only `progression_report.json`; never edit schedule baselines, pending cycle counts, `last*Ordinal`, or catch-up markers directly.
- Copy `sessionId`, `requestId`, and `turnNumber` exactly from the current request into every required report/receipt that carries turn correlation.
- Declare all changed Guardians, residents, Shining factions, halls, gates, head actors, and institutions in `gm_thoughts_markdown` actor scope.
- Afterlife spiritual conflicts are legal only through `afterlifeSpiritualConflictUpdate` and `game_state/meta/afterlife_spiritual_conflict_state.json`. They never use Mortal combat files (`enemiesData`, `alliesData`, `combat_log_markdown`), HP/energy/poise/status changes, Mortal skills, or NPC/world/faction files. Direct conflict rewards are allowed only through the strict `rewardAudit` contract below.
- Active afterlife spiritual conflicts may carry `combatConditions[]`: the dedicated layer for short-lived spiritual combat buffs/debuffs. Condition kinds are `mark`, `ward`, `burden`, `opening`, and `vow`. Each condition must name a target side/actor, source, affected operations, finite duration/uses, `counterplay`, and summary; it must answer what becomes easier, harder, costlier, risky, protected, or vulnerable. Legal mechanical axes are only `rollMode.*.advantageSources/disadvantageSources`, `conflictPosition`, `controlState` (softening/narrowing only through legal anti-control operations such as `break_binding`, `incarnation_resistance`, `counter`, or `guard`), `playerSideStrain`, `oppositionSideStrain`, `tempoAdvantage`, `counterPayoff`, `actionCostAudit` / ОД costs, and `specialArtAudit.effectNote`. This is no generic passive stat stacking: every active entry must be audited through an existing axis, and the current exchange/resolution must create, consume, expire, or clear combatConditions explicitly instead of hiding modifiers in prose. Player-facing output shows visible active combatConditions with name, target, source, affected operations, duration/uses, counterplay, and summary; hidden/gm_only combatConditions are private GM state and must not leak in ordinary player output. A condition-backed rollMode source uses a source object with `sourceType="combat_condition"` plus the matching `conditionId`/`sourceId`.

Use `afterlifeEntityProfileUpdates` when a significant afterlife actor is created, revealed, or materially changes: `actorType`, `actorId`, `displayName`, realm/location, `currencies`, `progression`, `standardArts`, `specialArts`, `customStates`, `fateCards[]`, `relationships[]`, `soulDissipationTier`, `progressionStrategy`, warnings, `progressionLedger`, and `ledger`. Use `afterlifeFateCardUnlocks[]` to unlock a profile `fateCards[]` entry only with current evidence, `appliedAtTurn`, and at least one active effect array: `guardianEffects`, `playerUnlocks`, `politicalEffects`, `combatEffects`, or `trainingUnlocks`; locked/hidden/available Fate Cards must not grant active training, scene, passive, political, or combat effects. Use `afterlifeActorGoalUpdates[]`, `afterlifeActorQuestUpdates[]`, `afterlifeActorActivityUpdates[]`, and `completeAfterlifeActorActivities[]` for actor agency: canonical profiles store `goals`, `personalQuests[]`, `currentActivity`, and `completedActivities[]`; every goal/current activity needs `gmThoughtsSummary`, `currentActivity` must link to current `goals.goalId` and an active `personalQuests[].questId`, and completed activity closure targets the actor's current activity rather than direct erasure. Use `afterlifeRelationshipChanges[]`, `afterlifeRelationshipLockUpdates[]`, and `afterlifeBreakthroughQuestUpdates[]` for afterlife-only relationship gates: supported axes are `trust`, `romance`, `rivalry`, `oath`, `fear`, `reverence`, and `debt`; value `>= 50` requires a positive `relationshipLock`/completed breakthrough proof, value `<= -50` requires redemption or `pointOfNoReturn` proof; completed breakthrough/redemption quests clear linked `breakthroughQuestId`/`redemptionQuestId` only with `_clear_`; do not use Mortal `NPCRelationshipChanges`. `specialArts[]` entries require `artId`, Russian `displayName`, `ownerActorType`, `ownerActorId`, `baseOperation`, `tier`, `costMultiplierPercent > 100`, `upgradeCost`, `effectSummary`, and, if teachable, `trainingConditions`; `upgradeCost` must be non-empty, use only `inkFeathers`/`lightSparks`, include at least one positive value, and may be Ink-only, Spark-only, or mixed, but Spark-only learned-art upgrades are available only through `/spiritual_arts` in ordinary active Shining Abode. Otherwise the client applies the strategy after existing `progressionControl` cycles only from the current-turn `progression_report.json` whose `sessionId/requestId/turnNumber` match the current request, may spend by `progressionStrategy.priorityOrder` entries such as a `specialArts[].artId` or `soul_dissipation`, and records `lastAutoProgressionCycleKey`. If both lists are present, the allow-list is applied first and the deny-list can still block the spend. Final soul death is never ordinary combat damage: if a resolved conflict attempts it, write `recentConflicts[].soulDissipationProof` with `targetStabilityCoefficient`, sufficient `dissipationTier`, victory proof, and explicit GM motivation; if the target is the player, also write exact `soul_state.terminalGameOver.message`. This is afterlife-only authority; do not mutate it from Mortal World turns.

## GM Decision Loop

Use this loop for every `Chaos Sea` / `Shining Abode` turn before writing files:

1. Classify the realm mode. If this is Shining pending-bootstrap handoff, stop ordinary afterlife processing and preserve `preparedIncarnationPackage`. If the package is present but invalid, fail closed: preserve the package and all pending Shining files for repair.
2. Read `progressionControl` and list every due contour, expected count, catch-up pressure tier, and catch-up contour.
3. Read all afterlife pending files. Each present pending file activates one row in this matrix and must close through the exact state surface and receipt listed here.

## Preview Ownership Rules

- A contract-backed preview is a player-facing audit for a GM-resolved afterlife action. If the preview names a `playerAction` tag, pending/control file, request id, cost, or closure surface, the GM must close that exact contract through the matrix row for the tag/file.
- A client-local mutation preview is not an afterlife-turn contract. Soul Relic equip/unequip is the canonical local example: no GM turn is sent, no pending/control file is created, no receipt/progression report/gm_thoughts output is required, and no existing pending contract is closed. The same ownership rule applies to the browser parity entry points `/soul_relic_equip` and `/soul_relic_unequip` plus their Russian aliases, which the client routes through `SoulRelicEquipmentService` against `game_state/meta/soul_state.json` without producing a GM turn.
- Do not convert a client-local preview into GM-authored state. Only the client applies the listed local state mutation after the player confirms the preview.
- High-cost or destructive Chaos Sea previews must expose the exact target/source identity before confirmation: Guardian id/name for donation/favor/offering/trade, resident id/name for resident notifications, Soul Relic/archive id/name/rarity/type for consumed objects, and companion/NPC id/name plus traits/personality markers for `SOUL_IMPRINT`.
- `SOUL_IMPRINT` receipt proof must include `stateEvidence.imprintId`, `stateEvidence.companionName`, source provenance (`sourceCompanionId`/`companionId` or `NPCId`/`sourceNpcId`), and `stateEvidence.affectedFiles` pointing at `game_state/meta/soul_state.json`; the persisted `soulImprint` must keep the same source provenance. It prepares a future companion/imprint path and does not create a Mortal NPC during the afterlife turn.
- The preview must show projected state/resource deltas when the client can know them: Ink Feathers before/after, Abode Power current/projected plus `baseDelta`/`finalDelta`, Guardian reputation expected change, trade/buyback price and projected balance, and the pending/control file or local state surface that will change.
- Post-resolution player-visible detail surfaces must expose the matching receipt/audit identifiers when available: `requestId`, `historyEntryId`, `guardianPowerEvents.powerEventId`, trade `slotId`, buyback `buybackEntryId`, archive action receipt id, resident roster/interaction/transfer receipt identity, and the derived current state snapshot.
- Guardian trade purchase/sale/buyback previews are client-local coordinated writes, not GM turns, but they still need full audit JSON so the player can see `priceInFeathers`, `currentFeathers`, `projectedFeathers`, sold-out or buyback status, and cloned `relicData`.

## Afterlife Spiritual Conflict Contract

Use this system when roleplay creates a real spiritual contest in `Chaos Sea` or ordinary active `Shining Abode`: coercive Guardian pressure, duels between Guardians/residents/radiant actors, contested bindings, forced-incarnation attempts, or side-vs-side champion contests. The GM starts the conflict when the scene requires it; the client does not pre-create the conflict. Conflict realm/mode authority is evaluated from the validated pre-turn `soul_state.json` and, for Shining, the validated pre-turn `shining_abode_state.json`; same-turn edits to `currentRealm`, Shining `availability`, or `preparedIncarnationPackage` cannot make a conflict legal. For a worked valid start/exchange pattern, see example 24 in `Examples/E_CLI_Afterlife_Turns.txt`. For Russian player/GM labels and canonical English JSON terms, use `OtherGuides/Afterlife_Combat_Terminology_Glossary.md`.

Canonical state lives in `game_state/meta/afterlife_spiritual_conflict_state.json`:

- `schemaVersion`: positive integer.
- `activeConflict`: object or null.
- `recentConflicts[]`: compact resolved conflict summaries.
- `activeConflict.sideModel`: one of `direct_duel`, `assisted_duel`, `champion_duel`.
- `activeConflict.playerSide` and `activeConflict.oppositionSide`: each has exactly one `leadContestant`; `supporters[]` are minor contributors unless the model chooses a champion lead.
- Side strain fields are `playerSideStrain` and `oppositionSideStrain`, each one of `clear`, `strained`, `fractured`, `overwhelmed`, `broken`.
- `conflictPosition`: `opposition_dominant`, `opposition_advantaged`, `contested`, `player_advantaged`, or `player_dominant`.
- `controlState` is the canonical control/оковы axis, separate from strain and position. Missing/null means no active control for legacy entries. Active control uses `level=hindered|bound|locked`, `controllerSide=player|opposition`, non-empty `controlId`, `sourceOperation=binding|force_binding|force_incarnation|break_binding|incarnation_resistance|counter|guard|repair`, non-empty `restrictedOperations`, and `summary`; `sourceOperation` is not a free operation id.
- `tempoAdvantage` is the one-use темповое окно защиты. Full `guard` success against direct `pressure` / forced pressure writes `after.tempoAdvantage` and the active root copy with `ownerSide=player`, `sourceOperation=guard`, `status=available`, `level=advantage|great_advantage`, `advantageId/sourceId`, `sourceExchangeId`, and `summary`. The next eligible non-terminal combat action (`pressure`, `maneuver`, `binding`, `force_binding`, `break_binding`, `counter`, `incarnation_resistance`, or `champion_coordination`) must either consume it through `diceAudit.rollMode.player.advantageSources[]` using `sourceType=guard_tempo_window` and the matching id, or explicitly expire/clear it. It does not apply to `recover_spiritual_power`, `withdraw`, `surrender`, or `negotiate`.
- `actionEconomy` is the afterlife ОД / очки духовного действия axis, separate from Mortal HP/energy/stamina. Active conflicts with current exchanges carry `actionEconomy.player` and `actionEconomy.opposition` (`current`, `max`, `source`). On `mode=start`, the player's `current/max` comes from client-owned `soul_state.afterlifeCombatProfile.spiritFocusTier` / `Средоточие Души`: tier `0/1/2/3/4/5` gives max ОД `6/7/8/10/12/15`, with source `Средоточие Души tier N`. New/current exchanges that spend or restore ОД carry `actionCostAudit.player` (`operationType`, `baseCost`, `minCost`, `artTier`, `effectiveCost`, `before`, `after`), using `effectiveCost = max(minCost, baseCost - artTier)`. Terminal/free player operations (`withdraw`, `surrender`, `negotiate`) must not include `actionCostAudit.player`; they cannot mutate player ОД through fake audit. Every new/current exchange that resolves an active costed opposition operation also carries `actionCostAudit.opposition` in the same shape; this remains required even when the player's own operation is terminal/free (`withdraw`, `surrender`, `negotiate`). The opposition operation is taken from `incomingAction.finalOperationType` when present; otherwise use `incomingAction.operationType` or the matching `matchupAudit.oppositionOperation`. `finalOperationType` is authoritative: do not fall back to an earlier/stale `incomingAction.operationType` for `matchupAudit`, `actionCostAudit.opposition`, or non-player special-art costs. `actionCostAudit.player.artTier` is not GM authority: it must match pre-turn authority from `soul_state.afterlifeCombatProfile.artTiers` or the player-owned `afterlife_entity_profiles.json` special art profile. `actionCostAudit.opposition.artTier` must match the validated pre-turn `afterlife_entity_profiles.json` profile for the opposition lead actor, with the pre-turn `oppositionSide.leadContestant.actorArtTierSnapshot` accepted only as compatibility fallback. The final `activeConflict.actionEconomy.<side>.current` must match the last current `actionCostAudit.<side>.after` for both player and opposition; if a side has no current `actionCostAudit.<side>`, keep that side's `current` unchanged from the validated pre-turn active conflict. If a special art is used, use either `specialArtAudit` for one used art or `specialArtAudits[]` when both player and opposition use named special arts in the same exchange; never write both fields on one exchange. Every audit object must carry `artId`, `ownerActorType`, `ownerActorId`, `baseOperation`, `costMultiplierPercent`, and non-empty `effectNote`, and must match the validated pre-turn owner profile. If the owner is `player_soul` and the special art powers the player's exchange operation, `actionCostAudit.player` must also include `specialArtId`, `specialCostMultiplierPercent`, `standardEffectiveCost`, and the multiplied `effectiveCost`. Non-player or incoming-action special arts do not multiply the player's ОД cost, but when they power the opposition operation they must belong to the resolved opposition actor from `incomingAction` or `oppositionSide.leadContestant`, `actionCostAudit.opposition.artTier` must use that actor's `specialArts[].tier`, and `actionCostAudit.opposition` must include `specialArtId`, `specialCostMultiplierPercent`, `standardEffectiveCost`, and the multiplied `effectiveCost`. A non-player `specialArtAudit` is invalid unless its `baseOperation` matches the single resolved opposition operation used for `actionCostAudit.opposition`; do not bind it to the player's `exchange.operationType` or an earlier `incomingAction.operationType` when `matchupAudit.oppositionOperation` / `finalOperationType` selected another costed action.
- `activeConflict.resolutionState`: only non-terminal live states: `active`, `concession_pending`, `surrender_pending`, `retreat_pending`, or `ready_to_resolve`.
- Terminal states `resolved` and `repair_cancelled` are valid only after closing the active slot through `mode=resolve` or `mode=repair_cancel`; do not leave terminal state under non-null `activeConflict`.
- `exchangeLog[]` records each meaningful operation with `operationType`, `outcome`, before/after audit, `diceAudit` when contested, `actionCostAudit` when ОД is spent/restored, `rewardAudit` when rewarded, and `incomingAction` when an operation is blocked/countered. Player command `/spiritual_combat_log` / `/журнал_духовного_боя` is read-only and displays this log plus `recentConflicts[]`; do not use Mortal `combat_log_markdown`.
- Spiritual Arts operations are mechanical lanes, not interchangeable prose labels: `pressure` targets `oppositionSideStrain`; `guard` protects `playerSideStrain`, even on setback against direct `pressure` must limit worsening to at most one strain rank, and on full success against direct pressure creates `tempoAdvantage`; `counter` requires `incomingAction` and, on `success`/`partial_success`/`countered`, a measurable payoff (non-empty `counterPayoff`, improved `conflictPosition`, worsened `oppositionSideStrain`, or weakened/reversed existing opposition `controlState`; it cannot create fresh player control from none); `maneuver` moves `conflictPosition` and must not directly change side strain or bypass active opposition `controlState`; if opposition `controlState.restrictedOperations` lists the attempted operation, that operation cannot succeed until the control is answered; `binding` / `force_binding` requires leverage (`player_advantaged`, `player_dominant`, setup, or `decisive_player_success`) and must create/strengthen player `controlState` only when no active opposition control remains; failed binding/force_binding outcomes (`blocked`, `countered`, `setback`) leave `controlState` unchanged on both sides, including player-control rewrites and opposition anti-control deltas; `force_binding` requires strong leverage (`player_dominant`, ready setup, or `decisive_player_success`) and a broader payoff than ordinary binding: at least two distinct `restrictedOperations`; `break_binding` requires binding/forced-handoff/coercive context and must weaken/remove/reverse opposition control; same-level narrowing of opposition `restrictedOperations` counts as weakened `controlState`, while equal/reordered sets do not count; `incarnation_resistance` is only for `force_incarnation` / `guardian_forced` control and must not clear ordinary binding control; failed incarnation_resistance outcomes leave forced-incarnation `controlState` unchanged; `champion_coordination` is only for `champion_duel`; `recover_spiritual_power` / Собрать Средоточие restores ОД and is strong against guard/counter/passive timing but weak against pressure, maneuver, binding, force_binding, and force_incarnation. New/current contested exchanges with `diceAudit` must include `matchupAudit` with `playerOperation`, `oppositionOperation`, `primaryResolutionLane`, `riskProfile`, and `matchupRationale`; when `incomingAction.finalOperationType` is present, `matchupAudit.oppositionOperation` must match that final operation, not stale `incomingAction.operationType`; unchanged historical pre-turn exchanges are not rewritten only to add this field. If an active conflict already has active `controlState`, or the current exchange creates/changes active `controlState`, the exchange must explicitly include both `before.controlState` and `after.controlState`; use `null` or `{ "level": "none" }` to record no active control instead of omitting the field. See `OtherGuides/Afterlife_Combat_Terminology_Glossary.md` for Russian labels, examples, matchup matrix, actionCostAudit, and allowed state deltas.

Tactical matchup audit:
- `pressure` / Давление is the offensive lane: it is strongest against `maneuver`, passive repositioning, and exposed guard because it worsens `oppositionSideStrain`; it must not act as a free position shift or binding.
- `guard` / Защита is the safe defensive lane: it counters `pressure` by reducing or preventing `playerSideStrain` / consequence; even on setback against pressure, `playerSideStrain` may worsen by at most one rank. Full success against direct pressure creates `tempoAdvantage`, a one-use Преимущество for the next eligible non-terminal combat action. It must not worsen `oppositionSideStrain`, improve `conflictPosition`, or remove existing control. It may only stop a new incoming control from being applied.
- `counter` / Контрприём is the risky reversal lane: it counters a named direct `incomingAction` such as pressure, binding, or coercion; it cannot target maneuver/withdraw/surrender/negotiate/passive/no-action and a setback must harm the player side through strain, worse position, or `counterBackfire`. Against control, success may visibly weaken/reverse existing opposition `controlState` or show another measured payoff, but it must not create fresh player control from none.
- `maneuver` / Манёвр is the position lane: it beats passive guard/inaction by improving `conflictPosition`; it is stopped by pressure, opposing maneuver, or control and must not directly change side strain. If opposition `controlState` is active, improve position only after a valid anti-control answer removes or weakens that control.
- `binding` / `force_binding`, `break_binding`, `incarnation_resistance`, and `champion_coordination` are context lanes: control after leverage, anti-control, anti-forced-incarnation, and champion-duel support respectively. `force_binding` is not a stronger synonym for `binding`: it needs stronger leverage and must restrict at least two distinct operations. Control is recorded through `controlState`, not loose prose.
- `recover_spiritual_power` / Собрать Средоточие is the recovery lane: restore ОД through `actionCostAudit`, capped by `actionEconomy.player.max`; it is strongest into guard/counter/passive/no-action and punished by pressure, maneuver, binding, force_binding, or force_incarnation.

Dice audit rule:
- Every contested `mode=exchange` must include `exchange.diceAudit`; every contested `mode=resolve` that determines loss, victory, surrender under pressure, concession under pressure, or Guardian-forced incarnation proof must include `resolution.diceAudit`.
- `diceAudit.diceSource` is `input/turn_request.json.preGeneratedDices1d20`; never use `gachaBaseResult`, hidden random rolls, or GM preference for afterlife conflict results.
- Use two visible d20 entries for a contested side-vs-side check: one player-side die and one opposition-side die. If another documented surface in the same turn already consumed visible dice, use the next unused indices and list them explicitly.
- Required fields: `formulaVersion="afterlife_spiritual_conflict_v1"`, `diceSource`, `diceUsed[]` with `side`, `sourceIndex`, `sides=20`, and `value`, `playerTotal`, `oppositionTotal`, `margin`, `outcomeBand`, and `modifierBreakdown`.
- Преимущество / Помеха in afterlife dice uses `diceAudit.rollMode.<side>` with `effectiveMode=normal|advantage|great_advantage|disadvantage|dire_disadvantage`, `advantageSources[]`, and `disadvantageSources[]`. `advantage` / Преимущество consumes exactly 2d20 and selects the highest; `great_advantage` / Великое Преимущество consumes exactly 3d20 and selects the highest; `disadvantage` / Помеха consumes exactly 2d20 and selects the lowest; `dire_disadvantage` / Тяжкая Помеха consumes exactly 3d20 and selects the lowest. Source arrays accept legacy strings as ordinary sources or source objects with `summary`/`source`/`sourceId`, `level`, and optional `sourceType`. Step cancellation uses strongest positive and strongest negative only: `great_advantage+disadvantage=>advantage`, `great_advantage+dire_disadvantage=>normal`, `advantage+dire_disadvantage=>disadvantage`, `advantage+disadvantage=>normal`; same-direction sources do not stack.
- If `game_state/core/game_settings.json.difficulty` is readable, every new/current contested `diceAudit` must include `difficultyAudit` and the canonical game-difficulty modifier. Difficulty table: `normal` / Нормальная gives opposition `+0` and reward multiplier `100%`; `hard` / Тяжёлая gives opposition `+1` and reward multiplier `125%`; `impossible` / Невозможная gives opposition `+2` and reward multiplier `150%`. `difficultyAudit` must contain `difficulty`, `source="game_state/core/game_settings.json.difficulty"`, `oppositionModifier`, and `rewardMultiplierPercent`; `modifierBreakdown.opposition[]` must sum exactly to that `game_difficulty` modifier, and player-side difficulty modifiers are invalid. The largest difficulty modifier is intentionally smaller than position dominance `+4` and `light_incarnate` lead `+8`, so difficulty raises pressure without making dice stronger than strategy/progression.
- Every exchange with `diceAudit` must include `before.conflictPosition`; omitting the starting position is invalid. Non-`contested` starting position is exactly one real dice modifier with exact matching `position`. If `before.conflictPosition` is `player_advantaged` or `player_dominant`, include one `modifierBreakdown.player[]` item `{ "modifierType": "conflict_position", "source": "conflictPosition", "position": "<before position>", "value": 2|4 }`. If it is `opposition_advantaged` or `opposition_dominant`, include the same single-item shape under `modifierBreakdown.opposition[]`. Do not split, duplicate, blank, omit, or add extra `conflict_position` entries. `contested` means zero `conflict_position` entries.
- Runtime validation compares every `diceUsed[].sourceIndex/value` against the current authoritative `input/turn_request.json.preGeneratedDices1d20`, recomputes side totals from `modifierBreakdown`, and rejects mismatched `margin` or `outcomeBand`. Natural 20/1 is bounded critical logic and bounded criticals are symmetric: a favorable critical for the player (player natural 20 or opposition natural 1) raises a worse margin result only to ordinary `player_success`; an unfavorable critical for the player (player natural 1 or opposition natural 20) lowers a better margin result only to ordinary `opposition_success`; opposed natural criticals cancel back to the margin band. Criticals do not create decisive success/failure by themselves.
- If natural 20/1 changes the margin-derived band, `diceAudit.criticalResult` is required with `playerNaturalRoll`, `oppositionNaturalRoll`, `marginOutcomeBand`, `normalizedOutcomeBand`, `scaleLimit`, and `narrativeConstraint`. Use it to explain why the critical result is plausible at the current side strength and operation scale; do not narrate impossible outcomes just because a die rolled 20.
- `margin = playerTotal - oppositionTotal`. The GM may narrate freely, but `outcome`, strain changes, `conflictPosition`, and terminal proof must match the audit.
- Outcome bands for v1: `margin >= 8` -> `decisive_player_success`; `margin 3..7` -> `player_success`; `margin -2..2` -> `mixed_or_no_effect`; `margin -7..-3` -> `opposition_success`; `margin <= -8` -> `decisive_opposition_success`.
- `no_effect` is allowed only when the action truly produces no state delta; if the player's or opponent's action is contested and changes position, strain, or terminal proof, write `diceAudit`.

Supported `afterlifeSpiritualConflictUpdate.mode` values:

- `start`: create `activeConflict` from `conflictSeed`, `conflictState`, or `activeConflict`.
- `exchange`: append an exchange and update conflict position/strain/resolution state.
- `resolve`: close active conflict, append `recentConflicts[]`, set `activeConflict=null`.
- `repair_cancel`: clear a malformed/impossible conflict without gameplay rewards or punishments.

Non-player lead contestants must carry `actorArtTierSnapshot` and `artAuthoritySource`; do not copy the player's `purchasedArtTierSnapshot` onto Guardians, residents, or radiant actors. Player profile lives in `soul_state.afterlifeCombatProfile` and may carry `enlightenmentRank`, `radianceRank`, `retainedRadianceRank`, `spiritFocusTier`, and `artTiers`.
Player spiritual art upgrades and `Средоточие Души` upgrades are client-owned local operations through `/spiritual_arts` (`sourceSurface=spiritual_arts_local_upgrade`): they may update `soul_state.afterlifeCombatProfile.artTiers`, `soul_state.afterlifeCombatProfile.spiritFocusTier`, or learned special arts under the player profile in `game_state/meta/afterlife_entity_profiles.json`, and spend Ink Feathers or, in ordinary Shining Abode, Light Sparks. `artTiers` reduce action cost; `spiritFocusTier` sets max ОД on new conflict start. The GM reads the resulting profile for conflict resolution but must not author upgrade receipts/reports or mutate art tiers / `spiritFocusTier` / player special-art tiers directly. `Средоточие Души` tier `0/1/2/3/4/5` gives max ОД `6/7/8/10/12/15`; upgrade costs are client-side: Ink Feathers `100 + nextTier * 100`, Light Sparks `8 + nextTier * 4`.

Victorious contested conflict resolution may grant a small validated currency reward. Chaos Sea victories grant `ink_feathers` / Чернильные Перья through `metaStateUpdates.inkFeatherChanges.add`; ordinary active Shining Abode victories grant `light_sparks` / Искры Света by increasing `shining_abode_state.json.lightSparks`. The terminal `recentConflicts[]` proof must contain `rewardAudit` with `realm`, `currency`, `baseAmount`, `opposingLeadStrength`, `sideModel`, `startingConflictPosition`, `challengeTier`, `outcomeMultiplierPercent`, `riskMultiplierPercent`, `riskReason`, `difficultyAudit` when `game_settings` difficulty is readable, `finalAmount`, and `narrativeReason`. For a current-turn reward that resolves the validated pre-turn `activeConflict`, `rewardAudit.sideModel` must match pre-turn `activeConflict.sideModel`, `rewardAudit.startingConflictPosition` must match pre-turn `activeConflict.conflictPosition`, and `rewardAudit.opposingLeadStrength` must come from the pre-turn `oppositionSide.leadContestant.actorArtTierSnapshot` as max standard spiritual-art/authority snapshot value + 1. Canonical formula: Chaos base `10`, Shining base `1`; `challengeTier` is derived from opposing lead strength + sideModel + starting position; `outcomeMultiplierPercent` is `100` for `player_success` and `150` for `decisive_player_success`; risk is `150/125/100/75/50` for `opposition_dominant/opposition_advantaged/contested/player_advantaged/player_dominant`; difficulty multiplier is `100/125/150` for `normal`/`hard`/`impossible`; cap is `120` Ink Feathers or `8` Light Sparks. Formula: `finalAmount = clamp(baseAmount * challengeTier * outcomeMultiplierPercent * riskMultiplierPercent * difficultyAudit.rewardMultiplierPercent / 1_000_000, 0, realmCap)`. Use `mathAudit` for non-trivial afterlife arithmetic authored by the GM and copied into state, especially `afterlifeSpiritualConflictUpdate.resolution.rewardAudit.finalAmount` or contested `diceAudit.margin`; if `referencedBy[]` names such a supported numeric path, `mathAudit.result` must exactly equal that field. Math Assistant is optional for trivial one-step sums and unnecessary for client-owned calculations that the GM does not author. No reward is allowed for `repair_cancel`, `no_effect`, voluntary withdrawal/surrender, pure negotiation/no-contest closures, duplicate reward for the same `conflictId`, invalid realm, or wrong currency.

Source of Light capstone (`Источник Света`) is a separate full-Radiance Shining contract. It is not a Shining core action and does not use `coreActionReceipts[]`. `light_incarnate` / `Воплощение Света` is combat-authoritative only when all closure surfaces are present: `soul_state.afterlifeCombatProfile.capstones.lightIncarnate`, `shining_abode_state.json.sourceOfLightCapstone.completed`, and exactly one matching `source_of_light_incarnated_light` / `Воплощенный Свет` Soul Relic. From `grantedAtTurn` onward, every contested `afterlife_spiritual_conflict_v1` `diceAudit` must explicitly include turn evidence (`exchangeAtTurn`, `resolvedAtTurn`, or `turnNumber`) and the player-side `light_incarnate` modifier: `+8` when the player is the lead contestant, `+4` when the player is only a supporter/champion-side contributor, plus `+4` extra for coercive operations `force_incarnation`, `force_binding`, or `break_binding`. Historical conflict logs before `grantedAtTurn` are not rewritten, and `light_incarnate` modifiers before Source of Light unlock or incomplete closure are invalid.

Forced incarnation rule: voluntary `TriggerIncarnation` remains ordinary Soul Gates/handoff flow. A Guardian forcing the soul into a life is coercive and must be backed either by legacy explicit provocation evidence or by current-turn resolved afterlife spiritual conflict proof. For the conflict path, `recentConflicts[]` must include `mode=resolve`, `resolutionState=resolved`, `resolvedAtTurn=<current turn>`, matching `guardianId`, `operationType=force_incarnation`, and `playerOutcome=lost|surrendered|conceded` or equivalent `resolutionKind=player_loss|player_surrender|player_concession`. The active Guardian, current Abode, reputation threshold, and severity band are evaluated from the validated pre-turn `game_state/meta/guardians.json` snapshot; same-turn edits to `guardians.json` cannot make forced incarnation legal. Do not treat force and consent as the same lifecycle path.

Shining faction lifecycle is canonical on every `factions[]` entry through `factionLifecycle.state`. `factionConflictCampaigns[]` is the canonical visible campaign ledger for long player conflicts against Shining factions. Breakthrough entries need `breakthroughId`, `type`, `resolvedAtTurn`, and `summary`. Do not complete a campaign without the corresponding target faction lifecycle/leadership state.

If one accepted active Shining turn closes a core action, scheduler debt, and another Shining pending contract, apply the contracts compositionally. Example: an accepted `pending_shining_faction_foundings.json` may create a new hall/faction and move supporter residents, while an accepted `open_gates` core action rebuilds gates from that resulting Shining state. If `progressionControl` also requires Shining/resident cycles, those living-world deltas are allowed only when `progression_report.json` is correlated and closes the exact requested bounded counts. The Shining scheduler allowance is narrow. A verified `progressionProcessingReport` may authorize only scheduler-owned Shining/resident/trade progression fields. It does not authorize unrelated Shining surfaces such as `availability`, `coreActionReceipts[]`, `gates`, `gachaSystem.gachaHistory`, `pendingNativeFactionDiscovery`, `preparedIncarnationPackage`, `lightSparks`, `treasury`, or `sourceOfLightCapstone` unless that same accepted turn also closes the separate client-authored contract that owns that surface.

Composite Shining closure validation is snapshot-backed. The client compares current `game_state/meta/shining_abode_state.json`, `game_state/meta/guardian_abode_residents.json`, and `game_state/meta/soul_state.json` against the pre-turn `game_state/control/pending_turn_snapshot` roots plus every accepted closure projection. Missing snapshots surface as `shining_closure_missing_pre_turn_shining_state`, `shining_closure_missing_pre_turn_resident_state`, or `shining_closure_missing_pre_turn_soul_state`; unrelated final diffs surface as `shining_closure_unexpected_shining_state_diff`, `shining_closure_unexpected_resident_state_diff`, or `shining_closure_unexpected_soul_state_diff`. If Soul state changes in the same turn, that change must come from a separate accepted afterlife contract such as `ABODE_OFFERING`; do not hide unrelated Soul edits inside a Shining closure.

Legacy `shining_abode_state.json.pendingNativeFactionDiscovery` is not the normal queue, but if it is non-null in a pre-turn save it is an active state-local contract or malformed fail-closed evidence and must be closed or repaired before starting a new `discover_native_faction` request or sealing the Abode through client-owned `return_to_chaos_sea`. Use the row above and example 14A for object payloads; do not duplicate it into `pending_shining_abode_actions.json`.

### Deterministic `open_gates` Projection

If the request is accepted, the safest GM path is to copy the sanitized client preview `projectedStateFragment.afterFullShiningRoot.gates` into the persisted full `shining_abode_state.json` and then append the matching receipt. If the preview is unavailable, rebuild the draft mechanically:

- Radiance thresholds: `experience 0..99 => tier 0`, `100..219 => tier 1`, `220..379 => tier 2`, `380..579 => tier 3`, `580+ => tier 4`.
- Draft size by Radiance tier: `0=>4`, `1=>6`, `2=>7`, `3=>8`, `4=>10`; pick cap: `0=>1`, `1=>2`, `2=>2`, `3=>3`, `4=>4`.
- Radiance rarity ceiling: `tier 0 common`, `tier 1 uncommon`, `tier 2 rare`, `tier 3 rare`, `tier 4 radiant`; faction strength ceiling: `0..24 common`, `25..49 uncommon`, `50..74 rare`, `75..100 radiant`; a head card uses the lower of those ceilings.
- Candidate sources are Shining faction heads, supported completed Shining projects, and resident descent sources from canonical Shining resident bindings. Do not use Mortal factions, Mortal NPCs, retired/unsupported projects, or non-ascended residents.
- Candidate generation is deterministic from the current canonical Shining root plus resident root. Runtime de-duplicates by `dedupeKey`, keeps deterministic order, writes all candidates to `allCandidateBlessingCards`, takes the first `draftSize` into `availableBlessingCards`, and writes their ids to `shownBlessingCardIds`.
- Rerolls are local later mutations, not the accepted `open_gates` receipt. Accepted `open_gates` starts with `selectedBlessingCardIds=[]`; stale behavior is explicit: later faction/project mutations set `gates.isStale=true`, and a stale draft cannot be used for `prepare_incarnation_package`.

### Exact Shining Forge Mutation Table

Every forge action requires ordinary active Shining Abode, a valid `factionId`, a real Soul Relic `relicId`, enough resources, and at least one supported completed `refinement` project in that faction. Base costs are before any client-authored entitlement discount or service quote already embedded in the pending request: `reshape=10 Feathers/10 Light Sparks`, `retune_property=20/15`, `strengthen_band=30/20`, `stabilize_echo=25/15`, `uplift_rarity=45/30`. Required Radiance tiers are `reshape 0`, `retune 1`, `strengthen 2`, `stabilize 3`, `uplift 4`.

Forge ladders are canonical. Soul Relic rarity upgrades one step only: `common -> uncommon -> rare -> epic -> legendary`. Property band strengthens one step on the same ladder, or numeric bands increment by `+1`. Minimum property counts after rarity uplift are `common=1`, `uncommon=2`, `rare=3`, `epic=4`, `legendary=5`; if uplift would be below the minimum, the request must provide exact `addedProperties[]` and the receipt must echo them. Service multiplier by faction strength is `0..24 => 0.75`, `25..49 => 1.0`, `50..74 => 1.25`, `75..100 => 1.5`; `stabilize_echo` adds `floor(15 * serviceMultiplier)` to `companionManifestationQualityBonus`. Consumed relic refinement entitlements are client/runtime state: supported statuses are `pending_relic_entitlement` before use and `consumed` after use with `consumedAtTurn`/`consumedAtUtc`; `expired` is not a valid `relicRefinementEntitlements` status. Deadline-based `expired` statuses belong only to route/lore/descent style deferred effect arrays.

  - `pending_shining_faction_realignments.json.requests[].realignmentMode`: `accepted_transfer`, `refused_transfer`, `departure_to_neutral`.
  - `factionRealignmentReceipts[].status`: `accepted`, `refused`, `withdrawn`, `departed_to_neutral`. `refused` is valid only for `refused_transfer`; `departure_to_neutral` closes as `departed_to_neutral` or `withdrawn`.
  - `projectArchetype`: `revelation`, `accord`, `provision`, `remembrance`, `refinement`, `passage`, `warding`, `subversion`.
  - `projects[].status`: `active`, `completed`, `retired`; completed/retired projects are retained as civic history, not deleted.
- Canonical Abode resident object fields used by roster, transfer, social, and Shining migration contracts:
  - Required identity/context: `residentId`, `residentName` or `displayName`, `residentKind`, `originType`, `isPresent`, `sourceGuardianId`, `sourceAbodeId`.
  - Required disposition/progression: `bondLevel`, `bondTier`, `abodeDevotionLevel`, `abodeDevotionTier`, `restlessness`, `migrationState`, `abodeDisposition`.
  - Optional but canonical when relevant: `formerGuardianId`, `formerAbodeId`, `linkedSoulRelicId`, `grantedRelicId`, `relatedQuestIds`, `historyLog`, `interactionLog`.
  - Shining-specific extension fields are allowed only for ascended residents: `ascensionState`, `shiningFactionId`, `residentRole`, `factionLoyaltyLevel`, `factionLoyaltyTier`, `factionRestlessness`, `factionRealignmentState`.
- Abode resident canonical disposition/devotion/migration vocabulary:
  - `abodeDisposition.powerSensitivity`, `communalOrientation`, and `stabilityNeed`: `low`, `medium`, `high`.
  - `abodeDisposition.migrationDisposition`: `rooted`, `selective`, `opportunistic`, `wandering`.
  - `abodeDevotionTier`: `alienated`, `uncertain`, `attached`, `devoted`, `steadfast`; derived from `abodeDevotionLevel` ranges `0..19`, `20..39`, `40..59`, `60..79`, `80..100`.
  - `migrationState`: `settled`, `wavering`, `restless`, `considering_departure`, `ready_to_transfer`; derive from devotion/restlessness: `ready_to_transfer` when devotion `<=15` and restlessness `>=70`, `considering_departure` when devotion `<=30` and restlessness `>=55`, `restless` when devotion `<=45` or restlessness `>=45`, `wavering` when devotion `<=60` or restlessness `>=30`, otherwise `settled`.
  - Founder-attraction and ordinary roster residents use the same Abode resident vocabulary; `guest` is never a valid `abodeDevotionTier`.
- Guardian project `assistAudit` / `sabotageAudit` scoring is deterministic. Every axis is an integer `0..2`. `assistScore = DomainRelevance + RiskOrCost + ScarcityOrUniqueness + DirectProjectImpact`; classifications are `<=2 not qualified as project assist`, `3..4 minor assist`, `5..6 meaningful assist`, `7+ major breakthrough`. With `auditKind=defense`, the same bands become `minor defensive help`, `meaningful protection`, and `major defensive breakthrough`, and the Abode Power reason routes as `rival_defense`.
- Guardian project sabotage uses `sabotageSeverityScore = HostileReach + ProjectExposure + DamageIntent + DamageAchieved + PlayerComplicity`; classifications are `<=2 nuisance`, `3..4 minor interference`, `5..7 major sabotage`, `8+ grand strike`. Abode Power deltas are assist `+1/+2/+3` for minor/meaningful/major and sabotage `-1/-2/-4` for minor/major/grand.
- Guardian project `soul_preparation` is next-life-only setup, not a current afterlife reward. Completed `soul_preparation` projects require `projectOutcomeAudit.preparationBudgetPoints` and `projectOutcomeAudit.preparationClaimPriorityBonus`; their `effectState` carries `targetIncarnation`, `preparationBudgetPointsGranted`, `preparationBudgetPointsSpent`, `preparationClaimPriorityBonusGranted`, and `consumedAtLifeStart`. Sabotaged `soul_preparation` projects require `projectOutcomeAudit.hostilePriorityTokensGranted`; their `effectState` carries `targetIncarnation`, `hostilePriorityTokensGranted`, `hostilePriorityTokensSpent`, and `consumedAtLifeStart`. The client consumes these fields during next-life Guardian correction resolution, so the GM must not spend them manually or leave them as perpetual bonuses.
- Guardian corrections are generated by the client at Mortal bootstrap from `next_life_scenario_core.json`, active Guardian state, rival claims, and temporary `soul_preparation` effects. The resulting `game_state/world/guardian_corrections.json` is a readable current-life journal, not a pending file. Matching Abode Power spends use `guardianPowerEvents.reasonType=correction_spend`, `sourceSurface=guardian_corrections`, `sourceId=<correctionId>`, and audit fields `correctionId`, `slotId`, `slotType`, `severity`, `claimStrength`, and `intent`; the event appears in Guardian/Abode Power chronology, but the GM does not author `guardian_corrections.json`.
- Shining blessing-card rarity order is `common -> uncommon -> rare -> epic -> legendary -> radiant`. Project-card bonuses upgrade only one step on that ladder; a tier-3 project that starts at `rare` becomes `epic`, not immediately `radiant`.
- Shining blessing-card token fields are strict everywhere they appear in `gates.*BlessingCards[]` and `preparedIncarnationPackage.selectedCards[]`: `sourceType = head | project | resident_descent`; `effectFamily = lore | social | resource | memory | descent | survival | relic | route`; `rarity = common | uncommon | rare | epic | legendary | radiant`.
- Shining forge blessing rerolls are a client-side `pendingShiningBlessingEffects.relicRefinementEntitlements` resource. The preview must show rerolls before/after; cancel preserves the entitlement, and the client consumes rerolls only after the final forge-request confirmation.
- Shining trade inventory must match the pending request's derived values: `tradeCycleId`, `generatedAtUtc`, `generationTradeTier`, `generationRarityCeiling` (`none`, `common`, `uncommon`, `rare`, `radiant`), `merchantProfile` (normally `shining_faction`), `serviceMultiplierSnapshot`, and item slots with positive `priceInFeathers` plus nested `relicData`. The player preview may show an `expectedTradeInventory` scaffold; it is an audit aid for the canonical `faction.tradeInventory`, not an extra response field.
- Shining trade `relicData.relicId` values are new Soul Relic identities. They must be unique inside one `tradeInventory.items[]` array and must not collide with any existing `soulRelics.equipped[]` or `soulRelics.stored[]` relic id; local purchase appends the relic and rejects overwrite/upsert collisions.
- Guardian trade inventory is stored on the Guardian, while Shining trade inventory is stored on the Shining faction. Do not swap these surfaces.
- Resident history log entries use canonical history identity fields such as `entryId`, `residentId`, `title`, `summary`, `revealedAtTurn`, and `revealedAtUtc`; receipts reference those entries by id when closing history requests.
- Actor journal entries require stable identity and timing. Use explicit entry ids/timestamps rather than anonymous narrative fragments.
- `preparedIncarnationPackage` is frozen state. During Shining handoff the GM preserves it; during `prepare_incarnation_package` the GM creates it with selected cards and draft version; only runtime clears it after successful bootstrap.
- Every `coreActionReceipts[]` entry that closes `pending_shining_abode_actions.json` must echo `quotedCostFeathers` and `quotedCostLightSparks` exactly from the request, including zero-cost actions. Forge receipts are stricter: `forge_relic.retune_property` echoes the exact `replacementProperty`, `forge_relic.uplift_rarity` echoes the exact `addedProperties`, and other forge actions must not invent those payload fields.
- `afterlifeArchiveUpdates` is a GM-authored Soul-state update surface only for exceptional/system archive rewards. Valid commands are `add` with a complete archive `entry` (`archiveId`, `entryType=lore_fragment|secret_record`, `title`, `summary`, `rarity`, `sourceLife`, `acquiredAtUtc`, optional source Guardian fields/tags/reservation) or `remove` with `archiveId`. Ordinary archive consultation/project-fuel closures use `archiveActionResolutions`, not improvised add/remove.
- Archive enum vocabulary is strict. Archive entries use `entryType = lore_fragment | secret_record`; `sourceKind = codex | system`; `reservation.kind = consultation | project_fuel`; pending archive requests use `requestedMode = consultation | project_fuel`; archive action resolutions use `status = accepted | rejected | cancelled`; project-fuel accepted results use `resultMode = project_work | pressure_relief`; consultation accepted outcomes may use `guaranteedArchiveQuestCount`, `questHookCount`, `specialQuestLineUnlocks`, `visibleRivalClueBonus`, and `archiveWarningTierBonus`. Every accepted archive resolution must preserve `requestId`, `archiveId`, requested mode, and the concrete reservation/source identity instead of summarizing them away.
- Derived notification triggers: `afterlife_notifications.json` is client-owned and derived from canonical state/receipts. The list below is the current exhaustive notification-type vocabulary; future runtime additions must update this matrix and coverage tests in the same change. The GM writes only the canonical receipt/state, never manual notification entries.
  - Guardian trade and quest/foundation: `guardian_trade_inventory_ready`, `guardian_trade_pending_attention`, `guardian_quest_available`, `player_guardian_foundation_resolved`.

Supported pending families/statuses include `memorySelection.status=pending_pre_turn_one_selection`, `resourceGrant.status=applied_at_bootstrap`, `relicRefinementEntitlements.status=pending_relic_entitlement`, `pendingSocialEffects.status=pending_first_relation_commit`, `pendingRouteEffects.status=pending_early_route_seed`, `pendingLoreEffects.status=pending_lore_insertion`, `pendingSurvivalEffects.status=pending_first_ruinous_failure`, and `pendingDescentEffects.status=pending_resident_descent`.
