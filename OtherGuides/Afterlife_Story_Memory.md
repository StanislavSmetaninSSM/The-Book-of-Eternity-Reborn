- Внешняя память посмертия lives in `game_state/meta/afterlife_chronicles.json`. Use `afterlifeChronicleUpdates[]` when a Chaos Sea region, Shining Abode district, Guardian Abode, Guardian scene, resident scene, faction zone, playable `Воспоминание`, Source of Light scene, or Saref story scene needs persistent memory. The canonical root is `schemaVersion` plus `chronicles[]`; each chronicle uses `chronicleId`, `scopeType`, `scopeId`, `displayName`, read-only archive `eventDescriptions[]`, current report `lastEventsDescription`, `persistentConsequences[]`, `openThreads[]`, and `lastUpdatedTurn`. Scope types are `chaos_sea_region`, `shining_abode_district`, `guardian_abode`, `guardian_scene`, `resident_scene`, `faction_zone`, `memory_scene`, `source_of_light`, and `saref_story`. The GM must write the current turn report through `lastEventsDescription`; `eventDescriptions[]` is read-only historical archive memory and must not be authored inside `afterlifeChronicleUpdates[]`. Do not put `afterlifeChronicleUpdates` into `output/narrative_response.json`; that file is only for player-facing `response` and `timestamp`. Visible chronicle prose must be fully localized and in-world: use `посмертие`, `Море Хаоса`, `Сияющая Обитель`, and `смертный мир`, not internal English labels such as `afterlife`, `ChaosSea`, `ShiningAbode`, or `MortalWorld`. This is the afterlife analogue of mortal external memory; do not use `worldEventsLog`, `currentLocationData`, `worldMapUpdates`, or Mortal lore files as substitutes.
- Глобальные флаги посмертия live in `game_state/meta/afterlife_global_flags.json`. They are the afterlife-only analogue of Mortal `worldStateFlags`, but they must not use `worldStateFlags` or `removeWorldStateFlags`. Use targeted `afterlifeGlobalFlagUpdates[]` for irreversible afterlife facts: Saref name/Wings reveal, Source of Light facts, Guardian memory restoration, Chaos/Shining politics, soul dissipation, realm lifecycle, and relationship gates. Supported `category` values are `saref`, `source_of_light`, `guardian_memory`, `chaos_politics`, `shining_politics`, `soul_dissipation`, `realm_lifecycle`, and `relationship_gate`. Canonical `flags[]` entries use `flagId`, `category`, `state=active|resolved|obsolete`, `visibility=visible|hidden|gm_only`, `createdAtTurn`, `updatedAtTurn`, `reason`, `evidence`, `linkedActors[]`, `linkedChronicles[]`, and `obsoleteReason` when obsolete. Every update needs `gmThoughtsSummary`, because the GM must document why the global fact changed. Never delete a flag by resending a shorter `flags[]`; mark it `state=obsolete` with `obsoleteReason`. Hidden/gm_only flags must not leak into normal player-facing status, narrative, or public summaries. These flags summarize facts and cannot override stricter canonical contracts such as `main_story_saref_state.json`, Source of Light reward tuples, spiritual conflict proofs, or Shining faction lifecycle.
- Политика Хранителей Моря Хаоса (`chaos_sea_guardian_politics_v1`) lives in `game_state/meta/chaos_sea_guardian_politics.json` and is Chaos Sea-only. Use `guardianPoliticalRelationUpdates[]`, `guardianPoliticalProjectUpdates[]`, `guardianPoliticalInfluenceUpdates[]`, `guardianPoliticalChronicleUpdates[]`, and `completeGuardianPoliticalProjects[]`; canonical state stores `relations[]`, `projects[]`, `influenceZones[]`, `chronicle[]`, optional `playerRole`, `sarefLinks[]`, and `openConflicts[]`. Relations use `relationType` such as `alliance`, `rivalry`, `debt`, `fear`, `patronage`, `memory_oath`, `trade`, `hostility`, or `hidden_dependency`; every political consequence must be explicit in `effects[]`, project outcome, influence zone, chronicle entry, or playerRole. Hidden relations/projects/zones use `visibility=hidden|gm_only` and must set `isPlayerVisible=false` or omit player-facing details; `/guardian_politics` may show a hidden count but not hidden details. This is not Shining faction politics and not Mortal `factionDataChanges`, `factionProjectUpdates`, `completeFactionProjects`, `factionChronicleUpdates`, or `worldMapUpdates`.
- Afterlife Writer's Room lives in `game_state/meta/afterlife_story_outline.json`. Use `afterlifeStoryOutline` for private GM planning in Chaos Sea / Shining Abode: `mainArc`, `realmArc`, `actorSubplots[]`, `factionOrInstitutionArcs[]`, `loomingThreatsOrOpportunities[]`, `pendingRevelations[]`, `nextLikelySceneBeats[]`, `playerAgencyNotes`, and `lastUpdatedTurn`. This is a flexible / гибкий planning surface, not player-visible text, not a prophecy, and не является приказом future GM to force outcomes. If player agency breaks the plan, update the plan rather than ignoring the player's choice. Hidden Saref / Wings notes may stay here as private planning, but must still obey reveal-stage/no-spoiler rules in all player-facing output.
- Hidden main-story state for `Крылья над Бездной` lives in `game_state/meta/main_story_saref_state.json`. Missing file is legacy-valid and means no discovered Saref story state. If present, it is a canonical root, not a loose prompt note: use `schemaVersion`, `revealStage`, `guardianQuestlines`, `latentTraces`, `sarefRevelations`, `sarefAdvantages`, `sarefAdvantageUses`, `factionLinks`, `finalConfrontation`, `defeatOutcomes`, `endings`, `postStoryAgenda`, `playerOathState`, and `sarefPersonalBond`. `guardianQuestlines[].questStates[]` stores `questOrdinal=1..4` with status `latent`, `recognized`, `active`, `ready_to_turn_in`, or `completed`; latent future traces are allowed without revealing the villain, but official memory restoration completes strictly in order `1 -> 2 -> 3 -> 4`. Physical mortal item transfer is forbidden here just like Guardian quest turn-in proof: use memory, image, echo, knowledge trace, or soul resonance. `sarefAdvantages[]` are explicit usable state: each entry has `state=available|spent|passive|disabled|suppressed` and non-empty `applicableScenes[]`; `suppressed` / `disabled` / unknown / already spent advantages cannot be claimed for new scenes. A one-use advantage that is consumed must end as `state=spent`, carry matching `spentAudit`, and have a matching `sarefAdvantageUses[]` usage entry with `usageId`, `advantageId`, `sceneType`, `usedAtTurn`, `consumesAdvantage`, and `summary`. `passive` advantages may be referenced only in applicable scenes and must not be consumed. No-spoiler stages `unknown` and `shadow` must not contain revealed Сареф/Крылья Ангелов proof; `wings_revealed`, `infiltration_active`, `confrontation_available`, or `completed` require enough Guardian fragments/advantages to prove the route was unlocked. The player command `/сареф найти_крылья` / `/saref find_wings` is client-owned and creates `game_state/control/pending_saref_wings_infiltration.json` only in ordinary active `Shining Abode`; the GM closes it through `sarefMainStoryUpdate.mode = reveal_wings | refuse_wings | block_wings`, not through free prose or Mortal faction files. A final confrontation is never off-screen: write `sarefMainStoryUpdate.mode=record_final_confrontation` or canonical `finalConfrontation.status=resolved` with `directScene=true`, `resolvedAtTurn`, `routeType=combat|political|oath_law|metaphysical|hybrid|deal`, `victoryTier=pyrrhic|clean|deep|deal`, `sarefOutcome`, `wingsFactionOutcome`, route proof fields for non-deal routes, and `advantageUseIds[]` that reference valid `sarefAdvantageUses[]`; `deep` victory requires 4 different Guardians with quest 4 completed, and Wings outcomes such as `broken`/`dissolved` must match `shining_abode_state.json.factions[].factionLifecycle.state`. A deal route must use `sarefOutcome=allied`, `wingsFactionOutcome=joined`, root `playerOathState.state=oathbound`, an `endings[]` entry with `endingType=deal`, matching `finalConfrontationId`, `resolvedAtTurn`, and `rewardBundle.resourceReward`, `wingsAccess`, `sarefArt`, `sarefPassive`, and `oathCost`, plus `postStoryAgenda.state=oathbound_to_saref`. The deal is not game over: `postStoryAgenda.assignments[]` stores Сареф's orders against non-Wings Shining factions and each active/completed assignment must point to matching `shining_abode_state.json.factionConflictCampaigns[].campaignId`; use `sarefMainStoryUpdate.mode=record_oathbound_agenda` to update the agenda. The player cannot leave Крылья Ангелов by ordinary voluntary action while `playerOathState.state=oathbound|strained`; breaking it needs a separate oath-break contract. If no significant non-Wings faction remains active/weakened/leaderless, write `postStoryAgenda.dominationScene.status=completed` with `resolvedAtTurn` and the final scene summary: “Больше не осталось никого, кто мог бы противостоять Сарефу.” Victory endings use `endingType=victory` and require `rewardBundle.antiOathProtection`, `antiForeignProtection`, `relic` or `passive`, and `guardianRelationshipEffects[]`; `deep` also requires both relic and passive plus `deepWorldStateEffects[]`. If the player loses a Saref confrontation, record the dramatic defeat only through `sarefMainStoryUpdate.mode=record_defeat_outcome` or the canonical `defeatOutcomes[]` root. Supported `outcomeType` values are `forced_oath`, `exile_to_chaos_sea`, `memory_suppression`, `soul_dissipation`, and `pyrrhic_escape`; every entry needs `outcomeId`, `sceneType`, `resolvedAtTurn`, `summary`, and explicit `gmMotivation`. `forced_oath` must write matching `playerOathState`; `exile_to_chaos_sea` must carry `exileAudit.destinationRealm=Chaos Sea`; `memory_suppression` must carry `memorySuppressionAudit`; `soul_dissipation` must link `conflictId` plus `soulDissipationProofId`; and `pyrrhic_escape` must carry `mitigation.mitigatedByAdvantages[]` referencing valid `sarefAdvantageUses[]`.
- After a deal, breaking Сареф's oath is never casual. Use `sarefMainStoryUpdate.mode=record_oath_break` to write `postStoryAgenda.oathBreakArc`; `state` is `not_started|active|failed|broken`, `route` is `seret|lucian|ilarion|veyra|deep_story_evidence`, and `state=broken` requires `proofSummary`, route proof, `advantageUseIds[]` referencing `sarefAdvantageUses[]` with `sceneType=oath_break`, root `playerOathState.state=broken|oath_reversed`, and serious `consequences[]` such as `renegade_from_wings`, `oath_reversed`, `beloved_traitor`, or `second_confrontation_unlocked`. Romantic/bonded breaks require `beloved_traitor` or an explicit tragic romance outcome note.
- Wings faction model: `factionLinks.shadowTraces[]` records Chaos Sea omens with stage `shadow|name|faction`, `traceId`, and `summary`; `factionLinks.knownAgents[]` records discovered agents with `agentId`, `supporterArchetype=deceived|oathbound|fanatic|opportunist`, optional `importance`/`agentRank`, and `interactionRoutes[]=persuade|free|expose|blackmail|defeat` for important agents. Do not make every known agent the same loyalty type: Сареф's faction contains обманутых, связанных клятвой, фанатиков, and оппортунистов. Before reveal, a materialized Shining faction for Wings may exist only as hidden runtime state with `sarefFactionRole=wings_of_angels` and `sarefVisibility=hidden|rumored`; it must not appear in normal faction UI, faction selection, or player-facing JSON audits. After `wings_revealed`, `factionLinks.wingsFactionId` must point at an actionable Shining `factions[]` actor and hidden `sarefVisibility` must become `revealed`.
- The issue #692 closure audit matrix for the hidden Saref line is archived under `docs/audits/afterlife/saref/`. It is developer/audit evidence rather than normal GM prompt context; read it only when a tracked audit or regression task needs the stage-by-stage walkthrough, player-facing command boundary, validation issue-code evidence, normalizer/cleanup evidence, docs/example evidence, or follow-up issue draft policy for `Крылья над Бездной`.
