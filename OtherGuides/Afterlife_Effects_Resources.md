### Unified afterlife resource authority

Afterlife numeric reserves use the client-owned common ledger: `spiritual_action_points`, `gacha_attempts`, and `blessing_rerolls` live in `game_state/resources/resource_state.json` with immutable transitions in `game_state/resources/resource_history.json`; `game_state/resources/resource_owner_authority.json` is the matching client-owned owner/capacity authority. Definitions, state, history, and owner authority are one guarded quartet. Direct spirit-focus, Shining return-cycle, and blessing-reroll transitions validate the exact persisted authority before-image and commit every changed owner/quartet after-image together. Missing authority in an existing session fails closed; only Fresh New Game may create the first root. Fresh New Game uses one deterministic plan and one coordinated resource write set for the quartet plus all seeded player/system-or-freeform-Guardian owner after-images; the applied result must pass exact existing-session validation. Mortal-incarnation bootstrap is an existing-session transition and requires the exact quartet before-image, with no implicit migration. Afterlife profiles and scoped Shining/conflict state retain only exact `resourceOwnerBindings`; the GM reads current/maximum values only from the documented read-only client projection or state context for the specific action and writes the established `actionCostAudit`, gacha result/history, or blessing-driven action, never direct ledger values or client-owned IDs. Client-owned actor-realm refs derive from exact actor ID + realm, conflict-side owner IDs/refs from realm + `conflictId`, and Shining scope IDs/refs from `shining_abode` + `returnCycleId`; the GM never authors these deterministic identities. Persisted `actionEconomy`, `chargesPerReturn`, `chargesUsedThisReturn`, numeric blessing `rerolls`, and `rerollsSpent` are forbidden. Ink Feathers, Light Sparks, treasuries, faction accounting, progression, relationships, and spiritual power/strain/shield remain in their specialized systems and are not resource definitions. The blessing contract is `blessing_rerolls + freeShape/freeRetune`: only the numeric reroll allocation enters the ledger; the two boolean entitlements remain typed fields. A selected blessing card may carry the client-generated transient `rerollAllocation` object with exactly `resourceKey = blessing_rerolls` and a non-negative integer `amount`. During Mortal bootstrap the client consumes and removes that object, materializes the amount through the common ledger, and leaves only the exact client-owned `rerollResourceBinding` in pending blessing state. The GM must not author, preserve, or reconstruct `rerollAllocation`, `rerollResourceBinding`, current, or maximum. No migration or legacy fallback exists.

A story-facing afterlife effect may also open the common client-owned
`pending_effect_resolutions.json` bounded-resource protocol. Answer the current
safe packet only. Resubmit the same complete semantic turn with receipts only
for that packet; the client carries earlier-wave terminal bindings. The original
candidate, mutation authority, and source authority remain immutable/client-owned.
Sequential packets are causal waves, so the GM does not repeat earlier receipts
in a later wave or reconstruct, retarget, merge, or alter their protected origin.
No resource, effect, use, or lifetime after-image publishes until the final
wave. Changed original commands, retargeted/extra fields, empty terminal replay,
or receipt internals copied into player text fail closed.
When the current safe packet advertises an inclusive minimum of `0`, a
`resource_delta` amount `0` is an explicit terminal zero result. The client
consumes its accepted use and receipt but emits no resource transition,
resource event, or dependent effect activation. This remains distinct from
`narrated_no_state_change`, which omits `amount`. Answer only the result that
matches the fiction in the current packet.
