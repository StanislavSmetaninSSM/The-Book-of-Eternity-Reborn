<instructionblock id="CLI_QTE">
 <title>
  QTE Offer Protocol
 </title>
 <description>
  This block defines the canonical rules for GM-authored QTE offers in CLI mode.
 </description>
 <content type="rule_text">
  <![CDATA[

                    QTE is a SPECIAL cinematic tool for bounded, highly directed scenes in Mortal World.
                    It is NOT a replacement for the normal action-check-driven RPG loop.

                    Core restrictions:
                    - QTE is allowed ONLY in Mortal World.
                    - QTE is allowed ONLY if `game_state/core/game_settings.json.qteEventsEnabled = true`.
                    - QTE is allowed ONLY on an ordinary player-driven turn.
                    - QTE is FORBIDDEN on incarnation turns, life-evaluation turns, validation-repair turns, automatic transition turns, and other system-driven flows.
                    - A QTE-offer turn MUST write `output/qte_offer.json`.
                    - A QTE-offer turn MUST NOT also resolve ordinary state changes for the same situation.
                    - Therefore a QTE-offer turn MUST leave ordinary `game_state/`, `lore/`, and `stories/` files untouched.
                    - In practice, a QTE-offer turn may write only:
                      - `output/qte_offer.json`
                      - `output/narrative_response.json`
                      - `output/interface_updates.json`
                      - `output/debug_logs.json`
                    - If the player declines the QTE offer, the client will request a new ordinary GM turn and the same `qteId` MUST NOT be re-offered immediately.
                    - If the player accepts, the full QTE scene resolves LOCALLY on the client; there is no extra GM turn after acceptance.

                    Client-owned accepted story continuity:
                    - After the ordinary offer turn is accepted, the client appends its ordinary story row before the local QTE starts. This is the client's accepted story append, not GM state authoring.
                    - The existing canonical QTE continuation retains internal `clientStoryAppend` evidence for only that exact client-written row: original source correlation, original prefix and exact afterimage. Local terminal validation and same-root paused/deferred resume verify that exact delta; every other story/history guard stays enabled.
                    - The GM MUST NOT write `stories/*.jsonl`, `clientStoryAppend`, QTE runtime/continuation state or their fingerprints. These are client-owned bookkeeping, never offer fields or GM receipt authority.
                    - A changed authorized story, unrelated new story, stale original source, mismatched runtime link or repeated story append is refused. No permissive history recapture or extra GM narrative turn is allowed.
                    - Same-root QTE continuation uses the current session generation. Active-QTE archive generation rebinding is outside this contract; physical occurrence save/load belongs after terminal QTE. Portable checkpoint hashes are corruption/correlation checks, not cryptographic anti-owner signatures.

                    Deferred terminal effect receipts:
                    - If a selected terminal outcome reaches a bounded effect/resource component, the client enters `awaiting_receipt` and creates `input/qte_effect_resolution_request.json` with `requestKind=qte_deferred_effect_resolution`.
                    - This is a receipt-only task and not an ordinary turn. Read only that request's `safePacket`; do not read or reuse `input/turn_request.json`, create a pending-turn snapshot, run story or progression work, advance lifecycle, or increment the turn counter.
                    - Answer the current wave only through closed `effectResolutionReceipts[]`. Do not write game state, narrative/interface output, `output/qte_effect_resolution_receipts.json`, or `ready/qte_effect_resolution_complete.json` directly.
                    - Construct the receipt objects in memory and call `Complete-BoeQteEffectResolution -Receipts $receipts` as the last action. The helper copies exact correlation, validates the response, writes `output/qte_effect_resolution_receipts.json`, and writes `ready/qte_effect_resolution_complete.json` last.
                    - Do not call `Complete-BoeValidationRepair`: this dedicated receipt task does not reuse the ordinary validation-repair request, helper, ready marker, or full-turn resubmission loop.
                    - On restart, resume the same sealed continuation and current wave. Earlier-wave bindings and the same preallocated identities remain client-owned; never resend prior receipts or reconstruct hidden mechanics.
                    - A next wave receives a new request/wave identity while preserving session, continuation, selected terminal, and semantic authority. Until the final wave, there is no resource/effect after-image, QTE history, story, progression, or turn counter publication.
                    - Only the final successful wave publishes the complete selected QTE outcome atomically. Missing, stale, tampered, cross-session, cross-generation, or mis-correlated files fail closed before mechanics write.
                    - The full shared rules are in `OtherGuides/Effect_Materialization_Contract.md`; the worked two-wave restart example is `mortal_qte_deferred_effect_receipt_waves_v1` in `Examples/E_CLI_QTE_Offer.txt`.

                    QTE Practice Mode:
                    - QTE Practice Mode is client-owned practice for learning implemented QTE mechanics.
                    - It has no rewards: no XP, achievements, Ink Feathers, inventory, quest progress, or other permanent benefits.
                    - It has no GM-authored practice scenes; the GM must not create offers, action types, response fields, or follow-up turns for practice.
                    - Practice does not mutate campaign state, pending campaign actions, ordinary turn state, or permanent reward state.






                    - Ordinary GM-authored QTE offers MUST NOT write client-owned New Game grant markers or permanent Ink Feather reward state.

                    GM authoring responsibility:
                    - A valid `qte_offer.json` MUST contain these top-level fields:
                      - `qteId`
                      - `title`
                      - `offerText`
                      - `introNarrative`
                      - `startChapterId`
                      - `chapters`
                      - `terminalOutcomes`
                    - Optional but supported top-level fields:
                      - `declineHint`
                      - `cinematicJustification`
                      - `sceneImagePrompt`
                      - `scoreModel`
                    - The GM must pre-author the whole scene graph:
                      - `startChapterId`
                      - chapters
                      - actions
                      - QTE checks
                      - routing
                      - terminal outcomes
                    - Every chapter MUST contain a non-empty `actions[]` array.
                    - Every chapter MUST contain:
                      - `chapterId`
                      - `narrative`
                      - `actions`
                    - Every action MUST contain:
                      - `actionId`
                      - `label`
                      - `check`
                      - `routing`
                    - Every `check` MUST contain:
                      - `type`
                      - `baseDifficulty`
                      - `primaryCharacteristic`
                    - `baseDifficulty` MUST be an integer in the range `1..5`.
                    - `startChapterId` is MANDATORY and defines the opening chapter of the scene.
                    - The order of entries inside `chapters[]` does NOT define the start; only `startChapterId` does.
                    - Every `chapterId` and every `outcomeId` MUST be unique within the scene.
                    - Every routing branch MUST point to exactly one target:
                      - `nextChapterId`
                      - or `terminalOutcomeId`
                    - Every action routing MUST contain all three branch objects:
                      - `success`
                      - `partial`
                      - `fail`
                    - Every referenced `nextChapterId` and `terminalOutcomeId` MUST resolve to a real node in the same scene.
                    - Every chapter in the scene MUST be reachable from `startChapterId`.
                    - The scene MUST contain at least one terminal outcome reachable through success-routing.
                    - Every `check.primaryCharacteristic` MUST use one canonical lowercase id:
                      - `strength`, `dexterity`, `constitution`, `intelligence`, `wisdom`, `faith`, `attractiveness`, `trade`, `persuasion`, `perception`, `luck`, `speed`
                    - Optional scoring for long QTE scenes:
                      - `scoreModel` MAY be used by ordinary GM-authored QTE offers.
                      - `scoreModel` is generic QTE scoring; it is NOT practice-mode rewards, achievements, Ink Feathers, inventory, gadgets, resources, or any permanent reward system.
                      - `scoreModel.metrics[]` defines stable lowercase metric ids, player-facing labels, numeric `initial`, `min`, and `max` values, and `visibility`.
                      - Supported metric `visibility` values are `always`, `final`, and `hidden`.
                      - `always` metrics may be shown during active play and in the final score summary.
                      - `final` metrics are shown only in the final score summary.
                      - `hidden` metrics are not shown in default player UI and must not leak as raw ids/debug text.
                      - `scoreModel.ranks[]` defines ending ranks. Non-fallback ranks use `allOf` threshold rules with `metric`, `op`, and `value`; exactly one rank MUST use `fallback: true`.
                      - `scoreModel.rankOrder`, when present, defines deterministic rank evaluation order and MUST include every non-fallback rank id.
                      - Action-level `scoreDeltas` MAY define `success`, `partial`, and/or `fail` arrays. Each delta entry uses `{ "metric": "...", "delta": number }`.
                      - The C# client applies only the selected grade's scoreDeltas, clamps metrics to their bounds, records score audit details in QTE history, and computes the final rank at terminal completion.
                      - Browser clients render scored QTE state read-only and still submit only the existing QTE action grade/result flow; do not add browser-only score authority fields or arbitrary metric-delta posts.
                    - For `BranchChoice`, `check.config.choiceGrade` is MANDATORY and may be ONLY:
                      - `success`
                      - `partial`
                      - `fail`
                    - Every terminal outcome MUST contain:
                      - `outcomeId`
                      - `title`
                      - `finalNarrative`
                      - `gmSummary`
                      - `responseFragment`
                    - Every terminal outcome MUST contain a complete `responseFragment` with the final local mechanical outcome for that branch.
                    - `responseFragment` uses ordinary `GameResponse` field names and is applied locally by the client.
                    - A bounded Mortal penalty may be authored only as `responseFragment.resourceChanges[]` under closed QTE resource contract v1:
                      - `operation` MUST be `damage`.
                      - `target` MUST be exactly `{ "kind": "player", "targetId": "player_current" }`.
                      - `resourceKey` MUST name an existing active resource and `amount` MUST be a positive exact decimal.
                      - `source` MUST be exactly `{ "kind": "narrative_outcome" }`; never author `sourceId`.
                      - `eventRef` MUST be exactly `turn_{sourceTurn}:qte_terminal:{one-based terminal outcome ordinal}:resource:{one-based command ordinal}`.
                      - `reason` MUST be non-empty and describe the selected narrative consequence.
                    - The client validates resource commands in EVERY terminal outcome, including unselected branches, and applies only the selected branch through the common resource reducer and guarded quartet transaction. Exact retry is replay, not a second penalty.
                    - Optional `terminalOutcomes[].physicalInjury` declares a potential player-health injury before selection. Omission preserves resource-only QTE. When present it has exactly five fields: `schemaVersion` = 1; `resourceCommandOrdinal` is a one-based index into that outcome's actual `responseFragment.resourceChanges[]` (existing mutation limit 512) and must name exact `damage` on canonical `health` for `player/player_current`; `maximumSeverityRank` is an explicit integer 1..4, independent of damage amount, with no default IV; `cause` is trimmed nonempty text of at most 2000 characters without controls; `allowedLocationKinds` contains 1..5 unique exact tokens from `anatomical`, `systemic`, `mental`, `spiritual_axis`, `other`. Explicit null, missing/unknown/duplicate/case-confusable or wrong-case fields reject as raw input in every terminal branch, including unselected branches. Do not supply owner/domain, source/profile IDs, hard caps, guarantees, worsening or seals. The client retains the declaration in the frozen offer and its existing continuation fingerprint before selection. After finalized positive Applied canonical health Damage from the selected declared branch, the client publishes one pending occurrence under mortal_qte_terminal_health_damage_v1 in the same resource/effect transaction. The explicit source maximum stays separate from the global hard cap IV; original session/request/snapshot/turn and complete ordered accepted sibling events remain bound to the occurrence. Exact retry preserves occurrence identity across pending or consumed receipts; resource-only/unselected declarations, zero applied damage, replay-only execution, awaiting receipt and preallocation publish no occurrence. On the next ordinary Mortal request use only the current offered public decision draft; never author an occurrence, receipt, source coordinate or seal.
                    - The next ordinary Mortal World request exposes client-owned `woundOpportunities`: default `[]`, or one first eligible player physical opportunity in canonical pending order after complete pending/consumed batch and ordered accepted-event validation against the official new-turn snapshot. A row has exactly `opportunityRef`, `domain`, `maximumSeverity`, `safeContext`; `safeContext` has exactly `target`, `cause`, `allowedLocationKinds`. The maximum is the explicit source bound I..IV, never a damage formula or default IV. The opaque reference is comparison data; the GM must copy no private occurrence ID, owner, carrier path, profile, source coordinates, event vector or fingerprint into it. This safe projection is read-only input. Return a single closed NONE/materialize draft in `output/mortal_wound_decisions.json`: exactly {opportunityRef, decision: none}, or {opportunityRef, decision: materialize, woundRef, proposal}. Copy the exact currently offered reference. With default `[]`, write no decision file. The proposal uses the existing Mortal creation grammar: severity I..offered maximum, a location kind from allowedLocationKinds, and acquisitionNarration verbatim in the ordinary scene. No wrapper, timestamp, source/binding/seal/max fields, permanent IDs or canonical state. The client owns commands, allocation, anchors, history and durable receipts, and consumes the draft only in the same resource/effect/wound transaction; NONE consumes the occurrence without a wound/history transition. Missing/unsolicited/stale/foreign/multiple/null/unknown/duplicate/case-confusable/wrong-case input refuses; changed replay refuses and exact durable replay preserves IDs/history/receipt once. The draft is transient and excluded from save/import archives. Ordinary repair workers may propose only the exact selected draft path for proposal errors; narration-only repair targets the existing output/narrative_response.json response/timestamp and preserves the entire pinned decision/proposal. Public request and decision context remain read-only; never client wound commands, canonical wounds/history/receipts or private source authority, and never broaden output/**. This is Mortal-only; afterlife/spiritual contracts stay unchanged and unsolicited Mortal drafts there refuse. Missing optional roots count as pristine only with signed observed absence; no live fallback.
                    - `resourceDefinitionCreations` and `resourceCapacityChanges` are forbidden inside QTE `responseFragment`. Direct gauge aliases and legacy `current*Change` fields are forbidden and are never converted.
                    - Therefore the GM must not rely on a follow-up GM turn to add the "real" reward after an accepted QTE.
                    - `declineHint` and `cinematicJustification`, if provided, are shown to the player in the QTE offer prompt, so keep them short and readable.

                    Reward rule:
                    - A SUCCESSFUL completion of a QTE scene MUST grant at least positive `experienceGained`.
                    - For validation purposes, a "successful terminal outcome" means any terminal outcome reachable by following one or more `success` branches from `startChapterId`.
                    - This is the minimum reward floor for a successful QTE resolution.
                    - The client will locally convert this successful `experienceGained` into a real increase of the authoritative XP counter in `game_state/player/experience.json`.
                    - If `experience.json` already contains level metadata (`level` or `playerLevel`) plus current-level progress (`experience` or `currentExperience`) and `experienceForNextLevel`, the client will also process the local level-up transition using the standard progression rules from `5.10.A.1` and `5.10.A.2`.
                    - Partial outcomes MAY grant smaller rewards or mixed rewards.
                    - Fail outcomes do not need to grant experience.

                    Recommended scene shape:
                    - Keep QTE scenes short: usually 2-5 chapters.
                    - Use them for:
                      - chase scenes
                      - escapes
                      - collapses / hazards
                      - short infiltration sequences
                      - tightly directed cinematic stunts
                    - Do NOT use them for:
                      - routine exploration
                      - ordinary dialogue
                      - generic action resolution
                      - replacing the normal RPG loop for convenience

                    Node types allowed in QTE v1:
                    - `BranchChoice`
                    - `TimingBar`
                    - `PromptChain`
                    - `BalanceMeter`
                    - `ChargeRelease`

                    Node types allowed in QTE v2:
                    - `MashInput`
                    - `PatternMemory`
                    - `RhythmPulse`
                    - `PrecisionChoice`
                    - `StealthNoise`
                    - `LockPinSet`

                    For `MashInput`, `check.config` is MANDATORY and MUST contain:
                    - `check.config.keys`: non-empty array of unique canonical QTE key tokens: `q`, `w`, `e`, `a`, `s`, `d`, `space`.
                    - `durationMs`: integer from 750 to 10000.
                    - `targetPresses`: positive integer from 1 to 80; it must also be physically possible for `durationMs` at the client limit of 12 presses per second.
                    - `partialThreshold`: number greater than 0 and less than or equal to 1.
                    - Higher `baseDifficulty` raises the effective required press count; a higher relevant `primaryCharacteristic` tier lowers it.
                    - Escape/cancel resolves as fail.
                    - Browser clients support MashInput through #918 mini-games and submit only `success`, `partial`, or `fail` to the existing C# QTE action resolver; do not add browser-only GM config fields.

                    For `PatternMemory`, `check.config` is MANDATORY and MUST contain:
                    - `check.config.alphabet`: non-empty array of unique canonical QTE key tokens: `q`, `w`, `e`, `a`, `s`, `d`, `space`.
                    - `sequenceLength`: integer from 2 to 12.
                    - `revealMs`: integer from 500 to 15000 for the фаза показа, when the client shows the generated sequence.
                    - `inputTimeoutMs`: integer from 1000 to 30000 for the фаза ввода; it must be at least `sequenceLength * 300`.
                    - `allowedMistakes`: integer from 0 to `sequenceLength - 1`, so failure remains possible.
                    - Higher `baseDifficulty` may increase effective sequence length, reduce reveal/input time, or reduce mistake tolerance.
                    - A higher relevant `primaryCharacteristic` tier must not make the same PatternMemory config harder.
                    - Perfect repeat resolves success; an imperfect repeat within tolerance and with meaningful progress resolves partial.
                    - Too many mistakes, timeout, or Escape/cancel resolves fail.
                    - Browser clients support PatternMemory through #918 mini-games and submit only `success`, `partial`, or `fail` to the existing C# QTE action resolver; do not add browser-only GM config fields.

                    For `RhythmPulse`, `check.config` is MANDATORY and MUST contain:
                    - `check.config.pulseCount`: integer from 2 to 16.
                    - `beatIntervalMs`: integer from 300 to 3000.
                    - `hitWindowMs`: integer from 40 to 1000; `hitWindowMs * 2` MUST be strictly less than `beatIntervalMs` so pulse windows do not overlap.
                    - `allowedMisses`: integer from 0 to `pulseCount - 1`, so failure remains possible.
                    - Optional `patternVariation`: `steady`, `accelerating`, or `swing`.
                    - Higher `baseDifficulty` may increase effective pulse count, reduce the hit window, or reduce miss tolerance.
                    - A higher relevant `primaryCharacteristic` tier must not make the same RhythmPulse config harder.
                    - Console RhythmPulse uses Space as the local pulse key and must show visual/textual pulse timing; audio cues are optional enhancement only.
                    - Success resolves when missed pulses stay within tolerance; at least half of pulses hit resolves partial.
                    - Too few hits, timeout, or Escape/cancel resolves fail.
                    - Browser clients support RhythmPulse through #918 mini-games and submit only `success`, `partial`, or `fail` to the existing C# QTE action resolver; do not add browser-only GM config fields.

                    For `PrecisionChoice`, `check.config` is MANDATORY and MUST contain:
                    - `check.config.choices`: array of 2..8 choice objects.
                    - Each choice MUST contain unique non-empty `id`, non-empty player-facing `label`, and `grade` exactly `success`, `partial`, or `fail`; optional `description` and `hint` are player-facing text.
                    - `correctChoiceId`: id of the single choice whose `grade` is `success`.
                    - `timeoutMs`: integer from 1000 to 30000.
                    - Optional `timeoutGrade`: only `fail` or `partial`; never `success`.
                    - Optional `decoyHints`: array of `{ "choiceId": "...", "hint": "..." }` objects, each referencing an existing non-success choice with non-empty hint text.
                    - Console PrecisionChoice must show stable numbered choices, a visible remaining-time cue, and escaped labels/descriptions/hints without layout instability.
                    - Higher `baseDifficulty` reduces effective timeout or hint clarity.
                    - A higher relevant `primaryCharacteristic` tier must not make the same PrecisionChoice config harder.
                    - Selecting a configured choice before timeout resolves to that choice grade.
                    - Timeout resolves as fail by default and may resolve partial when `timeoutGrade` is `partial`.
                    - Unknown choice ids and Escape/cancel resolve fail.
                    - Browser clients support PrecisionChoice through #918 mini-games and submit only `success`, `partial`, or `fail` to the existing C# QTE action resolver; do not add browser-only GM config fields or duplicate gameplay resolution.

                    For `StealthNoise`, `check.config` is MANDATORY and MUST contain:
                    - `check.config.durationMs`: integer from 1000 to 30000.
                    - `startingNoise`: number from 0 to 100; it MUST NOT start above `dangerThreshold`.
                    - `dangerThreshold`: number from 1 to 100.
                      Use a GM-authored value that fits the scene: 50-65 is the normal meaningful stealth band, while values near 70 are intentionally forgiving.
                    - `noiseDriftPerSecond`: positive number from 1 to 100; this is passive noise growth.
                    - `recoveryPerInput`: positive number from 1 to 100; this is how much the recovery input lowers current noise.
                    - `allowedOverThresholdMs`: integer from 0 to `durationMs`.
                    - `gradeThresholds`: object with `successMaxNoise`, `successMaxOverThresholdMs`, `partialMaxNoise`, and `partialMaxOverThresholdMs`; partial thresholds MUST NOT be stricter than success thresholds.
                    - Optional `recoveryKey`: canonical QTE key token; absent means Space. Do not encode RU/EN layout details in GM config.
                    - Optional `recoveryLabel` and `warningLabel`: non-empty player-facing text when present.
                    - Console StealthNoise must show current noise, danger threshold, remaining time, recovery control, and over-threshold warning as readable text; sound/color can only be an enhancement.
                    - Higher `baseDifficulty` increases effective noise pressure or lowers tolerance.
                    - A higher relevant `primaryCharacteristic` tier must not make the same StealthNoise config harder.
                    - Final noise plus accumulated over-threshold time resolve success/partial/fail through `gradeThresholds`; Escape/cancel resolves fail.
                    - Browser clients support StealthNoise through #918 mini-games and submit only `success`, `partial`, or `fail` to the existing C# QTE action resolver; do not add browser-only GM config fields or duplicate gameplay resolution.

                    For `LockPinSet`, `check.config` is MANDATORY and MUST contain:
                    - `check.config.pinCount`: integer from 2 to 8.
                    - `pinWindows`: array with exactly one object per pin. Each window MUST use numeric `min` and `max` bounds inside the 0..100 pin track, with `min < max`; optional `pin` MUST match the one-based window position.
                    - `timerMs`: integer from 1000 to 60000.
                    - `pickDurability`: integer from 1 to 20.
                    - `maxMistakes`: integer from 0 to `pickDurability`.
                    - `pinDriftPerSecond`: number from 0 to 100.
                    - `gradeThresholds`: object with `successMaxTimeMs`, `successMaxMistakes`, `partialMaxTimeMs`, and `partialMaxMistakes`; partial thresholds MUST NOT be stricter than success thresholds. Runtime clamps effective thresholds to the post-difficulty timer and mistake allowance so accepted hard locks still resolve success/partial/fail.
                    - Optional `adjustKey` and `setKey`: canonical QTE key tokens and must be distinct; absent means `q` raises the current pin, `Shift+q` lowers it, and `space` sets it. Do not encode RU/EN layout details in GM config.
                    - Optional `pinLabel`, `durabilityLabel`, and `warningLabel`: non-empty player-facing text when present.
                    - Console LockPinSet must show each pin state, target window, current position, remaining time, mistakes, and pick durability as readable text; sound/color can only be an enhancement.
                    - Higher `baseDifficulty` narrows effective pin windows, increases drift, or lowers timer/mistake forgiveness.
                    - A higher relevant `primaryCharacteristic` tier must not make the same LockPinSet config harder.
                    - Clean all-pins-open within success thresholds resolves success; slow or noisy open within partial thresholds resolves partial.
                    - Broken pick, too many mistakes, unopened pins at timeout, or Escape/cancel resolves fail.
                    - Browser clients support LockPinSet through #918 mini-games and submit only `success`, `partial`, or `fail` to the existing C# QTE action resolver; do not add browser-only GM config fields or duplicate gameplay resolution.

                    Keyboard/layout rule:
                    - QTE reaction checks use physical QTE keys, not ordinary typed prose.
                    - The player-facing key labels are `Q / Й`, `W / Ц`, `E / У`, `A / Ф`, `S / Ы`, `D / В`, and `Space` where those keys are used by the client.
                    - The client handles physical key/RU-EN normalization for QTE checks; the player should not be told to switch OS keyboard layout.
                    - GM-authored QTE configs do not encode player keyboard layout.
                    - This QTE-only normalization does not apply to normal text input, dialogue, action descriptions, names, or narrative text.

                    Image rule:
                    - During the active QTE challenge itself, the client must not interrupt the player with external image viewing.
                    - Scene images may be offered only on post-chapter or post-outcome result screens.
                    - `responseFragment` MUST NOT use the ordinary `image_prompt` channel.
                    - If a QTE scene needs images, use `sceneImagePrompt`, `chapterImagePrompt`, or `outcomeImagePrompt`.
