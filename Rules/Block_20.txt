<instructionblock id="20">
 <title>Mortal Location Materialization v1</title>
 <description>
  Current-schema rules for authoring Mortal locations, directed links, current
  selection, topology, storage/threat commands, bootstrap, and bounded repair.
 </description>
 <instructiontext><![CDATA[

MORTAL LOCATION MATERIALIZATION V1 — NON-NEGOTIABLE MODEL

1. The GM authors complete raw semantics. The client assigns every permanent
   location/link identity, materializationReceipt, seal, identity-index entry,
   lifecycle transition, and derived navigation surface.
2. `game_state/world/world_map.json.locations[]` is the sole durable semantic
   authority for Mortal locations. `world_map.json.links[]` is the sole durable
   authority for directed links.
3. `current_location.json` is a projection of one accepted map location plus
   current-only weather, interactions, chronology, and current storage contents.
4. Names, descriptions, coordinates, ordinals, paths, case-folded values, and
   Unicode-confusable values never identify a location or link. Identity is
   case-sensitive and Unicode-exact.
5. knownExits and adjacencyMap are client-derived. The GM never writes either
   field. One directed accepted link produces at most one directed visible edge;
   the reverse direction requires its own accepted link.
6. Receipt-less canonical locations/links are invalid. The game has not shipped,
   so no legacy promotion or missing-z compatibility exists.

The only raw creation routes are:

- `currentLocationData` + `materialization.route=current_scene_creation` for one
  genuinely new selected current scene;
- `worldMapUpdates.newLocations[]` +
  `materialization.route=world_map_creation` for each genuinely new remote scene;
- `worldMapUpdates.newLinks[]` +
  `materialization.route=world_map_link_creation` for each genuinely new
  directed link.

Every creation has `locationId = null` or `linkId = null`, one exact turn-unique
`initialId`, one independent materializationId, exact sourceTurn/sourceAuthority,
state `complete`, and a complete `materialization.sections` declaration.

Never author materializationReceipt, a permanent locationId/linkId,
`location_identity_index.json`, receiptId, seal, transition history, requestId,
sessionId, reservationId, or client rollback/snapshot state.

]]></instructiontext>

For `worldMapUpdates.newLocations[]`, use the same complete shape but route
`world_map_creation`. A remote location may be hidden, rumored, discovered, or
visited, but it receives no current-only fields and its storage `contents` must
be empty. For `currentLocationData`, currentWeather/currentInteractions/
currentChronology may be added without replacing any governed map section.

Physical shape is closed:

- outdoor: non-empty biome and biomeDescription, `indoorType: null`;
- indoor: `biome: null`, `biomeDescription: null`, non-empty indoorType.

Coordinates contain numeric/integer x, y, and z. They are unique placement,
never identity. Parent selectors use at most one exact `parentLocationId` or
`parentInitialId`; they must resolve uniquely and must not form a cycle.

Discovery pairs are closed:

- hidden/gm_only with null rumorSummary;
- rumored/player_known with non-empty rumorSummary;
- discovered/player_known with null rumorSummary;
- visited/player_known with null rumorSummary.

Every required section is `populated`. Each governed optional collection is
either physically populated with disposition `populated`, or physically empty
with disposition `empty_by_design` and a concrete in-world reason. Do not use
omission, null placeholders, or invented semantic defaults.

Ordinary source authority is exactly
`{ "kind":"turn_outcome", "authorityId":"turn_<sourceTurn>" }`.
Bootstrap authority is the exact open scaffold request described in Rule 20.7.

Exactly one source selector and one target selector is non-null. A permanent
selector binds one exact permanent locationId. A temporary selector binds one
accepted same-turn initialId. Missing, dual, non-string, whitespace-padded,
wrong-case, Unicode-confusable, historical, self, ambiguous, or cross-realm
selectors fail closed. Do not infer an endpoint from name, coordinates,
description, visible direction, or another link.

Set a location topology section to `populated` exactly when accepted incident
links exist in the same creation package. Otherwise use `empty_by_design` with
a reason. A narrative-only unresolved exit is ordinary prose/current
interaction with no initialId, linkId, endpoint selector, coordinate reservation,
or map node; it never asserts a canonical route.

  <rule id="20.3">
   <title>Existing movement and narrow location lifecycle</title>
   <instructiontext><![CDATA[

Move/select an existing scene with exact permanent locationId:

```json
{
  "currentLocationData": {
    "locationId": "loc_exact_destination",
    "lastEventsDescription": "Что изменилось при прибытии",
    "currentWeather": {},
    "currentInteractions": [],
    "currentChronology": []
  }
}
```

This selector carries no coordinates, name, initialId, placement, difficulty,
envelope, receipt, or derived exits. Re-selecting the exact current location is
allowed. Changing location requires one accepted pre-turn open directed link whose
sourceLocationId is the exact pre-turn current locationId, whose targetLocationId
is the requested exact destination, whose access is `open` with an empty
requirements array, and whose discovery and destination are non-hidden and
`player_known`. A reverse-only, hidden, `conditional`, or `sealed` link does not
authorize traversal. This selector never creates reachability.
Existing movement carries only exact selection and operational fields. Never
include locationStorages or contents in that payload. The client preserves
storage item contents, parks the previous current scene, and restores the
destination scene atomically. Storage metadata changes remain separate
`worldMapUpdates.storageUpdates[]` commands.

Persistent edits use `worldMapUpdates.locationUpdates[]`, exact permanent
locationId, and at least one field from this closed mutable catalog:
name, displayName, purpose, description, image_prompt, internalDifficulty,
externalDifficulty, lastEventsDescription, factionControl, actorBindings,
loreBindings, customStates. `eventDescriptions` is a system-managed archive;
`activeThreats` changes only through the atomic threat commands below. Do not
move, reparent, reidentify, reseal, or change discovery through this patch.

Discovery advances only through `worldMapUpdates.locationDiscoveryTransitions[]`:

```json
{
  "locationId": "loc_exact",
  "fromTier": "hidden",
  "toTier": "rumored",
  "toAudience": "player_known",
  "rumorSummary": "За болотом видели огни старой крепости.",
  "reason": "Герой получил точный слух от картографа."
}
```

Allowed forward edges are hidden→rumored/discovered/visited,
rumored→discovered/visited, and discovered→visited. The exact pre-state must
match. A transition never reveals a hidden link or supplies identity by itself.

]]></instructiontext>
  </rule>

  <rule id="20.4">
   <title>Exact link lifecycle</title>
   <instructiontext><![CDATA[

Update one accepted link with `worldMapUpdates.linkUpdates[]` and exact
permanent identity: use the exact permanent linkId. Allowed fields are name,
description, directionLabel, access,
and discovery. A complete access patch has state (`open`, `conditional`, or
`sealed`), reason, and requirements. A discovery patch carries exact fromTier,
toTier, toAudience, and rumorSummary. Endpoints, identity, linkType, route,
envelope, and receipt are immutable.

Remove one accepted link only through `worldMapUpdates.linkRemovals[]`:

```json
{
  "linkId": "lnk_exact",
  "sourceLocationId": "loc_exact_source",
  "targetLocationId": "loc_exact_target",
  "reason": "Мост окончательно разрушен паводком."
}
```

All three IDs must match the exact accepted pre-state. Removal retires only that
directed link and its client index entry. It never deletes either endpoint,
never removes a reverse link implicitly, and never permits reuse of retired
initial/materialization evidence.

]]></instructiontext>
  </rule>

  <rule id="20.5">
   <title>Exact governed companion commands</title>
   <instructiontext><![CDATA[

Location storages and threats remain semantic children of one exact accepted
location. Their IDs are case-sensitive and Unicode-exact; display names are not
authority.

- `worldMapUpdates.storageUpdates[]` binds exact targetLocationId + storageId
  and contains a non-empty `update` object with only `newName`,
  `newDescription`, `newCapacity`, and/or `newOwner`. The client applies this
  partial patch while preserving exact storage identity and item contents.
- `worldMapUpdates.storagesToRemove[]` binds exact targetLocationId + storageId.
  Removal is accepted only after that storage has no item contents; item
  lifecycle authority must move or destroy bound items first.
- `worldMapUpdates.threatsToAdd[]`, `threatsToUpdate[]`,
  `threatsToRemove[]`, and `completeThreatActivities[]` bind exact accepted
  location/threat authority according to their closed command shapes.
- A new threat has `threatId = null`. For an existing location use exact
  `targetLocationId`; for a same-turn new location use
  `targetLocationId = null` plus exact `initialTargetLocationId`. The client
  assigns the permanent `threat_...` ID. `threatsToUpdate[]` deep-merges its
  non-terminal partial threat/currentActivity patch; update, removal, and
  completion for the same threat cannot be mixed in one accepted turn.
- `completeThreatActivities[]` is valid only when the exact threat already has
  non-null currentActivity in the accepted pre-turn location. The client
  archives the completed activity in system-managed `eventDescriptions`, then
  sets `currentActivity` to null. Do not author that archive entry directly.

These commands mutate canonical `world_map.json`, rebuild the current projection
when present, and append client-owned location lifecycle evidence. The immutable
materialization section dispositions continue to describe the creation payload;
later accepted storage/threat count changes do not rewrite or reseal that
historical envelope. These dispositions are immutable creation evidence, not
live counters. Any unknown `worldMapUpdates` command fails closed.

Remote new location storages cannot contain raw items. A genuinely new item in
an accepted same-turn current-location storage follows the independent Mortal
Item Materialization v1 `storage_placement` route with exact
`<initialLocationId>:<storageId>` source authority. Moving an accepted item is
an exact itemId transfer and preserves its envelope/receipt. Location creation
does not authorize item, storage, actor, faction, lore, or threat identity
invention outside their own contracts.

]]></instructiontext>
  </rule>

  <rule id="20.6">
   <title>Client-owned canonical state and no-legacy policy</title>
   <instructiontext><![CDATA[

The GM reads canonical map/current state from Context but never writes canonical
receipts or identity history. The client owns:

- `game_state/world/location_identity_index.json`;
- materializationReceipt, receiptId, seal, permanent IDs, transitions;
- current projection assembly and all derived map/navigation DTOs;
- rollback snapshots, pending validation state, and repair diagnostics.

Never infer identity from a display name. Never use case-insensitive matching,
Unicode normalization, coordinate matching, slugs, ordinals, file paths,
knownExits, adjacencyMap, aliases, or historical retired origins as authority.
Never promote receipt-less development data. If the canonical snapshot is
missing, malformed, ambiguous, or inconsistent with the index, stop the turn.

]]></instructiontext>
  </rule>

  <rule id="20.7">
   <title>Mortal bootstrap</title>
   <instructiontext><![CDATA[

Fresh Mortal state contains neutral empty map/current/index roots and one
client-owned `game_state/control/mortal_bootstrap_scaffold.json`. The GM must
not create, delete, settle, or alter the scaffold.

For an open scaffold, one coherent full-turn response must materialize:

1. one complete visited/player_known start through `currentLocationData` with
   exact reserved initialId, coordinates, sourceTurn, and sourceAuthority
   `{kind:"mortal_bootstrap_scaffold", authorityId:<exact request>}`;
2. either one complete reserved neighbor through `newLocations[]` plus one
   complete reserved directed link through `newLinks[]`, or one narrative-only
   unresolved exit that asserts no canonical identity/endpoint/reservation.

The client validates the pre-turn scaffold byte/semantically exactly, accepts
the ordinary creation contracts, assigns permanent IDs/receipts, and only then
settles the scaffold. Missing, rewritten, forged-settled, wrong-case,
wrong-coordinate, or partially consumed reservations fail closed.

]]></instructiontext>
  </rule>

  <rule id="20.8">
   <title>Bounded repair and full-turn resubmission</title>
   <instructiontext><![CDATA[

A safe issue may produce a bounded `mortal_location_materialization_repair`
packet only when one exact actor, carrier, route, raw coordinate, target file,
and repairable field are proven. Permanent identity, receipt/seal, source
authority, bootstrap scaffold, identity index, snapshot/rollback state,
ambiguous selectors, confusables, historical replay, duplicate JSON properties,
or mixed protected targets always stop before GM dispatch.

Before an actionable packet is dispatched, the client restores the validated
pre-turn baseline. The GM/worker must perform full-turn resubmission: regenerate
one complete coherent raw package, including all intended location, actor,
faction, item, narrative, interface, and other turn outputs. Writing only a
ready marker, patching canonical files in place, or resubmitting only the named
leaf is invalid. Required paths must be freshly and semantically resubmitted;
stale or formatting-only output is rejected.

The player sees only a generic in-world failure/status. Validation codes,
repair instructions, actor IDs, paths, receipts, seals, indexes, snapshots,
rollback evidence, worker/harness terminology, and packet DTOs are operator-only
and must not appear in console/browser/narrative/map/quest/news output.

]]></instructiontext>
