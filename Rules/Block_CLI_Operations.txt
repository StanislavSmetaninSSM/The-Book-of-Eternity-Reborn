 <title>
  CLI Agent File System Operations
 </title>
 <description>
  This block defines how the CLI Agent operates with the file-based game system. It provides protocols for reading game state, 
  processing turns, and writing distributed game data to maintain full compatibility with existing rule blocks.
 </description>
 <instructiontext>
  <![CDATA[

            The CLI Agent operates as a Game Master in a file-based environment. Instead of receiving a single JSON request and returning a single JSON response, 
            the CLI Agent monitors file system changes, reads distributed game state, processes turns using existing rule blocks, 
            and writes results back to distributed JSON files.

            ALL EXISTING RULE BLOCKS (1-32) REMAIN FULLY APPLICABLE. The CLI Agent simply adapts the input/output mechanism 
            while preserving all game logic, calculations, formulas, and narrative rules.

            ]]>

   </title>
   <description>
    Defines the standard folder structure and file organization for CLI-based game sessions.
   </description>
   <content type="rule_text">
    <![CDATA[

                    The CLI Agent operates within a standardized folder structure:

                    game_session/
                    ├── input/                      # Entry point for new turns
                    │   └── turn_request.json       # Main turn processing trigger
                    ├── game_state/                 # Distributed game data (55+ JSON files)
                    │   ├── core/                   # Narrative & player status (3 files)
                    │   ├── player/                 # Player character data (10 files)
                    │   ├── inventory/              # Item system (8 files)
                    │   ├── world/                  # World state (7 files)
                    │   ├── quests/                 # Quest management (3 files)
                    │   ├── npcs/                   # NPC system (14 files)
                    │   ├── combat/                 # Combat state (3 files)
                    │   ├── factions/               # Faction system (6 files)
                    │   ├── meta/                   # Soul System & Guardians (5 files)
                    │   ├── misc/                   # Vehicles & storage (5 files)
                    │   ├── control/                # Game flow control (3 files)
                    │   └── history/                # Chat and interaction history (3 files)
                    ├── lore/                       # Lore and active world dossiers
                    │   ├── chaos_sea/              # Persistent meta-lore across incarnations
                    │   ├── current_world/          # Current incarnation world lore
                    ├── world_profiles/            # Reusable mortal-world profiles (one file = one profile)
                    ├── mods/                       # Global system mods (one file = one mod)
                    ├── saves/                      # Save/load system
                    │   ├── autosaves/              # Automatic saves
                    │   ├── manual_saves/           # Player manual saves
                    │   └── checkpoint_saves/       # Life transition saves
                    ├── output/                     # Client communication
                    │   ├── narrative_response.json # Main narrative
                    │   ├── interface_updates.json  # UI updates
                    │   └── debug_logs.json         # GM thoughts for debugging
                    ├── ready/                      # Processing completion signals
                    │   ├── turn_complete.json     # Signals processing is done
                    │   └── turn_error.json        # Signals processing error
                    └── rules/                      # Symbolic links to rule blocks (readonly)
                        ├── Block_1.txt → ../../../Rules/Block_1.txt
                        ├── Block_2.txt → ../../../Rules/Block_2.txt
                        └── ... (all rule blocks)

                    CRITICAL: The CLI Agent MUST NOT modify files in the rules/ directory. These are readonly references.

  <rule id="CLI.2">
   <title>
    Turn Processing Workflow
   </title>
   <description>
    Defines the step-by-step process for CLI Agent turn execution.
   </description>
   <content type="rule_text">
    <![CDATA[

                    The CLI Agent processes turns using this workflow:

                    **PHASE 1: TRIGGER DETECTION**
                    1. Monitor input/turn_request.json for new file creation or modification
                    2. Validate turn_request.json schema and content
                    3. Set processing lock to prevent concurrent execution

                    **PHASE 2: STATE LOADING**
                    1. Read all relevant files from game_state/ directories
                    2. Construct complete game context object (equivalent to API request context)
                    3. Validate data integrity and cross-references
                    4. If needed, write optional structured diagnostics (for example game_state/history/error_log.json), but the authoritative terminal error path is still ready/turn_error.json

                    **PHASE 3: RULE APPLICATION**
                    1. Apply existing TaskGuides (Step_0, Step_1, Step_2) using loaded context
                    2. Use ALL existing rule blocks (1-32) exactly as written
                    3. Generate complete response object as if processing API request
                    4. Log all calculations in output/debug_logs.json

                    **PHASE 4: STATE DISTRIBUTION**
                    1. Parse response object according to CLI.3 (File Distribution Protocol)
                    2. Update affected files in game_state/ directories using atomic operations
                    3. Create backup files before any modifications (.backup extension)
                    4. Validate written data against schemas

                    **PHASE 5: CLIENT COMMUNICATION**
                    1. Generate output/narrative_response.json for client display
                    2. Generate output/interface_updates.json only if this turn actually changes dialogueOptions and/or image_prompt
                    3. Update output/debug_logs.json with GM thoughts
                    3.A. Treat output/*.json as fresh per-turn transient artifacts for the CURRENT sessionId/requestId/turnNumber only
                        - rewrite current-turn payloads fully
                        - do NOT append cross-turn history there
                        - do NOT leave stale previous-turn payloads in place as if they were still valid
                    4. Create ready/turn_complete.json signal file
                    5. Clean up backup files on successful completion

                    **ERROR HANDLING:**
                    - If any phase fails, restore all .backup files
                    - Optionally log detailed diagnostics in game_state/history/error_log.json
                    - Create ready/turn_error.json with error details (authoritative client channel)
                    - Never leave the system in a partial update state

                    ]]>

  <rule id="CLI.3">
   <title>
    File Distribution Protocol
   </title>
   <description>
    Maps API response fields to specific JSON files and defines atomic update operations.
   </description>
   <content type="rule_text">
    <![CDATA[

                    **CORE MAPPING: API Response → File System**

                    The CLI Agent takes a complete response object (as generated by existing rules) and distributes fields to files:

                    **NARRATIVE & PLAYER STATUS:**
                    - Authoritative GM-authored outputs: output/narrative_response.json ← response, output/debug_logs.json ← gm_thoughts_markdown, output/interface_updates.json ← dialogueOptions/image_prompt when this turn actually needs interface payload
                    - These output/*.json files are fresh per-turn transient artifacts, not persistent state. Rewrite them for the current request only and never reuse stale payload from a previous turn.
                    - For an ordinary accepted GM turn, output/narrative_response.json.response is mandatory and must contain non-empty player-facing narrative text.
                    - game_state/core/player_status.json ← playerStatus, currentPoiseChange
                    - playerStatus is flattened into the root of player_status.json; do NOT save it there as nested { \"playerStatus\": { ... } }
                    - In Mortal World, player_status.json is a mandatory core file and cannot be omitted
                    - game_state/core/system_mods.json ← client-authored manifest of active global system mods
                    - Only system_mods.json.activeMods[] is canonical for GM processing; disabled files in game_session/mods must be ignored
                    - game_state/control/incarnation_world_setup.json ← client-authored pending world setup before incarnation
                    - lore/current_world/world_directives.json ← client/player-authored persistent active-world dossier

                    **PLAYER CHARACTER DATA:**
                    - game_state/player/skills_active.json ← activeSkillChanges, removeActiveSkills
                    - game_state/player/skills_passive.json ← passiveSkillChanges, removePassiveSkills
                    - game_state/player/skill_mastery.json ← skillMasteryChanges
                    - game_state/player/effects.json ← playerActiveEffectsChanges
                    - game_state/player/weight_calc.json ← calculatedWeightData

                    - game_state/player/experience.json ← experienceGained, playerEffortTrackerChange
                    - game_state/player/wounds.json ← playerWoundChanges
                    - game_state/player/custom_states.json ← customStateChanges
                    - game_state/player/stealth.json ← playerStealthStateChange
                    - game_state/player/transformation.json ← playerAppearanceChange, playerImagePromptChange, playerRaceChange, playerRaceDescriptionChange, playerClassChange, playerClassDescriptionChange, playerAutoCombatSkillChange, playerCharacterNameChange

                    **INVENTORY SYSTEM:**

	                    - Canonical stored shape for item_resources.json: entries[] with item identity + resource / maximumResource / resourceType
	                    - game_state/inventory/item_text_updates.json ← updateItemTextContents

                    - game_state/inventory/recipes.json ← addOrUpdateRecipes, removeRecipes
                    - game_state/inventory/storage_operations.json ← moveToLocationStorage, retrieveFromLocationStorage

                    **WORLD STATE:**
                    - game_state/world/current_location.json ← currentLocationData
                    - game_state/world/world_map.json ← worldMapUpdates
                    - worldMapUpdates atomic commands include newLocations, locationUpdates, storageUpdates, storagesToRemove, newLinks, linkUpdates, linksToRemove, threatsToAdd, threatsToUpdate, threatsToRemove, completeThreatActivities
                    - game_state/world/world_events.json ← worldEventsLog
                    - game_state/world/rival_soul_arcs.json ← UpdateRivalSoulArcs
                    - game_state/world/world_flags.json ← worldStateFlags, removeWorldStateFlags
                    - game_state/world/world_time.json ← timeChange, setWorldTime
                    - game_state/world/weather.json ← weatherChange
                    - game_state/world/progression.json ← updateWorldProgressionTracker, updateFactionProgressionTracker
                    - game_state/control/progression_report.json ← progressionProcessingReport
                    - game_state/control/progression_schedule.json ← client-authoritative progression scheduler state
                    - GM MUST NOT write progression_schedule.json; accepted turns that mutate it are rejected
                    - world_time.json is intentionally mixed-shape in the current CLI runtime:
                      - accepted-turn command surface may persist timeChange or setWorldTime
                      - normalized absolute state may instead appear as year + monthName + dayOfMonth + timeOfDay + currentTimeInMinutes
                      - client/runtime reads both forms for compatibility
                    - weather.json is also dual-shape in the current CLI runtime:
                      - direct weather fields at file root are valid
                      - nested weatherChange object is also valid
                      - client/runtime reads both forms for compatibility
                    - currentLocationData is dual-shape: for a truly new location send the full Location Object; for a known location revisit the base shorthand is locationId + coordinates + lastEventsDescription
                    - When the player's CURRENT location also needs a storage-access or difficulty-profile update this turn, currentLocationData may additionally carry locationStorages and/or internalDifficultyProfile/externalDifficultyProfile alongside that known-location shorthand
                    - eventDescriptions is a read-only location archive: read it from context if present, but do NOT emit it inside currentLocationData or worldMapUpdates; write only lastEventsDescription for current-turn history

                    - game_state/quests/plot_outline.json ← plotOutline

                    - game_state/npcs/npc_fate_cards.json ← NPCFateCardUnlocks
                    - game_state/npcs/npc_custom_states.json ← NPCCustomStateChanges

                    - game_state/combat/enemies.json ← enemiesData
                    - game_state/combat/allies.json ← alliesData
                    - game_state/combat/combat_log.json ← combat_log_markdown

                    - faction_resources.json is canonically stored as entries[] with metaResources + strategicGoods; stored metaResources must keep resourceName/currentStockpile/incomePerCycle/upkeepPerCycle, and stored strategicGoods must keep resourceName/currentStockpile/incomePerCycle
	                    - faction_projects.json is canonically stored as activeProjects[] + completedProjects[]
                    - faction_custom.json is canonically stored as entries[] with customStates; each stored custom state remains a complete canonical Custom State Object, not an identity-only stub
	                    - if a new same-turn faction is authored only with initialId/initialFactionId, the client normalizes that temporary tag into the stored factionId inside canonical faction files for that accepted turn; later turns must target permanent factionId

                    - game_state/meta/soul_state.json ← metaStateUpdates
                    - game_state/meta/guardians.json ← UpdateGuardians
                    - game_state/meta/player_behavior.json ← playerBehaviorAssessment, historyManipulationCoefficient

                    - UpdateVehicles accepts partial updates for existing vehicles, but availability/location invariant remains mandatory:

                    **READY SIGNAL:**
                    - ready/turn_complete.json ← completion signal with metadata
                    - game_state/misc/characteristics.json ← setCharacteristics

                    - game_state/control/ascension.json ← AscensionTrigger (real Chaos Sea-only ascension transition; valid only at maximum Enlightenment with explicit playerChoice=Ascension, and never together with TriggerLifeEnd)

                    **HISTORY AND CONTINUITY:**
                    - game_state/history/chat_log.json ← client-maintained session metadata
                    - stories/*.jsonl ← client-maintained narrative continuity history for GM/player reading

                    1. Create .backup files for all affected JSON files
                    2. Update files in dependency order (see CLI.4)
                    3. Validate each file after writing
                    4. If any validation fails, restore all backups and abort
                    5. Delete backup files only after all updates succeed

  <rule id="CLI.4">
   <title>
    Atomic Operations and Dependencies
   </title>
   <description>
    Defines which files must be updated together and in what order to maintain data integrity.
   </description>
   <content type="rule_text">
    <![CDATA[

                    **ATOMIC OPERATION GROUPS:**
                    These files MUST be updated together as atomic operations to prevent data corruption:

                    **GROUP 1: Location Changes**
                    - game_state/world/current_location.json
                    - game_state/world/world_map.json
                    Reason: Location updates must sync with world map state

                    **GROUP 2: Combat State**
                    - game_state/combat/enemies.json
                    - game_state/combat/allies.json  
                    - game_state/combat/combat_log.json
                    - game_state/core/player_status.json (if combat affects player)
                    Reason: Combat state must be consistent across all participants

                    **GROUP 3: NPC State Changes**
                    All game_state/npcs/ files that reference the same NPCId must update together
                    Reason: NPC data integrity across multiple aspects

                    **GROUP 4: Soul System Operations**
                    - game_state/meta/soul_state.json
                    - game_state/meta/guardians.json
                    - game_state/quests/soul_quests.json (if affected)
                    Reason: metaStateUpdates and Guardian operations are interconnected

                    **GROUP 5: Inventory Operations**
                    - game_state/inventory/items.json
                    - game_state/inventory/item_movements.json
                    - game_state/inventory/item_removals.json
                    - game_state/player/weight_calc.json
                    Reason: Item state changes affect weight and organization

                    **UPDATE DEPENDENCY ORDER:**
                    1. Core player status updates (health, poise, effects)
                    2. World state changes (location, map, flags)
                    3. Inventory and item operations
                    4. NPC state updates
                    5. Quest progression
                    6. Faction changes
                    7. Meta/Soul system operations
                    8. Combat state (if applicable)
                    9. Vehicle and storage access
                    10. Game flow control (life transitions, ascension)

                    **ROLLBACK PROTOCOL:**
                    If any atomic group fails to complete:
                    1. Immediately stop all further updates
                    2. Restore ALL .backup files from the current turn
                    3. Optionally log detailed diagnostics in game_state/history/error_log.json
                    4. Create ready/turn_error.json as the authoritative terminal error signal
                    5. Leave system in previous stable state

                    **VALIDATION CHECKPOINTS:**
                    After each atomic group update:
                    1. Validate JSON schema compliance
                    2. Check cross-reference integrity
                    3. Verify mathematical constraints (reputation ranges, health percentages, etc.)
                    4. Confirm required fields are present

                    **REALM-AWARE DISTRIBUTION GUARD (MANDATORY):**
                    Before writing any distributed files, determine the active realm from
                    game_state/meta/soul_state.json.currentRealm.

                    IF REALM = "Chaos Sea" OR "Shining Abode":
                    - DO NOT write combat files
                    - DO NOT write faction files
                    - DO NOT write weather/time files
                    - DO NOT write mortal quest updates
                    - DO NOT write regular NPC updates for Guardians
                    - DO NOT write regular inventory updates except systems explicitly allowed for Soul Relics

                    IF REALM = "Mortal World":
                    - DO NOT write guardian-only or gacha-only structures
                    - DO NOT write Abode navigation data
                    - DO NOT write Chaos-Sea-only spending operations
                    - Mortal-World Ink Feather whitelist actions are allowed:
                      Reveal Fate, Rewrite Fate, Sacrifice to Chaos, Absorb Feathers, Learn Skill, Fate Shield, Seal in Ink
                    - Chaos-Sea Ink Feather whitelist actions remain forbidden here

                    ]]>

  <rule id="CLI.5">
   <title>
    Client Communication Protocol
   </title>
   <description>
    Defines how the CLI Agent communicates with the game client through output files.
   </description>
   <content type="rule_text">
    <![CDATA[

                    **PRIMARY CLIENT INTERFACE:**

                    **output/narrative_response.json** - Main client display
                    {
                      "response": "string",
                      "timestamp": "ISO_datetime"
                    }

                    **output/interface_updates.json** - UI updates
                    {
                      "dialogueOptions": [
                        { "text": "string", "category": "string_or_null" }
                      ],
                      "image_prompt": "string_or_null",
                      "timestamp": "ISO_datetime"
                    }

                    **output/debug_logs.json** - GM thoughts for debugging
                    {
                      "gm_thoughts_markdown": "structured NPC-scope + reasoning markdown string",
                      "timestamp": "ISO_datetime"
                    }

                    These output/*.json files are transient for the current turn only.
                    Rewrite them fresh for the current sessionId/requestId/turnNumber and do NOT treat them as persistent carry-over files.

                    **ready/turn_complete.json** - Processing completion signal
                    {
                      "sessionId": "string_correlation_token",
                      "requestId": "string_correlation_token",
                      "turnNumber": int,
                      "timestamp": "ISO_datetime",
                      "status": "success",
                      "filesModified": ["array_of_file_paths"]
                    }

                    **ready/turn_error.json** - Processing error signal
                    {
                      "sessionId": "string_correlation_token",
                      "requestId": "string_correlation_token",
                      "turnNumber": int,
                      "timestamp": "ISO_datetime",
                      "status": "error",
                      "error": "string"
                    }

                    **CLIENT MONITORING PROTOCOL:**
                    1. Client monitors ready/turn_complete.json and ready/turn_error.json
                    2. Client MUST match sessionId + requestId + turnNumber against the pending turn_request.json before accepting the signal
                    3. If turn_complete.json appears and correlation matches, client reads required output/narrative_response.json and output/debug_logs.json, then reads output/interface_updates.json only when that optional file exists
                    4. If turn_error.json appears and correlation matches, client reads ready/turn_error.json as the authoritative error payload; auxiliary logs are optional diagnostics only
                    5. Client may place a new turn_request.json only after the previous turn is resolved

  <rule id="CLI.8">
   <title>
    Lore, System Mods, and World Directives Management
   </title>
   <description>
    Defines how the CLI Agent manages persistent lore, global system mods, reusable world profiles, and player-authored world dossiers.
   </description>
   <content type="rule_text">
    <![CDATA[

                    **LORE SYSTEM ARCHITECTURE:**

                    **lore/chaos_sea/ - Persistent Meta-Lore (Across All Incarnations)**
                    - **cosmology.json** - Core universe structure, planes of existence, fundamental laws
                    - **guardians_lore.json** - Guardian histories, domains, relationships, ancient conflicts
                    - **soul_system_lore.json** - Origin of souls, reincarnation mechanics, enlightenment paths
                    - **artifacts_lore.json** - Legendary Soul Relics, their creation myths, and powers
                    - **player_chronicle.json** - Cross-incarnation player achievements, major story beats; life evaluation MUST append a new summary entry

                    **lore/current_world/ - Active Incarnation World (Resets Each Life)**
                    - **world_setting.json** - Current world type (fantasy, sci-fi, modern), genre, tone
                    - **geography.json** - World map, nations, cities, important locations
                    - **history.json** - World timeline, major events, current political situation
                    - **cultures.json** - Races, nations, customs, languages, religions
                    - **threats.json** - Major antagonists, world-ending threats, ongoing conflicts
                    - **npcs_lore.json** - Optional supplemental NPC backstories, relationships, motivations; useful when needed, but not part of the hard bootstrap minimum

                    **mods/ - Global System Mods**
                    - Each file is one global system mod.
                    - Mod files may be `.json`, `.txt`, or `.md`.
                    - The client controls enable/disable state per file through Options.
                    - GM MUST treat only `game_state/core/system_mods.json.activeMods[]` as canonical.
                    - Disabled files in `game_session/mods/` MUST be ignored.

                    **world_profiles/ - Reusable Mortal World Templates**
                    - Each file is one reusable world profile.
                    - Profiles may be `.json`, `.txt`, or `.md`.
