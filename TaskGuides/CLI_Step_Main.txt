<InstructionBlock id="CLI_MainStep_TaskGuide">
    <Title>CLI Step: Main Turn Processing and File Operations</Title>
    <Description>
        This is the PRIMARY task guide for CLI agents operating in file-based mode.
        Unlike API mode with multi-step pipeline, CLI mode operates as a SINGLE COMPREHENSIVE STEP.
        You read input files, process the game logic, and distribute results to output files.
    </Description>

    <CLIWorkflow>
        <Phase name="INPUT_READING">
            <![CDATA[
            1. **Read Primary Input:**
               - input/turn_request.json (player's action, turn metadata, pre-generated dice)
               - Examples/E_CLI_Step_Main.txt (MUST-read examples for NPC scope, reasoning blocks, repair loop, and terminal protocol failures)
               - Examples/E_CLI_Ink_Feather_Actions.txt (MUST-read whenever the turn uses any GM-side INK_FEATHER_ACTION)
               - OtherGuides/Afterlife_Contract_Matrix.md (MUST-read whenever currentRealm is `Chaos Sea` or `Shining Abode`; use it to select the exact canonical state surfaces, receipts, reports, and forbidden substitutions before writing files)
               - Examples/E_CLI_Afterlife_Turns.txt (MUST-read after the matrix whenever currentRealm is `Chaos Sea` or `Shining Abode`; use examples 14-21 for Shining core actions, freeform Guardian commands, combined scheduler + pending-contract turns, ordinary living-world turns without pending files, system Guardian attraction, and protected return guard)
               - When writing JSON/state files from PowerShell, use explicit UTF-8 and data objects only (`[ordered]@{}` / `@()`), never script blocks (`{}`)
               
            2. **Read Current Game State:**
               - game_state/player/ files (character, inventory, status)
               - game_state/world/ files (location, time, weather)
               - game_state/npcs/ files (active NPCs and their states)
               - game_state/quests/ files (active quest progress)
               
            3. **Read System State:**
               - game_state/control/ files (life transitions, incarnation, ascension)
               - game_state/history/ files (recent events, patterns)
               
            4. **Read Reference Data as Needed:**
               - lore/ files (world information)
               - game_state/core/system_mods.json (active global system mods; only activeMods[] are canonical)
               - game_session/mods/ source files only for the mods listed in activeMods[]
               - game_state/control/incarnation_world_setup.json when authoring incarnation / the first mortal bootstrap
               - lore/current_world/world_directives.json on Mortal World turns when the file exists
               - game_state/meta/ files (session settings, preferences)

        <Phase name="REALM_GATE">
            <![CDATA[
            **🔥 ABSOLUTE LAW: REALM GATE — MUST RUN BEFORE ANY MECHANICAL PROCESSING**

            1. Read `game_state/meta/soul_state.json` and determine `currentRealm`.
            2. Expose and reason about this value as `Context.worldState.currentRealm`.
            3. Select ONE processing profile:
               - `AfterlifeProfile` (`Chaos Sea` or `Shining Abode`)
               - `MortalWorldProfile`

            **AfterlifeProfile (`Chaos Sea` / `Shining Abode`):**
               - Allowed: Guardians, Abodes, Soul Relics, afterlife Ink Feather whitelist actions, Gacha, Soul-system/meta progression, afterlife living-world scheduler, Shining-specific systems when in Shining Abode, `progressionProcessingReport`
               - Forbidden: combat, experience, leveling, stat gains/losses, regular NPC mechanics, mortal quests, normal inventory management, Mortal World factions, weather, world time, mortal location system
               - Afterlife Ink Feather whitelist: Donate to Guardian, Cultivate Enlightenment, Guardian Favor, Memory Gates, Soul Imprint, ABODE_OFFERING only when `pending_abode_offering.json.offeringType = ink_feathers`
               - `Sell Relic` is a separate guardian trade interaction and is NOT an Ink Feather action
               - Local guardian trade (`Buy / Sell` Soul Relics) is client-side, but canonically belongs to the current active Guardian's abode
               - Guardian sell-side remains local, but sold Soul Relics must persist canonically in `guardians[].buybackRelics[]`; do not treat them as disappearing after sale
               - `guardians[].buybackRelics[]` is separate from authored `guardian.tradeInventory`: it stores exact Soul Relics the player sold to that Guardian and powers local reverse-buyback without another GM stock-generation round-trip
               - If `pending_guardian_trade_request.json` exists, answer it with explicit `guardian.tradeInventory` **and** close it through `UpdateGuardianTradeInventoryReceipts`; matching stock without receipt is invalid on accepted turn
               - If the player asks the current active Guardian about a relic bought from Guardian local stock, the Guardian should know that relic as part of their own trade assortment
               - If `pending_npc_trade_inventory_requests.json` exists while AfterlifeProfile is active, treat it as stale or realm-wrong; do NOT author NPC trade from an afterlife turn
               - If a turn materializes the current active Guardian, you MUST also materialize the abode navigation state in `guardians.json`: `chaosSeaNavigation.currentAbodeId`, `chaosSeaNavigation.discoveredAbodes` containing that abodeId, and `abode.isDiscovered = true`
               - If `guardians.json.pendingGuardianCreation.mode = system_preset`, the client has selected a named Eternal Guardian preset; materialize THAT exact guardian, not a nearby substitute
               - If a guardian is materialized from an Eternal Guardian preset, write `sourcePreset` into the guardian object with `presetId`, `displayName`, `version`, `library`
               - Canonical guardian identity now uses `canonicalName`, `nameVariants`, `manifestation`, and `manifestationHistory`; do NOT rely on legacy raw `name` as the primary field
               - `manifestation` must contain the CURRENT visible form: `currentDisplayName`, `formFlexibility`, `currentPresentationStyle`, `currentPronouns`, `appearanceDescription`, optional `presentationReason`
               - `manifestationHistory` stores only past forms; when the Guardian changes form, move the previous visible form there and update the current `manifestation`
               - Guardian project lifecycle no longer uses `UpdateGuardians.updateProject`
               - Use dedicated top-level surfaces:
                 - `startGuardianProjects`
                 - `guardianProjectUpdates`
                 - `completeGuardianProjects`
               - Authoritative tracker lives in `game_state/meta/guardian_projects.json`
               - Player-facing readable chronology lives in `game_state/meta/guardian_project_journal.json`
               - Keep at most one active guardian project per guardian in v1
               - Any Abode Power change must go through `guardianPowerEvents` or be materialized by the client from project completion into guardianPowerEvents-compatible history; do NOT directly mutate `guardian.abodePower` as a raw GM patch
               - Temporary recipe project effects are client-tracked, not perpetual:
                 - `relic_forging` lasts only until the next local trade refresh and one guardian-mediated gacha use
                 - `lore_research` hook/clue bonuses are tied to a target incarnation
                 - `soul_preparation` applies only to the next life and is consumed at correction resolution
               - If `game_state/control/system_guardian_attraction.json` exists, the soul is deliberately seeking that exact Eternal Guardian; this attraction is deterministic for the turn and must resolve to the requested preset
               - If `game_state/control/afterlife_return_guard.json` exists with `remainingProtectedTurns > 0`, the soul has just returned from a mortal life and MUST receive at least one ordinary afterlife turn before any forced re-incarnation
               - Guardian-forced incarnation is legal only on an ordinary player-driven Chaos Sea turn and only as a reaction to explicit player provocation against the current active Guardian
               - For guardian-forced `TriggerIncarnation`, write `source='guardian_forced'`, `guardianId`, `severityBand='harsh'|'severe'`, `reason`, `provocationSummary`, plus the normal `worldDescription`, `characterDescription`, `circumstances`
               - A guardian-forced incarnation start must be harsh but survivable; do NOT create an unwinnable deathtrap
               - Do NOT use MortalWorldProfile-only systems here: rival soul arcs, local NPC trade, QTE offers, mortal world news/clues, mortal locations, mortal factions, or Mortal-World Ink Feather actions
               - For every GM-side `[INK_FEATHER_ACTION: TAG]`, you MUST also write `output/ink_feather_action_result.json`
               - `Memory Gates` MUST produce a mechanical next-incarnation reward, not just lore:
                 - write `metaStateUpdates.memoryLegacyGrant`
                 - canonical state must end with `soul_state.pendingMemoryLegacy`
                 - allowed types only: `startingCharacteristicBonus` (+2 to one starting stat) or `startingPassiveKnowledgeSkill` (one new passive Knowledge skill)
                 - only one active pending memory legacy may exist; a new one replaces the old one
                 - if a new purchase leaves the old pending legacy unchanged, the client will reject the turn
                 - if `pendingMemoryLegacy.applicationState == applied-awaiting-turn-accept`, do NOT overwrite the already applied bonus in `characteristics.json` or `skills_passive.json`

            **MortalWorldProfile:**
               - Allowed: combat, NPCs, quests, inventory, factions, weather, world time, mortal locations, explicit Mortal-World Ink Feather whitelist actions
               - Forbidden: Guardian interactions, Abodes, Gacha, afterlife-only spending of Ink Feathers
               - Mortal-World Ink Feather whitelist: Reveal Fate, Rewrite Fate, Sacrifice to Chaos, Absorb Feathers, Learn Skill, Fate Shield, Seal in Ink
               - For GM-side Mortal-World Ink Feather actions (`SACRIFICE_TO_CHAOS`, `ABSORB_FEATHERS`, `LEARN_SKILL`, `FATE_SHIELD`, `SEAL_IN_INK`) you MUST write `output/ink_feather_action_result.json`
               - Mortal-World and afterlife Ink Feather whitelists are mutually exclusive
               - In Mortal World, you may use `UpdateRivalSoulArcs` to track milestone-based parallel destiny lines of OTHER souls in the current life
               - Rival soul arcs are background pressure, not a second protagonist simulation; keep at most `1` active `major` and `1` active `minor`
               - If a hostile rival arc directly targets the player, it MUST leave at least two player-visible clues before direct collision or terminal harm
               - Every `publicSignals[]` item must include explicit boolean `visibleToPlayer`
               - If a rival arc becomes personal for the player, surface that through an ordinary player-facing soul quest in `UpdateSoulQuests` linked by `relatedRivalArcId`
               - If a world news item is one of those clues, mark that `worldEventsLog` entry with `relatedRivalArcId` too, so the player can recognize it as part of a parallel destiny line
               - Linked `worldEventsLog` entries count as player-visible rival clues only if `visibility` is `Public`, `Regional`, or `player_known`
               - If the underlying event is `Secret` or `Faction-Internal` but the player learned it through play, materialize the linked player-facing world event as `visibility = player_known`
               - Hidden linked `Secret` / `Faction-Internal` world events do not spend visible lore_research clue budget until they become `Public`, `Regional`, or `player_known`
               - When practical, include `turn` or `timestamp` on visible `publicSignals` / linked world news and describe `consequences` / `impact` / `followUp`, so the player's rival-thread journal can show chronology and world changes more clearly
               - If a player-visible rival clue is being revealed specifically through completed `lore_research`, include `bonusClueSourceProjectId`, `bonusClueRevealId`, and optional `bonusClueCost`
               - If the SAME extra clue is surfaced through both `publicSignals` and linked `worldEventsLog`, reuse the same `bonusClueRevealId` on both surfaces so the client spends clue budget only once
               - Local NPC trade may also exist as a client-side panel for mortal-world goods only
               - Local NPC trade uses `game_state/core/player_status.json.money`, never Ink Feathers, and never trades Soul Relics
               - If `pending_npc_trade_inventory_requests.json` exists in MortalWorldProfile, answer each request with explicit `npc.tradeInventory` for the requested world-time cycle **and** close it through `UpdateNpcTradeInventoryReceipts`; matching stock without receipt is invalid on accepted turn
               - If the player asks a merchant NPC about an item bought from that NPC's local stock, the merchant should know that item as part of their own local assortment
               - For canonical local NPC trade examples, read `Examples/E_CLI_NPC_Trade.txt`
               - QTE offers are optional cinematic scene graphs for Mortal World only
               - QTE is allowed only if `game_state/core/game_settings.json.qteEventsEnabled = true`
               - QTE is allowed only on an ordinary player-driven turn, never on incarnation, life-evaluation, repair, transition, or other system-driven turns
               - QTE offer turn writes `output/qte_offer.json` and does NOT also resolve ordinary state changes for the same situation
               - In a valid QTE-offer turn, leave ordinary `game_state/`, `lore/`, and `stories/` untouched; use only `output/qte_offer.json` plus narrative/interface/debug outputs
               - If the player declines a QTE offer, the client will ask for a new ordinary GM turn with standard resolution and the same `qteId` must not be offered again immediately
               - For full QTE protocol rules, read `Rules/Block_CLI_QTE.txt`
               - For canonical QTE offer example, read `Examples/E_CLI_QTE_Offer.txt`
               - A valid `qte_offer.json` must at minimum contain `qteId`, `title`, `offerText`, `introNarrative`, `startChapterId`, `chapters`, and `terminalOutcomes`
               - `qte_offer.json` MUST contain `startChapterId`; the order of `chapters[]` does not define the opening chapter
               - Every chapter in the QTE scene must be reachable from `startChapterId`, every chapter must contain a non-empty `actions[]`, and all routing references must resolve to real chapters or outcomes
               - Every chapter must contain `chapterId`, `narrative`, and `actions`; every terminal outcome must contain `outcomeId`, `title`, `finalNarrative`, `gmSummary`, and `responseFragment`
               - Every action must contain `actionId`, `label`, `check`, and `routing`; every routing must contain `success`, `partial`, and `fail`
               - `check.baseDifficulty` in QTE must be an integer in the range `1..5`
               - `check.primaryCharacteristic` in QTE must use a canonical lowercase stat id from the player-characteristic system
               - For `BranchChoice`, `check.config.choiceGrade` must be exactly `success`, `partial`, or `fail`
               - Successful terminal outcomes of accepted QTE scenes MUST include positive `experienceGained` inside `responseFragment`
               - A "successful terminal outcome" means an outcome reachable through one or more `success` branches from `startChapterId`
               - `responseFragment` is the final local mechanical outcome of an accepted QTE branch; do NOT rely on a follow-up GM turn to add the real reward later
               - If the player `experience.json` already has level/progress fields, the client will also process the local QTE level-up transition automatically
               - `declineHint` and `cinematicJustification`, if you provide them, are shown to the player in the QTE offer prompt
               - Do NOT put ordinary `image_prompt` inside QTE `responseFragment`; use `sceneImagePrompt`, `chapterImagePrompt`, or `outcomeImagePrompt`

            4. Record the chosen profile and the forbidden systems in `gm_thoughts_markdown`.
            5. Do NOT execute any subsystem that is forbidden for the active profile.

        <Phase name="PROCESSING">
            <![CDATA[
            **CRITICAL: Apply ALL existing Rules/Block_*.txt logic exactly as designed.**
            
            1. **Analyze Player Action:** Follow Block_12.txt (Action Check System)
            2. **Calculate Results:** Apply Block_15.txt (Combat), Block_16.txt (Magic), etc.
            3. **Update NPCs:** Process Block_19.txt and its NPC subblocks
            4. **Update Guardians:** Process Block_32.txt in afterlife realms (`Chaos Sea` or `Shining Abode`) when the turn changes Guardian state
            5. **Progress Quests:** Apply quest rules exactly as defined in Rules
            6. **Handle Special Cases:** Soul system, lore, control triggers
            7. **Update Lore Codex:** If player discovered new knowledge — add loreCodexUpdates entries
            8. **Check Achievements:** After resolving all mechanics, check achievement conditions and emit achievementUnlocks
            9. **Respect Strict Validation Surface:** accepted turns are now hard-checked for realm segregation, richer location/faction/quest contracts, and field-complete achievement/codex entries
            10. **Use Canonical Quest Update Flow:** for quest creation send the full quest object with detailsLog; for quest-log updates send questId + newDetailsLogEntry instead of resending the whole detailsLog array
            11. **Remember Quest History Canonical Shape:** game_state/quests/quest_history.json is stored canonically as questHistory + questRewards + questChains; legacy questLog is only shorthand input
            12. **Do Not Reproduce Location History Logs:** eventDescriptions is a read-only historical archive; read it from context if present, but write only lastEventsDescription in currentLocationData / worldMapUpdates
            13. **Use Full factionDataChanges Objects:** do not send fragment-only faction core patches; faction rank/bonus/resource/project/custom side-effects belong to their dedicated atomic commands, and faction sidecar files are canonically normalized after distribution
            
            **SPECIALIZED GAME MASTER GUIDES:**
            - **World Logic:** Apply OtherGuides/CLI_World_Logic_Guide.txt for consistent causality and NPC behavior
            - **Narrative Style:** Apply OtherGuides/CLI_Narrative_Style_Guide.txt for compelling storytelling and dialogue
            
            **SPECIAL SCENARIO PROCESSING:**
            
            **New Game (Turn 1):**
            - MANDATORY: Initialize lore/ directory files for the starting world/realm
            - If starting in Chaos Sea: populate lore/chaos_sea/cosmology.json, soul_system_lore.json, guardians_lore.json
            - Add initial loreCodexUpdates entries for basic knowledge the soul has
            - Initialize game_state/meta/achievements.json with empty structure
            - DO NOT rely on stale lore or old stories/*.jsonl from a previous run; fresh new game starts from a fresh session lore set
            - Turn 1 is invalid if bootstrap lore files are left as empty stubs or if lore/codex_entries.json still has zero entries
            
            **New Incarnation (entering mortal world):**
            - BEFORE authoring the turn, read game_state/control/incarnation_world_setup.json if it exists
            - Treat incarnation_world_setup.json as the client-authored contract for the next mortal world
            - MANDATORY: Create ALL lore/current_world/ files (world_setting.json, geography.json, 
              history.json, cultures.json, threats.json) describing the world being born into
            - If lore/current_world/world_directives.json exists after incarnation materialization, treat it as a persistent player-authored dossier and keep following it on every Mortal World turn
            - Optional but supported: create lore/current_world/npcs_lore.json when this life needs persistent NPC backstory/world-lore support
            - Add loreCodexUpdates for starting world knowledge
            - Previous-incarnation lore/current_world/* files are stale and must not be reused as the new life's bootstrap

            **Afterlife Turn Master Procedure (Chaos Sea / Shining Abode):**
            - Use this procedure for every accepted turn while `soul_state.json.currentRealm` is `Chaos Sea` or `Shining Abode`; do not treat afterlife as a simple dialogue scene
            - Step 1, realm gate: read `game_state/meta/soul_state.json.currentRealm` and classify the mode as ordinary Chaos Sea, ordinary active Shining Abode, or Shining Abode pending-bootstrap handoff
