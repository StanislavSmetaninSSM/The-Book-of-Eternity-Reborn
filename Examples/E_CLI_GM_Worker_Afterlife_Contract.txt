# Example: GM worker afterlife realm-aware contract

This example shows a proposal-only analysis worker reviewing afterlife state.
The worker is hidden/background, uses `gm_worker_cli_runner.ps1`, receives
`BOE_WORKER_TASK_PATH`, `BOE_WORKER_PROPOSAL_PATH`, and
`BOE_WORKER_SESSION_PATH`, and writes exactly one proposal JSON. It does not
write canonical `game_session` files and it does not decide the player turn.

Afterlife worker tasks must include `afterlifeContract`. The contract prevents
the worker from replacing afterlife surfaces with Mortal World substitutes such
as `worldStateFlags`, `worldEventsLog`, Mortal NPC relationships, Mortal combat
HP/status, Mortal factions, or Mortal map files. The main GM must review
`OtherGuides/Afterlife_Contract_Matrix.md` before accepting any recommendation.

Worker profile:

```json
{
  "workerId": "analysis_codex",
  "displayName": "Codex analysis worker",
  "launchCommand": "powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File \"BookOfEternityClient/Launcher/gm_worker_cli_runner.ps1\" -AgentCommand \"codex exec -m gpt-5.6-terra -c model_reasoning_effort=high --dangerously-bypass-approvals-and-sandbox --skip-git-repo-check -\" -TimeoutSeconds 120",
  "role": "analysis",
  "enabled": true,
  "launchVisibility": "hidden",
  "timeoutSeconds": 150,
  "maxConcurrentTasks": 1,
  "permissions": {
    "taskTypes": ["analysis"],
    "readPaths": [
      "game_state/meta/**",
      "game_state/control/**",
      "OtherGuides/Afterlife_Contract_Matrix.md"
    ],
    "proposalWritePaths": [],
    "proposalOnly": true,
    "requiresValidation": false
  }
}
```


The validator rejects these cases:

- an afterlife-scoped task without `afterlifeContract`;
- a proposal for an afterlife task without `afterlifeProposal`;
- a proposal whose `afterlifeProposal.realmGate` differs from
  `afterlifeContract.realmGate`;
- a proposal that targets `game_state/world/**`, `game_state/npcs/**`,
  `game_state/factions/**`, `game_state/combat/**`, or other Mortal World
  surfaces instead of allowed afterlife surfaces.

The inbox entry is diagnostic/read-only. If the main GM likes the proposal, the
main GM rewrites it into normal afterlife response surfaces and validation
remains authoritative.
