UNIFIED AFTERLIFE RESOURCE AUTHORITY: `spiritual_action_points`, `gacha_attempts`, and `blessing_rerolls` are client-owned entries in `game_state/resources/resource_state.json`; their immutable transitions are in `game_state/resources/resource_history.json`, and exact owner/capacity authority is in client-owned `game_state/resources/resource_owner_authority.json`. Definitions, state, history, and owner authority are one guarded quartet; the GM never authors any quartet root. A missing or stale owner-authority root in an existing session fails closed and is not migrated or self-healed; only Fresh New Game creates the first root. Fresh New Game publishes preset/freeform Guardian and player owner after-images with the quartet in one deterministic coordinated resource write set; Mortal-incarnation bootstrap requires the exact existing quartet before-image. Afterlife state retains only exact `resourceOwnerBindings`. Actor-realm refs are derived from actor ID + realm, conflict-side owner IDs/refs from realm + conflictId, and Shining scope IDs/refs from `shining_abode` + returnCycleId. These identities are client-owned, deterministic for the same accepted input, and never GM-authored. The GM reads current/maximum values only from the documented read-only client projection or state context for the specific action and never writes direct ledger values, `chargesPerReturn`, `chargesUsedThisReturn`, numeric blessing `rerolls`, or `rerollsSpent`; `actionEconomy` is forbidden as persisted state. Ink Feathers, Light Sparks, treasuries, faction accounting, progression, relationships, and spiritual power/strain/shield remain specialized. The blessing contract is `blessing_rerolls + freeShape/freeRetune`; only the numeric allocation enters the ledger. A selected card may show the client-generated transient `rerollAllocation` object with exactly `resourceKey = blessing_rerolls` and non-negative integer `amount`; Mortal bootstrap consumes it into the common ledger and leaves only the exact client-owned `rerollResourceBinding` in pending blessing state. The GM never authors either field. Old saves are not migrated and there is no legacy fallback.

## afterlife_effect_profile_v1 — common profile adapter

Effect Materialization v1 uses the same source/identity/lifecycle contract in both afterlife realms. A validated spiritual art owns its complete definition; the GM requests application through top-level `effectChanges[]`. The client alone publishes the resulting `activeEffects[]` on the exact afterlife profile and the matching `effect_identity_index.json` entry. The runtime carrier and accepted mechanical contribution are client-owned; remaining lifetime is client-owned too. The GM does not rescan raw effect values, decrement duration, or resend post-state.

This source-policy example contributes only if the client resolves a real typed
`defense_roll` for its exact target. It does not turn spiritual `guard` into that roll
or grant a spiritual-conflict bonus through generic roll policy; those contributions
belong to the dedicated afterlife condition/wound-profile contracts.

```json
{
  "artId": "art_resonant_guard",
  "activeEffectDefinitions": [
    {

      "definitionKey": "resonant-guard",

        "category": "buff",
        "visibility": "visible"

      "allowedRealms": ["chaos_sea", "shining_abode"],
      "allowedTargetKinds": ["afterlife_actor"],
      "components": [
        {
          "componentId": "resonant_guard_roll",
          "profile": "roll_modifier",
          "priority": 100,
          "payload": {
            "operations": ["defense_roll"],
            "contribution": "advantage",
            "scope": { "kind": "all" }
          }
        }

      "parameterBounds": {},
```

Shining blessing entitlement is not a generic active effect. Blessing allocation, freeShape/freeRetune, memory selection, and blessing rerolls stay on their dedicated Shining client-owned contracts.

## afterlife_ap_effect_v1

This complete source definition belongs to a validated spiritual art. Once its
effect has been accepted on the exact player target, an ordinary two-AP spend
at 6 emits resource_spent: 6 -> 4. The one-use periodic_gain restores one AP:
4 -> 5. A later three-AP exchange must use the actually accepted chronology.
The profile does not itself authorize an exchange or change its audit.
Canonical state, remainingUses, identities and receipts remain client-owned.
For bounded_receipt resolution, answer only the current resource_delta request
within its allowed amount; an unresolved receipt is not an accepted recovery.

grant a new wound consequence profile or bypass the normal full-turn protocol.

## afterlife_roll_scope_v1

The complete `afterlife_effect_profile_v1` source immediately above deliberately uses
`operations=["defense_roll"]` with `scope.kind=all`. The explicit broad selector is
mandatory: it means only a real typed `defense_roll` for the exact afterlife target,
not every actor or every operation. Spiritual guard is not a roll_modifier operation
and is not an alias for `defense_roll`; this definition gives no generic bonus to a
spiritual `guard` exchange. Use the dedicated afterlife condition/wound-profile contracts
for that spiritual operation. This example does not alter the spiritual combat model.
Focused scope is legal only for exactly `operations=["skill_check"]` and one canonical
skill in the exact target row of `effectSkillScopeCatalog`.

A source spiritual art is not the target skill authority: spiritual arts are not Mortal skill IDs.
Do not reinterpret `art_resonant_guard`, an art's display name or tier, or `player_soul`
as a Mortal `skillId`. The advisory catalog contains canonical Mortal player/NPC skills;
an afterlife-only actor without a selectable exact Mortal skill row cannot receive a
new focused binding. Keep this generic defense-roll source broad rather than fabricating
such a row.
The dedicated spiritual-wound profiles retain their own operation/axis/magnitude
contract. All common definition, source, privacy, and lifecycle rules still apply in
both Chaos Sea and Shining Abode; no spiritual art is converted into a Mortal skill.

## afterlife_resource_bounded_receipt_waves_v1 — sequential safe packets

A story-facing spiritual effect can ask the GM to choose a bounded common
resource result. The client owns the afterlife resource coordinate, operation,
effect identity, graph position, and every fingerprint. The GM receives only a
safe packet and returns the current request ID, one allowed result, and a
reason. For example, the first safe packet can be answered as:

```json
{
  "effectResolutionReceipts": [
    {
      "requestId": "resource_resolution_afterlife_wave_001",
      "resultKind": "resource_delta",
      "amount": 2,
      "reason": "Давление клятвы отняло часть запаса духовного действия."
    }
  ]
}
```

Answer the current safe packet only. Resubmit the same complete semantic turn
with receipts only for that packet; the client carries earlier-wave terminal bindings. The original candidate, mutation authority, and source authority remain immutable/client-owned. If replay of the resolved result reaches another
bounded component, the client returns a second safe packet and still publishes
no resource, active-effect, use, or lifetime after-image. The first receipt is
retained as client-owned terminal evidence:

```json
{
  "effectResolutionReceipts": [
    {
      "requestId": "resource_resolution_afterlife_wave_002",
      "resultKind": "narrated_no_state_change",
      "reason": "Оберег удержал вторичный резонанс без новой потери."
    }
  ]
}
```

The client replays wave 1 at its original causal position, resolves wave 2, and
publishes the complete accepted mechanics atomically only when no further safe
packet appears. Do not combine old and current packet IDs, add a target,
resource, operation, path, authority, or fingerprint, or change the original
resource/effect commands between waves. An exact terminal retry with the same
semantic command envelope is a no-op; a changed envelope fails closed.

If a current safe packet advertises an inclusive minimum of `0`, the GM may
return an explicit terminal zero without pretending that a resource changed:

```json
{
  "effectResolutionReceipts": [
    {
      "requestId": "resource_resolution_afterlife_zero_003",
      "resultKind": "resource_delta",
      "amount": 0,
      "reason": "Клятва отозвалась, но запас духовного действия не изменился."
    }
  ]
}
```

The client consumes that accepted receipt and use without emitting a resource
transition, resource event, or dependent effect activation. This explicit zero
remains distinct from `narrated_no_state_change`, which omits `amount`. A
positive request that reaches a resource bound may still have an ordinary
transition with zero applied amount; the GM never infers or authors either
transition form.
