# E_CLI_Afterlife_Guardian_Contracts.txt

Read when: Current nonempty pending_guardian_trade_request. Follow only the current dispatch/contract; Stale/empty Guardian trade bundle without contract does not independently activate this topic.
Prerequisites: Current request, authoritative realm and exact active pending/issued packet; [applicable common-core paragraphs](../OtherGuides/GM_Common_Core.md). Topic prerequisites: [Afterlife_Lifecycle.md](../OtherGuides/Afterlife_Lifecycle.md).
Author here: only existing contract-authorized outputs; this reading guide grants no additional authority.
Never author: do not invent client-owned identities, seals or unissued receipts, or mutate pending/canonical state outside the current contract. Legitimate GM-authored receipts and pending closures remain permitted only through their existing explicitly authorized owner/response surface.
Worked examples: [E_CLI_Afterlife_Guardian_Contracts.txt](E_CLI_Afterlife_Guardian_Contracts.txt); paired rules: [Afterlife_Guardian_Contracts.md](../OtherGuides/Afterlife_Guardian_Contracts.md). Whole original examples/negative labels remain below.

4. VALID — CHAOS SEA GUARDIAN TRADE REQUEST
==================================================

Scenario:
- Realm is `Chaos Sea`.
- The player tries to open the current Guardian's trade panel, but the client found missing/stale authored stock.
- `game_state/control/pending_guardian_trade_request.json` is present.
- There is no scheduler debt in this small example. If scheduler debt is also due, process it first and add `progressionProcessingReport` as in example 1.

Input fragment:

```json
{
  "turn_request.json": {
    "sessionId": "afterlife_session_trade_240",
    "requestId": "afterlife_turn_trade_240",
    "turnNumber": 240,
    "playerAction": "Я прошу Азалию открыть витрину Обители.",

    "guardianId": "guard_social_azalia_001",
```

Correct GM procedure:
- Preferred harness path: dot-source `game_state/control/gm_turn_helper.bootstrap.ps1` and call `Complete-BoeGuardianTradeInventoryRequest -RequestId 'guardian_trade_azalia_return_5' -Items <two authored relic slots>`. The helper computes canonical tiers/prices, writes `guardian.tradeInventory`, syncs `activeGuardian`, and appends `UpdateGuardianTradeInventoryReceipts`.
- Use the manual rules below only when the helper is unavailable or validation repair explicitly requires inspecting the persisted patch.
- Read the pending request exactly; do not change `requestId`, `guardianId`, `abodeId`, `returnCycleId`, slot count, or project bonus signature.
- Materialize `guardian.tradeInventory` for the same Guardian in `game_state/meta/guardians.json`; do not put trade stock into a commandless `UpdateGuardians` entry.
- `tradeInventory.tradeCycleId` must equal `returnCycleId`.
- `generationReputationTier` and `pricingReputationTier` must be derived from `currentReputation`; here `65` means `Friendly`.
- `items.length` must equal `derivedTradeSlotCount`.
- Every `tradeInventory.items[].slotId` must be unique inside this inventory. The client buys by `slotId`; duplicates make the purchase target ambiguous and are invalid.
- Every `tradeInventory.items[].priceInFeathers` must match canonical pricing for its `quality`/`rarity` and `pricingReputationTier`; do not preserve invented prices during repair.
- If `activeGuardian` is present, its `tradeInventory` mirror must match the same Guardian in `guardians[]` exactly: same cycle, timestamps, tiers, slots, prices, sold-out flags, and relic data.
- Close through `UpdateGuardianTradeInventoryReceipts`; matching stock without a ready receipt is invalid.
- Do not write `afterlife_notifications.json`; the client derives the ready inbox event.
- The fragment below shows the canonical persisted Guardian state patch; preserve all other fields on the existing Guardian object.

Repair-mode note:
- If validation rejects this route with `guardian_trade_request_missing_guardian_resolution`, `guardian_trade_request_missing_inventory_resolution`, or `guardian_trade_request_missing_receipt_resolution`, open `validation_repair_request.json.harnessRepairPackets[]` and use packet kind `guardian_trade_inventory_resolution_repair`.
- Prefer rerunning `Complete-BoeGuardianTradeInventoryRequest` with corrected relic slots instead of manually recalculating `priceInFeathers` or receipt fields.
- In repair mode, do not make a new turn and do not edit `game_state/control/pending_guardian_trade_request.json`; it is read-only client authority for request identity, cycle, slot count, reputation tier inputs, and project bonus signature.
- Patch only the matching Guardian in `game_state/meta/guardians.json` plus required `output/debug_logs.json` actor reasoning. The repair is complete only when the Guardian has a matching `tradeInventory` and a matching ready receipt through `UpdateGuardianTradeInventoryReceipts` or `guardians[].tradeInventoryReceipts[]`.

5. VALID — CHAOS SEA ARCHIVE CONSULTATION AND PROJECT FUEL REQUESTS
==================================================

Scenario:
- Realm is `Chaos Sea`.
- The player uses reserved afterlife archive entries.

Correct GM procedure:
- For consultation, return `archiveActionResolutions` with exact `requestId`, `archiveId`, `requestedMode = consultation`, `status`, `guardianId`, and at least one machine-readable outcome field.
- Accepted consultation must also create a completed `lore_research` Guardian project with `projectOrigin = archive_consultation`, `consultationRequestId`, `consultationArchiveId`, and `projectOutcomeAudit` matching the resolution fields.
- If that consultation creates a Guardian quest hook, the quest record in `questManagement.availableQuests`/`activeQuests`/`completedQuests` must carry `questOrigin = archive_consultation_hook` and `sourceProjectId = archive_consult_project_azalia_241`. Ordinary lore-research hooks use `questOrigin = lore_research_hook`; special lore-research lines use `questOrigin = lore_research_special_line`.
- For ordinary Wary/Neutral-or-better Guardian scenes that are not backed by lore/archive tokens, the GM may offer a voluntary / добровольное future mortal-life assignment with `questOrigin = guardian_baseline_mortal_life_hook`. Keep it in `availableQuests` until the player explicitly accepts it; do not create an `activeQuest` just because the offer exists, and do not treat an empty `availableQuests` array as a validation error.
- For project fuel, return `archiveActionResolutions` with exact `requestId`, `archiveId`, `requestedMode = project_fuel`, `targetProjectId`, `status`, `resultMode`, and `resultAmount > 0`.
- For project fuel, `archiveEntryType = lore_fragment` may resolve only as `resultMode = project_work`; `archiveEntryType = secret_record` may resolve only as `resultMode = pressure_relief`.
- Accepted archive entries are consumed/resolved by canonical archive state; rejected/cancelled entries return to availability.
- If project fuel is accepted, also reflect the exact effect in Guardian project state/journal. `pressure_relief` reduces pressure or improves stability; it does not advance `workDone`/`currentStage`.
- Do not invent mortal quests, mortal inventory, or manual inbox notifications.

7. VALID — DIRECT CHAOS SEA GACHA VS GUARDIAN-MEDIATED GACHA
==================================================

Direct Chaos Sea `/gacha`:
- Player action contains `[CHAOS_SEA_DIRECT_GACHA]` and an exact cost phrase such as `тратит 25 Чернильных Перьев`.
- Does not use `UpdateGuardians.processGacha`.
- Does not consume Guardian per-return charges.
- The client already spent the Ink Feathers before the GM turn; preserve the post-spend balance and do not write `metaStateUpdates.inkFeatherChanges.spend`.
- `turn_request.json.playerAction` must contain the exact prepaid cost phrase `<N> Чернильных Перьев` or `<N> Ink Feathers`; the validator extracts direct-gacha cost from that phrase.
- Must materialize exactly one new Soul Relic in Soul/meta state.
- Must read the full `turn_request.json.gachaBaseResult` audit (`diceUsed`, `baseScore`, `baseRarity`, `formula`) before choosing the relic.
