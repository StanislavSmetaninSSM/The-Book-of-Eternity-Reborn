Read `OtherGuides/Effect_Materialization_Contract.md` first. These examples show GM-authored source policy and transient lifecycle commands. Canonical carriers, IDs, index, pending state, transitions, stacks, deadlines, and receipts are client-owned and therefore are not fabricated here.

## effect_event_reaction_graph_v1

`event_reaction` is a closed dispatcher, not arbitrary scripting. This complete
same-source graph demonstrates all six result kinds and all three dependency
phases. Every reaction component belongs to exactly one trigger. A referenced
component belongs to the same definition; an applied definition belongs to the
same source owner. Resource-component reactions are explicit `after_component`
edges; an unconditional resource component is selected directly by its trigger.
`maxExpansion` limits executions of that reaction component inside one accepted
transition, while the client also enforces the global 64-operation ceiling.
After acceptance, a skipped/no-change/replayed predecessor suppresses only its
dependent `after_component` output. Unconditional `before_current_event` and
`after_current_event` reactions remain released, and a consuming trigger keeps
its one-use projection. A final use or unconditional deferred suspend/remove
blocks only later event boundaries: siblings already accepted in the frozen
batch still finish, and any created/replacement effect becomes eligible on the
next accepted mechanics transition. For `apply_definition(policy=replace)`, the
client derives the exact old target from the frozen realm/target/source/stack
coordinate, excluding `definitionKey`; release blocks that target from later or
nested boundaries, and `after_current_event` reserves it at acceptance. If two
accepted consuming activations carry budgets `2,1` before that target is folded,
the old identity records `consume,consume,replace` in activation order. Every
intermediate/final replacement keeps its complete initial lifetime. A
resource-event child also preserves both the outer producer requirement and its
exact `after_component` predecessor.

`before_current_event` executes before the current accepted lifecycle reduction.
For a reaction discovered from a resource event, the producing resource mutation
necessarily happens first; “before” means before continuation of that derived
event, never before its producer. `after_component` runs only if the exact
`afterComponentId` mutation applied. A `narrated_no_state_change` predecessor
does not authorize the dependent result. `after_current_event` runs when the
inner-first causal boundary closes and before the one final lifetime/use
projection. Direct selection and reaction dispatch of the same
component, ambiguous references, same-stack downstream application without an
explicit `replace`, cycles, and either source/global expansion overflow fail
before publication. Here `counter-pulse` is the worked same-stack exception:
its exact incoming `replace` retires the one active `reactive-aegis` identity
even though that prior definition used `independent`; a second prior identity
would make the coordinate ambiguous and fail closed.

## effect_mortal_dispel_v1

An accepted turn may request a dispel only for the exact opaque effect identity
shown by the current technical context. The authority kind must be one of that
effect definition's `removal.dispelCategories[]`; here it matches the
`mental_disruption` category declared by `battle-focus` above. The command does
not repeat a source definition, parameters, remaining lifetime, or post-state.

```json
{
  "effectChanges": [
    {
      "operation": "dispel",
      "effectId": "effect_battle_focus_7f9c2a",
      "target": { "kind": "player", "targetId": "player_current" },
      "authority": {
        "kind": "mental_disruption",
        "authorityId": "countermeasure_turn_43"
      },
      "eventRef": { "kind": "accepted_turn", "authorityId": "turn_43" },
      "reason": "Принятый контрприём рассеял боевое сосредоточение."
    }
  ]
}
```

The client resolves the exact active identity, verifies target and authority,
and publishes the terminal transition. The GM never deletes or rewrites
`activeEffects[]` directly.

## effect_mortal_lifetimes_v1

All eight lifetime modes are explicit; there is no numeric sentinel:

```json
{
  "lifetimeMatrix": [
    { "mode": "turns", "initialTurns": 3, "advancePhase": "owner_turn_end" },
    { "mode": "uses", "initialUses": 2, "consumingEventTypes": ["owner_damaged"] },
    { "mode": "until_time", "duration": 60, "timeAuthority": "world_time.currentTimeInMinutes" },
    { "mode": "scene", "onSceneExit": "expire" },
    { "mode": "source_bound", "activePredicate": "equipped", "onSourceLoss": "suspend" },
    { "mode": "condition_bound", "conditionKey": "hunger_threshold", "operandBounds": { "minimum": 50, "maximum": 100 }, "onConditionLoss": "expire" },
    { "mode": "permanent" },
    { "mode": "manual", "authorities": ["ritual_cleansing"] }
  ]
}
```

For `uses`, every consuming event must have exactly one trigger with `consumeUses=true`. `until_time` stores source duration only; the client computes the deadline. `scene`, source/condition loss, expiry, and manual closure are client lifecycle transitions, not carrier edits.
