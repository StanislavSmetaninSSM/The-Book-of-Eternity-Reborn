# Effect Materialization v1 — worked GM examples

Read `OtherGuides/Effect_Materialization_Contract.md` first. These examples show GM-authored source policy and transient lifecycle commands. Canonical carriers, IDs, index, pending state, transitions, stacks, deadlines, and receipts are client-owned and therefore are not fabricated here.

## effect_event_reaction_graph_v1

`event_reaction` is a closed dispatcher, not arbitrary scripting. This complete
same-source graph demonstrates all six result kinds and all three dependency
phases. Every reaction component belongs to exactly one trigger. A referenced
component belongs to the same definition; an applied definition belongs to the
same source owner. Resource-component reactions are explicit `after_component`
edges; an unconditional resource component is selected directly by its trigger.
`maxExpansion` limits executions of that reaction component inside one accepted

`before_current_event` executes before the current accepted lifecycle reduction.
For a reaction discovered from a resource event, the producing resource mutation
necessarily happens first; “before” means before continuation of that derived
event, never before its producer. `after_component` runs only if the exact
`afterComponentId` mutation applied. A `narrated_no_state_change` predecessor
does not authorize the dependent result. `after_current_event` runs after
lifetime/use advancement. Direct selection and reaction dispatch of the same
component, ambiguous references, same-stack downstream application without an
explicit `replace`, cycles, and either source/global expansion overflow fail
before publication.

        "name": "Боевое сосредоточение",

        "visibility": "visible"

      "allowedRealms": ["mortal_world"],

## effect_mortal_lifetimes_v1

All eight lifetime modes are explicit; there is no numeric sentinel:

```json
{
  "lifetimeMatrix": [
    { "mode": "turns", "initialTurns": 3, "advancePhase": "owner_turn_end" },
    { "mode": "uses", "initialUses": 2, "consumingEventTypes": ["owner_damaged"] },
    { "mode": "until_time", "duration": 60, "timeAuthority": "world_time.currentTimeInMinutes" },
    { "mode": "scene", "onSceneExit": "expire" },
    { "mode": "source_bound", "activePredicate": "equipped", "onSourceLoss": "suspend" },
    { "mode": "condition_bound", "conditionKey": "hunger_threshold", "operandBounds": { "minimum": 50, "maximum": 100 }, "onConditionLoss": "expire" },
    { "mode": "permanent" },
    { "mode": "manual", "authorities": ["ritual_cleansing"] }
  ]
}
```

For `uses`, every consuming event must have exactly one trigger with `consumeUses=true`. `until_time` stores source duration only; the client computes the deadline. `scene`, source/condition loss, expiry, and manual closure are client lifecycle transitions, not carrier edits.

## effect_mortal_source_families_v1

Supported exact source kinds are `skill`, `spiritual_art`, `item`, `wound`, `quest`, `location`, `hazard`, `faction`, `world_event`, `fate_card`, and `combat_action`. Representative selectors:

    { "kind": "item", "sourceId": "item_runic_glove", "definitionKey": "runic-guard" },

    { "kind": "location", "sourceId": "location_whispering_marsh", "definitionKey": "marsh-miasma" },
    { "kind": "hazard", "sourceId": "hazard_black_spores", "definitionKey": "spore-fever" },
    { "kind": "faction", "sourceId": "faction_ashen_watch", "definitionKey": "watch-ward" },
    { "kind": "world_event", "sourceId": "event_blood_moon", "definitionKey": "blood-moon-pressure" },

## effect_wound_independence_v1

A wound-consequence definition contains one exact wound component and one exact wound source link. The effect planner can observe the wound but cannot write it.

```json
{
  "component": {
    "componentId": "torn_side_consequence",
    "profile": "wound_consequence",
    "priority": 100,
    "payload": {
      "woundId": "wound_torn_side",
      "symptom": "bleeding",
      "consequence": "periodic_damage"
    }
  },
  "lifetime": { "mode": "source_bound", "activePredicate": "active", "onSourceLoss": "expire" },
  "links": [
    { "kind": "wound", "targetId": "wound_torn_side", "role": "source" }
  ]
}
```

Effect removal never heals or deletes the wound. A treatment turn submits the accepted wound transition and, if authorized, a separate effect removal request. An effect-only removal must leave the wound carrier byte-semantically unchanged.

## effect_bounded_repair_v1

Only one exact missing source parameter may produce an actionable packet after baseline restoration:

```json
{
  "kind": "effect_materialization_repair",
  "actor": "effect-apply:effectChanges[0]",
  "route": "effectChanges",
  "rawCoordinate": "effectChanges[0].parameters.intensity",
  "expectedSource": { "kind": "wound", "sourceId": "wound_torn_side" },
  "expectedTarget": { "kind": "player", "targetId": "player_current" },
  "expectedDefinitionKey": "bleeding-consequence",
  "expectedEventRef": { "kind": "accepted_turn", "authorityId": "turn_42" },
  "exactFieldCorrections": [
    {
      "path": "effectChanges[0].parameters.intensity",
      "expectedValue": "severe",
      "code": "effect_source_parameter_required",
      "repairHint": "Restore the full accepted response and add only the exact missing bounded parameter."
    }
  ],
  "targetFiles": ["game_state/effects/effect_commands.json"],
  "fullTurnResubmissionRequired": true,
  "resubmissionObligations": ["effectChanges[0]", "complete accepted turn response"]
}
```

The GM rereads the current repair request, restores no protected file manually, resubmits the complete turn, and finishes through the repair terminal protocol. Identity/source/target/realm/stack/history/receipt/direct-mutation failures never receive this packet.

## effect_legacy_rejection_v1

INVALID — explicitly rejected pre-v1 input, retained only as a negative test:

```json
{
  "playerActiveEffectsChanges": [
    {
      "effectType": "Buff",
      "description": "Permanent because prose says so",
      "duration": 999
    }
  ],
  "NPCEffectChanges": []
}
```

This must fail before publication. There is no runtime migration. The client does not translate aliases, prose mechanics, magic duration values, direct non-empty carriers, or GM-authored identities into Effect Materialization v1.
