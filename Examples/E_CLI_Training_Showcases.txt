Examples For CLI Training Showcases
===================================

Purpose
-------

This file documents the GM-authored side of the `/training` / `/обучение`
feature. The client owns purchases and currency/experience spending. The GM
prepares fresh, readable trainingShowcase data when the client creates
`game_state/control/pending_training_showcase_requests.json`, and finalizes
Mortal skill unlocks/level-ups when a paid lesson crosses a mechanical
threshold.

Shared rules
------------

- `pending_training_showcase_requests.json` is a client-authored request file.
- When `/обучение` creates or finds a pending showcase request, the console and
  browser clients send the matching dedicated GM action immediately. Treat that
  received action as the current request to resolve now; do not wait for the
  player to close the command screen, press a key, or type the next unrelated
  turn before preparing the showcase.
- Every showcase must copy the requested `sourceActorSnapshotHash` into
  `trainingShowcase.sourceActorSnapshotHash`. If the teacher changes, the
  client treats the showcase as stale, marks it unavailable for purchase, and
  requests a refresh. A stale cached showcase is not itself permission to edit
  old purchase receipts.
- For `mortal_teacher_showcase` on an existing NPC teacher, write a narrow
  `UpdateNPCs` patch only as a manual fallback. Preferred path: after
  dot-sourcing `game_state/control/gm_turn_helper.bootstrap.ps1`, call
  `Complete-BoeTrainingShowcaseRequest -RequestId '<requestId>' -Offers <offers>
  -Summary '<player-facing summary>'`. The helper finds the teacher by
  `sourceActorId`, validates costs/caps/duplicate offer ids, writes
  `trainingShowcase`, and leaves the fulfilled pending request for client
  cleanup after the accepted turn/view refresh. If the helper is
  unavailable and manual fallback is necessary, include only the identity
  (`npcId`/`name`) and the fresh `trainingShowcase`. Do not resend `inventory`,
  do not replace the whole NPC object, and do not repeat `teacherProfile` unless
  the turn is intentionally creating or changing the teacher profile itself. The
  client normalizer applies the showcase patch to the existing full NPC object.
- During validation repair, when `harnessRepairPackets[].kind` is
  `training_showcase_snapshot_hash_repair`, apply
  `exactFieldCorrections[]` first. Set each listed
  `sourceActorSnapshotHash` path to the exact `expected` value from the packet.
  Do not guess or recompute the hash manually. If you also change the teacher or
  mentor profile in the same repair, finish that profile patch first, then use
  the exact correction from the current validation request.
- A fresh showcase for the requested teacher or mentor satisfies that pending
  request. The client clears fulfilled entries from
  `pending_training_showcase_requests.json`, and deletes the file when no
  requests remain.
- GM does not spend player currency.
- During the first Mortal bootstrap, the client may grant a small starter purse
  and current-level XP buffer when the player-authored start asks for training,
  paid lessons, merchants, or trade. These resources live in
  `game_state/core/player_status.json.money` and
  `game_state/player/experience.json.currentExperience`. Preserve them as
  client-owned baseline resources; do not delete them as unexplained state.
- In afterlife showcase/self-training purchases, GM does not raise player tiers directly. The client applies standard spiritual-art, spirit_focus, and known special-art upgrades.
- In Mortal World training, the client may apply only simple active-skill
  mastery progress that does not cross a threshold. If a paid lesson unlocks a
  skill or crosses a mastery level, the client writes requestKind
  `mortal_training_skill_evolution`; the GM must author the full updated
  `activeSkillChanges` or `passiveSkillChanges` object plus matching
  `skillMasteryChanges`. Do not charge the player again.
- For `mortal_training_skill_evolution`, follow `details.targetKind` rather
  than the original showcase offer label. The client normalizes generic Mortal
  offer kinds such as `skill_mastery` to `active_skill_mastery`,
  `passive_skill_mastery`, `active_skill_unlock`, or `passive_skill_unlock`
  after inspecting the player's actual skill state. If `details.targetKind`
  names a passive target, write `passiveSkillChanges`; do not invent an active
  skill just because the original offer used generic `skill_mastery`.
- During validation repair, when `harnessRepairPackets[].kind` is
  `mortal_training_skill_evolution_repair`, open the pending
  `mortal_training_skill_evolution` request first and use
  `details.targetKind` as the active/passive authority. If validation rejected
  `skillMasteryChanges` because the skill is not active, remove the invalid
  active mastery entry and repair the paid lesson through `passiveSkillChanges`
  when the pending target is passive. Do not charge the lesson again.
- GM does not grant mastery or standard spiritual-art progression through free
  prose when the player used the showcase. Use the request/receipt surfaces.
- `trainingPurchaseReceipts` and `afterlifeTrainingPurchaseReceipts` are
  client-owned purchase-time audit records. If the teacher or mentor changes
  after the lesson, do not rewrite historical receipt hashes or costs just to
  match the current profile; repair them only when validation reports a concrete
  non-historical target/resource mismatch.
- Free roleplay training remains valid. In afterlife, learning a new teachable
  special art through roleplay still uses `afterlifeSpecialArtLearningReceipts`;
  that receipt starts the learned art at tier 0 and never substitutes for a
  purchased tier upgrade.
- Self fallback economics are intentionally expensive:
  `SelfStandardArtMultiplierPercent = 400`,
  `SelfSpiritFocusMultiplierPercent = 300`,
  `SelfSpecialArtMultiplierPercent = 500`.
- Mentor economics are client-owned discounts from the base training price:
  `MentorNeutralMultiplierPercent = 100`,
  `MentorGoodMultiplierPercent = 80`,
  `MentorExcellentMultiplierPercent = 60`.
- Every `trainingShowcase.offers[]` / `mentorTrainingShowcase.offers[]`
  entry must include a positive `cost` object. The client owns the actual
  purchase and spending, but the showcase still advertises the price the
  player will see. For afterlife standard spiritual arts and `spirit_focus`,
  the client normalizes missing or mismatched deterministic `cost` values from
  the base price and mentor relationship, but GM-authored examples and normal
  output should include the explicit `cost`.
- When New Game starts with a named system Guardian or a freeform Guardian
  description, the client already creates
  a valid `game_state/meta/afterlife_entity_profiles.json` profile for the
  matching Guardian actor. That profile is a starter mentor authority:
  it has `mentorProfile.canTeach=true`, starter `standardArts`, a
  `progressionStrategy`, and `ledger`. Do not replace it with a bare profile or
  try to materialize the Guardian again. If `/обучение` requests an
  `afterlife_teacher_showcase` for that actor, prefer
  `Complete-BoeTrainingShowcaseRequest` to update the existing profile with
  `mentorTrainingShowcase` and copy the requested `sourceActorSnapshotHash`.
- In afterlife, the player's current Ink Feathers, Light Sparks, ordinary
  Spiritual Art tiers, Spirit Focus tier, enlightenment, and radiance are read
  from client-owned `soul_state.json` / `shining_abode_state.json`. The
  `player_soul` entry in `afterlife_entity_profiles.json` mirrors those fields
  for display and mentor calculations; the GM must not use profile
  `currencies`, `standardArts`, `progression`, or `progressionStrategy` to grant
  the player a purchase.

Player soul authority note
--------------------------

When the GM prepares an afterlife mentor showcase, it may reference the player
profile only for identity, visible story state, Fate Cards, relationships, and
learned `specialArts[]`. It should not patch a purchase into the player profile.
The accepted response below is correct because Liora's profile advertises the
lesson price, while the client later handles the player's purchase and actual
currency spending:

```json
{
  "afterlifeEntityProfileUpdates": [
    {
      "actorType": "guardian",
      "actorId": "guardian_liora",
      "displayName": "Лиора, Хранительница Тихого Света",
      "standardArts": { "guard": 4 },
      "mentorTrainingShowcase": {
        "schemaVersion": 1,
        "requestId": "training_req_liora_001",
        "sourceActorSnapshotHash": "sha256:requested-hash-from-client",
        "offers": [
          {
            "offerId": "mentor_liora_guard_2",
            "targetKind": "standard_spiritual_art",
            "targetId": "guard",
            "targetValue": 2,
            "sourceCap": 4,
            "cost": {
              "inkFeathers": 105,
              "lightSparks": 0
            },
            "description": "Лиора показывает, как принять удар поворотом света; покупку и списание выполнит клиент."
          }
        ]
      }
    }
  ]
}
```

Do not add a parallel `afterlifeEntityProfileUpdates` entry for
`actorType=player_soul` that spends feathers or raises `standardArts.guard`.
That would fight the client-owned state and will be normalized away.

Mortal World teacher request
----------------------------

The client writes a pending request like this when a Mortal NPC has teacher
profile data but no fresh trainingShowcase:

```json
{
  "requests": [
    {
      "requestId": "training_req_hunter_roden_001",
      "requestKind": "mortal_teacher_showcase",
      "sourceActorId": "npc_hunter_roden",
      "sourceActorName": "Роден, охотник у северных ворот",
      "sourceActorKind": "mortal_npc",
      "realm": "mortal",
      "sourceActorSnapshotHash": "sha256:requested-hash-from-client",
      "createdAtTurn": 12,
      "status": "pending",
      "reason": "Игрок открыл /обучение рядом с NPC-учителем."
    }
  ]
}
```

Preferred Mortal helper call
----------------------------

When `game_state/control/gm_turn_helper.bootstrap.ps1` exists, prefer the helper
over a manual `UpdateNPCs` patch:

```powershell
. "game_state/control/gm_turn_helper.bootstrap.ps1"

$offers = @(
  [ordered]@{
    offerId = "train_roden_knife_handling_2"
    targetKind = "skill_mastery"
    targetId = "knife_handling"
    targetName = "Обращение с ножом"
    currentValue = 1
    targetValue = 2
    sourceCap = 3
    cost = [ordered]@{
      money = 65
      currentLevelExperiencePercent = 18
    }
    requirements = [ordered]@{
      minimumRelationship = 20
      lessonScene = "Короткая тренировка с настоящими ножами у старой стены."
    }
    description = "Роден учит держать клинок ниже взгляда противника и не тратить движение на красивость."
  }
)

Complete-BoeTrainingShowcaseRequest `
  -RequestId "training_req_hunter_roden_001" `
  -Offers $offers `
  -Summary "Роден готов провести короткое практическое занятие за оплату и часть опыта текущего уровня."
```

Mortal paid skill evolution request
-----------------------------------

When the player buys a Mortal lesson that unlocks a skill or crosses the
mastery threshold, the client has already charged the paid lesson: it checked
the teacher cap, spent money, spent current-level XP, and appended a training
receipt. It then leaves a pending request like this:

```json
{
  "requests": [
    {
      "requestId": "training_showcase_req_paid_knife_001",
      "requestKind": "mortal_training_skill_evolution",
      "sourceActorId": "npc_hunter_roden",
      "sourceActorName": "Роден, охотник у северных ворот",
      "sourceActorKind": "npc_teacher",
      "realm": "mortal",
      "sourceActorSnapshotHash": "sha256:requested-hash-from-client",
      "createdAtTurn": 13,
      "reason": "mastery_threshold_crossed",
      "details": {
        "offerId": "train_roden_knife_handling_2",
        "targetKind": "active_skill_mastery",
        "targetId": "knife_handling",
        "targetName": "Обращение с ножом",
        "currentValue": 1,
        "targetValue": 2,
        "sourceCap": 3,
        "moneySpent": 65,
        "currentLevelExperiencePercent": 18,
        "currentLevelExperienceSpent": 180,
        "skillStateBefore": {
          "currentMasteryLevel": 1,
          "currentMasteryProgress": 4,
          "masteryProgressNeeded": 5
        },
        "gmInstruction": "Создай или обнови полный activeSkillChanges объект с combatEffect и matching skillMasteryChanges для нового уровня."
      }
    }
  ]
}
```

The GM resolves this by writing the actual skill update through normal Mortal
skill surfaces. The response must not spend money/XP again; the purchase receipt
already proves payment.

```json

      "combatEffect": {
        "isActivatedEffect": true,
        "actionName": "Обращение с ножом",
        "actionDescription": "Короткий выпад в открытую сторону цели.",
        "damageType": "piercing",
```

Afterlife mentor trainingShowcase
---------------------------------

Afterlife mentors, Guardians, residents, or Shining representatives may expose
discounted spiritual-art lessons. They never bypass the player's progression
cap and cannot teach above their own tier/sourceCap.

Preferred helper path:

```powershell
. "game_state/control/gm_turn_helper.bootstrap.ps1"

$offers = @(
  [ordered]@{
    offerId = "mentor_liora_guard_2"
    targetKind = "standard_spiritual_art"
    targetId = "guard"
    targetName = "Защита"
    currentValue = 1
    targetValue = 2
    sourceCap = 4
    cost = [ordered]@{
      inkFeathers = 105
      lightSparks = 0
    }
    summary = "Лиора показывает, как принять удар краем света."
  }
)

Complete-BoeTrainingShowcaseRequest `
  -RequestId "training_req_liora_001" `
  -Offers $offers `
  -Summary "Лиора может удешевить обучение защите, но не поднимает искусство выше собственного уровня."
```

Manual fallback:

Afterlife self fallback
-----------------------

If no mentor showcase exists, `/обучение` may show expensive self-training.
The GM should not author a receipt for self-training. The client computes price
from the base spiritual-art cost and the multipliers documented above.
`/духовные_искусства` remains a direct self-upgrade surface with the same
expensive fallback prices. Use mentors when the story offers a teacher.
