==================================================
GLOBAL AFTERLIFE TURN RULE
==================================================

Every accepted afterlife turn must follow this order:

1. Realm gate:
   - Read `game_state/meta/soul_state.json.currentRealm`.
   - Decide whether this is ordinary Chaos Sea, ordinary active Shining Abode, or Shining Abode pending-bootstrap handoff.

2. Lifecycle guards:
   - Check `afterlife_return_guard.json`, `ascension.json`, `incarnation_trigger.json`, and `shining_abode_state.json.preparedIncarnationPackage`.
   - Do not mix return, life evaluation, ascension, incarnation, and Shining bootstrap logic.

3. Scheduler first:
   - Read `input/turn_request.json.progressionControl` before resolving the player action.
   - Every `mustEvaluate* = true` is mandatory.
   - `afterlifeCatchupRequired = true` is one bounded summary obligation, not thousands of raw cycles.

4. State loading:
   - Read `soul_state.json`.
   - Read `guardians.json`.
   - Read `guardian_projects.json`.
   - Read `guardian_abode_residents.json`.
   - In Shining Abode, also read `shining_abode_state.json`.

5. Pending contracts:
   - Read pending afterlife request files in `game_state/control/`.
   - Close every present pending contract through its canonical receipt/state surface.

6. Actor scope:
   - Declare every changed Guardian, resident, Shining faction, hall, gate, or institution as relevant.
   - Explain why plausible non-processed actors are outside scope.

7. Living-world debt:
   - Process due contours through Guardian/Soul/resident/Shining surfaces.
   - Do not use Mortal World NPC/faction/location/time/weather/combat/inventory channels.

8. Direct player action:
   - Process the player action only after the above context is known.

9. Report:
   - If any afterlife cycle is due, write `progressionProcessingReport` with exact processed counts and exact per-contour `newLast*Ordinal`.
   - Copy `sessionId`, `requestId`, and `turnNumber` from the current `input/turn_request.json`; do not invent new correlation values.

10. Final audit:
   - Remove stale Mortal World outputs.
   - Do not author `afterlife_notifications.json`; the client derives it from canonical receipts/state.

==================================================
COMBINED TURN DECISION TREE
==================================================

Use this decision tree when one turn contains several obligations at once: scheduler debt, catch-up, pending files, and a player action.

1. If `currentRealm = "Shining Abode"` and `preparedIncarnationPackage != null`, stop ordinary afterlife processing and use pending-bootstrap handoff rules only.
2. Otherwise, read `progressionControl` before selecting the scene. Record every due contour and every `afterlifeCatchupContours[]` value in `gm_thoughts_markdown`.
3. Read all pending afterlife control files before narration. A pending contract is not optional flavor; it must close through its exact canonical receipt/state surface.
4. Declare all changed Guardians, residents, Shining factions, gates, halls, and institutions in actor scope. Do not declare a non-actor environment as a relevant actor unless it has a matching reasoning block.
5. Resolve bounded catch-up first, then ordinary scheduler cycles, then pending contracts / direct player action. When a pending file is the client-authored mechanical form of the player action, close that contract as the action resolution and explain the ordering in reasoning.
6. Write only afterlife surfaces and exact receipts. Do not use Mortal World `worldEventsLog`, `factionDataChanges`, `UpdateNPCs`, `UpdateQuests`, `currentLocationData`, `timeChange`, `setWorldTime`, or `weatherChange`.
7. Finish with `progressionProcessingReport` when any afterlife cycle was due. Every processed contour uses its own count and own `newLast*Ordinal`; never copy the largest backlog marker to unrelated contours.

```markdown
## Оценка времени и мира
- Realm: Chaos Sea.
- Lifecycle guards: no active ascension, no incarnation trigger, no Shining bootstrap package.

## Охват NPC-анализа
- Режим: Mixed
- Релевантные акторы: Азалия, Лиора
- Почему они релевантны: Азалия владеет текущей Обителью и её проект продвигается; Лиора имеет pending history request.

## Guardian Thoughts
### Азалия
- Ситуация: Душа вернулась после долгой смертной жизни и пришла к её резиденту.
- Внутренние мысли: Азалия видит, что Лиора готова раскрыть часть прошлого, но не хочет ломать память души слишком резко.
- Действия: Она позволяет разговор, усиливает защитный шелк Обители и продвигает проект мягкого раскрытия воспоминаний.

### Лиора
- Ситуация: Душа прямо спрашивает о её памяти прошлой жизни.
- Внутренние мысли: Лиора боится снова стать лишь тенью чужого прошлого, но хочет быть полезной.
- Действия: Она раскрывает один фрагмент истории и оставляет понятный след в резидентской памяти.

## Afterlife Living World / Живой мир Посмертия
- Catch-up outcome 1: за время отсутствия души в Море Хаоса усилились тихие течения воспоминаний; это отражается в hub-summary и не требует mortal worldEventsLog.

- Chaos Sea hub cycle processed: 1.
- Guardian project cycles processed: 2.
- Resident agency cycle processed: 1.
- Stable contours: Shining contours are not active because currentRealm is Chaos Sea and no Shining catch-up contour is listed.

## Отчёт scheduler
- progressionProcessingReport will close Chaos Sea ordinal 31, Guardian project final marker 18, Resident agency ordinal 12.
- afterlifeCatchupProcessed=true and summary events processed=2.
```

14. VALID — SHINING CORE ACTION CONTRACTS
==================================================

`pending_shining_abode_actions.json` is the canonical client-authored contract for active Shining Abode actions. It is not optional flavor. If the file exists, the GM must close exactly the pending request through `game_state/meta/shining_abode_state.json.coreActionReceipts[]` and the exact state mutation required by that `actionType`.

Queue and mode rules:
- The file contains exactly one active Shining core request (`request` or `requests[0]`), not a GM-managed queue. Do not invent a second simultaneous Shining core request.
- Ordinary active Shining uses `shining_abode_state.json.availability = active` or another accepted value such as `sealed_until_next_ascension`; pending-bootstrap is not an `availability` value.
- Pending-bootstrap is derived from non-null valid `preparedIncarnationPackage`; in that mode the GM preserves the package and does not process ordinary Shining core actions.
- Cost fields in receipts identify the accepted request, but resource spends, Radiance XP, strength changes, gate invalidation, and package creation must also be reflected through canonical Shining/Soul state deltas.

Accepted Shining core actions are strict diff contracts: mutate only the canonical state surfaces projected by that `actionType` plus the matching `coreActionReceipts[]` entry. Refused, withdrawn, or expired outcomes close only through the receipt and must leave canonical Shining, Soul, and resident state unchanged.

Supported `actionType` values:

```text
forge_relic.reshape
  Requires: relic.formTag exists, targetFormTag is non-empty and different.
  State result: relic.formTag becomes targetFormTag.
  Receipt identity: factionId, relicId, targetFormTag.

forge_relic.retune_property
  Requires: propertyIndex and replacementProperty with the same canonical band as the old property.
  State result: relic.properties[propertyIndex] becomes replacementProperty.
  Receipt identity: factionId, relicId, propertyIndex.

forge_relic.strengthen_band
  Requires: propertyIndex pointing to a property with upgradeable band.
  State result: relic.properties[propertyIndex].band upgrades by one canonical step.
  Receipt identity: factionId, relicId, propertyIndex.

forge_relic.stabilize_echo
  Requires: companion_echo relic or relic with companionSeed / companionManifestationQualityBonus.
  State result: relic.companionManifestationQualityBonus increases by canonical service multiplier.
  Receipt identity: factionId, relicId.

forge_relic.uplift_rarity
  Requires: canonical rarity below legendary and enough addedProperties if the next rarity requires more properties.
  State result: relic rarity upgrades one step; missing minimum properties are appended from addedProperties.
  Receipt identity: factionId, relicId.
```

This example is for a deterministic Eternal Guardian attraction. The player-facing fiction is "I seek this Eternal Guardian." The technical contract is `game_state/control/system_guardian_attraction.json`, often paired with `guardians.json.pendingGuardianCreation.mode = system_preset`.

The GM must not improvise a nearby Guardian archetype. The result must point to the requested preset and persist `sourcePreset` on the materialized Guardian.

Important runtime marker: the canonical `turn_request.json.playerAction` for this flow starts with `[CHAOS_SEA_SYSTEM_GUARDIAN_ATTRACTION: <presetId>]`. This is a client-authored routing tag. Keep it in the input/audit context so the runtime can clear `system_guardian_attraction.json` after acceptance, but do not present the tag to the player as diegetic speech.

==================================================

22. VALID — DIRECT RESIDENT ACTION TAGS AND PENDING-BACKED ROUTING TAGS
==================================================

This example is a routing reference for exact tags that may appear inside `input/turn_request.json.playerAction`. The GM must recognize the tag first, then choose the matching row in `OtherGuides/Afterlife_Contract_Matrix.md`.

These tags are not all the same kind of contract:
- `[ABODE_RESIDENT_RELIC_GRANT]` and `[ABODE_RESIDENT_QUEST_REQUEST]` are direct resident actions. They have no pending control file and close no receipt arrays by themselves.
- `[GUARDIAN_TRADE_REQUEST]`, `[GUARDIAN_SOCIAL_TALK_REQUEST]`, `[GUARDIAN_SOCIAL_LORE_REQUEST]`, `[ARCHIVE_CONSULTATION_REQUEST]`, `[ARCHIVE_PROJECT_FUEL_REQUEST]`, `[ABODE_RESIDENT_ROSTER_REQUEST]`, `[ABODE_RESIDENT_HISTORY_REQUEST]`, `[ABODE_RESIDENT_TALK]`, `[ABODE_RESIDENT_TRANSFER_REQUEST]`, and `[PLAYER_GUARDIAN_FOUNDATION]` are pending-backed routing markers. The GM must read the matching pending file and close that exact pending contract.

Direct resident reward:

```text
playerAction:
[ABODE_RESIDENT_RELIC_GRANT] Игрок принимает реликвию связи от afterlife resident 'Лиора' (residentId=res_azalia_liora_001, guardianId=guard_social_azalia_001, abodeId=abode_azalia_memory_silk_001).

Required accepted-turn surfaces:
- metaStateUpdates.soulRelicOperations.addRelic:
  - relicType = companion_echo
  - sourceResidentId = res_azalia_liora_001
  - sourceGuardianId = guard_social_azalia_001
  - companionSeed is complete: companionNameHint, originWorldSummary, futureCompanionPrompt, bondReason, coreTraits, archetypeHints, appearanceMotifs, personalityProfile, abodeDisposition, abodeDevotionLevel / abodeDevotionTier, restlessness / migrationState
- UpdateGuardianAbodeResidents:
  - same residentId / guardianId / abodeId
  - bondRewardState = granted
  - grantedRelicId = the new relic id
  - optional bounded devotion/restlessness changes when the scene justifies them
- residentInteractionLogUpdates:
  - concise memory of why the resident granted the relic

Forbidden for this tag:
- no UpdateGuardianAbodeResidentInteractionReceipts
- no UpdateGuardianAbodeResidentRosterReceipts
- no UpdateGuardianAbodeResidentTransferReceipts
- no pending_resident_companion_manifestation_request.json output
- no UpdateNPCs
```

Direct resident quest:

```text
playerAction:
[ABODE_RESIDENT_QUEST_REQUEST] Игрок помогает обитателю загробья 'Лиора' (residentId=res_azalia_liora_001, guardianId=guard_social_azalia_001, abodeId=abode_azalia_memory_silk_001).

Required accepted-turn surfaces:
- UpdateSoulQuests:
  - ordinary Soul Quest identity, title, description, status, and objective data
  - guardianId = guard_social_azalia_001 when the quest belongs to that Abode
  - relatedAfterlifeResidentId = res_azalia_liora_001
- UpdateGuardianAbodeResidents when resident state changes:
  - linkedSoulQuestId = the new or progressed Soul Quest id

Forbidden for this tag:
- no Mortal UpdateQuests
- no UpdateNPCs
- no resident receipt arrays unless a separate pending resident file exists in game_state/control
```

```text
pendingShiningBlessingEffects is runtime-created from preparedIncarnationPackage.selectedCards after Shining bootstrap.
```

Correct reasoning checklist:
- First match the exact tag in `playerAction`.
- If the tag is direct resident reward/quest, do not search for a pending receipt to close.
- If the tag is pending-backed, read the named pending file before writing response state.
- Declare changed residents, Guardians, archive authority, or founded Guardian actors in `gm_thoughts_markdown`.
- Keep all outputs inside afterlife surfaces. Never use Mortal `UpdateNPCs`, Mortal `UpdateQuests`, `worldEventsLog`, or afterlife notifications for these tags.

Why this is valid:
- It separates direct resident player actions from pending resident contracts.
- It gives the GM exact tag names that the client puts into `playerAction`.
- It routes every hidden pending-backed tag to the same canonical surfaces that validators and normalizers expect.

==================================================
COMMON INVALID PATTERNS
==================================================

Invalid afterlife response:

```json
{
  "worldEventsLog": [
    {
      "title": "В Море Хаоса начался шторм"
    }
  ],
  "factionDataChanges": [
    {
      "factionId": "shine_faction_glass_light_001",
      "strengthChange": 5
    }
  ],
  "UpdateNPCs": [
    {
      "NPCId": "res_azalia_liora_001",
      "name": "Лиора"
    }
  ],
  "currentLocationData": {
    "locationName": "Сияющая площадь"
  },
  "timeChange": {
    "minutes": 60
  }
}
```

Why invalid:
- `worldEventsLog` is Mortal World world progression.
- `factionDataChanges` is Mortal World faction progression.
- `UpdateNPCs` is for regular mortal NPCs, not Guardians or afterlife residents.
- `currentLocationData` is Mortal World location state; afterlife uses Abodes and Shining state.
- `timeChange` is Mortal World time; afterlife scheduler uses `progressionControl` and `progressionProcessingReport`.

Correct replacement:

```text
Chaos Sea event -> Guardian/Soul/resident state + progressionProcessingReport
Guardian project -> guardianProjectUpdates / completeGuardianProjects
Resident agency -> residentThoughtJournalUpdates / residentInteractionLogUpdates / UpdateGuardianAbodeResidents
Shining civic change -> game_state/meta/shining_abode_state.json
Shining faction change -> Shining faction state inside shining_abode_state.json
Shining trade -> faction.tradeInventory + faction.tradeInventoryReceipts[]
Player-facing notification -> derive from canonical state/receipts; do not author afterlife_notifications.json manually
```
