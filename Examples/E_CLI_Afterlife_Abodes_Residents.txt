10. VALID — GUARDIAN ABODE RESIDENT ROSTER REQUEST
==================================================

This request is not ambient flavor. It is a client-authored contract asking the GM to create explicit residents for a Guardian's Abode. The answer must materialize resident objects and close the request with a roster receipt.

Input fragment:

```json
{
  "pending_guardian_abode_residents_request.json": {
    "requests": [
      {
        "requestId": "abode_roster_azalia_314",
        "guardianId": "guard_social_azalia_001",

        "abodeName": "Обитель Шёлковой Памяти",

        "requestMode": "standard_roster",
        "createdAtTurn": 314,
        "createdAtUtc": "2026-04-24T11:00:00Z"
      }
    ]
  }
}
```

Correct GM reasoning:

```markdown
## Оценка времени и мира
- Realm: Chaos Sea.
- pending_guardian_abode_residents_request.json exists and must close this accepted turn.
- The request asks for explicit Abode residents; they cannot be inferred from Azalia's domain or narrated without state.

## Охват NPC-анализа
- Режим: Guardian-centric
- Релевантные акторы: Азалия, Марин, Эйва
- Почему они релевантны: Азалия владеет Обителью; Марин и Эйва are newly materialized residents whose state and memory are written.
- Акторы вне охвата: остальные Хранители, Mortal World NPCs
- Почему они вне охвата: this roster contract touches only Azalia's Abode and afterlife resident state.

## Guardian Thoughts
### Азалия
- Ситуация: Обитель получила явный roster request and must stop being an empty implied location.
- Внутренние мысли: Азалия wants residents who reinforce memory, care, and careful disclosure.
- Действия: She opens two stable social roles in the Abode and accepts responsibility for them.

### Марин
- Ситуация: Марин becomes an attendant spirit in the silk-memory halls.
- Внутренние мысли: He is cautious but already oriented toward service and calm routine.
- Действия: He begins maintaining memory curtains and becomes available for talk/history hooks.

### Эйва
- Ситуация: Эйва arrives as a wayfaring soul who is not fully settled yet.
- Внутренние мысли: She wants shelter but still listens for roads beyond the Abode.
- Действия: She joins the roster with wavering migration state, not as a permanent fixture.
```

- Only saying "there are many spirits here" without `UpdateGuardianAbodeResidents`.
- Writing `UpdateNPCs` for residents.
- Receipt without matching `requestId`.
- Resident object without `mortalWorldImprint.futureCompanionPrompt`, `isPresent`, `residentKind`, `originType`, `bondTier`, or canonical abode devotion fields.
- For `requestMode = founder_attraction`, transferring residents from the former patron's Abode instead of creating first residents attracted by `founderFeatureTitle` / `founderFeatureSummary`.

10B. VALID — FOUNDER-ATTRACTION RESIDENT ROSTER

`founder_attraction` is a distinct roster mode. It appears after the player has founded a new Guardian/Abode, and the client asks the GM to materialize the first residents drawn by that founded Abode's feature. The GM must use the request's `founderFeatureTitle` and `founderFeatureSummary` as creative constraints. The GM must not move the old patron's residents and must not treat the former Guardian's roster as inherited property.

Input fragment:

```json
{
  "pending_guardian_abode_residents_request.json": {
    "requests": [
      {
        "requestId": "abode_roster_founder_lumen_318",
        "guardianId": "guard_founder_lumen_001",
        "guardianName": "Люмен",
        "abodeId": "abode_lumen_first_lantern_001",
        "abodeName": "Обитель Первого Фонаря",
        "currentReputation": 0,
        "requestMode": "founder_attraction",
        "founderFeatureTitle": "Первый Фонарь",
        "founderFeatureSummary": "Новая founded-Обитель зажигает маяк для душ, которые ищут безопасное начало без переноса старых клятв.",
        "createdAtTurn": 318,
        "createdAtUtc": "2026-04-24T12:00:00Z"
      }
    ]
  }
}
```

Correct GM reasoning:

```markdown
## Оценка времени и мира
- Realm: Chaos Sea.
- pending_guardian_abode_residents_request.json exists with requestMode=founder_attraction.
- The current Guardian is player-founded; the request's founderFeatureTitle/founderFeatureSummary define the first-resident attraction theme.

## Охват NPC-анализа
- Режим: Guardian-centric
- Релевантные акторы: Люмен, Ирис, Тарн
- Почему они релевантны: Люмен owns the new founded Abode; Ирис and Тарн are first residents created by the founder feature.
- Акторы вне охвата: previous patron's residents, Mortal World NPCs
- Почему они вне охвата: founder_attraction creates a new first roster and does not transfer old-patron residents.

## Guardian Thoughts
### Люмен
- Ситуация: The founded Abode is no longer an empty title; the First Lantern begins attracting souls.
- Внутренние мысли: Люмен wants residents who answer the new mantle rather than old obligations.
- Действия: Люмен welcomes first residents shaped by the beacon feature and records them as new Abode residents.

### Ирис
- Ситуация: Ирис follows the First Lantern because she remembers being lost between lives.
- Внутренние мысли: She wants a beginning that does not demand an inherited oath.
- Действия: She becomes a present resident of Люмен's Abode and takes a guiding role.

### Тарн
- Ситуация: Тарн arrives as a traveler-soul drawn by the safe-start beacon.
- Внутренние мысли: He is not settled yet, but the new Abode gives him a reason to pause.
- Действия: He joins as a restless resident, available for future talk/history hooks.
```

Correct reasoning checklist:
- First match the exact tag in `playerAction`.
- If the tag is direct resident reward/quest, do not search for a pending receipt to close.
- If the tag is pending-backed, read the named pending file before writing response state.
- Declare changed residents, Guardians, archive authority, or founded Guardian actors in `gm_thoughts_markdown`.
- Keep all outputs inside afterlife surfaces. Never use Mortal `UpdateNPCs`, Mortal `UpdateQuests`, `worldEventsLog`, or afterlife notifications for these tags.

Why this is valid:
- It separates direct resident player actions from pending resident contracts.
- It gives the GM exact tag names that the client puts into `playerAction`.
- It routes every hidden pending-backed tag to the same canonical surfaces that validators and normalizers expect.
