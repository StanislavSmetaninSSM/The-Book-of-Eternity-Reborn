## mortal_location_existing_movement_storage_continuity_v1

The accepted pre-turn map contains an open, player-known directed link from the
current courtyard to `loc_exact_old_oak_crossroads`. Existing movement carries
only exact selection and operational fields:

```json
{
  "currentLocationData": {
    "locationId": "loc_exact_old_oak_crossroads",
    "lastEventsDescription": "Герой вышел со двора и достиг развилки у старого дуба.",
    "currentWeather": { "summary": "Морось стихает" },
    "currentInteractions": [],
    "currentChronology": []
  }
}
```

Never include locationStorages or contents in this existing-movement payload.
The client preserves storage item contents: it parks the source scene and
restores the destination scene atomically. If storage metadata changes in the
same full response, use the separately governed `storageUpdates[]` command.

until the exact storage is empty. Threat updates deep-merge; completion writes
the system-owned archive entry and clears `currentActivity`. The immutable
materialization section dispositions remain creation evidence and are never
rewritten to follow later storage or threat counts. They are immutable creation
evidence, not live counters.

## mortal_location_receiptless_rejection_v1

For the canonical negative, take the complete remote location from the
bootstrap example, replace its raw null identity with a permanent locationId,
remove raw-only `initialId`, and deliberately omit `materializationReceipt`.
That receipt-less canonical location is rejected with exact diagnostic
`mortal_location_materialization_receipt_required`. The client never promotes,
reseals, or repairs it into accepted current state at runtime.
