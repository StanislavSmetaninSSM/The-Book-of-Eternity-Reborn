CLI STEP MAIN — EXTENDED EXAMPLE FOR VALIDATION, NPC SCOPE, AND REPAIR LOOP

This file supplements TaskGuides/CLI_Step_Main.txt.
Read BOTH files before EVERY turn and reread them before EVERY repair attempt and before handling any terminal protocol failure notice.

JSON/PowerShell reminder:
- write JSON/state files in UTF-8 explicitly
- use `[ordered]@{}` and `@()` for data objects
- never use `{ ... }` where you mean JSON data
- if JSON suddenly contains `Ast`, `StartPosition`, `Extent`, or `PipelineElements`, you serialized a PowerShell runtime object instead of game data

==================================================
1. SCENE-LOCAL TURN WITH NPC SCOPE
==================================================

Example gm_thoughts_markdown:

## Оценка времени и мира
- Прошло игрового времени: 15 минут
- Логические последствия: Существенных мировых или фракционных последствий нет
- Решение о прогрессии: Прогрессия мира и фракций не требуется

## Охват NPC-анализа
- Режим: Scene-local
- Релевантные акторы: Марта, Феликс
- Почему они релевантны: Оба физически присутствуют в сцене и непосредственно реагируют на действие игрока
- Акторы вне охвата: Капитан стражи, Совет ремесленников
- Почему они вне охвата: Локальная сцена не затрагивает их решения и не запускает off-screen последствия

## Reasoning / Размышления NPC
### Марта
- Текущая локация: Рыночная площадь. Она остаётся в лавке и не покидает сцену в этом ходу.
- Ситуация: Она видит, что игрок просит у неё помощь при свидетеле
- Мысли: Она хочет помочь, но боится потерять репутацию у хозяина лавки
- Действия: Она отвечает осторожно, даёт неполную информацию и наблюдает за реакцией Феликса

### Феликс
- Текущая локация: Рыночная площадь. Он уже находится рядом с Мартой и остаётся в этой же сцене.
- Ситуация: Он замечает, что игрок пытается обойти его через Марту
- Мысли: Он не хочет терять контроль над ситуацией и подозревает скрытый мотив
- Действия: Он вмешивается в разговор и переводит инициативу на себя

## Логика прогрессии
- Существенных off-screen обновлений не требуется

==================================================
2. WORLD-PROGRESSION TURN WITH OFF-SCREEN NPCS
==================================================

## Оценка времени и мира
- Прошло игрового времени: 8 часов
- Логические последствия: Несколько активностей НПС и один фракционный проект должны продвинуться
- Решение о прогрессии: Нужны world/faction/NPC updates

## Охват NPC-анализа
- Режим: World-progression
- Релевантные акторы: Лорд Хавьер, Интендант Ирис, Капитан Рувен
- Почему они релевантны: Их решения напрямую определяют реакцию гарнизона, снабжения и текущего фракционного проекта
- Акторы вне охвата: Бармен Йорик, Рыночные торговцы
- Почему они вне охвата: Этот цикл не меняет их состояние и не создаёт для них новых решений

## Reasoning / Размышления NPC
### Лорд Хавьер
- Текущая локация: Крепость гарнизона. Он остаётся в штабе и координирует решения оттуда.
- Ситуация: Он получил отчёт о нехватке провизии и угрозе с южной дороги
- Мысли: Нельзя показывать слабость гарнизона, но и игнорировать снабжение опасно
- Действия: Он перераспределяет охрану, ускоряет переговоры с Ирис и отменяет второстепенные поставки

### Интендант Ирис
- Текущая локация: Склады гарнизона. Она остаётся у складов и работает с поставщиками на месте.
- Ситуация: Она видит дефицит ресурсов и давление со стороны Хавьера
- Мысли: Ей нужно сохранить склады и не допустить паники среди поставщиков
- Действия: Она урезает выдачу припасов и запускает срочную закупку по повышенной цене

### Капитан Рувен
- Текущая локация: Южная дорога у караванного маршрута. Он смещается ближе к зоне риска и усиливает патрули там.
- Ситуация: На нём лежит ответственность за безопасность караванного пути
- Мысли: Он считает южную дорогу уязвимой и ждёт нападения
- Действия: Он усиливает патрули и меняет маршрут сопровождения

## Логика прогрессии
- Фракционный проект снабжения продвинулся
- Активности гарнизона и снабжения обновлены

3. GUARDIAN-CENTRIC TURN
==================================================

## Оценка времени и мира
- Прошло игрового времени: один hub-cycle Моря Хаоса
- Логические последствия: Нужно оценить настроение и проект активного Хранителя

## Охват NPC-анализа
- Режим: Guardian-centric
- Релевантные акторы: Аэлион
- Почему они релевантны: Ход целиком сосредоточен на прибытии в его Обитель и его реакции
- Акторы вне охвата: Прочие Хранители
- Почему они вне охвата: В этом ходе они не взаимодействуют с душой и не влияют на результат сцены

## Guardian Thoughts
### Аэлион
- Ситуация: Душа прибыла в его Обитель после долгого отсутствия
- Мысли: Он хочет понять, вернулась ли душа ради знаний или ради выгоды
- Действия: Он приветствует душу сдержанно, проверяет её настрой и открывает разговор на своих условиях

4. GUARDIAN GACHA CHARGES PER RETURN
==================================================

Guardian-mediated gacha is limited per Guardian per return from mortal life:
- Hostile(-100..-51): 0 attempts
- Wary/Neutral(-50..49): 1 attempt
- Friendly(50..129): 2 attempts
- Devoted/Legendary(130..300): 3 attempts

Direct `/gacha` remains neutral and does NOT consume Guardian charges.

Valid guardian state fragment:

```json
{
  "guardianId": "guard_magic_aelion_001",
  "name": "Аэлион",
  "relationshipData": {
    "currentReputation": 142
  },
  "gachaSystem": {
    "chargesPerReturn": 3,
    "chargesUsedThisReturn": 1,
    "gachaHistory": [
      {
        "timestamp": "2026-03-09T18:42:00Z",
        "costInFeathers": 120,
        "relicId": "sr_magic_aelion_starglass_001",
        "finalRarity": "Rare"
      }
    ]
  }
}
```

This means:
- Guardian-mediated pull is still allowed
- 2 charges remain for this return
- after the next successful `UpdateGuardians.processGacha`, used charges become `2`
- canonical guardian history stores compact result entries: `timestamp`, `costInFeathers`, `relicId`, `finalRarity`

If `chargesUsedThisReturn` already equals `chargesPerReturn`, do NOT emit `processGacha` for that Guardian.

4.5 MEMORY GATES — VALID MECHANICAL REWARD
==================================================

`Memory Gates` is not a lore-only action. It MUST create one pending Memory Legacy for the next mortal life.

Valid `metaStateUpdates.memoryLegacyGrant` example:

```json
{
  "metaStateUpdates": {
    "memoryLegacyGrant": {
      "legacyId": "memory_legacy_scholar_001",
      "legacyType": "startingCharacteristicBonus",
      "sourceLifeHint": "Эхо жизни мудреца, посвятившего десятилетия поиску истины.",
      "characteristic": "intelligence",
      "bonus": 2
    }
  }
}
```

Rules:
- Only one `pendingMemoryLegacy` may exist at a time
- A new `Memory Gates` purchase replaces the old pending legacy
- The client rejects a `Memory Gates` turn if no new valid pending legacy appears
- If an old `pendingMemoryLegacy` already existed before the turn and remains unchanged after the new purchase, the client rejects the turn as an invalid `Memory Gates` outcome
- Canonical `pendingMemoryLegacy` stores `legacyId`, `legacyType`, `sourceLifeHint`, `grantSource`, `applicationState`, `grantedAtUtc`, and `grantSnapshot`
- `applicationAudit` appears later only when the client has already applied the legacy locally during an incarnation turn

4.5B MORTAL WORLD TRAINING MUST MATERIALIZE SKILLS
==================================================

If a Mortal World scene says the player learned, trained, practiced, unlocked, or repeatedly applied a concrete skill, the result must not remain prose-only. Attribute-only checks are allowed when the character has not learned a durable skill yet, but the narrative should make that clear.

Example: a child in an archive spends repeated turns learning the difference between house seals and witness marks. Once the lesson crosses from early practice into a learned technique, the GM should add a passive skill:

4.5C MORTAL WORLD XP AND LEVEL-UP USE EXPERIENCE.JSON
==================================================

Ordinary Mortal World XP is stored in `game_state/player/experience.json`. If combat, a completed objective, or a meaningful victory grants mechanical progress, do not leave the reward as prose-only.

When an active skill was used, update mastery separately from character XP. The player-level reward belongs in `experience.json`; skill practice belongs in `skillMasteryChanges`.

Example: the player wins a dangerous archive duel using an existing active skill and crosses the next level threshold:

```json
{
  "response": "Тень отступает в щель между шкафами, оставляя на полу только холодную пыль. Искра не чувствует победного восторга, но рука уже запомнила короткий выпад: не широкий удар, а один точный толчок в момент, когда противник раскрывается. После этой схватки тело и память делают шаг дальше.",
  "experienceGained": 20,
  "skillMasteryChanges": [
    {
      "skillName": "Быстрый выпад",
      "newMasteryLevel": 1,
      "newCurrentMasteryProgress": 2,
      "newMasteryProgressNeeded": 5,
      "masteryLeveledUp": false
    }
  ]
}
```

Then write these values into `game_state/player/experience.json`, not into the top-level GameResponse:

- `playerLevel`: 2
- `level`: 2
- `currentExperience`: 10
- `experience`: 10
- `totalExperience`: 110
- `experienceForNextLevel`: 150
- `experienceGained`: 20

Include `game_state/player/experience.json` in `Complete-BoeTurn -FilesModified`. Do not edit `game_state/player/stat_points.json` for this ordinary level-up: after the accepted turn, the client detects the higher level, preserves its `levelUpStatPointsAwardedThroughLevel` marker, and opens the stat allocation flow.

Important invariant: after an XP reward, `totalExperience` must be lower than the current `experienceForNextLevel` for the persisted `playerLevel`. If the reward leaves `totalExperience >= experienceForNextLevel`, the level-up is not materialized yet. Repair it by advancing `playerLevel`/`level` and setting `experienceForNextLevel` to the next threshold above the new `totalExperience`; do not compensate by editing `stat_points.json`.

Because the example is a duel, it also needs Mortal combat state. Write `game_state/combat/combat_log.json` with a player-facing summary of the same exchange so `/бой` is useful after the turn. If the opponent remains active, defeated-but-important, or likely to act again, also write `game_state/combat/enemies.json`; if allies took part tactically, write `game_state/combat/allies.json`. Use `MORTAL_COMBAT_STATE_TEMPLATE.md` before writing these files, and include every touched combat file in `Complete-BoeTurn -FilesModified`.

4.6 LOCAL GUARDIAN TRADE AWARENESS
==================================================

Local guardian trade is client-side and does NOT create `turn_request.json`, but it is still canonical to the current active Guardian's abode.

Guardian-forced incarnation is a separate lifecycle sanction:
- NEVER use it on the immediate protected return turn if `game_state/control/afterlife_return_guard.json` still has `remainingProtectedTurns > 0`
- It is legal only on an ordinary player-driven Chaos Sea turn after explicit provocation against the current active Guardian
- Valid forced payload fragment in `game_state/control/incarnation_trigger.json`:

{

==================================================
9. CANCEL AND RESTART BEHAVIOR
==================================================

Cancel behavior:
- if rollback backup is available, client restores the last stable files and tells the player that rollback happened
- if rollback backup is unavailable for that flow, client tells the player explicitly that current files were left as is
- cancelling the wait does not make an already dispatched GM computation disappear; if GM finishes later, the client may still process it as a late response unless the flow has already been fully closed
- rollback restores pre-existing tracked files and also removes newly created tracked files from the rejected/aborted turn

Turn error behavior:
- if GM writes `ready/turn_error.json` for a transition flow, the client restores the last stable tracked file set before continuing
- this includes reverting local realm transitions and deleting new tracked files created only for the failed transition
- if GM writes `ready/turn_error.json` after the user already cancelled waiting, the client still consumes that late error signal and cleans it up on the next loop

Concrete late turn_error after cancel example:
1. Client dispatches turn `turnNumber = 42` and creates pending snapshot.
2. User presses `Escape` while waiting.
3. GM still finishes later and writes:
{
  "sessionId": "game-session-123",
  "requestId": "abc123",
  "turnNumber": 42,
  "status": "error",
  "timestamp": "2026-03-09T12:07:00Z",
  "error": "The CLI agent failed before writing valid state"
}
4. On the next game loop iteration, client:
   - reads and correlates the late `turn_error.json`
   - shows the GM error
   - restores rollback snapshot if one still exists
   - deletes `ready/turn_error.json`
   - clears pending snapshot artifacts

Valid terminal error example:

ready/turn_error.json
{
  "sessionId": "game-session-123",
  "requestId": "abc123",
  "turnNumber": 42,
  "status": "error",
  "timestamp": "2026-03-09T12:08:00Z",
  "error": "Rules validation inside the CLI workflow failed before final write"
}

Correct behavior:
- daemon treats this as a normal terminal outcome of the turn
- client shows the GM error
- client performs cleanup/rollback according to the current flow rules

Daemon-side stale terminal signal example:
1. Old file remains from a previous turn:

ready/turn_complete.json
{
  "sessionId": "game-session-123",
  "requestId": "old-request",
  "turnNumber": 41,
  "status": "success",
  "timestamp": "2026-03-09T12:06:00Z",
  "filesModified": [
    "output/narrative_response.json",
    "output/debug_logs.json"
  ]
}

2. A new turn request arrives with:
- `sessionId = game-session-123`
- `requestId = new-request`
- `turnNumber = 42`

3. Correct daemon behavior:
- read metadata from the existing terminal file
- detect that `requestId/turnNumber` do not match the current turn
- delete the stale `ready/turn_complete.json`
- continue waiting for a correlated `ready/turn_complete.json` or `ready/turn_error.json`

Important:
- file existence alone is not enough to complete a turn
- daemon must correlate terminal files by `sessionId`, `requestId`, and `turnNumber`

Restart behavior:
- daemon restart: daemon re-checks existing validation_repair_request.json on startup and pings GM again
- daemon restart: daemon also re-checks existing terminal_protocol_failure_request.json on startup and pings GM again
- client restart with active repair artifacts:
  - if pending snapshot manifest + ready/turn_complete.json + repair request still exist, client resumes through the correlated late-response/validation path
  - if repair files exist without a matching pending snapshot manifest or without ready/turn_complete.json, client treats them as stale and clears them
- client restart with `terminal_protocol_failure_request.json`:
  - the file is preserved by default
  - the client must not delete it only because a pending snapshot manifest still exists
  - this can be a valid crash/restart state after the protocol failure was already recorded but before later cleanup
- save/load does NOT preserve repair files or pending turn snapshots
