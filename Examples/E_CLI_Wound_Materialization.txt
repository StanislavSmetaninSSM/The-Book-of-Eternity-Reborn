Client lifecycle example: independently dispelling the cut's roll hindrance removes
its carrier, not its wound root binding or consequence slot; suppression is not wound
healing. If an already authorized severity-reduction treatment retains that coordinate,
the client creates a NEW runtime effect identity with the exact old canonical root as
its sole first-create parent. The old dispelled identity and its complete terminal
history remain unchanged. Full lineage and definition-derived coordinates must agree;
there is no missing-carrier fallback. The GM never authors these IDs or parent rows.
This lifecycle explanation does not enable spiritual treatment or a new healing art.

## wound_mortal_roll_scope_all_v1

The accepted impact from a shard of the Ash Tower's bell has already produced a
client-owned Mortal physical-wound opportunity for the player, permitting severity II.
The GM chooses this setting-specific injury; it is not selected from a wound catalog.
This request fragment shows the player's offered skill row even though broad scope does
not select a skill. The opportunity and accepted-event authority are supplied separately
by the client; these examples never manufacture their seals or permanent wound IDs.


Complete GM response to that opportunity: one rank-II wound, one root definition,
one whole `roll_modifier` component, and one `roll_modifier` consequence slot.
`scope.kind=all` applies the disadvantage to every `skill_check` of this target, not
to every operation. Every Mortal wound needs at least one complete treatment route.
This setting offers examination and cooling care using one linen cooling pad and a
provider's field-medicine capability. The route does not grant the item or capability:
the client must resolve the exact provider requirements when treatment is attempted.
Only a successful procedure stabilizes the wound; partial and failed attempts make no
improvement. Until accepted stabilization, recovery is blocked and grants no free cure.

The diagnosis paths are setting-specific examinations for the ashglass cuts, not a
universal wound or diagnosis catalog. Their IDs are exact and distinct: for example,
`INSPECT_ASHGLASS_CUTS` cannot be a second path ID next to `inspect_ashglass_cuts`;
the genuinely distinct second ID above is `assess_ashglass_tendon`. Selecting a path
uses its exact ID, never fuzzy or display-name matching, and merely identifies a
possible examination; it does not assert success or grant treatment.

Only that exact skill's checks receive this component; other skills and identity-less
checks do not. A same-response new skill cannot be selected, and removing or disabling
the offered skill in the same response rejects this new binding. A later accepted loss
makes the already bound component dormant without healing/removing the wound or changing
its severity, history, or lifetime. A different ID with a similar name stays unaffected;
restoring the same permanent usable ID reactivates a still-active component. The scene
and visible descriptions use only readable Russian text, never a technical skill ID.

## wound_treatment_scene_authority_v1

There is no universal catalog of facilities, environments, medicines, or consent.
The GM chooses setting-specific exact identifiers. The client accepts only these three
closed `schemaVersion: 1` location rows:

```json
[
  {
    "kind": "mortal_wound_treatment_facility",
    "schemaVersion": 1,
    "facilityId": "field_clinic_table",
    "displayName": "Чистый стол полевой лечебницы",
    "available": true
  },
  {
    "kind": "mortal_wound_treatment_environment",
    "schemaVersion": 1,
    "environmentId": "sterile_field",
    "displayName": "Стерильное поле",
    "state": "active"
  },
  {
    "kind": "mortal_wound_treatment_consent",
    "schemaVersion": 1,
    "consentRef": "field_medic_treats_player",
    "displayName": "Согласие полевого медика",
    "providerKind": "npc",
    "providerId": "npc_field_medic_01",
    "targetKind": "player",
    "targetId": "player_current",
    "status": "granted"
  }
]
```

`available: false` and `status: "withdrawn"` are valid negative evidence. Two
different `environmentId` values may share the same exact `state`. Do not add realm,
location, lifecycle, active, reachability, reservation, fingerprint, seal, or source
authority fields; the client derives those from canonical state.

## mortal_wound_treatment_scalar_course_v1

GM authors this complete `treatment` member inside an ordinary complete Mortal wound
proposal. It is not a canonical-state patch and does not enable a fresh alternative-treatment adapter.
The field medic and medicines here belong to this worked setting, not a global medical catalog.

An empty result is legal only for an active milestone. The client consumes only the current milestone's dose,
never future doses. Course start sets and continuations preserve the client's exact active course ID;
completion or trusted interruption clears it. Route completion is not necessarily full wound healing:
this course reduces severity II to I and stabilizes the wound, which remains active.
Stale history is invalid authority, not a missed-dose outcome; other treatment does not cancel a course.
A different pending attempt for the same course milestone conflicts even without resource claims; exact retry is inert.
Source IDs, course IDs, time evidence, attempt/operation coordinates and fingerprints remain client-owned.
The remaining producers `heal`, `add_complication` and
`apply_deterioration` are pending implementation; their approved authored contracts remain supported
by the complete route model, but scalar publication does not pretend to execute them.

нужного условия прерывает курс без расхода следующей дозы. Повтор уже принятого этапа не тратит
