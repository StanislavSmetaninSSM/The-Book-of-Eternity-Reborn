   1: # Сила Обители: дизайн-план
   2: 
   3: ## Цель
   4: Добавить для каждого Хранителя числовой параметр `Сила Обители`, который:
   5: 
   6: - растёт и падает по понятным игромеханическим причинам;
   7: - влияет на реальные системы клиента, а не только на ролевой текст;
   8: - усиливает как дружественную помощь, так и враждебное вмешательство;
   9: - не ломает явный сценарий следующей жизни, заданный игроком;
  10: - поддерживает политику Хранителей и проекты, направленные друг против друга.
  11: 
  12: ## Ключевая модель
  13: 
  14: - `Репутация` отвечает на вопрос: Хранитель хочет помочь, навредить или безразличен.
  15: - `Сила Обители` отвечает на вопрос: насколько сильным будет это воздействие.
  16: 
  17: Комбинации:
  18: 
  19: - высокая репутация + сильная обитель = сильная поддержка;
  20: - низкая репутация + сильная обитель = сильное наказание/давление;
  21: - слабая обитель ограничивает и помощь, и вред.
  22: 
  23: ## Шкала
  24: 
  25: `Сила Обители = 0..100`
  26: 
  27: Тиры:
  28: 
  29: - `0..19` — `Угасающая`
  30: - `20..39` — `Хрупкая`
  31: - `40..59` — `Стабильная`
  32: - `60..79` — `Могущественная`
  33: - `80..100` — `Сияющая`
  34: 
  35: Начальное значение для нового Хранителя в v1:
  36: 
  37: - `35` для обычного newly materialized Хранителя
  38: - допустим optional override пресетом для извечных Хранителей позже, но не в v1
  39: 
  40: ## Откуда берётся рост
  41: 
  42: ### 1. Квесты Хранителя
  43: 
  44: Изменение силы обители происходит только при значимом исходе, а не от каждого разговора.
  45: 
  46: - `Easy quest complete` = `+2`
  47: - `Normal quest complete` = `+4`
  48: - `Hard quest complete` = `+7`
  49: - `Epic quest complete` = `+11`
  50: 
  51: Модификаторы:
  52: 
  53: - если quest payload содержит `supportsCurrentProject = true`: `+50%` к приросту, округление вверх
  54: - если quest payload содержит `defendsAgainstRivalPressure = true`: ещё `+2`
  55: 
  56: ### 2. Помощь текущему проекту Хранителя
  57: 
  58: За самостоятельную помощь проекту, отличную от обычного квеста:
  59: 
  60: - `minor assist` = `+1`
  61: - `meaningful assist` = `+2`
  62: - `major breakthrough assist` = `+4`
  63: 
  64: Это должно оформляться не свободным текстом, а через project/progression outcome, который можно валидировать.
  65: 
  66: ### 3. Завершение проекта Хранителя
  67: 
  68: Проект — один из главных способов накачать силу.
  69: 
  70: - `Minor project completed` = `+5`
  71: - `Major project completed` = `+10`
  72: - `Grand project completed` = `+16`
  73: 
  74: Если проект был offensive и бил по другому Хранителю:
  75: 
  76: - атакующий всё равно получает свой прирост силы;
  77: - цель additionally теряет силу по формуле из раздела `Политика Хранителей`.
  78: 
  79: ### 4. Подношения в Обитель
  80: 
  81: Чтобы был прямой sink/source вне квестов:
  82: 
  83: - каждые `50 Ink Feathers`, осознанно пожертвованные в Обитель = `+1`
  84: - cap: не больше `+3` за одно возвращение между смертными жизнями
  85: - доменно-подходящая реликвия / знание / тайна / трофей = `+2..+4`
  86: 
  87: Это нужно формализовать отдельным whitelist-командным путём позже, а не оставлять на свободную импровизацию GM.
  88: 
  89: ### 5. Резонанс смертной жизни
  90: 
  91: В конце жизни, если прожитая жизнь сильно усилила домен Хранителя:
  92: 
  93: - `weak resonance` = `+2`
  94: - `solid resonance` = `+4`
  95: - `major resonance` = `+6`
  96: 
  97: Примеры:
  98: 
  99: - Хранитель Знания: игрок основал школу, библиотеку, создал трактат
 100: - Хранитель Власти: игрок построил устойчивую политическую систему
 101: - Хранитель Выживания: игрок поднял колонию или вытащил людей из катастрофы
 102: 
 103: ## Откуда берётся падение
 104: 
 105: Сила не должна только копиться. Падение должно быть таким же явным и проверяемым.
 106: 
 107: ### 1. Провалы квестов Хранителя
 108: 
 109: - `Easy quest failed/abandoned` = `-1`
 110: - `Normal quest failed/abandoned` = `-3`
 111: - `Hard quest failed/abandoned` = `-5`
 112: - `Epic quest failed/abandoned` = `-8`
 113: 
 114: Если игрок не просто провалил, а публично подорвал авторитет/замысел Хранителя:
 115: 
 116: - дополнительно `-2`
 117: 
 118: ### 2. Провал или саботаж текущего проекта
 119: 
 120: - `Minor project stalled/ruined` = `-3`
 121: - `Major project stalled/ruined` = `-6`
 122: - `Grand project stalled/ruined` = `-10`
 123: 
 124: Если игрок осознанно помог rival side сорвать проект:
 125: 
 126: - дополнительно `-3`
 127: 
 128: ### 3. Враждебные проекты других Хранителей
 129: 
 130: Успешный offensive project rival-Хранителя уменьшает силу целевой Обители.
 131: Это один из центральных элементов политики между Хранителями.
 132: 
 133: ### 4. Трата силы на вмешательство в следующую жизнь
 134: 
 135: Это важный расходный канал.
 136: 
 137: Когда Хранитель вносит `Коррективы Хранителя` в старт следующей жизни, это стоит силы:
 138: 
 139: - `minor correction` = `-5`
 140: - `medium correction` = `-12`
 141: - `strong correction` = `-20`
 142: 
 143: Это относится и к позитивным, и к негативным корректировкам.
 144: То есть даже дружественный Хранитель реально тратит мощь, чтобы помочь.
 145: 
 146: ### 5. Стагнация при нерешённых проектах
 147: 
 148: Если у Хранителя остаётся активный проект, а игрок полностью игнорирует его в течение полного цикла между смертными жизнями:
 149: 
 150: - `-2` за цикл для `Хрупкой/Стабильной` Обители
 151: - `-3` за цикл для `Могущественной/Сияющей`
 152: 
 153: Причина: большая Обитель требует подпитки и поддержки, а не может бесконечно стоять без движения.
 154: 
 155: Это мягкий decay, не основной источник падения.
 156: 
 157: ## На что Сила Обители влияет механически
 158: 
 159: Это ключевой раздел. Эффекты должны быть производными от силы и должны валидироваться клиентом.
 160: 
 161: ## 1. Торговля у Хранителя
 162: 
 163: Текущее число слотов `4` заменяется на derived rule от силы Обители:
 164: 
 165: - `0..19` = `4` слота
 166: - `20..39` = `5`
 167: - `40..59` = `6`
 168: - `60..79` = `7`
 169: - `80..100` = `8`
 170: 
 171: Дополнительно:
 172: 
 173: - высокая сила повышает ceiling ассортимента;
 174: - репутация продолжает влиять на цены и дружественность торговли;
 175: - сила влияет именно на `количество` и `качество` ассортимента.
 176: 
 177: Разделение ролей:
 178: 
 179: - `Репутация` = пустят ли тебя к хорошему и насколько выгодно
 180: - `Сила Обители` = существует ли у Хранителя богатый ассортимент вообще
 181: 
 182: ## 2. Пул квестов Хранителя
 183: 
 184: Текущий cap available quests должен стать derived от силы:
 185: 
 186: - `0..19` = `2` available quests
 187: - `20..59` = `3`
 188: - `60..79` = `4`
 189: - `80..100` = `5`
 190: 
 191: Дополнительно сила открывает потолок типов квестов:
 192: 
 193: - `Угасающая/Хрупкая` — только простые/обычные/локальные
 194: - `Стабильная` — серьёзные и более влиятельные
 195: - `Могущественная` — личные, редкие, меж-хранительские
 196: - `Сияющая` — судьбоносные, политические, доменно-уникальные
 197: 
 198: ## 3. Guardian Gacha / посредничество Хранителя
 199: 
 200: Сила Обители даёт дополнительные бонусы поверх репутации:
 201: 
 202: - `bonusGachaCharges`
 203:   - `0..39 = 0`
 204:   - `40..79 = 1`
 205:   - `80..100 = 2`
 206: - `guardianRarityCeilingBonusSteps`
 207:   - `0..59 = 0`
 208:   - `60..100 = 1`
 209: 
 210: Репутация остаётся основным gatekeeper, но сильная Обитель даёт больше реального ресурса.
 211: 
 212: ### Canonical definitions
 213: 
 214: - `guardianRarityCeilingBonusSteps`
 215:   - это чисто числовой derived-модификатор
 216:   - каждый `+1 step` поднимает допустимый ceiling качества/редкости на одну canonical ступень
 217:   - step никогда не может обойти глобальный абсолютный max rarity cap системы
 218: 
 219: - `upgradedTradeSlot`
 220:   - торговый слот, сгенерированный с применением `guardianRarityCeilingBonusSteps`
 221: 
 222: - `elevatedSlot`
 223:   - гарантированный upgradedTradeSlot
 224:   - effective rarity ceiling for elevated slot:
 225:     `baseCeiling + guardianRarityCeilingBonusSteps + 1`
 226:   - elevated slot не может превышать global absolute max rarity cap
 227: 
 228: ## 4. Чужие нити судьбы
 229: 
 230: Сила Обители должна влиять и на оборону, и на нападение.
 231: 
 232: ### Дружественное влияние
 233: 
 234: Если репутация с Хранителем положительная и он является действующим покровителем:
 235: 
 236: - `rivalArcDefenseClues`
 237:   - `0..19 = 0`
 238:   - `20..39 = 1`
 239:   - `40..59 = 1`
 240:   - `60..79 = 2`
 241:   - `80..100 = 3`
 242: - `rivalArcClarityTier`
 243:   - `0..39 = 0`
 244:   - `40..59 = 1`
 245:   - `60..79 = 2`
 246:   - `80..100 = 3`
 247: - `rivalArcCounterQuestAccess`
 248:   - `0..59 = false`
 249:   - `60..100 = true`
 250: - `rivalArcWarningTier`
 251:   - `0..79 = 0`
 252:   - `80..100 = 1`
 253: 
 254: ### Враждебное влияние
 255: 
 256: Если Хранитель hostile:
 257: 
 258: - `rivalArcOffenseCap`
 259:   - `0..19 = no formal hostile arc sponsorship`
 260:   - `20..39 = background pressure only, no direct-target hostile arc`
 261:   - `40..59 = one minor hostile arc`
 262:   - `60..79 = one major hostile arc or one direct-target minor arc`
 263:   - `80..100 = one major hostile arc with early-signal privilege`
 264: 
 265: ## 5. Следующая жизнь: Коррективы Хранителя
 266: 
 267: Это главный эффект силы, но он не должен ломать сценарий игрока.
 268: 
 269: ### Базовый принцип
 270: 
 271: Игрок задаёт `Сценарное Ядро`.
 272: Хранитель не имеет права его переписать.
 273: Он может добавить только `Коррективы Хранителя` поверх ядра.
 274: 
 275: ### Сценарное Ядро: что неприкосновенно
 276: 
 277: Нельзя отрицать или заменять явные утверждения игрока о:
 278: 
 279: - роли/статусе/идентичности на старте;
 280: - стартовом месте;
 281: - жанре, эпохе, тональности;
 282: - базовой premise мира;
 283: - явно указанных стартовых отношениях;
 284: - явно указанном стартовом положении/ресурсах, если игрок их зафиксировал.
 285: 
 286: Пример:
 287: 
 288: Если игрок написал:
 289: 
 290: - он король
 291: - королевство процветает
 292: - стартует во дворце
 293: 
 294: нельзя сделать:
 295: 
 296: - он не король;
 297: - королевство разрушено;
 298: - стартует рабом на другом континенте.
 299: 
 300: ### Что можно корректировать
 301: 
 302: Можно добавлять только совместимые давления или блага, не противоречащие ядру:
 303: 
 304: - скрытая угроза;
 305: - соперник;
 306: - долг;
 307: - тайный союзник;
 308: - проклятие;
 309: - политическая трещина;
 310: - незримая защита;
 311: - редкий ресурс;
 312: - связанный чужой квест судьбы;
 313: - стартовое преимущество, о котором игрок не просил, но которое не ломает premise.
 314: 
 315: ### Бюджет корректив от силы Обители
 316: 
 317: Вместо словесных combinations клиент должен считать единый derived budget:
 318: 
 319: - `nextLifeCorrectionBudgetPoints`
 320:   - `0..19 = 0`
 321:   - `20..39 = 1`
 322:   - `40..59 = 2`
 323:   - `60..79 = 3`
 324:   - `80..100 = 5`
 325: 
 326: Conversion:
 327: 
 328: - `minor correction = 1 point`
 329: - `medium correction = 2 points`
 330: - `strong correction = 3 points`
 331: 
 332: ### Типы корректив
 333: 
 334: #### Minor
 335: 
 336: Небольшое смещение старта, не перестраивает кампанию:
 337: 
 338: - скрытый наблюдатель;
 339: - удобный контакт;
 340: - маленький долг;
 341: - один важный документ;
 342: - ранний знак опасности;
 343: - мелкое защитное благословение.
 344: 
 345: Power cost: `5`
 346: 
 347: #### Medium
 348: 
 349: Заметное давление/помощь, формирует раннюю ось конфликта:
 350: 
 351: - тайный заговор;
 352: - скрытая болезнь под контролем;
 353: - сильный союзник;
 354: - локальный rival claimant;
 355: - доменно-подходящая стартовая возможность;
 356: - активный долг/обязательство;
 357: - заметный ресурс или серьёзная проблема.
 358: 
 359: Power cost: `12`
 360: 
 361: #### Strong
 362: 
 363: Крупная, но всё ещё совместимая корректива:
 364: 
 365: - опасная чужая нить судьбы уже движется против игрока;
 366: - встроенная сеть саботажа;
 367: - мощный закрытый покровитель;
 368: - тяжёлое доменное проклятие, не отменяющее стартовый статус;
 369: - политический/магический кризис, который не ломает explicit premise, а осложняет её.
 370: 
 371: Power cost: `20`
 372: 
 373: ### Friendly vs Hostile corrections
 374: 
 375: Коррективы не только негативные.
 376: 
 377: #### Friendly correction examples
 378: 
 379: Игрок: король процветающего королевства.
 380: 
 381: Дружественный Хранитель может добавить:
 382: 
 383: - тайный советник, уже лояльный игроку;
 384: - скрытый защитный договор;
 385: - преданный орден;
 386: - раннюю возможность укрепить трон;
 387: - доменно-подходящий дар.
 388: 
 389: #### Hostile correction examples
 390: 
 391: Тот же игрок:
 392: 
 393: - скрытая rival soul уже собирает переворот;
 394: - родовая клятва вот-вот потребует расплаты;
 395: - часть двора куплена чужой стороной;
 396: - в процветающем королевстве есть спрятанная трещина, о которой игрок не знает.
 397: 
 398: ### UI-инвариант: игрок должен видеть причину
 399: 
 400: Нужно отдельное меню:
 401: 
 402: - `/коррективы_хранителя`
 403: 
 404: Там показывается:
 405: 
 406: - какой Хранитель внёс коррективу;
 407: - friendly / hostile / neutral intent;
 408: - сила Обители на момент вмешательства;
 409: - тип и тяжесть коррективы;
 410: - power cost;
 411: - что именно было изменено;
 412: - почему это произошло.
 413: 
 414: Формат записи:
 415: 
 416: ```json
 417: {
 418:   "correctionId": "guid",
 419:   "lifeId": "guid_or_turn_anchor",
 420:   "sourceGuardianId": "guardian_x",
 421:   "sourceGuardianPresetId": "azalia",
 422:   "intent": "friendly | hostile | neutral",
 423:   "severity": "minor | medium | strong",
 424:   "category": "ally | threat | rival_arc | debt | resource | omen | illness | intrigue | blessing | curse",
 425:   "powerCost": 12,
 426:   "abodePowerAtApplication": 68,
 427:   "scenarioAnchor": "Игрок — король процветающего королевства",
 428:   "appliedAdjustment": "Во двор уже внедрён rival claimant, связанный с чужой нитью судьбы",
 429:   "reason": "Враждебный Хранитель ответил на оскорбление и сорванный проект",
 430:   "visibleToPlayer": true
 431: }
 432: ```
 433: 
 434: ## Политика Хранителей: проекты против других Обителей
 435: 
 436: Проект Хранителя может быть:
 437: 
 438: - `internal` — усиливает его самого
 439: - `supportive` — помогает душе или союзной линии
 440: - `offensive` — бьёт по rival-Хранителю
 441: 
 442: ### Offensive projects
 443: 
 444: Для offensive project нужны:
 445: 
 446: - `targetGuardianId`
 447: - `projectTier`: `minor | major | grand`
 448: - `offenseType`: `sabotage | theft | influence | curse | rival_arc | market_pressure | revelation`
 449: 
 450: ### Математика удара по цели
 451: 
 452: Грубая ранняя формула здесь больше не используется как источник истины.
 453: Для offensive-проектов см. ниже раздел `Revised offensive impact formula`.
 454: Именно он должен считаться canonical.
 455: 
 456: ## Критический gap текущей системы: проекты Хранителей слишком примитивны
 457: 
 458: Сравнение с проектами фракций показывает, что у фракций уже есть полноценный project tracker, а у Хранителей пока почти нет:
 459: 
 460: ### Что есть у фракций
 461: 
 462: - `activeProjects[]` и `completedProjects[]`
 463: - нетерминальный `activeState`
 464: - терминальный `finalState = Completed | Abandoned`
 465: - атомарные surfaces:
 466:   - `factionProjectUpdates`
 467:   - `completeFactionProjects`
 468: - обязательные trackable поля:
 469:   - `projectId`
 470:   - `projectName`
 471:   - `description`
 472:   - `totalResourceCost`
 473:   - `resourcesSpent`
 474:   - `totalTimeCostMinutes`
 475:   - `timeSpentMinutes`
 476:   - `totalSteps`
 477:   - `currentStep`
 478: 
 479: Это и позволяет системе честно понимать:
 480: 
 481: - что проект идёт;
 482: - насколько он продвинулся;
 483: - что именно потрачено;
 484: - что считается завершением;
 485: - что считается abandon/срывом.
 486: 
 487: ### Что есть у Хранителей сейчас
 488: 
 489: - только `currentProject`
 490: - и в нём в основном:
 491:   - `progressPercent`
 492:   - `estimatedTurnsLeft / estimatedCompletionTurn`
 493:   - `playerCanAssist`
 494:   - `assistDescription`
 495: - плюс history-like `completedProjects`, но без полноценного terminal lifecycle
 496: 
 497: ### Почему этого недостаточно
 498: 
 499: При такой модели мы не можем строго и валидируемо определить:
 500: 
 501: - что именно считается `assist`;
 502: - чем minor help отличается от meaningful/major help;
 503: - чем completion отличается от обычного progress tick;
 504: - когда project провален, stalled или intentionally sabotaged;
 505: - как offensive guardian projects бьют по rival-Обители;
 506: - как именно считать прирост/падение `Силы Обители`.
 507: 
 508: Иными словами: пока guardian project — это почти narrative progress bar. Для `Силы Обители` этого недостаточно.
 509: 
 510: ## Что нужно перенять из системы проектов фракций
 511: 
 512: Для v2 guardian projects должны стать отдельным project-tracker surface со своей математикой.
 513: 
 514: ### Новый canonical contract для guardian projects
 515: 
 516: Хранитель по-прежнему хранит ровно один текущий активный проект как основную ось, но сам объект должен стать полнее:
 517: 
 518: ```json
 519: "currentProject": {
 520:   "projectId": "guardian_project_x",
 521:   "projectName": "НАЗВАНИЕ",
 522:   "projectTier": "minor | major | grand",
 523:   "projectMode": "internal | supportive | offensive",
 524:   "activeState": "Active | Gathering | Testing | Negotiating | Infiltrating | Fortifying | non-terminal stage",
 525:   "description": "Текущая стадия проекта",
 526:   "totalWork": 12,
 527:   "workDone": 5,
 528:   "totalSteps": 4,
 529:   "currentStep": 2,
 530:   "startedTurn": 80,
 531:   "estimatedCompletionTurn": 95,
 532:   "playerCanAssist": true,
 533:   "assistDescription": "Чем именно может помочь душа",
 534:   "targetGuardianId": null,
 535:   "targetAbodeId": null,
 536:   "stakes": "Что изменится при успехе/провале",
 537:   "outcome": null
 538: }
 539: ```
 540: 
 541: Дополнительно:
 542: 
 543: ```json
 544: "completedProjects": [
 545:   {
 546:     "projectId": "guardian_project_x",
 547:     "projectName": "НАЗВАНИЕ",
 548:     "projectTier": "major",
 549:     "projectMode": "offensive",
 550:     "completionTurn": 97,
 551:     "finalState": "Completed | Abandoned | Sabotaged | Collapsed",
 552:     "outcome": "Краткий итог",
 553:     "targetGuardianId": "guardian_y"
 554:   }
 555: ]
 556: ```
 557: 
 558: ### Зачем новые поля
 559: 
 560: - `projectTier` нужен для математики силы Обители
 561: - `projectMode` отделяет обычный внутренний проект от offensive-политики
 562: - `activeState` делает видимой реальную нетерминальную стадию
 563: - `totalWork / workDone` создают внутриигровую математику самого проекта
 564: - `totalSteps / currentStep` дают дискретную progression axis
 565: - `targetGuardianId / targetAbodeId` обязательны для offensive projects
 566: - `finalState` нужен для честного различения:
 567:   - завершён
 568:   - брошен
 569:   - сорван соперником/игроком
 570:   - рухнул по своим причинам
 571: 
 572: ## Guardian project lifecycle: как считать ход проекта
 573: 
 574: ### 1. Создание
 575: 
 576: Каждый Хранитель обязан иметь ровно один активный `currentProject`.
 577: 
 578: При создании проекта задаются:
 579: 
 580: - `projectTier`
 581: - `projectMode`
 582: - `totalWork`
 583: - `totalSteps`
 584: - `workDone = 0`
 585: - `currentStep = 0`
 586: - `activeState = first stage label from recipe`
 587: 
 588: ## На чём считать математику проектов Хранителей
 589: 
 590: Короткий ответ: не на фракционных ресурсах, а на **метафизической работе проекта**.
 591: 
 592: Для Chaos Sea у Хранителей нет смысла копировать `Wealth / Influence / Manpower` один в один.
 593: Вместо этого у guardian projects должны быть свои canonical счётчики.
 594: 
 595: ### Базовые проектные оси
 596: 
 597: У каждого проекта должны быть 4 основные числовые оси:
 598: 
 599: #### 1. `totalWork` / `workDone`
 600: 
 601: Главная мера того, сколько усилия вообще нужно проекту.
 602: 
 603: - `totalWork` = полный объём работы проекта
 604: - `workDone` = сколько уже вложено
 605: 
 606: Это аналог `totalTimeCost + progress`, но в терминах Хранителей.
 607: 
 608: #### 2. `totalStages` / `currentStage`
 609: 
 610: Качественные этапы проекта.
 611: 
 612: Нужны, чтобы проект не был просто линейной полоской.
 613: 
 614: Примеры стадий:
 615: 
 616: - `Gathering`
 617: - `Testing`
 618: - `Binding`
 619: - `Negotiating`
 620: - `Infiltrating`
 621: - `Fortifying`
 622: - `Revealing`
 623: 
 624: #### 3. `stability`
 625: 
 626: Шкала целостности проекта: `0..100`
 627: 
 628: Она показывает, насколько проект устойчив.
 629: 
 630: Это важно для:
 631: 
 632: - sabotage;
 633: - collapse;
 634: - risky grand projects;
 635: - offensive counterplay.
 636: 
 637: #### 4. `pressure`
 638: 
 639: Шкала внешнего давления: `0..100`
 640: 
 641: Используется только если проект contested/offensive или в него уже вмешиваются rival стороны.
 642: 
 643: Она показывает не просто “мир опасен”, а именно накопленное вражеское давление на проект.
 644: 
 645: ### Почему именно эти 4 оси
 646: 
 647: Они позволяют честно и валидируемо различать:
 648: 
 649: - обычный прогресс;
 650: - помощь игрока;
 651: - тяжёлый, но ещё живой проект;
 652: - sabotage;
 653: - collapse;
 654: - abandon;
 655: - offensive-проект против rival-Хранителя.
 656: 
 657: Без этих осей всё снова схлопнется в narrative `progressPercent`.
 658: 
 659: ## Важное уточнение: проектам Хранителей нужны не только общие формулы, но и типовые рецепты
 660: 
 661: Если оставить только общую математику `work/stages/stability/pressure`, система останется слишком абстрактной.
 662: 
 663: Поэтому у каждого guardian project должен быть ещё и `projectType`, а у `projectType` — свой рецепт:
 664: 
 665: - что именно двигает этот проект;
 666: - что считается обязательным условием;
 667: - что считается completion;
 668: - что считается sabotage/collapse;
 669: - какой effect он даёт при успехе.
 670: 
 671: Примеры типов:
 672: 
 673: - `abode_expansion`
 674: - `abode_fortification`
 675: - `relic_forging`
 676: - `lore_research`
 677: - `soul_preparation`
 678: - `offensive_intrigue`
 679: - `counter_rival_operation`
 680: 
 681: Общая математика остаётся общей, но recipe делает её понятной.
 682: 
 683: ## Разбор на конкретном примере: проект `Расширение Обители`
 684: 
 685: Это как раз тот пример, на котором лучше всего объяснять механику.
 686: 
 687: ### Что делает проект
 688: 
 689: `abode_expansion` не даёт произвольный narrative reward.
 690: Он прямо увеличивает `currentPower` Обители после завершения.
 691: 
 692: Рекомендуемый effect в v1:
 693: 
 694: - `minor abode_expansion` = `+4 currentPower`
 695: - `major abode_expansion` = `+8 currentPower`
 696: - `grand abode_expansion` = `+12 currentPower`
 697: 
 698: ### От чего зависит его математика
 699: 
 700: Для `Расширения Обители` нужны 5 источников математики:
 701: 
 702: #### 1. Tier проекта
 703: 
 704: Это базовый масштаб:
 705: 
 706: - `minor` — локальное расширение
 707: - `major` — заметное усиление
 708: - `grand` — большой скачок Обители
 709: 
 710: #### 2. Текущий tier самой Обители
 711: 
 712: Чем сильнее Обитель уже сейчас, тем труднее её расширять дальше.
 713: Это принципиально важно, чтобы не было snowballing без сопротивления.
 714: 
 715: Modifier к сложности:
 716: 
 717: - если Обитель `Угасающая`: `+0` к сложности
 718: - `Хрупкая`: `+2`
 719: - `Стабильная`: `+4`
 720: - `Могущественная`: `+6`
 721: - `Сияющая`: `+9`
 722: 
 723: #### 3. Mood/состояние Хранителя
 724: 
 725: Не как flavour, а как реальный modifier:
 726: 
 727: - `focused` = `+1 CycleWork`
 728: - `energized` = `+1 CycleWork`
 729: - `irritated` = `-1 CycleWork`
 730: - `melancholic` = `-1 stability recovery`
 731: 
 732: #### 4. Помощь игрока
 733: 
 734: Игрок не “просто помогает текстом”, а даёт конкретный project outcome:
 735: 
 736: - `minor assist`
 737: - `meaningful assist`
 738: - `major breakthrough`
 739: 
 740: Для `abode_expansion` это может быть:
 741: 
 742: - принести якорь/реликт для расширения;
 743: - помочь стабилизировать новую часть Обители;
 744: - закрыть утечку хаоса;
 745: - добыть domain-compatible essence.
 746: 
 747: #### 5. Вражеское давление
 748: 
 749: Если другой Хранитель хочет помешать расширению:
 750: 
 751: - растёт `pressure`
 752: - падает `stability`
 753: - completion может сорваться
 754: 
 755: ### Конкретная формула для `abode_expansion`
 756: 
 757: Для этого типа проекта я бы считал так:
 758: 
 759: #### Шаг 1: считаем общий объём работы
 760: 
 761: `totalWork = BaseWorkByProjectTier + CurrentAbodeTierTax + ExpansionTypeTax`
 762: 
 763: Где:
 764: 
 765: - `BaseWorkByProjectTier`
 766:   - `minor = 8`
 767:   - `major = 14`
 768:   - `grand = 22`
 769: 
 770: - `CurrentAbodeTierTax`
 771:   - `Угасающая = 0`
 772:   - `Хрупкая = 2`
 773:   - `Стабильная = 4`
 774:   - `Могущественная = 6`
 775:   - `Сияющая = 9`
 776: 
 777: - `ExpansionTypeTax`
 778:   - для обычного `abode_expansion = 2`
 779: 
 780: Пример:
 781: 
 782: У Хранителя сейчас `currentPower = 35`, то есть `Хрупкая` Обитель.
 783: Он запускает `major abode_expansion`.
 784: 
 785: Тогда:
 786: 
 787: - `BaseWorkByProjectTier = 14`
 788: - `CurrentAbodeTierTax = 2`
 789: - `ExpansionTypeTax = 2`
 790: 
 791: Итого:
 792: 
 793: `totalWork = 18`
 794: 
 795: #### Шаг 2: задаём стадии
 796: 
 797: Для `major abode_expansion`:
 798: 
 799: - `totalStages = 3`
 800: 
 801: Стадии можно назвать так:
 802: 
 803: 1. `Закрепление нового контура`
 804: 2. `Наполнение силы`
 805: 3. `Стабилизация расширения`
 806: 
 807: #### Шаг 3: стартовые параметры
 808: 
 809: - `workDone = 0`
 810: - `currentStage = 0`
 811: - `stability = 75`
 812: - `pressure = 0`
 813: 
 814: Если проект offensive-contested:
 815: 
 816: - `pressure` может стартовать с `10..15`
 817: 
 818: ### Как проект движется по ходам
 819: 
 820: Каждый Chaos Sea turn = один cycle.
 821: 
 822: Формула:
 823: 
 824: `CycleWork = 1 + MoodBonus + AssistanceBonus - ContestPenalty`
 825: 
 826: Где:
 827: 
 828: - базовая работа для `major abode_expansion` = `1`
 829: - `MoodBonus`
 830:   - `focused/energized = +1`
 831:   - иначе `0`
 832: - `AssistanceBonus`
 833:   - `minor assist = +2`
 834:   - `meaningful assist = +4`
 835:   - `major breakthrough = +6`
 836:   - если игрок не помогал в этот turn: `0`
 837: - `ContestPenalty = floor(pressure / 25)`
 838: 
 839: Минимум:
 840: 
 841: - `CycleWork` не может быть меньше `0`
 842: 
 843: ### Как двигаются стадии у `abode_expansion`
 844: 
 845: Порогами от `totalWork`:
 846: 
 847: - Stage 1: достигнут при `workDone >= 6`
 848: - Stage 2: достигнут при `workDone >= 12`
 849: - Stage 3: достигнут при `workDone >= 18`
 850: 
 851: Но есть важное условие:
 852: 
 853: Для перехода в финальную стадию нужно:
 854: 
 855: - `stability >= 40`
 856: 
 857: Это означает:
 858: 
 859: - можно “набить работу”,
 860: - но если расширение нестабильно, финализировать его нельзя.
 861: 
 862: ### Как влияет sabotage
 863: 
 864: Пример hostile interference:
 865: 
 866: - rival action даёт:
 867:   - `pressure += 20`
 868:   - `stability -= 12`
 869:   - `workDone -= 2`
 870: 
 871: Это не просто flavour:
 872: 
 873: - проект реально замедляется,
 874: - может не дойти до completion,
 875: - может рухнуть.
 876: 
 877: ### Когда `abode_expansion` завершён
 878: 
 879: Только если одновременно:
 880: 
 881: - `workDone >= totalWork`
 882: - `currentStage >= totalStages`
 883: - `stability >= 40`
 884: 
 885: Тогда:
 886: 
 887: - проект получает `finalState = Completed`
 888: - Обитель получает power gain по tier:
 889:   - `minor +4`
 890:   - `major +8`
 891:   - `grand +12`
 892: 
 893: ### Когда проект считается сорванным
 894: 
 895: #### `Sabotaged`
 896: 
 897: Если:
 898: 
 899: - external enemy pressure выбил проект,
 900: - или игрок помог rival sabotage,
 901: - и итогом стало `stability <= 0`
 902: 
 903: Тогда:
 904: 
 905: - `finalState = Sabotaged`
 906: - loss to abode power:
 907:   - `minor = -4`
 908:   - `major = -8`
 909:   - `grand = -12`
 910: 
 911: #### `Collapsed`
 912: 
 913: Если:
 914: 
 915: - внешнего sabotage не было,
 916: - но расширение само развалилось,
 917: - например из-за слишком рискованной стабилизации
 918: 
 919: Тогда:
 920: 
 921: - `finalState = Collapsed`
 922: - penalty softer than sabotage:
 923:   - `minor = -3`
 924:   - `major = -6`
 925:   - `grand = -10`
 926: 
 927: #### `Abandoned`
 928: 
 929: Если:
 930: 
 931: - Хранитель сам остановил расширение
 932: 
 933: Тогда:
 934: 
 935: - `finalState = Abandoned`
 936: - `0 / -1 / -2` по tier проекта
 937: 
 938: ## Почему эта модель лучше
 939: 
 940: На примере `Расширения Обители` уже видно, что математика зависит не от “что GM почувствовал”, а от:
 941: 
 942: - типа проекта;
 943: - tier проекта;
 944: - текущего tier Обители;
 945: - помощи игрока;
 946: - настроения Хранителя;
 947: - вражеского давления;
 948: - устойчивости проекта.
 949: 
 950: То есть проект можно:
 951: 
 952: - ускорять,
 953: - тормозить,
 954: - защищать,
 955: - срывать,
 956: - завершать
 957: 
 958: по понятным правилам.
 959: 
 960: ## Нормальная математическая модель для guardian projects
 961: 
 962: Ниже — более строгая версия, которую можно потом переносить в rules/validator.
 963: 
 964: ## 1. Разделение на recipe и runtime state
 965: 
 966: У любого проекта Хранителя есть:
 967: 
 968: ### Recipe
 969: 
 970: То, что задаётся типом проекта и tier’ом:
 971: 
 972: - `projectType`
 973: - `projectTier`
 974: - `baseWork`
 975: - `baseStability`
 976: - `exposure`
 977: - `basePressurePerCycle`
 978: - `baseRecoveryPerCycle`
 979: 
 980: ### Runtime state
 981: 
 982: То, что меняется по ходам:
 983: 
 984: - `workDone`
 985: - `pressure`
 986: - `stability`
 987: - `currentStage`
 988: - `pressureSources[]` optional later
 989: 
 990: ## 2. Обязательные числовые поля проекта
 991: 
 992: Минимальный v1 math contract:
 993: 
 994: ```json
 995: "currentProject": {
 996:   "projectId": "guardian_project_x",
 997:   "projectName": "Расширение Обители",
 998:   "projectType": "abode_expansion",
 999:   "projectTier": "minor | major | grand",
1000:   "projectMode": "internal | supportive | offensive",
1001:   "totalWork": 18,
1002:   "workDone": 7,
1003:   "totalStages": 3,
1004:   "currentStage": 1,
1005:   "pressure": 18,
1006:   "stability": 67,
1007:   "activeState": "Fortifying",
1008:   "startedTurn": 80,
1009:   "estimatedCompletionTurn": 95,
1010:   "playerCanAssist": true,
1011:   "assistDescription": "..."
1012: }
1013: ```
1014: 
1015: ## 3. Базовые recipe-константы
1016: 
1017: ### Tier constants
1018: 
1019: #### `minor`
1020: 
1021: - `baseWork = 12`
1022: - `baseStability = 80`
1023: - `basePressurePerCycle = 1`
1024: - `baseRecoveryPerCycle = 1`
1025: 
1026: #### `major`
1027: 
1028: - `baseWork = 18`
1029: - `baseStability = 70`
1030: - `basePressurePerCycle = 1`
1031: - `baseRecoveryPerCycle = 1`
1032: 
1033: #### `grand`
1034: 
1035: - `baseWork = 26`
1036: - `baseStability = 60`
1037: - `basePressurePerCycle = 2`
1038: - `baseRecoveryPerCycle = 1`
1039: 
1040: ### Exposure by project type
1041: 
1042: `exposure` показывает, насколько проект уязвим к внешнему давлению.
1043: 
1044: - `abode_expansion = 2`
1045: - `abode_fortification = 1`
1046: - `relic_forging = 2`
1047: - `lore_research = 3`
1048: - `soul_preparation = 2`
1049: - `offensive_intrigue = 4`
1050: - `counter_rival_operation = 3`
1051: 
1052: Чем выше `exposure`, тем больнее sabotage и давление.
1053: 
1054: ## 4. Стартовые значения runtime state
1055: 
1056: ### Total work
1057: 
1058: `totalWork = baseWork + AbodeTierTax + ProjectTypeTax`
1059: 
1060: Где:
1061: 
1062: #### `AbodeTierTax`
1063: 
1064: - `Угасающая = 0`
1065: - `Хрупкая = 2`
1066: - `Стабильная = 4`
1067: - `Могущественная = 6`
1068: - `Сияющая = 9`
1069: 
1070: #### `ProjectTypeTax`
1071: 
1072: - `abode_expansion = 2`
1073: - `abode_fortification = 3`
1074: - `relic_forging = 2`
1075: - `lore_research = 1`
1076: - `soul_preparation = 2`
1077: - `offensive_intrigue = 4`
1078: - `counter_rival_operation = 3`
1079: 
1080: ### Start stability
1081: 
1082: `startStability = baseStability + floor(currentAbodePower / 25) * 5`
1083: 
1084: То есть:
1085: 
1086: - power `0..24` → `+0`
1087: - `25..49` → `+5`
1088: - `50..74` → `+10`
1089: - `75..99` → `+15`
1090: - `100` → `+20`
1091: 
1092: Clamp:
1093: 
1094: - максимум `100`
1095: 
1096: ### Start pressure
1097: 
1098: `startPressure = projectModeModifier + scriptedContestModifier`
1099: 
1100: Где:
1101: 
1102: - `internal = 0`
1103: - `supportive = 5`
1104: - `offensive = 15`
1105: 
1106: Обычно:
1107: 
1108: - обычный внутренний проект стартует с низким давлением
1109: - offensive project сразу contested
1110: 
1111: ## 5. Что такое pressure математически
1112: 
1113: `pressure` — это текущая интенсивность внешних помех.
1114: 
1115: Диапазон:
1116: 
1117: - `0..100`
1118: 
1119: ### Pressure bands
1120: 
1121: - `0..9` — `спокойно`
1122: - `10..24` — `низкое давление`
1123: - `25..44` — `повышенное`
1124: - `45..69` — `высокое`
1125: - `70..100` — `критическое`
1126: 
1127: ### Pressure update per cycle
1128: 
1129: `pressure_next = clamp(pressure + basePressurePerCycle + hostileInput - pressureRelief, 0, 100)`
1130: 
1131: Где:
1132: 
1133: #### `hostileInput`
1134: 
1135: Это суммарный вход внешнего давления за цикл:
1136: 
1137: - no interference = `0`
1138: - `minor interference = 10`
1139: - `major sabotage = 20`
1140: - `grand strike = 30`
1141: 
1142: #### `pressureRelief`
1143: 
1144: `pressureRelief = 1 + floor(currentAbodePower / 30) + playerDefenseBonus`
1145: 
1146: То есть:
1147: 
1148: - power `0..29` → `+1`
1149: - `30..59` → `+2`
1150: - `60..89` → `+3`
1151: - `90+` → `+4`
1152: 
1153: `playerDefenseBonus`:
1154: 
1155: - none = `0`
1156: - minor protective help = `1`
1157: - meaningful protection = `2`
1158: - major defensive breakthrough = `3`
1159: 
1160: ### Что pressure делает practically
1161: 
1162: Pressure:
1163: 
1164: - замедляет `workDone`
1165: - увеличивает износ `stability`
1166: - повышает шанс terminal failure при долгом накоплении
1167: 
1168: ## 6. Что такое stability математически
1169: 
1170: `stability` — это запас прочности проекта.
1171: 
1172: Диапазон:
1173: 
1174: - `0..100`
1175: 
1176: ### Stability bands
1177: 
1178: - `80..100` — проект очень устойчив
1179: - `60..79` — устойчив
1180: - `40..59` — шаткий, но ещё жизнеспособный
1181: - `20..39` — опасная зона
1182: - `1..19` — предаварийное состояние
1183: - `0` — terminal failure
1184: 
1185: ### Safe pressure threshold
1186: 
1187: Проект умеет терпеть ограниченное давление без износа.
1188: 
1189: `safePressure = 15 + floor(currentAbodePower / 20) * 5`
1190: 
1191: Итого:
1192: 
1193: - power `0..19` → `15`
1194: - `20..39` → `20`
1195: - `40..59` → `25`
1196: - `60..79` → `30`
1197: - `80..99` → `35`
1198: - `100` → `40`
1199: 
1200: То есть сильная Обитель лучше выдерживает помехи.
1201: 
1202: ### Stability wear from sustained pressure
1203: 
1204: Каждый цикл:
1205: 
1206: `stabilityWear = max(0, floor((pressure - safePressure) / 15))`
1207: 
1208: Примеры:
1209: 
1210: - pressure `18`, safePressure `20` → wear `0`
1211: - pressure `38`, safePressure `20` → wear `1`
1212: - pressure `55`, safePressure `20` → wear `2`
1213: 
1214: Это означает:
1215: 
1216: - небольшое давление терпимо
1217: - высокое давление начинает реально точить проект
1218: 
1219: ### Direct stability damage from hostile actions
1220: 
1221: Помимо износа, sabotage наносит прямой урон:
1222: 
1223: `directStabilityDamage = max(0, baseHitDamage + exposure - defenseRating)`
1224: 
1225: Где:
1226: 
1227: #### `baseHitDamage`
1228: 
1229: - `minor interference = 4`
1230: - `major sabotage = 8`
1231: - `grand strike = 12`
1232: 
1233: #### `defenseRating`
1234: 
1235: `defenseRating = floor(currentAbodePower / 25) + playerCounterplayBonus`
1236: 
1237: База:
1238: 
1239: - power `0..24` → `0`
1240: - `25..49` → `1`
1241: - `50..74` → `2`
1242: - `75..99` → `3`
1243: - `100` → `4`
1244: 
1245: `playerCounterplayBonus`:
1246: 
1247: - none = `0`
1248: - minor = `1`
1249: - meaningful = `2`
1250: - major = `3`
1251: 
1252: ### Stability recovery
1253: 
1254: Каждый цикл:
1255: 
1256: `stabilityRecovery = baseRecoveryPerCycle + playerRepairBonus + moodRecoveryBonus`
1257: 
1258: Где:
1259: 
1260: - `baseRecoveryPerCycle = recipe value`
1261: - `playerRepairBonus`
1262:   - none = `0`
1263:   - minor = `1`
1264:   - meaningful = `2`
1265:   - major = `3`
1266: - `moodRecoveryBonus`
1267:   - `focused = 1`
1268:   - `energized = 1`
1269:   - иначе `0`
1270: 
1271: ### Full stability update
1272: 
1273: `stability_next = clamp(stability - stabilityWear - directStabilityDamage + stabilityRecovery, 0, 100)`
1274: 
1275: Это и есть основная формула живучести проекта.
1276: 
1277: ## 7. Как считается workDone
1278: 
1279: `CycleWork = BaseWorkByTier + MoodBonus + AssistanceBonus - ContestPenalty`
1280: 
1281: Где:
1282: 
1283: ### `BaseWorkByTier`
1284: 
1285: - `minor = 2`
1286: - `major = 1`
1287: - `grand = 1`
1288: 
1289: ### `MoodBonus`
1290: 
1291: - `focused = +1`
1292: - `energized = +1`
1293: - `irritated = -1`
1294: - иначе `0`
1295: 
1296: ### `AssistanceBonus`
1297: 
1298: - no assist = `0`
1299: - `minor assist = +2`
1300: - `meaningful assist = +4`
1301: - `major breakthrough = +6`
1302: 
1303: ### `ContestPenalty`
1304: 
1305: Зависит от pressure:
1306: 
1307: - pressure `0..9` → `0`
1308: - `10..24` → `1`
1309: - `25..44` → `2`
1310: - `45..69` → `3`
1311: - `70..100` → `4`
1312: 
1313: Минимум:
1314: 
1315: - `CycleWork` не может быть меньше `0`
1316: 
1317: ### Work update
1318: 
1319: `workDone_next = clamp(workDone + CycleWork - directWorkLoss, 0, totalWork)`
1320: 
1321: Где:
1322: 
1323: - `directWorkLoss`
1324:   - none = `0`
1325:   - `major sabotage = 2`
1326:   - `grand strike = 4`
1327: 
1328: ## 8. Как проект переходит между стадиями
1329: 
1330: Стадии двигаются threshold’ами от `totalWork`.
1331: 
1332: Для:
1333: 
1334: - `2 stages`
1335:   - stage 1 at `50%`
1336:   - final at `100%`
1337: - `3 stages`
1338:   - stage 1 at `33%`
1339:   - stage 2 at `66%`
1340:   - final at `100%`
1341: - `4 stages`
1342:   - stage 1 at `25%`
1343:   - stage 2 at `50%`
1344:   - stage 3 at `75%`
1345:   - final at `100%`
1346: 
1347: Но финальная стадия разрешена только если:
1348: 
1349: - `stability >= 40`
1350: 
1351: Иначе проект “почти готов”, но не может быть safely finalized.
1352: 
1353: ## 9. Как строго определять completion / sabotage / collapse / abandon
1354: 
1355: ### `Completed`
1356: 
1357: Только если одновременно:
1358: 
1359: - `workDone >= totalWork`
1360: - `currentStage >= totalStages`
1361: - `stability >= 40`
1362: 
1363: ### `Sabotaged`
1364: 
1365: Если:
1366: 
1367: - был внешний hostile action
1368: - и `stability <= 0`
1369: 
1370: или
1371: 
1372: - проект явно завершён terminal outcome с враждебным срывом
1373: 
1374: ### `Collapsed`
1375: 
1376: Если:
1377: 
1378: - внешнего hostile action в этом cycle-resolution нет
1379: - но `stability <= 0`
1380: 
1381: То есть проект рухнул сам.
1382: 
1383: ### `Abandoned`
1384: 
1385: Если:
1386: 
1387: - Хранитель сам прекращает проект до terminal failure
1388: 
1389: ## 10. Почему проект потерял стабильность: обязательный audit trail
1390: 
1391: Чтобы это не выглядело как произвол GM, у terminal/non-terminal update должен быть разбор причин.
1392: 
1393: Пример:
1394: 
1395: ```json
1396: "stabilityAudit": {
1397:   "previous": 75,
1398:   "pressureWear": 1,
1399:   "directDamage": 9,
1400:   "recovery": 2,
1401:   "newValue": 67,
1402:   "reason": "Major sabotage by rival guardian project plus minor stabilization by the Soul"
1403: }
1404: ```
1405: 
1406: То же самое можно делать для pressure:
1407: 
1408: ```json
1409: "pressureAudit": {
1410:   "previous": 0,
1411:   "basePressure": 1,
1412:   "hostileInput": 20,
1413:   "relief": 3,
1414:   "newValue": 18
1415: }
1416: ```
1417: 
1418: Это нужно не обязательно сразу светить игроку в raw виде, но это должен понимать validator и от этого должен работать `repairHint`.
1419: 
1420: ## 11. Что это даёт системе Силы Обители
1421: 
1422: Теперь change `Силы Обители` можно привязывать не к vague narration, а к terminal outcome проекта:
1423: 
1424: - `Completed`
1425:   - даёт power gain по tier/type
1426: - `Sabotaged`
1427:   - даёт power loss по tier/type
1428: - `Collapsed`
1429:   - даёт меньший loss
1430: - `Abandoned`
1431:   - даёт `0` или мягкий loss
1432: 
1433: То есть:
1434: 
1435: - сначала честно считается проект;
1436: - потом проект меняет `Силу Обители`;
1437: - а уже `Сила Обители` влияет на торговлю, квесты, gacha, rival arcs и корректировки следующей жизни.
1438:

1769: - `Collapsed = backlash, -3 / -6 / -9 to attacker`
1770: - `Sabotaged = counterstroke, target inflicts mirrored loss 1 / 2 / 3 to attacker`
1771: 
1772: ## 12.7 `counter_rival_operation`
1773: 
1774: ### Смысл
1775: 
1776: Защитный ответ на уже начатую враждебную операцию rival-Хранителя.
1777: 
1778: ### Базовый профиль
1779: 
1780: - `projectMode = supportive`
1781: - `exposure = 3`
1782: - `ProjectTypeTax = 3`
1783: - `targetGuardianId` обязателен
1784: 
1785: ### Типичные стадии
1786: 
1787: - `Tracing the hostile thread`
1788: - `Blocking entry points`
1789: - `Severing the rival pressure`
1790: 
1791: ### Что двигает проект
1792: 
1793: - информация о rival operation
1794: - помощь игрока
1795: - defensive rituals
1796: - successful counterplay against rival arc
1797: 
1798: ### Что чаще всего ему мешает
1799: 
1800: - lack of evidence
1801: - too-high current pressure
1802: - simultaneous second offensive project
1803: 
1804: ### Эффект при `Completed`
1805: 
1806: - immediate `pressure -= 15 / 25 / 35` for target project family or active hostile pressure pool
1807: - `stability += 5 / 10 / 15` to defended project if still active
1808: - `+1 / +2 / +3 abode power`
1809: 
1810: ### Эффект при провале
1811:

1813: - if `Sabotaged`, hostile side gains additional `+10 pressure`

1815: ## 13. Как использовать recipes на практике
1816: 
1817: Алгоритм для GM/системы должен быть простым:
1818:

1820: 2. Выбрать `projectTier`
1821: 3. Сгенерировать theme/flavor поверх recipe

1823:    - `totalWork`

1825:    - `startPressure`

1830: То есть flavour остаётся живым, но математика у типа проекта уже готова заранее.

1853: ## Canonical per-cycle order of operations
1854: 
1855: Чтобы одинаковый state не обсчитывался по-разному, для каждого `Guardian Project Cycle` нужен жёсткий порядок.
1856: 
1857: Порядок на один цикл:
1858: 
1859: 1. Прочитать предыдущий runtime state проекта
1860: 2. Собрать все входы текущего цикла:
1861:    - passive base pressure
1862:    - hostile actions
1863:    - player assist
1864:    - player defense / repair
1865:    - mood modifiers
1866: 3. Посчитать classification scores:
1867:    - assist score
1868:    - defense score
1869:    - sabotage severity score
1870: 4. Обновить `pressure`
1871: 5. Посчитать `directStabilityDamage` и `directWorkLoss`
1872: 6. Посчитать `stabilityWear`
1873: 7. Посчитать `stabilityRecovery`
1874: 8. Обновить `stability`
1875: 9. Посчитать `CycleWork`
1876: 10. Обновить `workDone`
1877: 11. Пересчитать `currentStage`
1878: 12. Проверить terminal conditions:
1879:    - `Completed`
1880:    - `Sabotaged`
1881:    - `Collapsed`
1882:    - `Abandoned`
1883: 13. Если terminal outcome есть:
1884:    - применить delta к `abodePower`
1885:    - записать history/audit
1886: 14. Если terminal outcome нет:
1887:    - сохранить updated currentProject state
1888: 
1889: Completion check происходит после full update, не раньше.

1891: ## Scoring-контракты: как уменьшить произвол GM
1892: 
1893: Ниже — шкалы, которые превращают “вкус GM” в повторяемый score.
1894: 
1895: ## 1. Assist Score
1896: 
1897: Каждая помощь игрока проекту оценивается по 4 осям, каждая `0..2`.
1898: 
1899: ### Assist axes
1900: 
1901: - `DomainRelevance`
1902:   - `0` не связано с доменом проекта
1903:   - `1` косвенно полезно
1904:   - `2` прямо бьёт в нужду проекта
1905: - `RiskOrCost`
1906:   - `0` почти бесплатно
1907:   - `1` умеренный риск/расход
1908:   - `2` заметная жертва, цена или опасность
1909: - `ScarcityOrUniqueness`
1910:   - `0` обычный вклад
1911:   - `1` редкий вклад
1912:   - `2` очень редкий / трудно заменимый вклад
1913: - `DirectProjectImpact`
1914:   - `0` только flavour support
1915:   - `1` реально помогает
1916:   - `2` напрямую двигает текущую bottleneck-стадию
1917: 
1918: ### Formula
1919: 
1920: `assistScore = DomainRelevance + RiskOrCost + ScarcityOrUniqueness + DirectProjectImpact`
1921: 
1922: ### Classification
1923: 
1924: - `0..2` = not qualified as project assist
1925: - `3..4` = `minor assist`
1926: - `5..6` = `meaningful assist`
1927: - `7..8` = `major breakthrough`
1928: 
1929: ## 2. Defense / Repair Score
1930: 
1931: Когда игрок защищает или чинит проект, используется такая же схема `0..8`.
1932: 
1933: Оси:
1934: 
1935: - `ThreatAddressed`
1936: - `Timeliness`
1937: - `RepairDepth`
1938: - `CostOrRisk`
1939: 
1940: Classification:
1941: 
1942: - `0..2` = no meaningful defense
1943: - `3..4` = `minor defensive help`
1944: - `5..6` = `meaningful protection`
1945: - `7..8` = `major defensive breakthrough`
1946: 
1947: ## 3. Offering Score
1948: 
1949: Для подношений в Обитель:
1950: 
1951: Оси `0..2`:
1952: 
1953: - `DomainMatch`
1954: - `Rarity`
1955: - `PlayerSacrifice`
1956: - `CurrentNeedFit`
1957: 
1958: `offeringScore = sum(axes)`
1959: 
1960: Classification:
1961: 
1962: - `0..2` = no power gain
1963: - `3..4` = `+1 power`
1964: - `5..6` = `+2 power`
1965: - `7..8` = `+4 power`
1966: 
1967: Это заменяет расплывчатое `+2..+4 на глаз`.
1968: 
1969: ## 4. Resonance Score
1970: 
1971: Для итогового резонанса смертной жизни:
1972: 
1973: Оси `0..2`:
1974: 
1975: - `DomainAlignment`
1976: - `WorldScale`
1977: - `Permanence`
1978: - `Sacrifice`
1979: - `PublicImpact`
1980: 
1981: `resonanceScore = sum(axes)` with range `0..10`
1982: 
1983: Classification:
1984: 
1985: - `0..2` = no resonance gain
1986: - `3..4` = `weak resonance = +2 power`
1987: - `5..7` = `solid resonance = +4 power`
1988: - `8..10` = `major resonance = +6 power`
1989: 
1990: ## 5. Sabotage Severity Score
1991: 
1992: Чтобы sabotage не определялся “по ощущению”, нужен score:
1993: 
1994: Оси `0..2`:
1995: 
1996: - `HostileReach`
1997: - `ProjectExposure`
1998: - `DamageIntent`
1999: - `DamageAchieved`
2000: - `PlayerComplicity`
2001: 
2002: `sabotageSeverityScore = sum(axes)` with range `0..10`
2003: 
2004: Classification:
2005: 
2006: - `0..2` = nuisance / no formal sabotage tier
2007: - `3..4` = `minor interference`
2008: - `5..7` = `major sabotage`
2009: - `8..10` = `grand strike`

2231: ## 4.1 Correction claim resolution
2232: 
2233: Friendly и hostile корректировки не должны конфликтовать по неявному вкусу GM.
2234: Для этого нужен детерминированный алгоритм захвата correction slots.
2235: 
2236: ### Candidate correction object
2237: 
2238: ```json
2239: {
2240:   "candidateCorrectionId": "corr_x",
2241:   "sourceGuardianId": "guardian_a",
2242:   "intent": "friendly | hostile",
2243:   "slotId": "slot_political_hidden_layer",
2244:   "severity": "minor | medium | strong",
2245:   "powerCost": 12,
2246:   "claimStrength": 0,
2247:   "budgetSource": "base_abode_power | soul_preparation_bonus"
2248: }
2249: ```
2250: 
2251: ### Claim strength formula
2252: 
2253: `claimStrength = PowerBand + SeverityWeight + PreparationBonus + IntentModifier`
2254: 
2255: Где:
2256: 
2257: - `PowerBand`
2258:   - `0..19 = 0`
2259:   - `20..39 = 1`
2260:   - `40..59 = 2`
2261:   - `60..79 = 3`
2262:   - `80..100 = 4`
2263: - `SeverityWeight`
2264:   - `minor = 1`
2265:   - `medium = 2`
2266:   - `strong = 3`
2267: - `PreparationBonus`
2268:   - none = `0`
2269:   - completed `soul_preparation` bonus token = `1`
2270:   - hostile priority token from sabotaged `soul_preparation` = `2`
2271: - `IntentModifier`
2272:   - default `0`
2273:   - active patron guardian = `+1`
2274: 
2275: ### Resolution order
2276: 
2277: 1. Собрать все candidate corrections, которые укладываются в budget guardians
2278: 2. Посчитать `claimStrength`
2279: 3. Сгруппировать по `slotId`
2280: 4. Для каждого slot оставить кандидата с максимальным `claimStrength`
2281: 5. При равенстве:
2282:    - побеждает active patron guardian
2283: 6. Если равенство осталось:
2284:    - побеждает higher currentPower
2285: 7. Если равенство всё ещё осталось:
2286:    - lexical guardianId tie-break
2287: 8. После выбора winners списать `powerCost`
2288: 9. Если guardian overspent из-за нескольких winning slots, prune его weakest winner до возврата в budget
2289: 
2290: Это делает correction-layer детерминированным.

2292: ## Revised offensive impact formula
2293: 
2294: Ранняя грубая формула `BaseLoss + AttackerTierBonus` недостаточна.
2295: Итоговый урон по rival-Обители должен зависеть и от защиты цели.
2296: 
2297: `TargetLoss = max(0, BaseLossByTier + AttackerBonus - TargetShield)`
2298: 
2299: ### `BaseLossByTier`
2300: 
2301: - `minor = 3`
2302: - `major = 6`
2303: - `grand = 10`
2304: 
2305: ### `AttackerBonus`
2306: 
2307: `AttackerBonus = floor(attackerCurrentPower / 25)`
2308: 
2309: То есть `0..4`.
2310: 
2311: ### `TargetShield`
2312: 
2313: `TargetShield = BaseTargetShield + FortificationBonus + CounterOperationBonus + PlayerDefenseBonus`
2314: 
2315: Где:
2316: 
2317: - `BaseTargetShield = floor(targetCurrentPower / 30)` giving `0..3`
2318: - `FortificationBonus`
2319:   - none = `0`
2320:   - minor active fortification effect = `1`
2321:   - major = `2`
2322:   - grand = `3`
2323: - `CounterOperationBonus`
2324:   - none = `0`
2325:   - minor = `1`
2326:   - major = `2`
2327:   - grand = `3`
2328: - `PlayerDefenseBonus`
2329:   - none = `0`
2330:   - meaningful defense this cycle = `1`
2331:   - major defense = `2`
2332: 
2333: Это делает offensive politics двусторонней, а не только “атакующий всегда прав”.

2550: ## Deterministic RNG rule for probabilistic effects
2551: 
2552: Если derived-эффект использует вероятность, она не должна зависеть от “настроения GM”.
2553: 
2554: Правило:
2555: 
2556: - все probabilistic guardian-derived effects используют deterministic client-side RNG
2557: - seed строится из стабильных canonical значений соответствующего цикла
2558: 
2559: Базовый seed pattern:
2560: 
2561: `guardianId + tradeCycleId + projectId + currentPowerBand`
2562: 
2563: Это относится как минимум к:
2564: 
2565: - upgraded trade slot chance from `relic_forging`
2566: - elevated stock generation
2567: - future similar abode-power probabilistic effects
2568: 
2569: Таким образом, вероятность остаётся математической, а не narrative whim.
