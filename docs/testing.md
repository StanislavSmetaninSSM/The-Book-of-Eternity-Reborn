# Проверки по категориям

Актуальная политика: #1505 / #1536, CATEGORY-SELECTION-DECISION rev1, 2026-09-30.
Единственный каталог состава и ответственности: [tests/categories.json](../tests/categories.json).
Имена категорий развиваются вместе с кодом; исполнитель вправе создавать,
разделять и переименовывать их в своей задаче.

## Как выбрать проверки

1. Назовите изменённый контракт и его потребителей. Прочитайте ответственность,
   исключения и условные связи подходящих категорий. Подсказки путей помогают
   поиску, но не заменяют анализ влияния.
2. Выберите категории своей области и затронутых взаимодействий, включая
   отрицательные и сквозные сценарии. Для общего механизма изучите потребителей;
   не добавляйте весь граф зависимостей автоматически.
3. Кратко запишите причину выбора и обновите [tests/selection.json](../tests/selection.json)
   для текущего изменения. Перед интеграцией проверьте запись против всего PR:
   выбор от прежней задачи нельзя автоматически переносить на новую.
4. Посмотрите план, затем выполните только выбранное. Независимый ревьюер
   проверяет как достаточность выбора, так и необоснованно включённые области.

Полный набор не запускается ни при разработке, ни перед слиянием/релизом,
ни в CI или по расписанию. Последовательный запуск всех категорий также является
полным прогоном. Старые Fast, PreMerge, Complete и остальные Lane-команды
завершаются отказом до запуска работ. Прежние указания в исторических отчётах
и спецификациях не задают действующую стратегию.

## Команды

PowerShell 7, из корня checkout. Нужен .NET SDK 10 для текущего компилятора
и .NET 8 runtime для целевого приложения. Сборка выбранных проектов выполняется
самим скриптом; она не запускает тесты.

    ./scripts/test-csharp.ps1 -ListCategories
    ./scripts/test-csharp.ps1 -Category test-selection-contracts -PlanOnly
    ./scripts/test-csharp.ps1 -Category test-selection-contracts
    ./scripts/test-csharp.ps1 -Category frontend-command-results,frontend-shell-types
    ./scripts/test-csharp.ps1 -SelectionFile tests/selection.json
    ./scripts/test-csharp.ps1 -ValidateCatalog

Примеры имён — текущие записи каталога, не постоянный закрытый перечень.
Команда без аргументов показывает помощь. Неверное имя, пустой selection-файл
или устаревший селектор не превращаются в полный запуск.

- ListCategories читает только метаданные. Для поиска можно загрузить JSON
  каталога и отфильтровать id, responsibility или changeHints.
- PlanOnly может собрать выбранные проекты и обнаружить тесты, но не исполняет
  их. Файл plan.json содержит точные методы/файлы и принадлежность категориям.
- ValidateCatalog собирает и обнаруживает C#-тесты, перечисляет frontend и
  PowerShell-файлы, проверяет владельцев и устаревшие селекторы. Это проверка
  инвентаря, а не исполнение всех тестов.
- NoBuild допустим только после свежей успешной сборки всех выбранных проектов.
  Старые бинарные файлы не доказывают проверку изменённых исходников.
- TimeoutMinutes задаёт общий защитный предел команды, включая подготовку и
  очистку; максимум 30 минут. По умолчанию используются бюджеты выбранных
  категорий плюс пять минут подготовки, с тем же общим потолком.

- Parallelism ограничивает внешние процессы (1–4); для unit-проекта одновременно
  не больше двух. Категории не перекрываются во времени; exclusive-категории
  исполняются последовательно. Внутренние ограничения xUnit сохраняются.

Для выбранных frontend-проверок сначала установите зависимости:

    npm ci --prefix BookOfEternityClient.WebFrontend

Runner запускает только указанные Vitest-файлы или компилирует выбранные
standalone TypeScript-проверки и исполняет их через Node. Чистые typecheck-контракты
отмечены отдельно от выполненных утверждений. Если C#-категории нужны собранные
ресурсы интерфейса, requirements.frontendBuild включает сборку без полного
frontend-тестирования. Старые npm verify и test:player-facing отклоняются;
отдельные typecheck и build доступны.

Тестовые файлы — отдельные точки входа: нельзя импортировать другой *.test-файл
ради его выполнения. Общий код выносится в helper. Проверка инвентаря отклоняет
буквальные test-to-test imports; ревью также проверяет вычисляемые импорты.
Категории frontend не требуют сборки production-ресурсов, если проверяют только
исходники или компоненты.

## Платформа выбранного CI

Общий `.github/workflows/dotnet-ci.yml` планирует только текущий явный selection
через `scripts/plan-test-ci.ps1`. Необязательное поле категории
`requirements.ciRunner` принимает `ubuntu-24.04` или `windows-latest`. Без поля
сохраняется прежний Windows runner; это соглашение CI, не доказательство
переносимости категории. Для native Linux bodies укажите Linux runner после
анализа фактических consumers. Это поле не фильтрует локальный запуск тестов.

Planner сохраняет все entries/reasons/contracts и группирует их по runner;
пустой, неизвестный или неверный selection завершается отказом. Каждая группа
проверяет фактическую ОС и запускает точный selection через test-csharp.ps1.
Frontend готовится только для требующих его групп.
Frontend-группа проверяет уже установленный на hosted runner Node.js 22.12+
(major 22, минимум текущего lockfile); отсутствие, другая версия или ошибка
проверки завершают группу отказом. Workflow не устанавливает Node и не меняет
repository action allowlist; conditional `npm ci` сохраняется.
Итоговый check `Selected category verification` требует успеха планирования и всех групп;
failed/skipped/cancelled не являются PASS. Фактический native Windows прогон
и hosted Actions исполнение указываются отдельно от локальных metadata-тестов.
Перед интеграцией selection всё равно сверяется со всем intended diff:
платформенная маршрутизация не делает выбор от прежнего блока достаточным.

## Как добавить тест или категорию

Каждый обнаруживаемый тест должен иметь хотя бы одного документированного
владельца. Одна категория может охватывать оба C#-проекта и frontend; техническое
размещение не определяет её предметную ответственность.

Для новой категории скопируйте близкую запись из каталога и задайте:

```json
{
  "id": "example-contract",
  "responsibility": "Admission and rejection of the example contract",
  "excludes": "Rendering and unrelated resource rules",
  "changeHints": ["BookOfEternityClient/Services/Example*.cs"],
  "related": [],
  "requirements": { "frontendBuild": false, "exclusive": false },
  "timeoutMinutes": 5,
  "expectedSeconds": null,
  "selectors": [{ "project": "unit", "tests": ["BookOfEternityClient.Tests.ExampleTests.*"] }]
}
```

Это шаблон: замените фиктивный класс реальным и опишите его потребителей в related
(id и when). Отсутствующий класс будет отклонён проверкой инвентаря.

| Поле | Содержание |
|---|---|
| id | Короткое уникальное имя текущего контракта |
| responsibility / excludes | Что проверяется и что остаётся за границами |
| changeHints | Подсказки путей для поиска затронутых областей |
| related | Другие категории и конкретное условие совместного выбора |
| selectors | Проект, точные методы/файлы или шаблон методов одного буквального класса |
| requirements | Нужна ли сборка frontend и исключительное исполнение |
| timeoutMinutes | Защитный бюджет категории, от 1 до 15 минут |
| expectedSeconds | Измеренное время; null, пока его нет |

Проекты selector: unit, integration, frontend, powershell. Для C# допустим,
например, BookOfEternityClient.Tests.SomeTests.*; нельзя выбрать всю namespace.
Для больших partial-классов предпочтительны явные семейства или списки методов,
чтобы новый несвязанный сценарий не попадал в старую категорию незаметно.
Frontend использует точный путь и runner node, vitest либо typecheck;
PowerShell — точный файл scripts/tests/*.tests.ps1.

Укажите все влияющие окружения и связи, выполните ValidateCatalog, посмотрите
PlanOnly новой категории и проверьте её поведение. Новый enum в runner не нужен.
При переименовании одновременно исправьте related, selection-файлы и инструкции.
Повторная принадлежность допускается: объединённый запуск выполняет каждый
метод/файл один раз, сохраняя строгие требования и все причины выбора.
Строки параметризованного метода продолжают исполняться как отдельные случаи.

Если категория смешивает обязанности или регулярно занимает больше пяти минут,
изучите её длительности и разделите по контрактам. Пять минут — повод разобраться,
а не причина выкинуть важную проверку. Не заменяйте смысловое разделение
пронумерованными корзинами и не повышайте предел автоматически. Низкое число
методов не доказывает быстроту; неизвестное время остаётся неизвестным.

## Фикстуры и изоляция

Обычный вариант — своё изменяемое состояние, каталог, сервисы и жизненный цикл
на каждый тест. Запрещены общий изменяемый объект, зависимость от порядка,
состояние предыдущего теста, разделяемые активные lease, владельцы и транзакции.
Кэширование не является обязательной оптимизацией.

Неизменяемый шаблон допустим при измеренной пользе и независимой копии всех
изменяемых данных. Ключ учитывает все входы; произвольный callback не становится
безопасным ключом. Копирование шаблона не должно обходить подготовку, холодное
восстановление, регистрацию или проверку полномочий, если именно они проверяются.
Изменение/удаление одной копии не влияет на другую и на шаблон. Проверяйте это
адресно при изменении соответствующего helper, не добавляя новую полную матрицу.

Текущий аудит фикстур и подтверждённые результаты хранятся в активном
[плане #1505](../specs/1505-test-suite-performance/plan.md). Не удаляйте безопасные
шаблоны только из-за слова cache и не сохраняйте сложный кэш без пользы.

## Результаты и диагностика

Каждый запуск создаёт уникальный каталог TestResults/test-categories/.
Он содержит журнал, plan.json, summary.json, TRX и отчёты frontend-адаптеров.
Инвентаризация дополнительно пишет catalog-audit.json. Результаты привязаны к
Git revision и отпечатку изменённых файлов checkout.

В summary видны выбранные категории, причины из selection-файла, запланированные
и завершённые дескрипторы/случаи, время категорий, ошибки, пропуски и очистка.
PhaseResults отдельно показывает подготовительные команды, компиляцию адаптеров
и runtime-очистку; исходные журналы сборки сохраняются в Build-*.log.
Динамический Theory может выдать больше строк, чем было видно при discovery;
лишние строки одного метода не компенсируют отсутствие другого метода.
Ноль тестов, неполный набор, ошибки отчёта, неуспешные/пропущенные случаи и
незавершённая очистка не являются успешной проверкой.

После ошибки прочитайте причину, TRX/отчёт и незавершённый состав. Исправьте
конкретную причину и повторите затронутые категории. Не добавляйте весь набор
«для уверенности» и не повторяйте успешные проверки без новых изменений.

На Windows дочерние процессы удерживаются собственными Job Objects запуска.
Остановка, тайм-аут и ошибки очищают только принадлежащие ему деревья процессов.
Runtime-каталог также уникален, его очистка ограничена бюджетом и проверяет
границы пути. Runner не убивает процессы по имени. Нельзя вручную удалять чужие
каталоги или выдавать отменённый/частичный прогон за завершённый.

## Текущая миграция

Исторические результаты Fast/PreMerge сохранены в истории #1505 и #1536;
они не измеряют новые категории. Приёмка миграции проверяет весь инвентарь без
исполнения, затем только категории инфраструктуры и нужные frontend-адаптеры.
Изменения игровых механик не входят в эту работу. Миграция прошла независимое
ревью Astra XHigh; итоговые свидетельства находятся в плане #1505. Проверены
91 категория и 10 180 идентичностей без исполнения всего набора. Время большинства
категорий пока не измерено; известные результаты не следует переносить на них.
