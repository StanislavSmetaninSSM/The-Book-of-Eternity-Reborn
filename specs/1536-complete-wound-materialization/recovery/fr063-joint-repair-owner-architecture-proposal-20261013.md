# FR063 joint repair owner: bounded architecture ruling

2026-10-13. Retained Astra XHigh; source-backed read-only consultation. No implementation, project execution, Git operation, provider call, repository edit, or additional agent. Only this external report was written. Sole Sol's component pending-pair work is independent and was not reviewed or changed here.

**Verdict: BLOCKED as a single entrance/persistence patch using the unchanged publication contracts.** The missing capability is not only ownership of `wound_commands.json`. The existing wound-stage and common-publication authorities explicitly make an acquisition publication and a treatment continuation mutually exclusive. A narrowly admitted branch at the validation boundary can obtain and preserve a genuine repair wave, but cannot successfully complete its corrected acquisition together with the identical held treatment through the unchanged six-argument publisher. Calling that branch complete would leave a second, independently proven dead end.

The smallest defensible production target is **one typed joint wound-stage owner inside the existing accepted-turn coordinator**, with one combined preparation/effect/finalization/common-plan transaction. This is an owning-contract extension across the wound planner, common-plan authority and lifecycle—not a codec hookup, new public endpoint, general authority framework, or request re-signing scheme. The concrete target and stopping conditions below are proposed design only. They are not SOURCE acceptance or permission to implement production.

These are confirmed source blockers to the proposed unchanged-contract handoff, not runtime failures and not evidence against the separately qualified ordinary treatment path.

Sequentially publishing the acquisition and then the treatment is also not the minimal solution: both write the wound identity/history/carriers and effect/resource state, both use the same original turn, and each invokes its own effect/common planning. It would need an additional intermediate accepted-state authority, scheduler ordering, and transaction/rollback protocol to prevent duplicate periodic effects and partially committed turns. Re-exporting from the intermediate live files is not a proof that the original sealed treatment source is unchanged. The current accepted-state authority fingerprints wound identity/history, effects and resource inputs (`MortalWoundTreatmentAcceptedStateAuthority.cs:624–685`); the original reader and common before-image checks remain authoritative. Do not implement a two-publisher sequence under the label of one handoff.

## Smallest proposed owning target

The narrow first contour should be explicit: one current-Mortal, original-bound, confirmed guaranteed treatment of an already-existing player wound; one genuine QTE acquisition occurrence for the same original turn; one genuine actionable construct/repair packet; no unrelated raw resource/effect/party/owner commands. The initial useful correction can preserve the complete ordinary scene while changing only the packet-authorized proposal fields. This avoids silently widening the sealed treatment command's final-scene contract to solve narration repair at the same time. Existing item/course/procedure/diagnosis and general mixed-family entry points are not automatically included.

The physical wound command should remain the exact homogeneous treatment root for the entire repair. The private pending root should contain that same complete request set through existing `ComposePendingRoot`. The corrected acquisition should be a separate **typed, adapter-issued contribution owned by the coordinator**, never another raw command written into the occupied slot and never a second treatment request. This keeps the persisted catalog's exact treatment-set agreement unchanged. It necessarily requires a new private joint admission/stage variant; the present physical-QTE-command retry predicate cannot be reused as proof for an unwritten command.

The target lifecycle is:

1. **Admit before the existing homogeneous-owner refusal, without changing that owner's behavior.** At `ValidationService.ResourceMaterialization.cs:503–537`, after ordinary upstream/original/resource-owner validation, recognize only an explicitly admitted joint candidate. The candidate requires fresh official original/frame/G, strictly parsed and recomposed homogeneous treatment command, fresh `ExportCurrent`/`RestorePersistedTreatmentRequests`, exactly one matching ConfirmedHeld claim, and an actual adapter-issued QTE opportunity under the same participating lease. Mere simultaneous file presence is insufficient. A typed `NotApplicable` must leave existing guards intact; an applicable but invalid candidate must refuse rather than fall through. No new resource reservation is made.

2. **Capture genuine rejection plus dormant held treatment.** Call the real QTE adapter read-only on the actual draft and scene. Only its real public semantic rejection, private opportunity and resulting matching nonempty packet can enter repair. Preserve the complete original source/frame/G, exact treatment command and request graph, packet/receipt, raw draft/scene, and expected before-images as a coordinator-owned private checkpoint. The checkpoint represents repair provenance, not accepted acquisition or publication authority. Preserve exact request IDs/seals and the existing claim throughout repeated invalid resubmission.

3. **Preserve the complete graph across baseline restoration.** Extend the existing `CaptureWoundRepairRetryObligationsAsync` → `RestorePreTurnBaselineForRepairSessionAsync` boundary with a typed private wound checkpoint. Today the latter only reinstalls an optional resource-pending checkpoint (`SessionAndSnapshots.cs:2091–2115`). The joint branch needs an exact coordinated restore/install/readback of its command and private pending wave while retaining the confirmed claim. A pre-restore pending write alone will disappear. A post-restore unowned write is not sufficient. Failure before public dispatch must restore the previous exact bytes and leave one well-defined claim state; uncertain publication must stay blocked, never be converted to absent pending or a released hold. The private command/pending paths must explicitly remain outside GM resubmission and repair targets.

4. **Validate the correction into the same private owner.** Re-read official original/frame/G, current command/pending/history and the same held claim. Re-run the genuine adapter and `MatchesCorrectedDecision`/source/scene constraints. Obtain the actual accepted acquisition composition, without staging a competing QTE command. A new joint retry obligation must prove this typed contribution plus the still-exact treatment graph; the current `_mortalQteOwnedCommand` predicate remains unchanged for ordinary QTE callers. No codec or self-consistent pending JSON can mint this ownership. On a cold continuation, the owner must reconstruct provenance through the original and genuine adapter again; the pending packet alone is not hidden source authority.

5. **Build one combined wound/effect/common plan.** This is the missing production capability and must be designed before step 1 is released as a complete implementation. The joint prepared stage must contain the acquisition's client-allocated wound/transition and anchor evidence together with the existing treatment's exact typed request/resolution and treat transition. It must use one coherent baseline and identity/history allocator, one effect schedule, and one common resource reduction. Existing pure acquisition preparation, treatment outcome preparation, treatment Finalize and registered resource outcome can supply their bounded contributions; their already-finalized after-images must not be spliced together. Revalidate final guarantee/capability and aggregate bounds against the actual composed accepted owner/source state, rather than assuming the new wound cannot affect them.

6. **Publish and settle once through the existing coordinator transaction.** The completed joint authority must prove the union of both contributions, full before-images and ordered effects, the QTE occurrence/receipt and creation history, full treatment request/result history, exact treatment resource Finalize, and consumption of the owned command/private wave/public draft. The existing normalizer and treatment publication transaction are the integration points; do not allocate a second hold, call two common publishers, finalize treatment early, or leave stale repair packets. Retryable failure compensates the entire union and retains exactly one request/hold; terminal cancellation removes its exact command/pending copies and releases the matching hold atomically, with compensation on failure. Session replacement and unknown-byte publication uncertainty remain fail-closed.

This is a concrete target lifecycle, not a claim that a suitable typed joint input or combined constructor already exists. The key semantic choice is simultaneous composition under one original—not publication of an intermediate canonical wound state.

## Required contract delta and actual implementation boundaries

The existing six-argument `ComposeMortalWoundTreatmentPublication` cannot be reused unchanged for step 5. FR-063 explicitly names that publication path (`spec.md:537`), so a proposal must state how the joint path enters that publication family while preserving its public six-argument contract and existing callers, or explicitly document the tightly scoped owning-contract amendment. Do not silently add ambient generic authority or claim that the current six parameters already carry the acquisition proof.

The minimum connected source responsibility would span:

- `GameEngine.MortalGuaranteedTreatment.cs`, `GameEngine.MortalQteWoundDecision.cs`, and `ValidationService.ResourceMaterialization.cs`: a private joint admission/correction branch and exact typed handoff, with all old branches unchanged.
- `GameEngine.ValidationAndRepair.cs`, `GameEngine.PrivateImplementation.cs`, and `GameEngine.SessionAndSnapshots.cs`: the typed repair obligation/checkpoint, source/G lifetime, client-owned path exclusion, baseline restore and cancellation behavior. `StateDistributor`'s existing public/mixed/competing-command guards need not be weakened; the joint contribution is not staged through its generic occupied-slot method.
- `WoundAcceptedTurnPlanner.MortalTreatmentPublication.cs`, `WoundAcceptedTurnPlanCache.cs`, and `AcceptedTurnAuthorityRegistry.cs`: one privately minted joint prepared/effect/final authority with exact contribution agreement, plus reservation/cache invalidation rules. Merely increasing the existing singleton limits is invalid.
- `AcceptedMechanicsWoundCommonInputComposer.cs`, `AcceptedMechanicsPlan.cs`, `AcceptedMechanicsPlanCache.cs`: an explicit joint context/common-plan proof that binds acquisition anchors and treatment finalization together. Existing disjoint constructor branches stay strict for all other callers.
- `CanonicalStateNormalizer.AcceptedMechanics.cs`, the existing treatment publication transaction and its coordinator callers: full union publication, readback and compensation. Existing quarantine removes only submitted request rows, not repair packets (`MortalWoundTreatmentResourcePublicationTransaction.cs:121–145,1393–1448`); the joint owner must own wave completion/cleanup explicitly.
- `MortalQteDecisionPublication.cs` requires an affected-contract review: its current fixed published footprint does not include the wound pending root. The new branch must not use an old completion marker to claim that its additional private wave and treatment hold were settled. Whether the existing marker is extended or a separately typed joint completion check proves this is a source design decision still required; no new general journal is justified.

These are bounded ownership dependencies, not a request to refactor all mechanics or broaden GM grammar. They show why this cannot truthfully be scheduled as one local repair-writer insertion. The current component pending-pair and new-root representation proofs remain useful independent responsibilities, but do not provide this normal entrance or final combined publication.

## Finite causal acceptance responsibilities for a later proposal

Select exact cases only after the concrete source/fixture inventory exists; the following are obligations, not invented category counts or permission for a broad rerun:

1. A real ordinary entry with one existing held request reaches the genuine semantic rejection, emits a nonempty public repair wave and the complete private command/pending graph, preserves one claim, and survives the actual baseline restore. Observe the packet before cancellation; direct calls to `ComposePendingRoot` alone cannot qualify this responsibility.
2. Actual correction through that same loop reaches full ordinary completion with the identical request/claim IDs, one treatment spend/finalization/history receipt, one acquisition/occurrence receipt and client allocation, exact scene/source constraints, one effect schedule and one final story turn. The initial expected refusal is an owning-path causal RED only if these real prerequisites are reached; upstream fixture failures remain blockers.
3. Exact duplicate command/pending graphs coalesce through fresh owned reconstruction. Divergent nested graph, foreign wave, changed original/G, unauthorized correction sibling and competing command refuse without overwrite, allocation or claim loss. Existing raw mixed/external calls still fail their old guards.
4. Producer restore/write/readback failure and later joint publication failure exercise the distinct required compensation boundaries. Terminal cancellation must remove exact copies and release the corresponding hold; retryable publication failure must retain both graph and hold and only rearm its exact valid plan. Unknown bytes remain blocked.
5. The existing acquisition/treatment periodic-effect and final guarantee-source checks are exercised where the joint after-state can affect them. No silent discarded outcome, second scheduler pass, or independently overlaid identity/history root is acceptable.
6. Cold/fresh-root ownership reconstruction must eventually prove the joint repair provenance and same request lifetime under FR-063. It is a later explicitly selected responsibility; neither the component pair nor this architecture report qualifies it.

No additional gameplay-policy permission is needed to recognize the normative gap: FR-012 and FR-063 already require full private persistence and safe same-request lifecycle. But the above production ownership expansion needs an explicit bounded design/source gate. Until its stage/anchor/finalization proof exists, the correct disposition is **live joint-owner integration BLOCKED; no capture-only workaround; ordinary13 retained qualified, mandatory pending/live/new-root/full-FR work OPEN**.
