# T197 custodian host location alternatives — 2026-10-16

## Recommendation for review, not a selected mode

**Yes: making the original per-run Client process the custodian can provide the same specified GMBridge-presentation-loss guarantee with less client-UI coupling.** Keep the actual GameEngine/FileSystemManager/StoryService and console/agent presentation where they already live. Construct original main coordinator/native owners in that same process before the protected run starts. Make the separate GMBridge process a detachable terminal presentation/input client. For that failure case, the old renderer/input remoting proposal is unnecessary; only the GM terminal boundary needs transport.

Recommend this **Client-owned candidate for affected architectural review before expanding the earlier GMBridge-owned renderer seam**. This is a conditional recommendation, not an automatic mode choice or implementation release. The previous hosting and story/A4 pairs remain immutable and unaccepted as complete contracts. The new comparison does not change the required user outcome or accept a permanently unresolved lawful death.

Equivalence has an exact condition: the original Client keeper survives. In the earlier GMBridge-custodian proposal, a separate game-console frontend could die while its graph survived in the keeper. In the Client-owned candidate, killing the console Client process kills the keeper. Thus the candidates are equivalent for **loss of the detachable GM terminal frontend**, not automatically for loss of every UI process. If survival of the game-console process is itself a requirement, retain a distinct keeper or design another approved lifetime boundary; do not silently narrow the promise. Keeper loss/cold/reboot/container or host migration/distinct-root recovery remains unsolved in both candidates. HOLD is preservation, not successful ordinary-death resolution.

All new APIs/locations remain PROPOSED/UNACCEPTED. Whole B01/A1, source closure, B03/B04, platform qualification, DEP-C/I/L/full target/H2/H3/HQ/new QTE remain open/blocked. D4/guided/visual/Windows/D8 are preserved. No new G, source replay, extra Mortal turn/dice/reward, target acceptance or child receipt retiring a parent.

## Exact proposed construction and invocation seams

1. **Client composition and lifetime.** Add `Client/Services/GmRuntime/OriginalMainRuntime.cs` and `Client/Core/OriginalClientRunLifetime.cs` as proposed original owners. Program's existing DI constructs exactly one run-lifetime service using the same FileSystemManager/StateManager; GameEngine and StoryService remain the existing singletons. Native constructor/IO/work registrations are installed before effects. Do not invoke the Client executable again or instantiate another GameEngine from request bytes.
2. **Bootstrap before main acquisition.** Preserve StateManager.BootstrapLocalStorageAsync and current health/startup decisions. An explicit initialization boundary in GameEngine.RunAsync around198–211 is needed so the owner can start a main run with the actual established G before admitting protected player actions, without replaying bootstrap. The startup ticket covers constructor/bootstrap/health effects. Do not hold the main guard then recursively enter bootstrap's ordinary main admission. Start timing relative to menu/new-game/load requires the actual run-lifetime state machine; this comparison does not declare one native run for the whole multi-session application. Replacements still stop the old run and use the actual load/current-G owners.
3. **Native launch from the actual Client owner.** `OriginalMainRuntime.StartOriginalAsync` calls current OpenProductionAsync/Windows startup observation and Launch methods. Original coordinator acquires main guard and production worker conjunction, prepares exact metadata and native owner, checks current G and releases the held child once. Insert the same pre-effect promise registration and before-release task-binding seams required in the prior hosting report. Default source APIs are not themselves exhaustive enrollment.
4. **Real local Access.** At actual source admission (ordinary ProcessPlayerTurn before1495; late reconciliation before888), the run lifetime reserves the parent lane/registry and invokes `coordinator.RunOperationAsync` around the existing SessionOperationContext body. That creates the real local pin and ambient Access. MainRunFence can then borrow it without contacting the owner's endpoint or reacquiring its physical main guard. Root equality, same process or a DI singleton alone is not Access. Preserve nested lease/refcount/outcome/finalization rules and the story child boundary.
5. **Terminal presentation extraction.** Keep original PTY input writer, native output reader/drain, terminal screen/readiness observer, prompt tasks and status writer in OriginalMainRuntime. The detachable bridge receives terminal display frames and offers typed input/resize requests; it cannot own native streams, handles, main pins or original close receipts. The owner validates current input lifetime and registers actual IO before effects. No raw input stream handed to a reconnecting process. It must keep draining native output when the bridge stalls/dies, independently of frontend capacity. Readiness facts used for prompt dispatch must come from the owner's actual original terminal observation, not an untrusted frontend screenshot/status DTO.
6. **Server ownership.** Extract BridgeHost.MainOperations and the runtime-facing load/stop/dispatch handlers into the same original Client run owner. External helper pin transport must terminate at that owner, not through the detachable bridge. Otherwise bridge loss still drops all external pins before their work is known stopped. The current pipeName/status-based discovery and strict close frames need the outstanding B04 endpoint/caller contract; do not invent a new endpoint/key or treat that status as proof. Console, agent API and browser read views remain data consumers.
7. **Loss and shutdown.** GM presentation loss triggers the reviewed source-seal/join policy while the Client keeps original tasks/leases/native authority. It must not become player Escape, terminal wait Cancelled, deletion/rollback, canonical error log or reissued prompt. Current source cancellation branches and parent guards still need exact changes. Explicit application quit, native exit and process death remain different events. Program's existing finally disposes audio/input/API and GameEngine.RunAsync finally stops audio; an actual run-lifetime shutdown must finish genuine main/native/parent settlement before normal exit. A killed Client loses original authority; no restart rehydrates it.

**What changes less:** no movement of the38-service console graph, no player-console output-over-IPC protocol, no input transport for ordinary local console keys, no new game renderer abstraction just to survive GMBridge presentation loss. **What still changes:** ownership extraction from BridgeHost; Windows native adapter location; terminal-only transport; startup/stop/load timing; exact registration/seal integration; helper/server authority; publication permission after seal. This is less coupling, not a claim of a tiny or already authorized implementation.

It does **not** prove survival of terminal hangup, login/session manager termination, parent-job policy, container death or the game-console process. **Windows:** native Job implementation is already in Client; ConPTY adapter extraction is the concrete dependency seam. Cloud/source inspection cannot qualify Windows. The native EOF O1 rule and all original uncertainty remain unchanged.

**Browser:** source proves that --web currently builds a web-only graph while the GameEngine cooperative consumer lives elsewhere. Therefore a “web Client is keeper” declaration is not enough. Proposed composition must keep the actual BrowserPlayerActionService/BrowserLocalWriteCoordinator and the **one actual GameEngine source consumer** in the supported per-run owning arrangement from birth, with shared original services/serialized relevant state and exact staged→idle→expected-G-finalize boundaries. If console+web are concurrently available, define one authoritative original consumer and exact request/phase lanes; do not silently choose a product mode or suppress a supported action.

Neither location closes direct native CLI writes, external daemon/helper processes, worker inventory, escaped/service-submitted work or arbitrary callback IO. They must be enrolled/owned before a legal source outcome, with exact publication and stop receipts. Moving the server to Client prevents presentation loss from being the pin transport loss; it does not prove already-lost external work completed. Source-child receipt remains subordinate; same-G retirement still requires original whole-parent and native proof. No new OS guarantee is asserted beyond the prior read-only official-source analysis; no network access or platform probe was performed in this follow-up.

## Remaining engineering contracts and bounded recommendation

For the named bridge-presentation-loss objective, the Client-owned direction removes a broad game-renderer remoting requirement and uses the existing shared layer. It is the preferred next candidate for independent review **if the accepted failure requirement is that named event with original Client survival**. The event comparison above must remain visible; this report does not accept a narrower user outcome or choose a final mode.

Before code release, close these concrete contracts:

* Original run start/stop/load composition around actual bootstrap/G and menu/source entry; retention through normal app shutdown, with no second graph or recursive main-guard acquisition.
* Exact extracted native/bridge-runtime ownership: Windows adapter/helpers, terminal observation/readiness, PTY pumps, status/prompt/draft work, external main-operation and Load handlers. Pre-effect enrollment precedes native launch and all async synchronous prefixes.
* Genuine source parent registration and complete finite writer/debt inventory, including other Client helper processes/daemon/CLI/worker/browser owners. Existing current-G/Lost/worker guards and no extra semantic work after seal remain mandatory.
* Exact post-seal permission and native attempt/recovery interception from prior SV-B02/SV-B03; host location supplies none. Stop ordering must not deadlock a source waiting on GM, nor use timeout as receipt.
* B03 strict durable codec/CAS/version/bounds/terminal retention and B04 endpoint/caller/data-retirement authorization. Terminal display and legacy main pin protocol must be separate in authority even if one owner serves them.
* Browser actual source-loop/graph integration and separately qualified Linux/Windows launch/stop/IO behavior. Keeper-loss/cold/reboot/migration/distinct-root issuer, DEP-I/L/full target/H2/H3/HQ remain OPEN.

The comparison changes only the proposed placement recommendation. It is not a rewrite or acceptance of the prior immutable design, a permanent runtime refusal policy, an implementation plan release, a new lifecycle/gameplay/OS/service grant or F2 activation.
