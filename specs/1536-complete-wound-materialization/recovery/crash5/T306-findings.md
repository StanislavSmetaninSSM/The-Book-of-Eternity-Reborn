# Причина длительности измеренного восстановления Windows

На уровне кода установлено многократное выполнение полного графа проверок исходного состояния и текущих файлов. Это конечная работа с большой стоимостью: в общем плане восемь проверок ресурса порождают 24 проверки базового состояния, continuation и механических исходников. Затем опубликованный результат заново проходит проверки при входе владельца истории. Воспроизведённый тест исчерпал исходное ожидание 600 с во время этой работы.

Независимый ревьюер gpt-6-astra/high принял эту причину на уровне приложения для измеренного Windows timeout; T302/T306 и TIM3-5 закрыты в этих границах. Конкретный системный вызов, файловый фильтр или драйвер этим исследованием не установлен; причина Linux-сбоев также не установлена.

## Что добавляет стоимость каждому чтению

Чтение через действующую lease включает проверку доступа и физического пути. Для **явных байтовых API `ReadFileBytesSync(lease, path)` и `ReadFileBytesAsync(lease, path)`** на нормальном успешном пути существующего ordinary-файла код выполняет четыре проверки lease: byteSync — две внешние и две внутренние, byteAsync — одну внешнюю и три внутренние. Это не общее правило для всех read API: `ReadFileSync(lease, path)` имеет три проверки на своём нормальном пути. Это **количество по коду при указанных условиях**, не измеренный счётчик всех завершённых чтений.

`EnsureValidCanonicalWriteLease` (`FileSystemManager.cs:4443–4449`) проверяет владение, main admission и применимые worker-гарантии. В соответствующих ветвях `MainRunFence.cs:233–270` проверяются persisted main-run state, owner guard, worker namespace и generation. Какая именно ветвь main admission работала в T305, отдельно не утверждается.

Запрошенный путь дополнительно проходит `ResolvePath`/`EnsureCanonicalPathStillSafe`; `TrustedLocalFileScope` проверяет компоненты пути, ancestors и leaf, в Windows через `File.GetAttributes` (`TrustedLocalFileScope.cs:102–138,322–335`). Повторяются проходы по компонентам пути и метаданным; это не утверждение о рекурсивном сканировании всего игрового дерева при каждом чтении. Непосредственное открытие/копирование байтов находится внутри этой обвязки (`FileSystemManager.OrdinaryReads.cs:197–202,262–294`).

Ранее изолированный T284 показал около2мс для16raw-reads против263мс для16leased-reads на маленьком подлинном original. Это независимое подтверждение стоимости обвязки конкретного компонента; его нельзя умножать на43тыс. hook-вызовов и выдавать результат за измерение полного сценария. Начальный callback не является счётчиком успешно завершённых чтений.

Retries чтения допускаются только для определённых sharing/lock ошибок, до20задержек по50мс; факт таких ошибок в T305 не установлен. Причина не приписывается этим задержкам, сети, сканеру или системной блокировке без соответствующего наблюдения.

## Где закончился тест

Публикация целиком завершилась за420,684с. Первый postpublication-проход завершился за91,271с. Владелец истории затем повторно вошёл в completed continuation и второй postpublication/game-state проход; точная цепочка вызовов сохранена в [T302-findings.md](T302-findings.md). Первый и второй проход видят разную фазу progression/current state, их идентичность или возможность удалить второй проход не доказана.

Второй game-state проход начался на575,890с часов коллектора и успел завершить ряд отдельных фаз. Последняя запись — **начало `GameState.ClientOwnedControlFiles` на599,788с**. Его end отсутствует. Это не600-секундная длительность этого валидатора; родительское ожидание имеет другое начало отсчёта. Дальнейший результат истории и хвоста неизвестен.

## Что показывают независимые счётчики CPU

33снимка стандартных Windows CPU-счётчиков связаны с PID27992 и точным birth ticks639280844877931604 из actual native report. После первого отдельного снимка наблюдатель каждые15с собирал данные до выхода процесса, без квоты и ограничения срока сбора.

Последний снимок: total CPU567,438с, user184,078с, kernel383,359с. Между первым и последним снимками накоплено524,859с CPU за559,213с по UTC. Это активная процессная работа на существенной части наблюдаемого времени. Сумма относится ко всем потокам, счётчики считываются последовательно, часы UTC отличаются от часов таймеров. Она не назначает CPU конкретному методу и не выявляет конкретный kernel call/driver/антивирус. Периодический наблюдатель завершился при выходе процесса; raw JSONL, состояние и его исходник включены в архив.

## Результат и границы

Фактическая причина длительности на уровне приложения — большая частота и объём fresh validation/readback одного исходного состояния в конечном вложенном графе. Замер показывает конкретные методы, их кратность и затраты; из-за этой работы исходного ожидания теста не хватает. Для исправления нужно сокращать повторную работу с доказанным сохранением current-original/lease/authority/readback контрактов. Простое удаление второго прохода или свежих проверок этим исследованием не обосновано. Оптимизация и увеличение тайм-аутов не выполнялись.

Точный вклад отдельных OS-вызовов, стоимость конкретного filesystem driver и возможного сканера остаются неизвестными. Бесконечный цикл/глобальное отсутствие любых блокировок не объявляется ни доказанным, ни опровергнутым для всех путей. Linux cloud-причины локальным Windows замером не установлены. Дальнейший незавершённый хвост не квалифицирован. Исходные пять Windows случаев остаются0/5PASS; это не игровой PASS.

Продюсер38224 завершился crash-кодом73; resumer27992 остановлен по тайм-ауту. Оба EOF/join подтверждены, оба собственных корня удалены и отсутствие проверено;3DLL/seed неизменны. Никаких привилегированных диагностических подключений, изменений process ownership, системной политики или игровых assertions не было.
