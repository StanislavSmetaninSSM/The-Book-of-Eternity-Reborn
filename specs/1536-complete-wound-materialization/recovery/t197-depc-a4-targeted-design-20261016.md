## Ruling and scope

This is a proposed, source-grounded G-C/A1–A5 contract for **one operation whose original custodian survives bridge loss**. It is not an implementation or a closed DEP-C qualification. The recommended architecture makes an outliving, per-run application custodian the original launcher and keeper of native authority. A bridge becomes a frontend; losing it does not lose the native owner. All mutable work for the protected operation must have been enrolled before its first side effect. The custodian first seals admission, proves real work exhaustion, and then settles the exact already-started publication debts. It never completes the gameplay operation by rerunning it.

The minimum successful case is bridge/transport loss with the original custodian, original native scope and exact publication owners or qualified recovery adapters still available. Custodian loss before authoritative retirement cannot be repaired by decoding these proposed records. This is a deliberate remaining limitation, not a claimed full crash/reboot solution. Unknown descendant escape, unregistered writers, incomplete native I/O or missing publication provenance likewise remain blocked. A stronger systemd/OS service authority is an alternative decision, not silently part of this recommendation.

## Chosen ownership topology and one-operation boundary

The proposed application custodian is launched for this one main run using ordinary user privileges. It owns the original coordinator, main guard, native owner, launch controls, terminal input gate, output drain pumps, recovery reservation and operation ledger. It outlives bridge and UI transport disconnection. It is not an installed service, not auto-started on boot, not an elevated broker and not a machine-wide registry. No tool in this task launched it. Keeping such a run alive while references/debts remain is intentional lifecycle custody, not an OS service installation.

The frontend passes admitted commands through a bounded authenticated channel. It owns no canonical write handle, operation borrow or native terminal input endpoint. A frontend reader may display output; the original custodian always drains PTY/ConPTY output independently even when no reader exists. Frontend disappearance cannot abandon an output callback that has mutation authority: any such callback belongs to registered operation work in the mutation executor.

**Managed mutation execution:** the recommended complete A1 contract is a dedicated single-operation runner owned from birth by this custodian, or an equivalent audited executor with actual joinable exhaustive task ownership. The dedicated runner is the defensible forced-stop option: its entire process, all threads and allowed descendants belong to the operation's native scope. UI processes are not terminated to approximate operation cancellation. The runner executes existing authorized owner logic once and publishes through its original admitted file APIs; transferring serialized originals never reconstructs a capability. Before beginning a publication it freezes the exact native recovery evidence and registers its owner-bound debt. Death of that runner permits only a specifically qualified recovery adapter for the already-started journal. A surviving runner may instead perform its own original finalization and return real work/debt receipts. An unjoined managed task still in the custodian blocks retirement; killing the custodian would destroy the proof issuer.

This runner split is an explicit engineering proposal, not evidence that the present delegate-based SessionOperationContext can be moved across processes unchanged. Exact source owner extraction and recovery-capability transport are an OPEN interface. A cooperative in-process implementation can support successful join, but cannot promise retirement of a hung arbitrary thread. It must not abort/forget the thread or pretend its cancellation token was completion. If an exact runner adapter cannot preserve an owner's live original authority, that source path is not yet recovery-qualified.

**Run scope vs operation scope:** the current main CLI scope is shared at run level. Recovering one lost operation may stop that entire original native run, but only after the exclusive lifecycle lane has excluded unrelated work from the beginning. The lane serializes mutating admission, allows separately proven read-only displays, and retains nested work under the same operation. Existing durable helpers must already have actual owner-issued retirement/debt clearance before lane acquisition, or be explicitly part of the same operation's finite enrolled inventory with their existing original owner. The initial proposal chooses the first, narrower condition. It does not drain arbitrary other operations by timeout, nor relabel their work as this operation. If the existing workflow cannot provide this lane before a possible death, DEP-C remains incomplete rather than rejecting a legal death after acceptance.

**Scope exclusions are not permission to ignore effects:** calls to external daemons, WMI/schedulers, service managers, remote tools, shared worker pools, shared writable mappings, io_uring/shared native executors or non-child process launchers can escape ordinary lineage/job accounting. This operation profile may not use any such writer without a separately registered genuine exhaustion/settlement owner. An audit proving their absence is required; a string `profile=safe` is no proof. Direct CLI writes are not guarded by the current lock files. The native scope must first be truly exhausted, and each direct writer's finite write set and pending I/O must be owned by an accepted adapter. Until that is demonstrated, a full all-writers claim is unavailable. No security sandbox or OS policy that prevents those escapes is silently assumed.

## Platform alternatives and recommendation

**Linux L1 — recommended narrow bridge-loss route.** Start the existing original managed NativeLineageOwner inside the outliving custodian, and its original C subreaper beneath it. The bridge is never the supervisor's stdin/status/PTY owner. Keep original descriptor transfer and held-before-release handshake. Keep the native supervisor's one exclusive reaper and same-PID-namespace scope; fork/setsid/double-fork alone do not justify abandoning descendants. Original pidfds identify processes; `/proc` discovery is not terminal proof. On bridge loss the custodian seals launches/input, requests original stop, observes the original terminal status and actual helper/root/I/O completion, then retains that observation while settling debts. The existing C EOF→Uncertain behavior need not be weakened: EOF from custodian death still means proof loss. All native source uncertainty—including namespace violation, child capacity overflow, invalid status or observation deadline—remains a blocker. This design does not clear that uncertainty after a later empty-looking scan.

Requirements: currently supported Linux x64 package, native subreaper/pidfd/descriptor bootstrap prerequisites, same declared namespace profile, observable original helper/status, no environmental policy that kills custodian with bridge, and actual qualified local filesystem. No minimum kernel is claimed beyond the required calls: the package already checks its prerequisites. New runtime qualification must establish the exact supported distro/kernel/libc/.NET/storage combinations. Container PID1/session teardown or whole container death can kill both processes; L1 does not promise recovery through that event. `/proc` restrictions, seccomp restrictions or unavailable APIs produce refusal, not a sudo/remount workaround. No Linux qualification was run here.

**Linux L2 — separately considered stronger manager/cgroup route.** Bind a manager-owned cgroup from before release, keep the original unit invocation and cgroup physical identity, and require no permitted migration out of that family plus actual recursive emptiness after sealed kill. A proposed existing-user-manager adapter could use a transient scope or a per-run service, but automatic restart must never relaunch the source action. A fresh connection after custodian death needs a new narrowly specified manager attestation/retained unit identity contract, not the current SystemdUserBus original-reference API. Unit name, path, recreated cgroup, Inactive state or PID absence are insufficient. Require exact invocation, manager/boot continuity, source membership binding, stable cgroup reference, sealed admission, native I/O and publication debt owners. If the manager removes the unit before recovery can authenticate it, proof is unavailable. Service/unit retention policy is an unresolved prerequisite, not supplied by this report. Installing a service, enabling lingering, changing delegation/permissions, namespaces or mount/security policies is decision-only and not authorized. L2 is not recommended as the default merely because cgroup.kill exists.

**Windows W1 — recommended narrow bridge-loss route.** The outliving same-user custodian creates ConPTY, its I/O pumps and an unnamed job, starts the original child suspended, assigns it to the job and verifies the chosen non-breakaway job limits before its single resume. It retains original process/job/terminal handles and original completion tasks. Frontend death cannot close the last job handle or the only ConPTY host. On recovery, first seal launch/input; request termination through the original job; query that same live object until real active-process exhaustion; wait actual original process and all owned native I/O/close tasks; retain terminal evidence before disposal. Job notifications are wakeups, not a substitute for the actual query and closed admission. No ordinary job or process handle is inherited by children unnecessarily. Original handles must remain live through the last proof read. A handle duplicate, when used, is acknowledged by the receiving live custodian before sender release; it is never reconstructed from a saved integer. The chosen design creates ConPTY in the keeper from the outset and does not assume HPCON can be rescued after host death with DuplicateHandle.

Requirements: supported Windows ConPTY API and compatible job assignment/nesting environment; original child starts suspended and cannot perform a write before job assignment and metadata ACK; no breakaway/silent-breakaway profile; all operation writers inside the approved scope or separately proven owned. Existing outer jobs/launcher policies may prevent the required topology; failure must be reported as a platform prerequisite, not worked around by elevated rights. WMI-created processes and work submitted to external services are not covered by ordinary child job inheritance. Terminating a process/job does not justify skipping native I/O completion or publication recovery. No Windows host or backend qualification exists in this task; cloud/Linux source inspection cannot supply it.

**Windows W2 — alternatives not recommended for this slice.** An additional original handle keeper can extend job custody across one keeper death only if that exact live duplicate was installed before release and all ConPTY/I/O/managed obligations still have original owners. Duplication does not preserve arbitrary managed state or a dead ConPTY host. A named job plus OpenJobObject is insufficient: the name can disappear/rebind and does not attest the old operation's work/publication closure. An installed Windows service could be a longer-lived original custodian, but service identity/installation/rights and its own crash proof are separate explicit decisions; this task grants none. W1 gives the narrower ordinary-user, per-run bridge-loss guarantee.

**Recommendation boundary:** select L1/W1 for further contract review, with original-custodian survival as an explicit guarantee boundary. Do not advertise total process/host restart recovery. If the required product guarantee includes custodian death, neither selected backend closes it; choose a genuinely stronger accepted issuer and qualify its source/debt custody before claiming DEP-C complete. The coordinator can proceed autonomously with ordinary application changes only after the exact contract is accepted; OS/security/service changes remain separate decisions.

## Closed metadata proposal and live authority

The proposed on-disk family is `.boe_runtime/main-operation-recovery-v1/<runId>/<operationId>/`. It is outside `gm-runs`, whose current strict reader rejects additions. No directory is created in this task. A coordinated version change to main schema is still required to link its immutable recovery descriptor and to prevent an old binary from opening a run using a newer recovery protocol. The proposal is fail-closed version separation, not automatic migration of an already-Lost schema1 run. Existing unknown or legacy records remain refused by the new route.

Closed files: `manifest.json` (immutable before release), `state.json` (one exact-byte CAS state), `state.tmp` (only the exact original pending candidate), `debts/<sequence>.json` (immutable owner-produced descriptor), `receipts/<sequence>.json` (immutable owner result), and `retirement.json` (one terminal record). No wildcard files, symlink/reparse targets, duplicate/case-aliased paths, alternate numeric spellings or unknown properties. A write-ahead ledger entry is flushed and acknowledged before its corresponding release/start. An incomplete metadata mutation remains metadata debt. Proposed Linux metadata publication uses original validated directory handles plus file/directory synchronization; Windows uses the qualified write-through/flush/readback path. These are new adapter requirements; no claim of general power-loss qualification is made.

**Manifest v1 exact keys:** `schemaVersion`, `sourceRun`, `physicalRoot`, `sourceOperation`, `sourceBinding`, `backendProfile`, `custodian`, `operationExecutor`, `admissionInventory`, `limits`. `sourceRun` is the existing exact RootKey/RunId/GenerationId/Epoch/Backend/HostInstanceId/BootId tuple, with nonempty current G required for this handoff. `physicalRoot` is the existing platform physical directory identity plus normalized root key; numeric PID/path equality is not physical identity. `sourceOperation` is exactly operationId/pinId/closeId. `sourceBinding` contains only the existing source owner kind, admitted source-original and source action identifiers, n, k_death and source original-proof reference. It neither contains nor derives a target request. The exact source proof type remains the named handoff adapter's obligation.

`backendProfile` is a closed union: `LinuxOriginalLineageV1 {nativePackageDigest, guarantee, namespaceIdentity}` or `WindowsOriginalJobV1 {launchImageDigest, jobPolicyDigest, conPtyProfile}`. These fields describe/refuse; live original objects prove custody. `custodian` has `instanceId, protocolVersion, endpointKind, endpointName, publicChallengeKey, startupBindingDigest`; process ID/start identity may be recorded as diagnostics, never the proof. `operationExecutor` is `OriginalRunner {instanceId, imageDigest, scopeBinding}` or `OriginalJoinableExecutor {instanceId, registrationCatalogDigest}`; only a reviewed concrete executor variant is admitted. `admissionInventory` is an ordered exact array of original work/worker slots and close identities (including the absence witnesses required by the exclusive lane). It is not a namespace snapshot. `limits` fixes admitted maximums before release.

**State v1 exact keys:** `schemaVersion, manifestDigest, sequence, previousFrameDigest, phase, sealedAdmissionSequence, workRows, debtRows, terminalFrame, pendingMetadata`. Each work row is `workId, parentWorkId, kind, ownerInstanceId, registrationSequence, terminalReceiptRef`; kind is one of `ManagedBody, ManagedContinuation, NativeProcessScope, TerminalInput, TerminalOutput, NativeIO, PublicationOwner, Finalization`. Each debt row is `debtId, kind, ownerInstanceId, armedSequence, descriptorRef, resolutionReceiptRef`. No arbitrary handler name or serialized callback is dispatchable. `terminalFrame` is null or an exact original normal Close frame or a private retirement record reference; those alternatives cannot be interchanged. `pendingMetadata` binds the exact before/after bytes and one stage identity for the currently attempted CAS, or null.

**Debt descriptor v1 exact keys:** `schemaVersion, manifestDigest, debtId, kind, originalOwnerBinding, transactionId, armedSequence, generationBefore, generationAfter, members, guards, nativeEvidenceRefs, allowedResolution`. A member is exactly `ownerRole, canonicalRelativePath, beforeRef, afterRef, operation`, with operation in `Replace, Create, Delete`; guards carry exact typed before-image/presence evidence. Image references name immutable original owner artifacts with byte length, digest and physical provenance; hashes alone never authorize reading/writing arbitrary paths. `allowedResolution` is a closed owner-derived disposition set; e.g. an uncommitted trusted-local cohort permits its exact rollback, not execution of an unstarted next phase. Same-G before and after are mandatory here. Runtime generation changes, archive loads and incarnation bootstrap are not admitted debt variants.

**Retirement v1 exact keys:** `schemaVersion, manifestDigest, sourceRun, sourceOperation, sealedAdmissionSequence, workClosureDigest, nativeReceiptRef, sourceDebtReceiptRefs, metadataReceiptRef, disposition, consumerBindings`. Only `RetiredAfterExhaustion` is the retirement disposition. Any committed/rolledback business result is separately retained from its real publication owner; retirement itself does not assert business success. Each receipt ref is issued by the named original owner and compared under its live authority, not trusted merely because a file exists. `consumerBindings` restricts consumption to the retained same-G handoff/HC and its exact original references; it grants no H2/H3 by itself.

Proposed admission bounds: 32 outstanding operation records per run as a hard upper bound, one active lifecycle mutation lane, 128 enrolled work tickets, 64 armed debt descriptors, 4,096 exact member/guard rows in total, 1 MiB metadata per frame, depth 16, 4,096 UTF-8 bytes per normalized path and bounded existing-owner image sizes. These are proposed engineering limits, not measured adequacy. Before admission an executable owner catalog must establish that the legal operation fits; if it cannot, the recovery-capable route is not qualified. Never discover overflow after release and silently drop work. Historical retained records cannot be evicted while any handoff or publication reference remains; storage exhaustion blocks new admission. The source's native CHILD_LIMIT=128 is a separate bound and any native overflow remains uncertainty, not a reason to omit a descendant.

**Endpoint identity and replay:** a live original endpoint is required for bridge restart. Suggested protocol: original custodian creates an ephemeral P-256 challenge key in memory before release; publishes only its public key and original launch binding through the guarded manifest; a new frontend sends a fresh 32-byte nonce and exact tuple. Custodian responds with a signed digest of nonce + protocol/version + tuple + current sequence + requested receipt, and internally validates its actual original objects. Verify platform peer/process binding as well. The private key is never persisted, exported, logged or recovered from JSON; it is protocol identity, not native authority. Native authority still comes from the original retained handles and state. Cryptographic serialization and transport framing require independent review; no credential store or OS settings are changed. This proposal assumes the project's trusted-local filesystem model, not resistance to hostile same-user arbitrary code editing the ledger or stealing process memory.

A fresh channel is only a query/recovery channel to the same still-live original custodian. It never reconnects the old active pin or accepts new normal work under that pin. Nonce replay, stale sequence, wrong root/G/run/epoch/boot/key/operation or changed receipt is refusal. Copied JSON on another root cannot identify the actual live custodian. If the custodian died, challenge authentication and native proof are unavailable: stop. A durable retirement file is not a replacement live capability. ## State machines and lock coverage

**Run:** `PreparedCustody → RunningExclusive → RecoverySealed → NativeExhausted → SourceDebtsSettled → RetirementPublished → RetiredQueryOnly → Released`. `CustodyLost` is a one-way failure branch from any phase before legitimate release. It retains all evidence and blocks new mutation. Existing run `_uncertain` is not cleared; the new path terminates that old run through independently verified recovery proof. `Released` requires genuine transfer/release of all retained reference obligations, not a TTL.

**Operation:** `PreparedGrant → Active → {OriginalCloseObserved | LostUnresolved}`. Recovery uses `LostUnresolved → AdmissionSealed → WorkExhausted → DebtsResolved → RetiredAfterExhaustion`. Normal close preserves the existing exact terminal frame. Lost remains a historical fact. The two terminal alternatives are different. A closure ACK lost after original CloseObserved is a query of the retained original terminal frame; it is not Lost retirement and never reexecutes the operation.

**Publication debt:** `Reserved → Armed → {CommittedPendingCleanup | RollbackRequired | Uncertain} → {CommittedSettled | RolledBackSettled}`. Reserved work that never reached its owner-authorized durable begin is not forward-executed by recovery. Armed means the original owner acknowledged its exact durable publication intent before any member effect. In a crash gap the owner journal and exact registration evidence determine whether arming occurred; ambiguity stays Uncertain. Committed data is never rolled back because close/ACK was lost. If a semantic follow-up was not started, it remains future work of its existing owner and is not a settlement privilege.

**Order:** original main guard is outermost. Acquire short admission/metadata mutexes to seal and publish reservation, then release them before waiting for any task/process. Do not hold canonical or lifecycle leases across participant drain/native stop; an operation may need its existing closing lease to finish an already-started publication. All pre-seal publication entries have been registered and owner-authorized; they may settle their own exact intent, but cannot start a new semantic phase. Native/task drain must finish, with no future callbacks/writer continuations, before obtaining the recovery lifecycle lease and then canonical write lease. Recovery uses a new private main recovery access issued by the same original custodian, validated against the sealed tuple; it does not reopen a normal pin. Main metadata lease is never recursively requested while canonical is held. Its exact lower-level lock order must reuse the existing fence implementation and receive focused review.

The custodian itself holds the main guard, so it executes recovery or issues a narrow original recovery access; a restarted frontend cannot acquire that guard and then wait for the custodian that owns it. While holding lifecycle/canonical, verify physical root, exact current G, original manifest, no other run/worker debt, native/task proof, full armed debt inventory and source originals. Resolve only those debts. Release canonical and lifecycle with their real finalization outcomes; persist final retirement under main metadata ownership. A metadata failure retains the original stop/debt proof and exact pending CAS. Only after that ACK may the original pin be retired exactly once and the ordinary main run's Stopped record be published/acknowledged by the new verified recovery method. If ordering requires a final cross-record commit, the recovery store's terminal frame is the durable decision and main.json is a retryable dependent metadata debt; admission refuses either partial state. Do not expose Stopped while the retirement decision or source debt is missing.

Final consistency: the main guard is released only after terminal decision, dependent main metadata, lease release and every pin/worker conjunct is observed. The custodian can then remain alive read-only to authenticate the exact retained receipt to the same-G successor. New normal work under the old run is permanently denied. A new ordinary main owner must independently acquire the physical guard, verify current G and the fully acknowledged retired predecessor; its epoch changes, G does not. The handoff adapter binds the exact receipt to the retained source and genuine target instead of rebinding old live authority.

## Handoff and user-visible behavior

The retirement receipt resolves only the exact old source-operation close debt, after all publication and native obligations above. It does not say the business action completed, does not validate a new target, and cannot manufacture H2. If an earlier H2 cohort genuinely committed, its exact after-images/target originals remain; a close failure does not roll them back. HC records the original owner's real closure/retirement only through the named handoff adapter. H3 releases source artifacts only after all existing target/H2 obligations and HC are valid. HQ is its own exact browser dequeue/target-preservation operation and close obligation. No old pin is resurrected for those operations.

The browser displays an in-progress or unresolved transition and keeps the new-action composer blocked. Reload or another frontend can query the same original custodian; a reconnect neither recreates the pin nor reruns source input. Already accepted narrative/result is retained and not presented as a new choice. Console/agent paths use the same status and gates; they cannot continue by pressing a force-close option. A timeout may yield control and show that evidence is retained. Definitive unsupported custodian-loss recovery is reported honestly instead of silently dropping a lawful death/evaluation. Because that branch is required for full qualification, activation remains blocked until the product's accepted recovery contract covers it.
