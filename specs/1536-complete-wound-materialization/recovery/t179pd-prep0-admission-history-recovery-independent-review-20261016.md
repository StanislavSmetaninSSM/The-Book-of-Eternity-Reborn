## PH-D01 — choose legacy dispatch from the original contract, not the request alone

**Severity: medium, confirmed specification defect; no implemented runtime defect claimed.** Location: proposal `Version-first cold reader`, line 173 (step 2), with lines 71–79 and step 3 at 174.

Step 2 currently states “Old unversioned request -> existing old route” before step 3 checks the original-issued seed. That branch is broader than the proposal's own original-selected lifecycle. Consider an intact newly versioned original whose request/control is accidentally replaced by an old-format same-session/request/turn repair request, or a partial migration that leaves an old writer/cleanup consumer active. The request is unversioned and correlated, but the original still requires durable history. Following step 2 literally selects Legacy without checking that obligation, permitting dispatch or cleanup through the old transport behavior and losing the versioned history requirement. Existing tuple-based consumers make this a meaningful boundary: daemon correlation at `game_master_daemon.ps1:4294–4312` and the ordinary reader's context matching do not establish the new origin/history contract. No hostile-edit or cryptographic threat assumption is needed.

Required correction: after native debt settlement and actual original/G validation, derive the lifecycle mode from the authenticated original's supported seed/version (and genuine terminal disposition where applicable). Return Legacy only when that original/context is genuinely eligible for the unchanged old protocol. A versioned original paired with missing, unversioned, unknown-version, wrong-kind, malformed or foreign control is SourceConflict/MissingOwnerProof or a specifically proved terminal settlement; it is never an implicit legacy downgrade. Conversely a versioned control cannot upgrade an old/no-seed original. A control's discriminator selects its parser, not the original's protocol obligations. Apply this matrix consistently to dispatch, correlation, validation and cleanup, not only the cold reader.

Finite future cases: (1) genuine old original + old request retains old behavior; (2) genuine new original + valid new control uses the new lifecycle; (3) new original + same-tuple old request refuses before dispatch/cleanup; (4) new original + missing/unknown/malformed control retains evidence; (5) old original + new control cannot mint history; (6) terminal deletion requires actual terminal/original/M3 proof. These are UNRUN. This is a concrete correction within R02, not a requirement to add a pathname or revise the trusted-local threat model.

## What is sound in the conditional direction

The proposal keeps final frozen evidence in existing M3, avoids mutable history in an already-issued original and avoids an informal prepublished completed M. It distinguishes client-owned history from worker ChangedFiles. A staged worker_applied companion is correctly not proof while the B1 decision is pending; hot validation and cold readers must honor the real pending-decision owner. The committed companion plus independent task/proposal/scope/after-image semantics can be a durable application observation under the existing trusted-local model without minting a live worker permit.

Leaving frozen control unchanged as a pre-seal guard and letting verified M3 establish handoff avoids an unnecessary split transferred acknowledgement. Exact control/source guards and evidence must already participate before common input/preparation/cache/take seals. The existing pathname does not implicitly expand write membership. Any alternate control mutation in common needs its actual owner, member and seal relation designed explicitly.

The distinction between durable observations and lost in-memory work is correct. A crash can lose a sampled UTC or allocated identity before persistence; a history filename cannot recover it. An unfinished read-only attempt could only be restarted under an expressly chosen no-publication/source/policy contract. It must not replace a frozen sample, reschedule source mechanics, allocate replacement identities for accepted work, or replay the player's action/committed consequences. The proposal correctly leaves both this choice and the stronger lost-C/result policy open.

Named historical samples remain client-owned observation facts under trusted-local SHA256-PAYLOAD-JSON semantics, not cryptographic proof against coordinated rewriting. Cold checkers must derive all available semantic relations; a persisted success flag, self-hash, predecessor hash or plausible receipt alone is insufficient. “Semantic tamper rejected” should retain this relational meaning, not universal historical attestation of irrecoverable clock samples.
