## Решение и граница первого блока

Пользователь уже определил поведение: собственная принятая рана видна сразу, вместе с понятными **как лечить / чем / что требуется**. Первоначальная рекомендация не требует diagnosis attempt, оплаты или удачи. Требования и цена самого лечения сохраняются. Дополнительная диагностика, скрытые осложнения и экспериментальные альтернативы не подключаются этим блоком.

Самый небольшой законченный вертикальный блок — **read-only рекомендации собственной активной Mortal-раны**: общая проверенная C# projection → немедленное accepted-result уведомление console → постоянная `/раны`/`/wounds` read surface → та же projection в browser scene и command result. Он использует уже принятые маршруты лечения и не включает provider selection, quote, confirmation, treatment execution, NPC targeting или History implementation. Это ограниченная часть T113/T115/T116/T117/T118/T119/T123–T126/T128–T129, не закрытие US5 целиком. Общую политику пользователя нельзя объявлять выполненной для Spiritual-ран этим Mortal-тестом; духовные формулы/Healing tier 0 остаются вне изменения, а current-realm filtering проверяется явно.

## Данные рекомендации и единственный подтверждённый presentation gap

Pure view должна возвращать только разрешённые русские поля: name/rank, известные locus/cause/symptoms, care, видимые effect summaries, полный уже известный список route alternatives. Внутри route: **как** = accepted DisplayName и readable mode; **чем/условия** = ordered typed requirements с человеческими названиями; группы requirements — AND, routes — OR; course milestones не теряются. Numeric quantity/tier, owner/provider role, policy расхода и публичный риск переводятся по existing typed schema. Не выдавать procedure за гарантированное исцеление, stabilization за heal, пустой requirements[] за отсутствие риска/времени. Не вычислять новую цену, шанс или healing formula.

Source naming gap требует конкретного технического решения до production patch, не нового вопроса о diagnosis:

* `MortalWoundTreatmentContract.cs:438–534` допускает 11 закрытых kinds: item/resource quantity, skill tier, source capability, provider, consent, facility, location, quest state, effect state, environment. Requirement содержит exact ref + typed fields, **не readable name**.
* `MortalWoundTreatmentAuthority.cs:43–119,135–159` содержит displayName в snapshot entities. Однако `MortalWoundTreatmentAcceptedCanonicalProjection.cs:36–87` требует signed pending treatment context и selected coordinates; это treatment authority composer, не public UI read service. `ResolveProvider` на 954–1037 требует точного выбранного provider и текущего присутствия. Нельзя заводить provider/signed turn или запускать treatment resolver лишь ради просмотра.
* Public scene shapes (`MortalWoundTreatmentSceneAuthorityContract.cs:49–73`) содержат readable facility/environment/consent labels. Это не универсальный именник отсутствующих medicines/skills/providers. Current accepted CREATE fixture вообще имеет `requirements: []` (`GameEngineTurnLifecycleTests.QtePhysicalInjuryConsumerCreate.cs:323–326`), поэтому не доказывает проблему отсутствующих средств.

Рекомендуемый минимальный путь: сначала pure display binding из **существующих принятых, разрешённых игроку** item/resource/skill/scene/provider names, с exact identity и visibility; отсутствующая quantity или provider availability никогда не скрывает route. Не передавать внутренний accepted-treatment snapshot в browser: он содержит NPC inventories/skills и не является public projection. Известное имя может быть показано при количестве 0; несуществующий exact reference нельзя назвать посредством `snake_case` humanization, raw ID, выдуманного каталога или поиска по scene narrative.

Для ссылки, у которой readable subject отсутствует во всех разрешённых canonical источниках, current shape **не гарантирует** полноценное «чем». До реализации writer должен выбрать и показать bounded presentation binding: либо доказать, что existing accepted route DisplayName уже полностью задаёт понятную инструкцию со всеми нужными средствами/условиями и это требование закреплено в текущем authoring contract, либо предложить минимальное presentation-only дополнение текущего route/requirement contract с точной связью к уже существующим requirement indices/refs. Второй вариант — schema/design delta для обычного независимого review, не одобренная этой запиской grammar. Он не вправе давать resource authority, вводить каталог лечения или дополнительную механику. Сообщение «нужен неизвестный предмет» допустимо как error state, **не** как PASS требования понятных рекомендаций.

Availability — отдельное non-authoritative read status: `имеется`, `не хватает`, `помощник сейчас недоступен`, `проверяется при выборе лечения`. Если current public facts не позволяют утверждать availability, показывать последнее, не ложное «можно лечить». Полная recommendation остаётся видимой; точная quote/consent/reservation/fresh authority остаются обязанностью будущего actual treatment flow. Provider не выбран — это не отсутствие recipe и не основание читать private NPC состояние.

### Выбор: один presentation object вместо перегруженного DisplayName

`displayName` оставить кратким названием метода. Единственная существующая строка не обеспечивает проверяемую связь названия средства с одним из ordered requirements, а у курса есть и общие requirements, и отдельные requirements каждого milestone. Примеры: `Examples/E_CLI_Wound_Materialization.txt:158–174` имеет разные item/skill prerequisites; `:1699–1717` — provider в common requirements и три дозы в разных milestone arrays. Наличие всех этих слов в одной строке нельзя структурно проверить; распознавать recipe из прозы нельзя. Поэтому DisplayName-only не рекомендован как полное закрытие confirmed gap.

Предлагается **одно** дополнительное поле route, без нового ID, schemaVersion, registry, цены, authority или action:

### Exact structural rules и область обязательности

1. `presentation`, если присутствует, — exact closed object `{instructions, requirementLabels}`, не null. Каждая row — exact closed object `{scope, milestoneOrdinal, requirementIndex, label}`. Никаких `ref`, `kind`, `quantity`, `minimumTier`, `role`, `price`, `available`, `visibility`, `known`, HTML или action-полей внутри этого объекта. JSON unknown/duplicate/confusable keys отвергаются существующим strict shape путём. HTML не исполняется; обычные угловые скобки в readable text не являются разрешением raw rendering.
2. `instructions` и `label` используют существующий `ReadText/TryReadText` contract (`WoundMaterializationContract.cs:2578–2606`): непустая trimmed строка, текущий `MaxReadableTextLength=2000`. Не вводить свободный JSON/Markdown renderer. Нет normalizing/truncating до fingerprint. Общий existing envelope bound сохраняется.
3. `scope` ровно `common` либо `course_milestone`. Для common `milestoneOrdinal` — строго null; индекс — строгий целый 0..Count-1 в `route.requirements`. Для course scope ordinal — строгий integer, exact existing milestone Ordinal, а индекс относится к requirements этого milestone. Не путать ordinal с array index. Для procedure/guaranteed course scope запрещён.
4. Labels образуют **полное взаимно-однозначное покрытие** существующих requirement coordinates: common в исходном порядке, затем course milestones в принятом порядке и requirements внутри каждого. Count должен равняться сумме этих массивов, duplicates/missing/extra/reordered coordinate rows запрещены. При отсутствии всех requirements допустим только `[]`, но instructions остаётся обязательной. Не deduplicate одинаковые refs между разными этапами: это разные prerequisites и возможные расходы. Capacity выводится из existing 16 requirements на member и максимум 32 outcomes: не более 16×33 rows, без нового arbitrary unbounded массива.
5. Нельзя считать отсутствие у own known route допустимым с DisplayName fallback. Будущая законная операция reveal должна дать complete current-contract known state; новую reveal механику сейчас не вводить.

### Значение label, privacy и предел машинной проверки

Label — принятая читаемая подпись **данного** prerequisite. Для item/resource/skill/capability/facility/location/provider это название средства/навыка/места или разрешённое ролевое описание; для consent/quest_state/effect_state/environment — понятное описание требуемого условия. Например, разрешённая подпись «Допуск в лечебницу получен» поясняет exact quest-state predicate; она не заменяет typed `questRef/requiredState`. Raw state token не выводится как обязательный player text. Renderer всегда дополняет подпись количеством, уровнем, ролью, milestone time и consumption policy из typed mechanics там, где они существуют. AND внутри group / OR между routes сохраняются.

Это декларация readable meaning принятых данных, не проверенный inventory факт: label не доказывает наличие предмета, доступность NPC, согласие, достаточный tier, exact resource key или разрешение лечения. Известная рекомендация сохраняет label и при quantity0/отсутствии предмета; availability вычисляется отдельно из разрешённых current public facts, иначе «проверяется при лечении». Не нужно invent предмет/помощника или резервировать что-либо, чтобы отрисовать название.

Полный route/presentation раскрывается только после existing own/current-realm/known filter. Presentation hidden route не переносится в публичный DTO; поле не расширяет visibility NPC, скрытых complications/effects и provider facts. Для baseline с закрытым provider игроку можно дать разрешённое ролевое условие («нужен доступный лекарь»), но нельзя через label раскрыть private identity/причину недоступности. Строгий parser докажет shape, completeness и точное binding по координатам; он **не способен доказать смысловую истинность естественного языка** или распознать скрытый факт, умышленно пересказанный в prose. Это тот же предел accepted `displayName`/`readableCause`. Не обещать автоматическое semantic truth proof. Ограничить instructions описанием метода, labels — предмета/условия; численные условия/исход/стоимость/доступность выводятся клиентом из mechanics.
