## Recommended named writer and exact cold proof

Keep old console/browser/QTE writer behavior unchanged. Add one internal joint-only operation on StoryService with an explicit result such as appended/already-appended/held, not nullable success and not a swallowed-error void return. The result is a story-only proof; it is not Accepted for the entire lifecycle.

Preconditions under one current canonical lease:

1. Reconstruct and validate a fresh `applied` phase capability, full joint mechanical union, same original request/snapshot/turn/G, and the actual accepted narrative/output. A cached witness, parsed marker or caller-provided row coordinates cannot mint this permission. Reacquire a fresh capability after lease turnover; do not carry its old lease object across calls.
2. Derive the story path from the authenticated original realm/incarnation; derive player action, requestId and turn from the actual original. Obtain narrative and other row content from the same validated accepted output/current owner reads, not a stale StateManager copy or raw caller string. Freeze location/entity refs once under that owner and verify their source agreement before append. Preserve all unrelated story/chat hashes and path spellings; reject aliases and additional story files.
3. Derive the exact new row reproducibly. Use the existing StoryEntry fields, including requestId/G. A narrow compatible choice is the already-frozen progression `preparedAtUtc` for this joint row's timestamp, exposed through the validated owner rather than reparsed as untrusted authority; old writers retain their clock behavior. This makes the cold expected row byte-reproducible without a new receipt file or a second free timestamp. Canonical JSON serialization and newline/UTF-8/BOM behavior must be exact.
4. Authenticate the current prefix against the sealed original history hash and presence inventory. Preserve the actual prefix bytes instead of parsing/reserializing old history. For original absence, permit only the expected empty-prefix/BOM creation rule for the one derived story path. Do not interpret absent coverage as permission to adopt an arbitrary current story.

The reader/writer may classify only:

- **Original prefix:** current file is exactly the authenticated original story (or authenticated absence). Append the one frozen row through the existing trusted local atomic writer, with exact before-image protection, then exact readback.
- **Original prefix + that one exact row:** remove only the deterministic final row bytes for proof, authenticate the remaining prefix against the original binding, and validate the complete current file, row coordinates and immutable contents. Return already-appended without another append or timestamp rewrite. Merely finding a matching requestId/G anywhere is insufficient. An extra row, changed prefix, changed row/refs/narrative, wrong G or other turn holds the original.
- **Anything else:** refuse/hold without trimming, rewriting or adopting the file.

The durable evidence is the actual authenticated-prefix-plus-exact-owned-row together with the actual applied joint source. It does not confer same-user anti-owner security and needs no new key. Both the fresh append and cold reconstruction should mint a narrow private joint story proof after exact physical readback. Add a named validation path for that proof, reusing the existing one-suffix/unrelated-history checks. Do not grant a generic story-hash exception, mutate original hashes, forge an existing QTE/browser proof, or suppress history errors by code string. Check this proof before the ordinary client-history validator can reject the lawful suffix.

On ordinary write/readback failure, report held or propagate a typed failure to the joint owning caller. Retain original/request/ready/output/backups and committed mechanics/progression; never invoke pre-turn rollback, release the finalized hold, log-and-return success, or clean terminal artifacts. After trusted local recovery, exact before/after classification can recognize a committed append whose return was lost. Unknown bytes or unresolved publication remain held. An exact already-appended result is safe to recognize in a fresh process without replaying mechanics or progression.

## Required integration and bounded tail ordering

Current live path increments the loop before story (`TurnLifecycle.cs:1861–1878`); late idle does the same at `:1053–1067`. Both then call `ProcessMortalProgressionAfterAcceptedTurnAsync` (`:1882`, `:1071`). The named variant must be integrated into both paths, not only the normal caller. Recognize an already-appended joint original before the generic late signal-turn mismatch/discard and before another increment/rotation. Reconcile only the authenticated original turn: prior turn → advance once after successful story result; same turn → no increment; any unrelated loop state → held. Do not discard the active original simply because a persisted owned row already advanced the recovered loop. Route joint failure around the existing destructive post-accepted rollback branches (`:1834–1855`, `:1040–1049`).

`ProcessMortalProgressionAfterAcceptedTurnAsync` (`:2375–2383`) is separate from schedule/report progression: it runs statsIncreased, derived characteristics and level-up. `ProcessStatsIncreasedAsync` (`:2391–2466`) applies changes and later clears the request in separate writes, with ordinary errors logged. `CheckLevelUpAsync` (`:2474–2541`) can award points, mark the processed level and prompt for distribution. `CharacteristicsService.ComputeAndWriteAsync:130–143` also catches ordinary errors; its writer at `:884–912` always changes `_lastComputed`. Therefore neither applied progression nor an owned story row makes this tail once-only, byte-inert or successful.

For the accepted first contour, use these explicit preconditions and ordering:

- Before taking/publishing the joint common plan, prove **no actionable statsIncreased**, no unprocessed level-up or stat-point initialization/award (actual durable processed-level marker already covers the canonical level), and no fresh QTE offer/runtime handoff for this decision turn. The prior finalized QTE occurrence is still required; it is a different source. Freeze/recheck these refusal-only inputs. Unchanged inputs alone do not prove absence of work. Existing mechanical admission (`GameEngine.MortalJointRepairMechanicalAdmission.cs:71–135`) checks unchanged inputs; it does not itself establish all these no-work predicates.
- Do not call the whole stats/level-up handler and infer success from its return. With the above no-work checks satisfied, the only remaining characteristics task is the deterministic derived projection from the actually committed state. For the joint-only path, complete/verify that projection **before** the story append. Use its real calculation and exact owner readback; the old swallowed-error void method is not success evidence. This is a bounded ordering change, not a new stats action. It allows the owned row to fence completion of that preceding projection without claiming the row authorized it.
- Then append/read back the one row, reconcile the loop once, and perform only the eligible ordinary terminal cleanup. On already-appended replay, revalidate current derived projection semantically against its actual source and the no-work tail conditions, without rewriting `_lastComputed`; then finish remaining terminal cleanup. Do not rerun a scheduler, stats, level award or projection writer merely because cleanup was interrupted.
- Preserve the actual original and rollback evidence until the story result and the eligible completion tail are proven. Cleanup failure is not permission to duplicate the append or rollback committed mechanics. If partial cleanup prevents fresh original authentication, hold rather than manufacture a new source. This report does not claim arbitrary partial cleanup is already recoverable.

These no-work conditions implement the design's narrow one acquisition + one treatment contour, which excludes unrelated actions; they are not a new gameplay policy and must be explicit in admission/tests. They must not be inserted only after committing unsupported work. If the coordinator intends this same slice to accept pending stat/level-up actions or a **new** QTE offer, then the row is insufficient: the missing authority is a once-owned completion/handoff proof for that concrete additional action. That requires an explicit bounded scope decision before claiming support; do not silently skip it or broaden this consultation into a general tail transaction.

QTE handling specifically consumes the optional accepted story proof at `TurnLifecycle.cs:2276+`/`HandleAcceptedQteOfferAsync`, and existing deferred continuation reconstructs it from the actual runtime/continuation pair (`StoryService.AcceptedStoryAppend.cs:153–173`). For this first no-new-offer contour, keep those old paths untouched and reject a new offer before joint take. If new-offer support is later required, it needs a genuine named joint story provenance accepted by that actual QTE source boundary; neither passing null after swallowed failure nor pretending the new row is an old coordinate-free console row is lawful.

## Architectural ruling and focused proof obligations

The named owner writer, exact suffix validation and joint-only inactive-tail ordering above are compatible with the approved once-story/applied-progression design. ROOT can incorporate this concrete engineering disposition into the remaining bounded sole-author work; it is not a fresh whole-design/SOURCE gate or release from this consultant. **The writer by itself, or returning Accepted immediately after phase-applied, remains insufficient.** If the inactive-tail restriction is not the intended first contour, the exact additional-action ownership dependency must be decided by the coordinator; no new speculative receipt format is selected here.

Later meaningful controls: real fresh append with request/G; fresh-PID exact prefix+row recognition and inert repeat; changed row/prefix/G rejected; a real existing writer/readback failure retains original/committed union; actual inactive stats/level markers with derived projection ready before row; pending stats/level or new QTE refused before joint take; actual live and late-idle completion each advances the same turn once. Counts, runtime results and optional fault infrastructure are not invented. Source and actual evidence must show the genuine joint applied capability and authenticated original, not a handbuilt story proof.
