# T460 — крупные затраты восстановления и кандидаты на кэширование

Задача #1536, revision55, 2026-10-23. Исследован прежний полный r54 FULL:
код `781e9051ed2b3febddd2d7fc5dc15e4bbc06a768`, запуск `be0c22e00`.
Новых игровых прогонов и изменений поведения нет. После уточнения владельца
приоритет имеют крупные повторные вычисления, а не отдельные мелкие I/O-вызовы.

## Почему общее время почти не изменилось

|---|---:|---:|---:|
| До ожидания resumer, по shared budget | 97,723 с | 110,981 с | +13,258 с |
| Первый основной вызов восстановления | 421,936 с | 411,689 с | −10,248 с |
| Остальное время testcase, по разности | 43,358 с | 39,886 с | −3,472 с |
| Весь testcase | 563,018 с | 562,557 с | −0,461 с |

Сокращение времени восстановления перекрыто ростом другого участка. Это
арифметическое согласование реально измеренных часов, не доказательство, что
оптимизация замедлила producer. Shared clock начинается после подготовки пакета
в родителе; остаток включает более раннюю подготовку, запуск/ожидание процессов,
прочую работу resumer, проверки результата и очистку. По одному запуску версии
нельзя отделить устойчивую разницу от вариации времени исполнения.

В r54 producer: импорт фикстуры 1,038 с; stage fixture — 1,060 с;
от engine enter до exit — 108,558 с. Внутри последнего участка подробные
operation timings не собирались. Назвать конкретную внутреннюю причину +13,258 с
по сохранённым данным нельзя. Для неё нужен отдельный замер producer с вложенными
таймерами; такой прогон здесь не выполнялся. Импорт не объясняет разницу:
в r53 он занимал 0,977 с, разница только +0,062 с.

## Главный повторный вычислительный граф

| Повторная работа | Вызовы | r54 inclusive |
|---|---:|---:|
| `JointContinuation.ValidateSeal` | 7786 | **79,142 с** |
| Его `TreatmentOutcome.AgreesWith` | 7786 | 45,576 с |
| Его `TreatmentResources.Finalize` | 7786 | 31,861 с |
| `JointFinal.ReplayAgreement` | 84 | **50,982 с** |
| `JointPreparation.Replay` | 1185 | **47,956 с** |
| `WoundBundle.DetachedCopy` | 58 | **48,752 с** |

Это вложенные и частично пересекающиеся группы: сумма строк не является
затратами восстановления и не предсказывает возможное ускорение.

Источник каскада в коде:

1. `TryReadJointRepair` каждый раз вызывает `HasValidSeal`; даже получение
   continuation fingerprint проходит этот маршрут. `HasValidSeal` снова вызывает
   проверку outcome и `Finalize(Resolution)`. В `ValidateCurrentAsync` эта работа
   стоит **перед** существующим `ValidateRecoveryDataAsync`: попадание в файловый
   DATA-кэш её не устраняет. См. [continuation](../../BookOfEternityClient/Services/WoundAcceptedTurnPlanner.MortalJointRepair.cs#L175).
2. `JointRepairPreparedAgrees` воспроизводит подготовку, а
   `JointRepairFinalPlanAgrees` — финализацию. Последний вызывается из
   `JointBaseline.HasValidSeal`. Вложенные проверки опять входят в continuation.
   См. [replay](../../BookOfEternityClient/Services/WoundAcceptedTurnPlanner.MortalJointRepair.cs#L564).
3. Getter `JointCommonAuthority.Bundle` вызывает `DetachedCopy`, а
   `ComputeFingerprint` обращается к этому getter ради `BundleFingerprint`.
   Из 17,010 с вычисления common fingerprint **16,794 с** заняло получение bundle.
   Это 20 повторных копирований. См. [common authority](../../BookOfEternityClient/Services/WoundAcceptedTurnPlanner.MortalJointRepairCommonPlan.cs#L97).
4. `DetachedCopy` снова входит в конструктор bundle. Из его 48,751 с:
   validation final — 20,997 с, effect — 10,770 с, prepared — 9,709 с,
   cross-checks и detachment — 6,854 с. Повторная валидация, а не простое
   копирование, составляет основную измеренную работу.
   См. [bundle](../../BookOfEternityClient/Services/AcceptedMechanicsPlan.cs#L438).

Эти количества почти не затронуты r54: continuation — те же 7786 вызовов
(78,793 → 79,142 с), replay preparation — те же 1185, final replay — те же 84,
bundle copies — те же 58. Поэтому публикация осталась на 218,277 → 218,709 с.
Из крупных улучшившихся участков: `FinalMaterializationLeaseAndCleanup`
сократился с 59,485 до 48,144 с. Общее время восстановления уменьшилось,
но главный вычислительный каскад остался.

## Что кэшировать в первую очередь

**1. Результат проверки неизменяемого графа continuation и детерминированной
финализации.** Один принятый закрытый снимок request/resolution/outcome с
реальными companion identities должен давать повторно используемые DATA:
mode evidence, проверенный outcome, рассчитанную finalization и их fingerprints.
Размещать результат в существующем сервисе, с ключом `(rule version, приватный
идентификатор снимка, версия данных)` и сроком текущей цельной операции.
Ключ не должен требовать повторного вычисления всего fingerprint-графа.
Для синхронных потребителей нужна типизированная точка входа без блокировки
асинхронной задачи через `.Result`/`GetAwaiter().GetResult()`.

Это требует доказанной глубокой неизменяемости снимка. `readonly` и
`IReadOnlyList` сами её не обеспечивают. Кэшировать `HasValidSeal=true` только по
ссылке на текущий изменяемый граф или по сохранённой строке seal нельзя.
Замена любого входа/companion создаёт новый ключ или инвалидирует результат.
Live lease/generation, текущие файлы и подтверждённый held claim остаются
отдельными свежими проверками; cached semantic DATA не разрешают публикацию.

**2. Принятые стадии bundle и replay; отделить чтение скалярного seal от
экспорта изменяемой копии.** Использовать проверенный закрытый снимок стадий и
его результаты preparation/effect/final replay через тот же сервис. Getter,
нуждающийся только в fingerprint, не должен ради этого создавать и повторно
принимать весь bundle. Для внешнего потребителя выдавать независимую mutable
копию; не возвращать кэшированный JsonObject или общий изменяемый DTO.

Однако нынешний контракт обнаруживает повреждение **частного** final history
при `DetachedCopy`, даже когда ссылки и сохранённые seal не изменились:
[контроль](../../BookOfEternityClient.IntegrationTests/JointBundleComponentTests.Copy.cs#L138).
Поэтому простая отмена валидации копии небезопасна. Нужно сначала отделить
неизменяемые проверенные DATA от mutable-представлений; любые изменяемые данные
продолжать проверять либо снабдить обязательной версией всех путей мутации.
Существующий отказ на повреждённой истории должен сохраниться.

**3. Повторные полные проверки game state — следующий большой кандидат,
72,330 с.** Переиспользовать можно результаты отдельных чистых правил от
неизменившихся DATA и полный набор их зависимостей. Два запуска разделены
изменениями состояния, поэтому кэш `вся игра валидна` неприменим. Запись,
удаление, изменение присутствия и зависимых перекрёстных ссылок должны
инвалидировать затронутые правила; свежие границы завершения остаются.
Разбор полноты зависимостей здесь ещё не выполнен — это кандидат, не готовый
безопасный контракт реализации.

Первые два пункта адресуют общий каскад на десятки секунд; их оценки
пересекаются. Без реализации и нового полного замера обещать экономию 79+49 с
нельзя. Простое глобальное кэширование SHA-256 или разрешений файлов не является
предложением этого исследования.
