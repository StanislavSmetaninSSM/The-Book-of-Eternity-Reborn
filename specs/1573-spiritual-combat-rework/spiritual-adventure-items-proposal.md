# Предметы духовных приключений: custom и перенос смертных возможностей

2026-10-30. T098, часть [spec v1.59](spec.md), [#1573](https://github.com/StanislavSmetaninSSM/The-Book-of-Eternity-Reborn/issues/1573).
Связанная предметная основа — [#1572](https://github.com/StanislavSmetaninSSM/The-Book-of-Eternity-Reborn/issues/1572)
и [SR-01–08 feature532](../532-golden-mask-backstory/spec.md).
Автор запросил отдельный тип custom; следующие возможности/правила — проект
на рассмотрение. Код, GM-пакет, схемы и работающие маршруты здесь не реализуются.

## Зачем и какой подход

Духовному миру нужны вещи для исследования, истории, обмена, подготовки и боя:
записка с настоящим текстом, памятная красная нить, плод с эффектом, ключ,
инструмент или ритуальный компонент. У вещи может не быть магии/численного бонуса.
Система должна работать для игрока, Хранителей, резидентов, странников, торговцев
и иных поддерживаемых духовных сущностей, а не только для воспоминаний Маски.

Рассмотрены копия всего смертного инвентаря и расширение общей духовной предметной
основы подходящими возможностями смертной системы. Рекомендован второй путь:
переиспользуются текст/эффекты/жизненный цикл, сохраняется духовный realm и
не появляются обязательные голод, масса тела, огнестрельные боеприпасы или
параллельный инвентарь. Называть каждый предмет реликвией не подходит запросу.

Предлагаются три явных вида: **реликвия, духовный камень, custom**. Точные имена
JSON-полей/enum ещё не выбраны. Вид определяет специальные правила; назначение
и поведение задаются отдельными возможностями: readable, consumable, usable,
quest-linked, equippable, container. Это проектные понятия, не уже принятая схема.
Один custom может совмещать несколько: запечатанное письмо можно прочитать и
передать; напиток использовать в бою; связку ключей применять к разным замкам.
В UI показывать понятный вид «Записка», «Памятная вещь», «Расходник», «Инструмент»,
а не техническое слово custom. Название/поэтичное описание не дают скрытой механики.

## Что брать из смертной системы

| Возможность смертных предметов | Предлагаемое применение в духовном мире |
|---|---|
| Описание, происхождение, известные свойства, количество | Общая карточка; неизвестное не раскрывать автоматически |
| Книги, записки, записи текста | Перенести textContent и общий просмотр текста по точному ID |
| Квестовые связи/памятные предметы | custom без обязательного бонуса; явная связь с заданием/владельцем |
| Расходование, заряды, эффекты применения | Плоды, настои, печати, приманки; явная цена/цель/условия и духовные эффекты |
| Инструменты/материалы | Открытие прохода, ремонт, обмен, ритуал, подготовка; не каждый инструмент экипировка |
| Экземпляры, владение, стеки, передача | Общее основание всех трёх видов; однократность и сохранение свойств |
| Контейнеры | Для нужного предмету содержания — шкатулка/футляр/мешочек; не вводить всю весовую логистику |
| Структурированные свойства/эффекты | Общий существующий effect framework с духовными характеристиками/целями |
| Ношение/удержание | Только при явной возможности и совместимости с духовной экипировкой; не по имени вещи |

Смертные `type`/`group` — описательные строки, а не закрытый enum всех видов.
Действующее разделение presentation/mechanics/equipment/container/consumption/
readable/crafting/quest полезнее буквального переноса перечня «оружие, броня,
зелье, материал». Реликвии сохраняют свои слоты/улучшения/условия; custom не
получает автоматически forge, rarity, mortal-бонус или право на экипировку.
Если custom явно носимый и даёт бонус, его источник должен проходить общие
условия духовного ношения/слота; новая бесплатная пачка слотов не вводится.
Само нахождение вещи в сумке не даёт бонуса атаки или характеристики.

Не переносить по умолчанию смертные уровни/силовые требования снаряжения,
физические HP/броню/энергию, голод/жажду, вес/объём/перегруз, магазины патронов,
универсальный износ/ремонт всей экипировки, полную экономику крафта/разборки.
Материал/инструмент допустим без готовой промышленной системы. Разумные предметы
с собственной волей, связью и журналом остаются отдельной возможностью, а не
требованием для любой записки. Не вводить обязательный численный эффект каждому
custom, не ограничивать их заведомо слабыми предметами лишь по названию вида.

## Три авторских примера

**Записка/книга:** описание отвечает, как выглядит предмет; `textContent:string[]`
содержит то, что написано. При чтении показывать сохранённый текст, а не новую
версию ГМ. Запись принадлежит точному экземпляру; одноимённые книги различимы.
Новое содержание добавляется через согласованный append-путь; прежние записи
сохраняются. Запечатанный/зашифрованный/нечитаемый документ имеет явную причину;
отсутствие текста не маскируется предметным описанием. Чтение секретного письма
может открыть сведения/цель, но не автоматически телепортировать к месту.

**Красная сплетённая нить:** уникальная памятная вещь с происхождением и при
необходимости questLinks. Можно показать, исследовать, подарить или вернуть
нужной душе. Бонус и слот не обязательны. Предлагается запрет обычной продажи
для явно quest-bound предмета по аналогии со смертным контрактом; квестовая
передача остаётся допустимой. Не распространять это на все памятные вещи и не
обещать автоматическую неуничтожимость/невозможность потери. Если квест допускает
уничтожение/расходование, его последствия должны быть частью принятого действия.

**Кровавый плод:** custom с расходованием и явным эффектом. Например, временное
усиление атак или восстановление здоровья; конкретные числа, побочный эффект
и цена в Перьях пока не выбраны. До подтверждения применения понятны известные
свойства, цель и расход. Один принятый результат уменьшает количество/заряды
и применяет ровно тот эффект к реальному actor. Сбой/retry не даёт бесплатного
бонуса, повторного расхода или двойного эффекта. Постоянное усиление допустимо
только как явно описанное свойство с условиями, а не вывод из художественного текста.

## Использование, предметный бой и информация

Предлагаемый обычный профиль расходника: одно Основное действие в бою, без
дополнительной ДЭ, если её стоимость явно не задана предметом. Это кандидат
для custom; принятое применение обычного камня40ДЭ/Основное/минута не меняется.
Бросок нужен для неопределённого воздействия (попасть, навязать эффект), но не
для любого проглатывания доступного плода. Приманка, печать или инструмент
могут иметь собственное действие/условия; нет одного обязательного набора умений.
Вне боя длительность по профилю действия, не универсальная минута для всей категории.

Профиль определяет цель, допустимость, расход/заряды, длительность, stacking,
снятие/истечение и эффект. Использовать уже существующие механизмы сопротивлений,
барьеров, состояний, восстановления и духовного урона; новая параллельная система
эффектов не нужна. Дублирующие временные эффекты не обходят общие правила наложения
оттого, что один пришёл от плода, другой от искусства. Точные бюджеты силы/цены
предметных эффектов ещё требуют согласования; бесплатное действие не подразумевается.

Действующие mortal onConsume/onEquip/onUse — правила для подготовки GM-изменений,
а не доказанный автоматический C#-исполнитель. Нужен проверяемый путь применения
с допустимым источником/целью; художественное свойство без него не считается
работающим предметом. Известные игроку свойства и скрытая истина различаются;
выяснение неизвестного эффекта — событие мира, не всеведение карточки.

## Общее владение и жизненный цикл

Развивать общий предметный договор #1572: stable instance ID, один владелец/
место хранения, количество/состояние, происхождение, содержимое/свойства и
проверяемые передачи. Не создавать отдельный кошелёк вещей custom рядом с
другим источником тех же предметов. Игровое владение NPC существует до обыска;
личные вещи отличаются от магазинного каталога/склада. Покупка, продажа, подарок,
квестовая передача, добыча и явный обыск используют ту же идентичность.
Не всё продаётся каждому торговцу; доступность/цена берутся из реального предложения.

Обыск переносит выбранную доступную вещь, включая текст/заряды/свойства, а не
создаёт новую копию. Применённый плод отсутствует среди трофеев. Источник ушёл,
вещь передана или изменена после открытия списка — действие перечитывает допуск,
не восстанавливает прежний экземпляр. Обновление профиля NPC не возвращает
проданное/потраченное. Исторические вещи воспоминаний сохраняют изоляцию роли
и не переходят в нынешний инвентарь через обычную добычу/чтение/квест.

Стеки допустимы лишь для действительно одинаковых предметов: разные тексты,
эффекты, questLinks, происхождение с игровой значимостью или заряды не сливать
по одному имени. Split/merge сохраняют учёт количества/происхождения. Уникальная
памятная нить обычно quantity1. Контейнер использует точные ID вложений и одного
носителя; циклы/самовложение и двойное владение запрещены. Лимиты веса/объёма
не вводятся без отдельного решения, существующая тара не означает бесплатное
копирование содержимого. Смертные исторические примеры путей по именам не переносить.

При полном расходовании/уничтожении предмета надо явно обработать связанные
тексты/квесты/источники эффекта: предмет нельзя оставлять доступным для чтения
как находящийся в сумке, но принятый результат/необходимое происхождение эффекта
сохраняются. Source-bound эффект прекращается по договору источника; уже выпитое
временное усиление длится свой срок, если так определён эффект. Это требование
к будущему lifecycle, не разрешение молча удалять sidecar или квестовые связи.

Духовные вещи остаются в духовном контуре при воплощении; проникновение custom
в смертный инвентарь и влияние на смертную жизнь не предоставляются автоматически.
Существующие mortal-бонусы реликвий сохраняются. Переход Море↔Сияющая Обитель
не теряет личные вещи; будущий Новый Порядок подключается по собственному realm-
договору, как #1572. Сохранять одинаковые возможности в обоих клиентах и GM-пути.

## Реальные опоры и границы реализации

- [MortalItemMaterializationContract](../../BookOfEternityClient/Services/MortalItemMaterializationContract.cs)
  содержит capability-секции. Они опора разделения поведения, не готовая
  духовная authority и не повод обходить её через mortal root.
- [ReadableInventoryDocumentAuthority](../../BookOfEternityClient/Services/ReadableInventoryDocumentAuthority.cs#L37)
  объединяет textContent/sidecars по accepted itemId. Сейчас перечисляет mortal
  items и требует mortal identity. Нужен нейтральный слой чтения с духовным
  источником; [ShelfProjection](../../BookOfEternityClient/UI/ReadableInventoryDocumentShelfProjection.cs)
  уже используется двумя интерфейсами и подходит для повторного использования.
- [MortalItemConsumptionPlanner](../../BookOfEternityClient/Services/MortalItemConsumptionPlanner.cs#L64)
  сохраняет count/identity/receipt; не выдаёт свойства плода. Полное расходование
  блокируется при неподдержанных связанных данных. Духовному пути нужны свои
  явные правила связей и публикация эффекта совместно с расходованием.
- [GuardianPolicyContracts](../../BookOfEternityClient/Services/GuardianPolicyContracts.cs#L1114)
  сейчас допускает лишь soulRelics.equipped/stored и требует relicId/rarity.
  [GuardianTradeService](../../BookOfEternityClient/Services/GuardianTradeService.cs#L384)
  и [ShiningTradeService](../../BookOfEternityClient/Services/ShiningTradeService.cs#L627)
  покупают relicData в soulRelics. Строка relicType=custom это не исправит.
- [ActorMaterializationContract](../../BookOfEternityClient/Services/ActorMaterializationContract.cs#L45)
  не содержит ownsItems/inventory у afterlife. #1572 уже требует расширить
  NPC-владение для реликвий; новые виды должны войти в тот же общий путь.
- [EffectSourceDefinitionContract](../../BookOfEternityClient/Services/EffectSourceDefinitionContract.cs)
  и существующий effect framework использовать с правильными source/actor/realm,
  не копировать mortal_world источники и физические бонусы в духовный бой.

Приёмка будущей реализации: записка хранится/читается/передаётся с тем же текстом;
нить показывается/возвращается и закрывает допустимую цель один раз; плод
расходуется с эффектом один раз у игрока и NPC; предмет после торговли/обыска
не остаётся у прежнего владельца; память изолирована; обе UI-поверхности работают.
Точные storage/field names, predicates, fixtures, effect-бюджеты и schema ещё
нужно закрепить в executable плане после согласования. Не переносить устаревшие
name-fallback и container-name примеры из GM-текста вопреки действующим ID-контрактам.

Повторное чтение определений, текстов и стабильных проекций — существующий
service/repository/cache; ключи включают source revision, item/owner/realm/role
и зависимости. Передача/расход/правка текста инвалидируют зависимое. Текущее
владение/количество/допуск эффекта/публикации проверяются свежими. Не кэшировать
тривиальные проценты; экономия не заявлена без замеров. Source-аудит и проверка
документов не заменяют будущие дешёвые фикстуры/интеграционную приёмку.
