# Команды и решения духовного боя — проект #1573

Это предлагаемый контракт, не существующий API. Автор должен утвердить
[spec](../spec.md)/[gameplay](../gameplay.md) до реализации.

## Обычное намерение

Console prose и browser form сходятся в одном typed SpiritualCombatIntent:
scope/instance/revision, participantId, actor-turn/slot, operationId/mode,
targetParticipantIds, optional effectId/itemId/zoneId и текст намерения.
Список допустимых действий выводит клиент из текущих правил. Неявная единственная
цель допустима только если однозначно выводится из текущего контекста; в группе
не подставлять lead вместо пропущенного адресата.

GM переводит свободный текст в это намерение, объясняет недопустимое и планирует
NPC. Проверяемые правила/клиентские броски определяют последствия. Существующий
GameResponse.afterlifeSpiritualConflictUpdate остаётся транспортной точкой,
но получает новый versioned schema: actions/events/opportunities/outcome.
Старые side snapshots не являются запасным способом записать новые HP.

## Порядок GM-планирования и расчёта

Текущий TurnRequest/preview передаёт кости заранее; для NPC это нельзя оставить
источником выбора удачного действия. Предлагаются раздельные контрактные этапы:

1. Planning input: наблюдаемая ситуация, доступные actions/targets, текущая очередь,
   известные эффекты. Будущие скрытые результаты НЕ передаются. GM возвращает
   typed намерение текущего NPC либо заранее ограниченный последовательный
   план с условиями по видимому состоянию. Интерпретация свободного намерения игрока
   тоже фиксируется до раскрытия костей. Preview показывает правила/шансы, не будущий исход.
2. Admission: клиент проверяет intent, фиксирует actionId/targets/assigned dice
   и при необходимости открывает reaction decision. Недопустимое намерение
   возвращается GM для исправления без показа будущих бросков и без расхода.
3. Resolution: production kernel выводит события; общий planner валидирует
   dependencies и публикует разрешённый сегмент через существующую транзакцию.
4. Narration: GM получает подтверждённые результаты и описывает их, не переписывая
   HP/оплаты/очередь. Ошибка текста не откатывает уже принятые механические события;
   требуется связанное исправление повествования, не новый бросок.

Это изменение нормального GM workflow, не просто поле новой формы. Технические
сегменты/normal-repair отличают intent proposal, unresolved decision,
accepted result и narration. Нельзя выдать GM весь старый dice pool и полагаться
на просьбу «не смотреть». Для уже известных результатов доступ по visibility.
В accepted state сохраняется также необходимость недостающего повествования,
чтобы после reload продолжить описание без повторного боя.

Не требуется отдельный дорогой GM запрос для арифметики каждого бойца: допустимый
заранее зафиксированный план исполняется клиентом до нового осмысленного выбора.
Ветка плана может опираться на опубликованное состояние, но не на будущие кости.
При утрате предпосылок клиент возвращает ситуацию на планирование, не самовольно
выбирает другую цель. Количество GM обращений/latency измеряется в T025;
обещание ускорения только за счёт локальной арифметики не делается.

## Реакция игрока

1. NPC intent, target, timing и dice reservation фиксируются до просмотра результата.
2. Если есть выбор, общий accepted plan сохраняет завершённый префикс и
   PendingCombatDecision без применения ещё не разрешённого попадания.
3. GM request завершается. UI показывает объявленную угрозу, адресата,
   доступные варианты/видимые цены, возможность pass. Текст не сообщает скрытые кости.
4. Dedicated CombatDecisionResponse содержит decisionId, presented token,
   scope/instance/action/expectedRevision, responder, optionId/допустимую цель.
5. Submit проверяет actual session generation и текущую authority внутри
   обычной координации записи. Дублированный exact response не оплачивает снова;
   изменённый повтор/stale token отклоняется.
6. Следующий принятый сегмент продолжает ту же action, не создаёт дополнительный
   ход/раунд и не выпускает новые кости для уже назначенных subchecks.

Новый submit нельзя реализовать простым снятием запрета activeGM на обычном
composer. Нужен собственный route/admission и lifecycle state; QTE — пример
token/fingerprint fencing, не готовый боевой канал. GM wound continuation —
канал repair/решения GM, не ответ игрока. Across-segment combat clock должен
быть независим от технических accepted turn numbers.

Закрытие клиента/пауза/истечение UI-сессии сохраняют canonical pending decision;
при reload выдаётся актуальное представление/token. По умолчанию нет таймера
и автоматического pass. Явная автополитика игрока может выбрать допустимый ответ,
с теми же правилами/ценой и записью причины. Неподходящий response ничего не меняет.
Нельзя удерживать filesystem lease/живую capability на время размышления игрока.

## Вывод и журнал

Для каждой видимой души: имя/роль, точный current/max HP, ОД по правилам видимости,
состояние, видимые effects, зона, следующий ход, доступность реакции. Полоса HP
типизирована числами, не получается парсингом русской подписи. Невидимый актор
и секретный эффект не раскрываются через count/tooltip или отказ действия.
Журнал связывает инициатора, цель, реакцию, броски, HP/barrier/ОД изменения,
источник эффекта и личный исход. Общая победа имеет своё основание.

Console и browser семантически равны. Оба позволяют выбирать цели, отказываться
от реакции, продолжать сохранённый бой и читать личные последствия. Инженерные
идентификаторы не печатаются в обычном игровом выводе; доступны в debug-аудите.
