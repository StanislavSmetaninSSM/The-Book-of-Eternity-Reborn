### B. Bounded prompt retention with non-replay identities

Both daemon and bridge currently cap full-body dictionaries at 256; `InputLifetime.PromptTasks` also grows. Proposal: use a monotonically increasing prompt sequence scoped to the **current input binding**, encoded into the operation identity and included in delivery/query frames. Bridge status exposes the next admissible sequence; admission under `_sync` permits only that next sequence, advances a high-water mark and freezes content hash/profile/body. A colliding body or stale/gapped sequence is a proven zero-write refusal; retry/availability logic must retain the original sequence/body until its outcome is known. Every direct producer (daemon and launcher direct prompt path) and fixture is updated together; no silent legacy fallback admits old random IDs after compaction.

At most the existing two live admitted operations retain payload/tasks/CTS. Retain a bounded window (proposal 256) of compact completed receipts: sequence, ID, binding, kind/revision, content hash, disposition/phase. Old sequences below high-water but outside the window return an explicit expired/unknown query result and **never repaste**. An old ID cannot be reminted with a new sequence because its encoded binding/sequence must agree. Another binding is stale. Dispose settled CTS/remove completed task references only after original work settles; unresolved tasks remain in stop/drain ownership and block unsafe replacement. Daemon drops full payloads only when source authority has advanced/closed and no unresolved delivery needs them; keep a compact per-binding high-water/current pending operation instead of a lifetime hash table. Tests must exercise query/duplicate/conflict on both sides of retirement and late completion during Stop.

Daemon restart on a still-live input binding must not allocate a new sequence for an ambiguously delivered current source. Persist one bounded current dispatch record (or the at-most-two active records), including pending source identity/hash, binding, sequence, frozen payload hash and delivery phase, through the existing client-owned control publication before dispatch. Proposed owner: `game_state/control/gm_prompt_delivery.json`; deny it to GM writes/FilesModified. Restart queries that same original operation; source advancement/definitive zero-write or settled outcome governs retirement. Missing/corrupt/changed records never justify a fresh automatic submit. A new binding is not permission to retry an old uncertain turn: reconcile relay application/client pending authority first. Add `DaemonRestart_SameLiveBindingQueriesOriginalSequence` and `ChangedBinding_DoesNotMintLostDispatchAuthority` tests.

This is prompt-delivery idempotency, not durable run authority. A bridge restart has a new binding and rejects old prompt frames. Relay queue identity/current session witnesses independently prevent applying the same response again after a legitimate fresh terminal admission.
