## Proposed interfaces and authority decisions (ARCH review required)

### A. Byte admission and exact exchange

Add one small stdlib relay limits module/config read by CLI and worker. Proposed defaults for review: prompt `4 MiB`, response `16 MiB`, total prepared helper transfer `64 MiB`, owned queue disk quota `256 MiB`; diagnostic retained log `8 MiB` with an explicit bounded in-memory tail. No semantic write-count or line/character-count limit. Positive integer configuration and a fixed implementation safety ceiling are validated before launch; no `0=unlimited`, overflow, negative or unknown-key acceptance. These numbers are proposals: real measurements in the audit do not establish their adequacy or peak-memory behavior. Before SOURCE acceptance, record actual parser/base64/normalizer/publication peak allocations and per-case disk use, then justify/revise defaults against those observations. A refusal preserves bytes/current request and identifies limit, observed bytes, configured bytes and safe remediation; it never changes game files.

Keep 32 KiB helper chunks/64 KiB control frames and two admitted bridge prompts. Bound the general prompt-bearing bridge frame before full allocation using the same prompt byte policy plus envelope overhead. The currently unbounded helper `request-begin.length` receives a total budget before buffering. Neutral-relay prompt evidence must use complete hash/length-backed observation rather than the rolling diagnostic tail; keep actual terminal readiness/manual takeover/current input binding. Do not enlarge Mini/editor first-turn limits or all control-frame bounds by association.

Add an atomically published small `current-request.json` descriptor naming one immutable queue request, its exact files/hashes and status. This is a stable address for existing computer/file tools, not a file UI or context collector. The AI reads prompt/game request and referenced current docs/state itself. `relay_worker.py` remains an optional operator/adapter convenience. Response/reply publication can be performed through the existing computer write capability; missing stages can be completed only for an exact retained response hash and identity, never with another body. A worked shell-less exchange records the AI's actual read/write tool boundary separately from operator CLI startup; a Python worker test alone cannot satisfy SC-004.

### B. Bounded prompt retention with non-replay identities

Both daemon and bridge currently cap full-body dictionaries at 256; `InputLifetime.PromptTasks` also grows. Proposal: use a monotonically increasing prompt sequence scoped to the **current input binding**, encoded into the operation identity and included in delivery/query frames. Bridge status exposes the next admissible sequence; admission under `_sync` permits only that next sequence, advances a high-water mark and freezes content hash/profile/body. A colliding body or stale/gapped sequence is a proven zero-write refusal; retry/availability logic must retain the original sequence/body until its outcome is known. Every direct producer (daemon and launcher direct prompt path) and fixture is updated together; no silent legacy fallback admits old random IDs after compaction.

At most the existing two live admitted operations retain payload/tasks/CTS. Retain a bounded window (proposal 256) of compact completed receipts: sequence, ID, binding, kind/revision, content hash, disposition/phase. Old sequences below high-water but outside the window return an explicit expired/unknown query result and **never repaste**. An old ID cannot be reminted with a new sequence because its encoded binding/sequence must agree. Another binding is stale. Dispose settled CTS/remove completed task references only after original work settles; unresolved tasks remain in stop/drain ownership and block unsafe replacement. Daemon drops full payloads only when source authority has advanced/closed and no unresolved delivery needs them; keep a compact per-binding high-water/current pending operation instead of a lifetime hash table. Tests must exercise query/duplicate/conflict on both sides of retirement and late completion during Stop.

Daemon restart on a still-live input binding must not allocate a new sequence for an ambiguously delivered current source. Persist one bounded current dispatch record (or the at-most-two active records), including pending source identity/hash, binding, sequence, frozen payload hash and delivery phase, through the existing client-owned control publication before dispatch. Proposed owner: `game_state/control/gm_prompt_delivery.json`; deny it to GM writes/FilesModified. Restart queries that same original operation; source advancement/definitive zero-write or settled outcome governs retirement. Missing/corrupt/changed records never justify a fresh automatic submit. A new binding is not permission to retry an old uncertain turn: reconcile relay application/client pending authority first. Add `DaemonRestart_SameLiveBindingQueriesOriginalSequence` and `ChangedBinding_DoesNotMintLostDispatchAuthority` tests.

This is prompt-delivery idempotency, not durable run authority. A bridge restart has a new binding and rejects old prompt frames. Relay queue identity/current session witnesses independently prevent applying the same response again after a legitimate fresh terminal admission.

### C. One authoritative multi-file response decision

Proposed narrow additions: `GmHelperCanonicalScope.PublishBatchAsync` and a dedicated helper `publish-batch` payload handled through the existing chunk protocol. It consumes an exact prepared member list plus all original read witnesses and returns the existing Committed/RolledBack/Uncertain publication decision. It is available only to the existing dedicated helper role/lease, not default participating control or ordinary GM packet fields. It calls `FileSystemManager.PublishLocalFilesAsync` once; reuse its current journal, images, generation checks and recovery. Do not add a Python canonical undo journal or change generic trusted-local recovery policy.

Refactor only the existing script preparation seam needed to reuse exact `Write-BoeJson` normalization, depth, Read-BoeJson baselines, normalized duplicate-target checks, GM path/realm/client-owned policy and Complete-BoeTurn/Complete-BoeValidationRepair checks before the batch. A staged read view lets terminal checks inspect the prepared result while rechecking real baseline/witnesses at commit. Ordinary helper calls retain their current behavior. Include the correlated terminal signal and a compact **client-authored** latest apply receipt in the same existing trusted-local publication; terminal remains the last logical output. Proposed exact receipt owner: `game_state/control/gm_relay_apply_receipt.json`, explicitly denied to GM writes and FilesModified. The receipt contains protocol version, original queue ID, request/repair identity, response hash, complete prepared-member digest, terminal kind and current generation; it grants no gameplay acceptance. It is a latest bounded receipt, not an unbounded per-turn archive. Any lifetime/cleanup interaction with pending-turn closure is verified before implementation acceptance.

The batch prepares all ordinary members and client-owned receipt before its terminal member. The daemon's authoritative read must acquire its existing canonical-reader/helper lease and settle any retained trusted-local journal before trusting receipt or terminal; an early raw filesystem notification is not permission to consume half a batch. `ActualDaemon_CannotConsumeTerminalDuringUncommittedBatch` must hold the publication cut and prove no terminal processing until the complete journal decision is established. This ordering and the receipt's survival/retirement at client pending cleanup are mandatory ARCH/SOURCE proof, not assumptions supplied by file order alone.

Queue states: `RequestReady → ResponseReady → Applying → HelperPublished → RelayAcknowledged`, or typed `Rejected/Unresolved/Closed`. Queue files carry correlation and diagnostic evidence only. Under a new queue-owner serialization gate, recovery verifies protocol/root/generation/current request and uses the actual existing publisher decision plus exact apply receipt. All-before/absent receipt after an established rollback permits the same retained packet to be applied under fresh admitted authority. Matching committed receipt means read-only ACK reconciliation, even if original targets' preimages no longer match. Pending/client authority advanced means stale/superseded, not permission to write or an invented Accepted status. Mixed/corrupt/uncertain evidence remains blocked with explicit diagnostics. A crash after terminal publication but before relay ACK cannot mint another terminal or replay the response. Actual client validation/story/history acceptance is observed separately by the real game chain.

Settled queue payloads are retired only after a definitive application outcome and advanced/closed client source authority; retain the current unresolved request, latest application decision/high-water and a bounded compact status window. Queue quota exhaustion never deletes an unresolved winner or canonical history. A bounded observation test must show that retained prompt/response bytes and task/CTS counts stabilize over repeated cycles; a larger disk limit is not a substitute for retirement. FIRST evidence archives in this feature remain immutable and are not runtime retention inputs.

Closed queues remain closed. A replacement relay takes fresh native queue ownership and normal current terminal/run admission; queue locks/PIDs do not substitute for that authority. No automatic blind retry of ambiguous helper/transport outcomes or whole-game restart is prescribed.
