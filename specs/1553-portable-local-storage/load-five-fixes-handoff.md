## 5. Исправления

### А. Исключить неоднозначность имён с пробелами по краям

Проблема: NormalizeArchiveEntryPath сохраняет такие пробелы, а FileSystemManager.ResolvePath удаляет их через Trim. Запись может пройти проверки под одним именем и обратиться к другому пути.

Ориентир: SaveLoadService.Loading.cs, участок подготовки записей около строк 237–247 исходного коммита; FileSystemManager.ResolvePath около строки 621.

Требуемое поведение:

- Сначала выполнить существующую проверку исходного архива, схемы, manifest и хешей
- После нормализации относительного пути отклонить имя, если оно отличается от своего Trim при ordinal-сравнении
- Сделать это до классификации служебных путей, исключений, проверки коллизий и добавления записи на извлечение
- Не исправлять такое имя молча и не менять общий контракт ResolvePath ради этого случая

### Б. Согласовать регистр только у фиксированных путей состояния

Проблема: проверка архива допускает варианты регистра, а потребители на Linux читают точные имена. Windows-сохранение может иметь допустимые варианты регистра.

После проверки оригинального manifest/хешей и проверки пробелов привести к существующим каноническим константам только восемь объявленных путей:

- Состояние Soul
- Четыре пути Resource: definitions, state, history и owner authority
- config.json
- Профили сущностей Afterlife
- Состояние Shining Abode

Точные пути и константы взять из кода.

Сопоставлять полный относительный путь без учёта регистра. Каноническое имя использовать далее для проверки коллизии с исходным архивом, топологии, извлечения, описи образа, декодирования настроек и подготовки профилей.

Канонизация должна предшествовать проверке коллизий: CONFIG.JSON после преобразования может совпасть с config.json, в котором находится выбранный исходный архив.

Не переводить весь архив в нижний регистр. Посторонние пути и содержимое файлов оставить неизменными. Сохранить существующее платформозависимое сравнение описи.

### В. Правильно классифицировать сбой восстановления предыдущего B1-журнала

Проблема: RecoverTrustedLocalStorage вызывается при получении права на замену сессии, до возврата lease в Load. Поэтому существующая обработка неопределённости внутри Load не перехватывает этот случай; ошибка восстановления может ошибочно возвращаться как обычный безопасный отказ.

Ориентир: FileSystemManager.cs около строки 3667; SaveLoadService.Loading.cs около строки 121.

Требуемое поведение:

- Выделить ошибку именно этого этапа восстановления для session replacement
- Использовать существующий CoordinatedStatePublicationUncertainException либо столь же явную типизированную ошибку, распознаваемую Load
- Не относить автоматически к неопределённости обычную конкуренцию за блокировку, отмену, невалидный архив или другие ошибки допуска
- Не терять исходную типизированную ошибку, если освобождение lease тоже завершилось ошибкой

Результат: Uncertain, NeedsFollowUp=true, ContinuationBlocked=true, EstablishedGeneration=null. Диагностические данные сохраняются; обновление runtime не выполняется.

### Г. Отразить незавершённую очистку подготовки

Проблема: сейчас совместная ошибка подготовки и её очистки превращается в общий AggregateException; внешний обработчик не распознаёт оставшийся временный каталог.

Ориентир: SaveLoadService.Loading.cs около строк 301–313.

Требуемое поведение:

- Ввести узко применяемую внутреннюю типизированную ошибку для сочетания ошибки подготовки и ошибки очистки
- Сохранить обе исходные причины и необходимые сведения об оставшемся временном состоянии
- Распознавать этот случай при формировании результата

Результат: NotLoaded и NeedsFollowUp=true. Сам по себе сбой удаления приватных временных данных не должен становиться неопределённостью публикации или блокировать продолжение работы с каноническим состоянием. Не трактовать любой AggregateException как такой случай.

### Д. Не утверждать установленное поколение при неопределённости

Ориентир: SaveLoadService.Loading.cs около строки 162.

Заменить выбор «Committed либо всё остальное» явным соответствием:

- Committed → поколение замены
- RolledBack → предыдущее поколение
- Uncertain → null

При Uncertain выставлять NeedsFollowUp независимо от наличия отдельного объекта Failure.

Обновлять runtime только после подтверждённого Committed. Поздняя ошибка обновления runtime или освобождения ресурсов не должна переписывать уже достоверно установленный результат публикации и поколение.

## 6. Порядок реализации и проверки

Сначала проверить сохранённую правку подготовки Shining Abode и установить причинный результат теста: он должен доходить до проверяемого поведения Load.

Далее применять узкие регрессионные проверки и исправления по правилам TDD. Сохранять свидетельства неуспешного и успешного этапов.

Помимо существующих тестов проверить:

- Архивы с manifest и вариантами регистра фиксированных путей
- Разный регистр компонентов каталогов, а не только имени файла
- Сохранение посторонних Linux-имён без преобразования
- Коллизии, возникающие после канонизации
- Ошибку восстановления предыдущего журнала на этапе получения lease
- Ошибку подготовки вместе с ошибкой очистки
- Правильные поля результата для Committed, RolledBack и Uncertain
- Отсутствие обновления runtime при неподтверждённой публикации

Изменение общего участка получения lease требует проверки затронутых потребителей session replacement.

Тесты запускать через scripts/test-csharp.ps1 только по затронутым категориям. Имена категорий и параметры взять из текущего каталога и docs/testing.md. Не запускать Fast/PreMerge, полный набор или последовательный обход всех категорий. Не повторять неизменённые успешные проверки без причины. Не использовать общие изменяемые фикстуры.

Каталог проверить через -ValidateCatalog без исполнения всех тестов.

Среда по текущим инструкциям проекта: PowerShell 7, .NET SDK 10 и runtime .NET 8. Установленные версии проверить. Если работа идёт только на Windows, прямо указать, что Linux-проверки ещё остаются.

## 8. Что остаётся за рамками этой приёмки

Не объявлять весь Load завершённым. Отдельными открытыми задачами остаются:

- Потоковая обработка больших метаданных загрузки
- Полная замена образа/поколения через B1
- Преобразование топологии «файл ↔ каталог»
- Сохранность библиотеки сохранений и выбранного исходного архива
- Семантика отсутствующего config.json и значений по умолчанию
- Защита от вложенной привязки поколения того же корня
- Холодные и ресурсные проверки
- Публичные клиенты, нативные проверки Windows/Linux и живые игровые проверки

Публичное подключение Load не выполнять до закрытия необходимых предварительных условий из спецификации.
