## Alternatives

1. **Capture first, release, then run unchanged callbacks.** A whole-group eager capture changes failure order (later read can fail before an earlier callback), bypasses draft refusal precedence, and does not capture conditional nested controls or signed authority. Even the smaller strict triple cannot make its proof pure: current-turn/life-transition reads happen later. Releasing between capture and output introduces a freshness/owner gap; final compare requires another real admission and cannot legitimize a stale cached PASS. Reject whole-group form; a triple-only capture is a possible smaller experiment only if fresh end/result publication and old first-error behavior are independently solved.
2. **Explicit bounded read view through ONLY the adjacent signed capture stage (preferred conditional pilot).** Pass a private concrete object into the strict builder’s three signed reader calls, without AsyncLocal view installation, global cache, ambient authority bypass or arbitrary delegate registry. Use an actual canonical lease/original owner; exact consumed bytes/absence and same-lease authority qualify the tuple. Close before original1113 proof, leaving all nested current/quest/gacha/tracker operations scalar. A whole-strict held view was considered but rejected by the concrete recursive leaves above. This reduces adapter scope but does NOT solve the stale-after-close/result-publication gap; that remains a design blocker, not an implemented guarantee.
