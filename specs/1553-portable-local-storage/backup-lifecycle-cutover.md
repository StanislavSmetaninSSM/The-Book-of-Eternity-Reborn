## Recommendation

The ordinary **backup lifecycle** can be isolated as a coherent follow-on slice: create exact-byte backup, restore it and dispose of its evidence, clean up an accepted backup, and preserve the resulting disposition through the immediate StateDistributor/QTE consumers. **CreateBackup alone is not a complete safe port.** Existing B1 member publication suffices; do not invent a backup journal or replace the physical publisher globally.

This is a read-only recommendation for a later tracked slice, not accepted implementation or an expansion of T030-F. It would close only a prerequisite. It would not make StateDistributor, accepted turns, QTE completion, or LiveTurnPreparationService one atomic crash-recoverable operation. The approved FR-001–009 require exact bytes/absence, path/type/link/schema/generation/lease checks, no accidental loss, original-handler-or-block for old evidence, and truthful unresolved outcomes. Current-schema closed-game editing remains allowed; physical identity and owner-resistant protection are not common-route requirements.

## Actual source boundary

Paths in this section are under `BookOfEternityClient/`.

1. `Core/FileSystemManager.cs:5632–5659`: public sync/async creation acquires a canonical lease; supplied-lease overload validates ownership/activity, then both call `CreateBackupCore` without passing the lease. Core reads with the **private physical** `ReadFileBytesCoreAsync`, returns null for absence, normalizes the source, selects `<source>.backup.<UtcNow.Ticks>`, calls private `WriteFileAtomicBytesCoreAsync`, discards its physical result, and returns an absolute canonical path. There is no physical identity in this helper's public result.
2. `:5662–5695`: restore similarly acquires/validates the lease, derives a canonical relative path from the supplied absolute backup path, reads exact bytes through the physical core, throws `FileNotFoundException` for missing before-image, writes the target through the old private core, then deletes the backup through `DeleteFileCore`. The write and evidence deletion are currently separate operations.
3. `:5697–5718`: accepted cleanup also bypasses normal dispatch and calls `DeleteFileCore`. Unlike creation/restore, Linux deletion has an existing by-name fallback in `PhysicalFileAuthority.cs:1304–1316`; do not claim this particular method is the observed descriptor-create failure. It still lacks the common B1 evidence/outcome boundary.
4. `:5720–5748`: old absolute-to-relative conversion uses ordinal-ignore-case comparisons and unconditional backslash replacement. Ordinary adaptation should use validated scope plus `GetLocalRelativePath` (`FileSystemManager.SessionReplacement.cs:10–21`), including extended Windows spelling and Linux case semantics. Validate that a backup input is a file below game_session, not the root. Preserve the existing API's arbitrary valid canonical backup filename contract; tests use `.test-backup`, so do not silently impose a new suffix-only reader.
5. The actual blocker is `WriteFileAtomicBytesCoreAsync:1053–1063` → `EnsureAuthorityFilePublicationSupported:3838–3876`. An absent destination requires a Windows-only descriptor-bound backend before staging/hook invocation. Supported original publication stages/flushes through `PhysicalFileAuthority`, uses reversible replacement or descriptor create-only rename, and returns `CanonicalMutationPublication` (`:1070–1147`). Do not delete OS guards or fabricate its FileIdentity.

Only production `IO/StateDistributor.cs` calls the three FileSystemManager backup APIs: create `:108`, restore `:629`, failed-operation cleanup `:650`, accepted cleanup `:686`. Similarly named GameEngine/QTE/browser backup helpers are different mechanisms.

## Existing reusable common mechanism

`FileSystemManager.TrustedLocalStorage.cs:47–55` selects ordinary writes only outside recorder, legacy-recovery, and browser rollback-evidence contexts. `ReadLocalFileBytesAsync:184–220` provides generation-bound exact reads with ordinary type/link checks and boundary revalidation. `PublishLocalFilesAsync:105–114` and `PublishLocalCoreAsync:117–163` retain participating mutation registration, actual lease checks, hooks, generation binding and bounded transient retries. `VerifyCurrentSessionOperation` is `FileSystemManager.cs:3702–3705`; validating lease activity alone (`:3797–3805`) is insufficient fencing.

`TrustedLocalFilePublication.cs:122–180` recovers old B1 work, validates generation and the complete expected member set, stages flushed bytes, and publishes by name. `Before=null` is create-only (`overwrite:false`), so a destination collision cannot overwrite an earlier backup. Before/after images and original/member hashes are distinct from physical identities. `:75–104` returns Committed/RolledBack/Uncertain; `:195–279` preflights the entire journal before any recovery and preserves unknown bytes/evidence. `ScratchScope:380` already grants only derived sibling scratch names.

Suggested concrete shape:

- Thread the existing lease into dedicated ordinary lifecycle methods; retain current original core unchanged behind explicit dispatch. Avoid reacquiring a canonical lease from the supplied-lease route.
- Creation captures source exact bytes once; absent source returns null without a new publication or invented generation. Select a fresh destination and publish `{backup, null, sourceBytes}`. Use collision-resistant private naming or reject/reselect a positively untouched collision; never overwrite it. Existing ticks-only naming can collide and, on the original reversible path, replacement is possible, so merely forwarding to ordinary overwrite would preserve an unsafe accident. The `.backup.*` test contract allows an added unique component.
- Restoration captures exact backup bytes and current target bytes/absence, rejects backup/target resolving to the same destination, and declares **target restore + backup deletion together** in one existing B1 member set. A pre-decision failure restores the target and keeps the backup; committed outcome gives exact restored bytes and backup absence. Same-content restoration remains an explicit operation. No reserialization/BOM conversion is permitted.
- Accepted cleanup declares exact current backup bytes → absence. Missing evidence cleanup can be a validated no-op; restore must still fail when evidence is missing. Hard-linked source reads are allowed; restore replaces the target name and cleanup unlinks the backup name without modifying other hard-link names.
- Preserve existing generation. If the ordinary slice promises a fresh-root backup and its generation as one decision, reuse the T030-F generation-snapshot/member pattern (`DirectoryDeletion.cs:18,52–65`); `PublishLocalFilesAsync` otherwise creates generation separately. Make that distinction explicit in tests. Do not create a zero-member journal for absence.
- Capture the durable outcome before warnings/owned-lease release. `RequireCommittedLocalPublication:165–175` logs on committed cleanup failure and emits a generic InvalidDataException for uncertainty; it is not by itself sufficient for safe enclosing compensation. T031's `CoordinatedStateWriteHelper.cs:68–121,266` and T030-F `DirectoryDeletion.cs:55–87` provide existing disposition/release/diagnostic patterns.

## Immediate consumers and accepted-state effects

`StateDistributor.cs:51–77` owns or receives one lease. At `:97–149`, it backs up all fixed target/output paths, updates files one by one, writes accepted wound commands and outputs, then confirms persisted treatment resources. This is **not** one multi-file journal. It marks mutations applied only after each write returns (`:116–120,598–604`).

The catch at `:151–181` always logs, calls reverse compensation, and after apparent rollback can release treatment resource holds. `RollbackMutations:607–659` restores changed preexisting files, deletes newly created ones, cleans unused backups and accumulates failures. Accepted cleanup is outside that catch (`:185`, `:662–696`), intentionally preserving the accepted result on cleanup failure.

A backup publication uncertainty must not enter ordinary compensation, release treatment claims, be hidden in a generic aggregate, or produce an unchanged-state/safe-retry claim. In ordinary rollback, unresolved restore/cleanup must halt further dependent mutations and retain evidence. Confirmed rollback retains existing behavior. Accepted backup cleanup uncertainty is cleanup debt after the domain result was already accepted; preserve that result and evidence.

The only direct production distributor consumer found is `Services/QteSceneService.cs:2197–2208`, followed by experience application and normalizer work. Its enclosing compensation catches at `:1922,2004,2041` currently exclude **only** `CoordinatedStatePublicationUncertainException`; a new backup-specific exception would otherwise trigger wider baseline restoration. Include this propagation boundary in the slice (or deliberately reuse a coherent existing unresolved-publication classification), with a reached-cut test. Do not infer that every I/O/parse/setup exception means uncertainty. Acquisition already resolves or blocks pending evidence before returning a lease (`FileSystemManager.cs:3649–3664`).

QTE's other baseline copies (`:2223–2243`), GameEngine pre-turn snapshots (`GameEngine.SessionAndSnapshots.cs:1824–1906`) and accepted histories/receipts are separate. Their unchanged once-only acceptance and later compensation semantics cannot be replaced by “one backup committed.”

## Original routes and exclusions

- **Browser v6:** `ExplorerLocalTurnRollbackArtifacts.cs:413–432` explicitly reads original tracked bytes and writes before-images before attaching a recorder at `:511`. Receipts require real physical identity/link count/hash (`:37–41,219–272`). Warm `BrowserLocalWriteCoordinator.cs:284` clears the recorder before restoration at `:292`; cold acquisition sets `IsLegacyStorageRecovery` (`FileSystemManager.cs:3650–3660`). Thus recorder presence alone cannot authorize a portable conversion. Existing explicit original reads and conditional physical write/delete APIs at rollback service `:699–787` must remain. Dynamic-directory original cleanup introduced in T030-F remains required. **These routines do not call CreateBackup/RestoreBackup/CleanupBackup**, so a narrowly separate ordinary backup implementation need not migrate them. If shared physical cores are changed, the scope immediately expands unsafely.
- Dispatch restore based on both backup and target context; never silently mix ordinary target publication with an original evidence backup. Original backup operations under a recorder/recovery must retain existing receipt behavior, including their current direct-core bypass of recorder callbacks. The generic byte writer `FileSystemManager.cs:793–819` records original mutation intent/publication; do not substitute it casually into original restore and change the outer recorder's authority history.
- **Save/load/archive/workspaces:** `SaveLoadService.cs:176,318` uses runtime ZIP staging/create-only move, not CreateBackup. Its exact archive readers `:381,642`, physical staged-set retention, and profile authority yield/write/rebind `:498–525` remain original. Runtime save move gates are `FileSystemManager.cs:1931–2042`; load extraction/physical inventory and worker workspace capture (`Services/GmWorkers/GmWorkerExecutionWorkspace.cs:276–339,669–735`) are separate. Preserve the saved save/load map and admission addendum. No ZIP generation/load test is a prerequisite for this backup-only slice; optional synthetic manual/autosave/checkpoint ZIP sentinels should be created directly and remain byte-identical through backup/restore/cleanup and recovery.
- **External Daren:** `DarenQteRewardProfileService.cs:13` fixes `client_profile/qte_showcase_rewards.json`; `DarenRewardProfileFileStore.cs:27–62,92–151` retains physical read/publication and exact lease validation. Browser external entries retain parent/baseline/published identities and deferred transaction id (`ExplorerLocalTurnRollbackArtifacts.cs:55–64,519–533,1288–1300`). Do not broaden a canonical backup input to BasePath or client_profile. Future external portability needs an exact-file grant, with existing `TrustedLocalFileScope:80–96,161–169` and B1 derived scratch grants; it is not part of this slice.
- No current direct FileSystemManager backup consumer uses the returned backup's physical identity. Physical evidence users are the explicit browser receipts, Daren rollback transaction, and load staging/rebind, not the string backup handle.
