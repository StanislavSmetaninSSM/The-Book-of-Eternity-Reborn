# Next portable save/load boundary after T030-G

Read-only engineering reconciliation for [#1553](https://github.com/StanislavSmetaninSSM/The-Book-of-Eternity-Reborn/issues/1553), 2026-10-01. This is a source proposal, not an implementation, plan reorder, test result, or acceptance decision.

## Recommendation

Record one bounded **T032-A: ordinary save creation and its immediate callers** as the next candidate. It can precede the remainder of T031 on a current-schema, admitted, quiescent session. It does not need a redesign of accepted-turn receipts or normalizers. Its complete boundary is snapshot preparation, one create-only ZIP decision, private staging cleanup, browser guard/outcome delivery, and immediate autosave consequences. A final-rename-only change is insufficient.

Three engineering prerequisites belong to that capability: remove the browser save's zero-member v6 wrapper through the existing prepared route; give ordinary StateManager profile-mirror refresh a Task-only common publication path while retaining the receipt-returning original load path; preserve the save producer's resource envelope rather than silently turning a streamed ZIP into an unqualified whole-ZIP-memory operation. These are concrete source dependencies, not new product questions. Do not mark T031 or T032 complete after this slice.

The existing B1 decision/recovery protocol is adequate for the save member, and later for a fully declared load file set plus generation. No second journal, whole-folder grant, synthetic identity, privileged service, or power-loss guarantee is needed. If faithful large-save support needs streaming B1 image handling, refine the same protocol before accepting the save capability; do not hide that work behind a smaller invented size limit.

The public overload takes one canonical write/snapshot lease at 133; the supplied-lease overload validates it at 155 and holds it across required-root/resource validation, payload reading, archive construction and publication. The source set at 186–275 is durable `game_state`, `lore`, `mods`, `world_profiles`, `stories`, non-scene entity images, `output`, and optional exact `config.json` bytes. `saves/` is not included. The existing directory-link exclusion is intentional (`SaveLoadServiceTests.cs:720–750` expects a successful archive without the junction target). Preserve the exclusions and no-follow behavior; ordinary file reads still reject invalid types/links before opening. Linux case-distinct live names must not be silently collapsed; the archive's existing case-insensitive duplicate policy must still reject an unportable payload set.

The direct SaveGame API does not establish provider quiescence or independently reject all pending-turn artifacts. A canonical lease serializes participating writers, not arbitrary surviving provider processes. Browser pending/owner admission exists; console save is reached from the serialized in-game menu. Autosave runs during accepted-turn continuations, before terminal artifact cleanup. Do not apply the browser pending-turn ban indiscriminately to autosave or claim the lease proves B4 stop ownership. The next capability is qualified on coherent current state and existing caller gates; real GM continuity remains T033/B4.

## Proposed interfaces and the single decision

Use existing types, not a new transaction layer:

- Current `CanonicalLocalFileChange(string RelativePath, byte[]? Before, byte[]? After)` and `PublishLocalFilesAsync(CanonicalWriteLease, IReadOnlyList<CanonicalLocalFileChange>, CancellationToken)` are at `Core/FileSystemManager.TrustedLocalStorage.cs:8,105–114`
- Current B1 result has `Committed`, `RolledBack`, `Uncertain`, publication members/generation and failure (`Core/TrustedLocalFilePublication.cs:16–21`)
- Prepare-save should return an owned archive candidate containing the destination relative path, complete validated image/source, and cleanup ownership; it must not publish. Ordinary service orchestration and prepared browser orchestration use the same preparation and final publication implementation
- A save-facing result should retain disposition, destination/created-save identity, and follow-up status. Bool compatibility, if retained, is a projection for known committed/known noncommitted outcomes only; uncertainty must retain its type/status rather than becoming false

Before the first publication hook: validate the lease/route, settle pending evidence, capture exact generation snapshot, validate destination and absence, and complete/flush/close the ZIP. Revalidate generation and destination absence after boundary hooks. The declared ordinary set is `{new save ZIP: before absent → exact finished ZIP}`. Already present, even identical, means collision; it must remain byte-identical and must not be a success. An injected destination change after preflight remains B1 conflict/evidence, not permission to overwrite.

For ordinary clients bootstrap already established generation. A low-level fresh-root save can otherwise cause `PublishLocalFilesAsync` to create generation in a separate preliminary decision (line 111). If such a caller is kept, reuse T030-G's pattern: explicit absent binding plus generation creation in the **same nonempty save set** (`FileSystemManager.BackupLifecycle.cs:109–140`). Do not invent generation on a failed/no-op preparation. Existing generation remains unchanged for a save; loading is the operation that replaces it.

Original recorder/recovery/evidence routes stay explicit (`TrustedLocalStorage:47–55,105–114`). Normal save must not be nested inside a v6 recorder. Old physical save overloads may remain explicit for supported original paths; their semantics must not be silently converted while other original consumers depend on them.

### Outcome contract

- Preparation/admission failure or known collision: no new ZIP, previous library/state/config bytes intact; owned scratch cleaned or reported as private cleanup follow-up. No false claim that unresolved prior evidence is a harmless failed preparation
- Confirmed B1 rollback: destination returns to absence; old library intact; no source-state rollback or gameplay replay
- Committed: exact complete new ZIP exists; old library intact except separately authorized autosave retention; success remains established through logging, scratch cleanup, owner release or menu-refresh failure
- Committed with journal cleanup debt: preserve commit and report follow-up. Before any same-lease list/read/retention/next write, settle retained debt using its journal generation before ordinary fencing. A debt conflict blocks continuation; it never authorizes undo of the ZIP or gameplay baseline
- Uncertain: keep journal and unknown member bytes; do not promise a retry is harmless, run retention, release wider gameplay claims, apply domain compensation, or hide the result behind menu reconstruction failure
- Cold recovery: normal canonical acquisition performs original-handler-or-block, then B1 (`FileSystemManager.cs:3649–3664`). Uncommitted restores before bytes/absence; committed preserves after; unknown bytes/generation/type/journal conflicts retain evidence (`TrustedLocalFilePublication.cs:195–258`)

Immediate callers are part of this scope. Console bool display is `GameEngine.OptionsAndSettings.cs:1223–1225`. Autosave calls SaveGame then a separate cleanup lease (`SaveLoadService:354–368,1680–1701`); its three callers are `GameEngine.TurnLifecycle.cs:226,965,1526`, with accepted-state follow-on work after each. They currently ignore the returned bool. Do not swallow an uncertain save as an ignored false and continue. A narrow typed propagation can use the existing game-loop uncertainty handling at 1207–1221, with causal tests proving no subsequent cleanup/compensation. Retention failure after a committed save is follow-up; it cannot turn the save into failure. Do not silently make retention part of the save ZIP transaction or expand to atomic accepted-turn work.

Browser outcome must survive actual transport and UI: `LocalWebUiMainMenuService.cs:161–173,587–591`, `LocalWebUiHost.cs:106–112`, frontend `src/api/contracts.ts:144–149`, `src/components/SettingsView.tsx:81–106`. Current bool/error/menu-only DTO and unconditional success/retry wording cannot describe uncertain/committed-follow-up states. Return the destination identity established by preparation/publication rather than inferring the created ZIP by same-name/latest-menu search. A post-commit list/refresh failure must retain the established result.

## Filesystem, volume and memory implications

B1 already writes each `.boe-local-<transaction>-<index>.stage/.undo` beside its member (`TrustedLocalFilePublication:376–385`) and renames only sibling names (175–177,230–234). Its journal stages/renames occur together under `.boe_runtime/trusted-local-publication-v1` (68–72,159–186). Therefore a save does not require moving the runtime ZIP across volumes into `game_session/saves`; runtime scratch is only a byte source. Different member directories need not be renamed as one tree. Participating-writer logical recovery spans the set; this is not simultaneous filesystem atomicity or power-loss durability.

Save needs canonical destination authority and private scratch ownership, plus exact runtime generation authority if first generation is part of the decision. Later load needs selected canonical files and exact generation, not authority to replace all BasePath. `PublishLocalCoreAsync` currently uses `[BasePath]` but routes non-generation members through canonical relative mutation hooks (`TrustedLocalStorage:121–142`), so passing arbitrary external paths through `PublishLocalFilesAsync` is not supported.

Memory is a real acceptance constraint:

- Current save builds ZIP on disk; `AddDirectoryToArchive` materializes one source payload at a time. It does not call `ValidateTrustedArchiveBudget`. The 8,192 entries, 64 MiB per entry, 512 MiB expanded total, 2 MiB entry-name bytes, 4 MiB manifest, 8 MiB soul and ratio bounds (`SaveLoadService:28–53`) are **reader** admission limits, not a proven producer/ZIP-size ceiling
- B1 `Image.FromBytes` clones each input (`:416–419`). With ZIP size Z, a naive adapter holds the caller Z and image clone Z, then allocates roughly 4Z/3 of base64 JSON per serialization at intent and commit (`:159,184`). `Matches` also uses a full `File.ReadAllBytes` (`:370–374`). This is an amplification model, not a measured peak; GC overlap, JSON overhead and runtime buffers make a fixed peak claim unsafe
- For eventual load, let A be imported payload bytes and B be live before-images. A is budgeted on read, but B is not bounded by the incoming 512 MiB limit. Current B1 has copies proportional to A+B plus serialized base64 and recovery reads. An external selected ZIP may reside elsewhere; only its exact file is read, never written
- Preserve streaming ZIP construction, bounded entry validation/extraction and preflight order. Do not substitute a MemoryStream for the whole ZIP, add an arbitrary compressed-size cap, claim OutOfMemoryException handling proves the envelope, or accept changed archive limits without a product decision. Qualify representative large/incompressible archives and constrained-memory failure in the save block. If the complete supported envelope needs stream-backed images/hash/JSON handling, make that refinement within B1's one durable decision and exact-byte recovery contract, with matching cold tests before acceptance

Concrete planning alternatives, neither executed here:

1. **Reuse B1's byte-array API unchanged.** Keep disk-backed ZIP creation, read the closed candidate once for the declared member, and measure peak allocation/resident memory and successful publication plus cold recovery for the largest current loadable, incompressible archive envelope on the declared target resources. Also measure the existing producer baseline. This is the smallest implementation if evidence shows it preserves usable resources; a small smoke archive or clean allocation failure is insufficient. No new compressed-ZIP cap may be introduced to manufacture a pass, and the producer's current lack of a budget check must remain explicit
2. **Refine B1 image transport before save cutover.** Keep the same strict v1 intent/member/commit model and exact before/after authority, but use an owned immutable file/image source with bounded chunked hashing and journal serialization/recovery reads. This must address cold journal deserialization and `Matches`, not only avoid the caller's first byte-array copy. Keep all publication scratch beside its destination and journal stages inside the existing journal root. This is a shared B1 prerequisite requiring a focused implementation plan and affected recovery review, not a second journal or a shortcut that references disposable save scratch as the only recovery copy

Recommended first bounded implementation step inside T032-A planning: establish the actual save-entry causal RED and the resource baseline/maximum-envelope feasibility for alternative 1 **before** committing to its adapter. If that is not viable on supported target resources, make alternative 2 the explicit prerequisite and finish it before save cutover. This ordering resolves an engineering uncertainty without changing the product limits or silently expanding T031; it is a recommendation for the coordinator to record and review, not an approved source change.

Daren is **not a dependency of save/load** in the inspected chain. The external state is exactly `Path.Combine(fs.BasePath, "client_profile/qte_showcase_rewards.json")` (`Services/DarenRewardProfileFileStore.cs:14–24`, `DarenQteRewardProfileService.cs:13`), not a user-home path. Its physical publication at 92–148 remains separate T031 work. A later canonical-plus-Daren transaction can isolate that exact file and derive only its sibling stage/undo names; publication and cold recovery must use the same approved exact-file grant. No grant over unrelated `client_profile` files or home folders is needed. Current save/load must leave the entire external profile untouched.
