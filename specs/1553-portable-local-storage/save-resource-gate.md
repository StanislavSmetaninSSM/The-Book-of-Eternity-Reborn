The existing producer constructs a disk ZIP and reads one payload at a time. ## Chosen transport, same transaction protocol

A completed disk ZIP remains the save candidate. Introduce an internal read-only image abstraction with presence, exact length, SHA-256 and a validated sequential reader; existing byte-array callers retain their existing API and byte snapshot semantics. A file image must be captured only from an explicitly approved scope, reject links/wrong types, and revalidate length/hash while copying. It never grants authority to mutate its source. Candidate mutation/disappearance before durable intent rejects without authorizing a destination overwrite.

Use a **self-contained version-2 framing in the same B1 active journal**, keeping the existing `trusted-local-publication-v1` root and active/intent/commit filenames, one decision, phase order, derived sibling stage/undo names, lease/generation guards and complete conflict preflight. The historical `.json` filename need not determine the encoding; distinguish the framed version by an exact magic/version prefix before decoding. Keep v1 JSON handling explicit and unchanged for existing byte-only consumers and old supported evidence. Do not reinterpret v1 evidence as v2, create a parallel journal, or automatically discard unknown formats.

The proposed v2 frame is fixed magic/version plus checked header length, strict metadata and contiguous raw before/after image regions. Metadata contains transaction ID, committed flag, generation before/after, member paths and each image's presence/length/hash/relative region offset. The payload region is owned by the journal itself. Region offsets are relative to the payload start, so changing the committed flag does not change image identities. Every region reader must use the parsed payload start of its current intent/active/commit image after metadata length changes; never reuse an old absolute offset. Validate checked arithmetic, exact file length, region order/non-overlap/coverage, presence-vs-zero-byte distinctions, unique properties/members, current generation schema and complete image hashes before any mutation/recovery cleanup. Unknown/truncated/corrupt framing, metadata or payload in the authoritative active journal retains evidence. Temporary filenames follow the explicit authority matrix below, not a competing journal-decoding rule.

Serialization writes metadata and copies each source in bounded chunks directly into intent.tmp, verifies hashes/lengths, flushes/closes it, then atomically publishes active. Only that completed journal can authorize member mutation. After intent, sibling stage/undo creation reads exact regions from the durable active journal; disposable save scratch is never the recovery copy. Commit writes a complete bounded-copy commit.tmp containing the same regions with committed metadata, flushes/closes, then atomically replaces active. Keep active until all sibling and journal scratch cleanup finishes. No image sidecars/pre-intent image directories are introduced, so interrupted preparation has only the existing disposable intent.tmp and cannot orphan new evidence.

The current temp/active authority matrix remains exact for both formats:

- No active and no commit.tmp: a confined ordinary intent.tmp is disposable, even if partial, malformed or unknown-format. Validation means namespace/path/type validation, not successful journal decoding; no live mutation could have been authorized
- No active but commit.tmp exists: block and retain it, whatever its content format
- Valid active v1 or v2: its validated decision alone governs recovery. The contents/formats of intent.tmp and commit.tmp are not competing authority. Remove those ordinary temporary files only after complete active/member/generation/type preflight and the required rollback/committed cleanup
- Unknown or malformed active, unexpected namespace entries, linked/wrong-type journal/member/scratch paths: block and retain evidence before recovery mutation
- Unresolved original legacy evidence still uses its original supported handler or blocks before B1 admission

Cold decoding must not materialize the entire journal or image. Frame/header reads are bounded by validated file ranges; parse only metadata, then represent images by validated journal regions. Hash/match/stage/rollback copy through a fixed-size buffer. Metadata memory remains proportional to member/path metadata, not image bytes; read only the strictly capped metadata header after bounded framing checks so a corrupt header length cannot cause a whole-bundle allocation. This is a required codec property, not an invitation to weaken duplicate/unknown-member detection. Any parser budget needed for malformed metadata must be justified by the actual v2 producer shape and recorded during review; it must not impose a smaller ZIP payload limit. All source-image, journal input/output and sibling stage/undo streams close before the applicable Windows by-name rename or deletion; no region reader outlives the journal version it describes.

Tradeoff: a small explicit codec/format branch and additional journal disk I/O replace whole-image memory/base64 amplification. There are still two complete journal copies during commit and one sibling stage per current member, as in B1; this is process-crash recovery, not power-loss durability. Keep normal byte-only publications on v1 until their own need justifies migration. The v2 path shares B1's decision/recovery engine and outcome model rather than duplicating a second transaction implementation.

## T032-A1 implementation decisions

The first codec candidate uses exact `BOELP2\r\n` magic, an eight-byte little-endian signed header length, a strict UTF-8 JSON metadata header, then contiguous raw regions. It bounds the metadata header to 1 MiB before allocating or decoding it and uses 64 KiB image copy/hash buffers. This is **not a compressed/expanded ZIP or image limit**: lengths/offsets are checked 64-bit values. The immediate save producer declares one archive plus at most one generation member. Even two [32,767-character extended Windows paths](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation), each pessimistically escaped to six JSON bytes per character, occupy under 400 KiB including their fixed descriptor fields. No larger member-set producer is cut over here; a future such producer needs its own metadata qualification. Existing byte-only v1 producers retain their original encoding/admission. Generation documents retain their original BOM-aware, case-insensitive, extension-tolerant decoder; their metadata allocation is distinct from bulk image copying and must remain visible in resource reports.

The frame serializer writes bounded metadata directly to the new journal stream and patches only its private length slot before image copies/flush; only the completed file is published. The recognized-v2 reader allocates only the validated bounded header, using the existing strict duplicate/unknown-property parser, and validates every region hash by streaming. Intent/commit readers are rebound to their own payload start/whole-file length after renames, and temporary readers close before by-name operations. The code remains a candidate until the scoped GREEN/cold/resource/original-v1 checks and independent review complete.

The nonmatching-magic dispatch gap was reproduced in three separate bounded cold processes: 128 MiB framed evidence with unknown/partial/JSON-looking magic reached legacy `File.ReadAllBytes` and OOM under a 64 MiB child heap. The original v1 reordered/256 KiB-whitespace control passed. The candidate correction inspects the first JSON object/property/value prefix with a fixed 98-byte property-name buffer derived from the six supported v1 field names; it streams arbitrary JSON whitespace and permits every supported first-property order/escape. Unknown binary prefixes block before the legacy whole-file reader. Plausible v1 retains its original strict decoder and original memory characteristics; this is not a claim that legacy JSON images are now stream-backed. [Causal dispatch RED](recovery/evidence/save-stream-dispatch-red/manifest.json) remains distinct from the already completed [4/4 correction GREEN](recovery/evidence/save-stream-dispatch-green/manifest.json) at tested `26c0327c`, verified by subsequent source/artifact readback. Both predate the 02:08 UTC platform restriction recorded in the plan; this source-only block neither reruns nor extends that diagnostic.
