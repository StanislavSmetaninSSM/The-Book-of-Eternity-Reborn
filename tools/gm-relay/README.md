# Maintained developer GM relay

Source/task: [#1553](https://github.com/StanislavSmetaninSSM/The-Book-of-Eternity-Reborn/issues/1553),
T043-RELAY-REUSABLE-CONTRACT. This folder is shared, maintained code: preserve it
during packaging/cleanup. It provides a small persistent terminal transport and
local worker boundary for tests and future **separately authorized** API adapters.
It contains no model client, credentials, network request or provider integration.
It cannot proxy a forbidden endpoint or qualify arbitrary APIs.

## Install and configure for a developer test

Copy the **whole folder** to an absolute path, including the fixed PowerShell
consumer and input profile. No source checkout, SDK or compiler is needed at relay
startup. Dependencies: Python3 (qualified here with3.12.14, POSIX `termios`/PTY),
PowerShell7, and the game's normal .NET8/runtime package and generated session
`game_state/control/gm_turn_helper.bootstrap.ps1`. These are developer relay
dependencies; Python is not a prerequisite for players selecting another CLI.
Native Windows execution is unqualified and scheduled separately after merge.

Use a disposable **new game/session**, a new empty queue directory, and the
existing ordinary owned-terminal launcher/settings. Do not create a second
launcher or borrow an old run's JSON/PID as authority. Example configured CLI:

```text
/usr/bin/python3 '/absolute/relay/relay_cli.py' --session '/absolute/new game/game_session' --queue '/absolute/new empty queue' --model 'your-test-model-label'
```

Set `GmCliLaunchCommand` to that command, `GmBridgeShellWorkingDirectory` to the
same session, and `GmCliInputProfile` to the exact object in `input-profile.json`.
The model label is copied into each request/reply for correlation; the relay
never chooses or invokes a model. Preserve the selected game's command/model
settings outside your separate test profile. Use the existing explicit
NativeLineage route in the qualified Linux environment. SystemdUser/Auto remain
closed pending their separate implementation/manager qualification.

The original M1 terminal/run fence/T042 own dispatch and stop. Readiness is the
observed `NEUTRAL READY`/`RELAY> ` presentation, working is `NEUTRAL WORKING`, and
plain `RELAY ERROR` blocks readiness. Supported input is bounded UTF8 bracketed
paste followed by actual CR. Paste alone never submits. LF is displayed as CRLF
so the Bridge observes the exact multiline composer; stored bytes remain LF.
Unknown sequences/control characters are refused; this is not an arbitrary TUI.
Bounds:65000characters,120lines,262144pastebytes,3actual submissions per relay,
1MiB per request/packet/consumer output,32writes per packet. Start with a fresh
queue; existing content refuses startup and is never replayed.

## External worker: exact request and one response

After actual terminal submit, the relay creates `request-N-UUID/` with
`request.json`, exact `prompt.txt` and exact `game-request.json`. Do not treat
the first file or directory appearance as a complete request. The worker API
checks all three, hashes and original turn/pending witnesses. A worker must
receive the actual prompt and read the current game instructions/context before
generating its answer. Model generation and permission to invoke a provider are
the worker's responsibility; fixed synthetic packets are only transport tests.

Credential-free commands (replace paths with this run's real queue/request):

```sh
python3 /absolute/relay/relay_worker.py inspect /absolute/queue/request-N-UUID
python3 /absolute/relay/relay_worker.py answer /absolute/queue/request-N-UUID /absolute/generated-packet.json --adapter your-worker-task-id
python3 /absolute/relay/relay_worker.py close /absolute/queue
```

`inspect` returns the original header, UTF8 prompt and exact game-request text.
`answer` publishes the generated bytes, then the matching reply envelope exactly
once. The tiny `relay_contract.py` API is also available to a local adapter:
`read_request`, `publish_response`, `request_close`, `read_close`. `RelayRequest`
is frozen; it carries bytes/correlation, never a main pin or ownership. Typed
`RelayPending`, `RelayMismatch`, `RelayClosed`, `RelayAnswered` refuse incomplete,
stale/wrong, closed or already answered work. OS/filesystem publication errors
remain errors; do not regenerate an unknown response.

Example **synthetic transport-only** packet, no credentials:

```json
{
  "Completion": "turn",
  "Writes": [
    {"Path": "output/response.json", "ExpectedSHA256": "missing",
     "Data": {"message": "synthetic packet for transport test only"}}
  ],
  "FilesModified": ["output/response.json"]
}
```

This demonstrates the existing packet shape, not a valid gameplay response. Real
generated content must satisfy current game schemas/instructions. `ExpectedSHA256`
is the hash of the output actually read by the worker, or `missing`. The fixed
consumer uses the session's actual Read/Write-BoeJson and
Complete-BoeTurn/Complete-BoeValidationRepair functions; it does not evaluate
response scripts. Repair requires `Completion: "repair"` and the original
validation repair request/pending witnesses, not a new turn. No game rules,
receipts/history or accepted-turn semantics change here.

Response and reply use atomic same-directory no-overwrite publication. Only the
writer's own temporary file is removed. A response without reply is an unresolved
winner: never overwrite, salvage, re-submit or issue another model request for
it. Publication is **not** execution/acceptance. The relay rechecks witnesses,
takes an immutable executing snapshot and starts only the one fixed child.
`execution.json` distinguishes refusal from actual consumer exit/I-O; a zero
exit is still not proof that the game's acceptance/history pipeline accepted a
turn. Check those game outcomes independently.

## Close, errors and original cleanup

Ask the queue to close before cancellation/rollback. `close` requests closure;
it does not claim ACK. New execution is disabled; a child whose start was already
linearized must finish and drain stdout/stderr. `read_close` returns `None` until
`closed.json` confirms ExecutionDisabled + ChildExited + IoDrained, and refuses
inconsistent ACK. A response racing close may remain inert. The CLI remains alive
after ACK until the **original** terminal's scoped stop.

Then use the same original Bridge/fence stop and confirm native reap, terminal
I/O/disposal and Stopped ACK. Queue closure, child/PID/EOF or guardian cleanup
alone never grant logical stop, replacement/load or fresh epoch. Lost ACK,
partial publication, consumer error, unexpected terminal input or ownership loss
retain their typed unresolved/error outcomes; there is no automatic replay.
If forced termination leaves a child unresolved, no close ACK is fabricated;
the retained owner/guardian still has independent cleanup authority.
